## 二、项目目标

做一个**能重复、能给理由、能批量**的岗位匹配工具：

- 输入：一段 JD 文本 + 一份简历文本（+ 可选的 JD 列表）
- 输出：0–100 的匹配分、六个能力域的得分、缺口清单（每条附 JD 原句 + 具体动作）、岗位排序
- 形态：命令行 + 单文件 HTML 报告 + 一个 WorkBuddy 技能包
- 硬约束：零第三方依赖，任何装了 Python 的电脑 clone 下来就能跑

具体的 7 条验收标准（AC-1～AC-7）写在
`联合成果/jd-insight/docs/需求规格_v1.md`，由我在还不会写代码的时候写下。

## 三、为什么单独做不到（这是 C3C 的核心问题）

### 3.1 如果没有陈屿，我缺什么

不是"缺一个人帮我写代码"这么笼统。具体缺三样：

**（1）我无法把判断变成可重复的程序。**
我能读一条 JD，五分钟后说出"这岗位其实想要的是指标体系能力，不是 SQL"。
但我没法让这个判断对 24 条 JD 各跑一遍、且每次结果一样。
我试过用 Excel 手工标注，标到第 9 条就开始前后不一致了
（同一种要求在 J03 标成"数据分析"，在 J06 标成"用户研究"）。**人的判断不稳定，而工具必须是稳定的。**

**（2）我卡在第一个报错上就动不了。**
10 月 9 日我第一次自己跑代码，`ModuleNotFoundError: No module named 'jd_insight'`
——我不知道这是因为"当前目录不对"，我以为是代码写错了，然后把代码删了重写了一遍。
陈屿看了一眼说："你在 /Users 目录下跑的。"**这类问题对他来说是常识，对我来说是死路。**

**（3）我不知道什么算"做完了"。**
我认为"能跑出分数"就是做完了。陈屿说不算，因为：
没有测试 = 改一行不知道会不会崩；
没有错误处理 = 用户输错路径会看到一屏红色报错；
没有 README = 除了我没人能用。
这三件事我一件都想不到，因为我没有"交付"这个概念，我只有"完成作业"这个概念。

### 3.2 如果没有我，陈屿缺什么

**（1）他无法判断分数对不对——这是最硬的一条。**
证据在 `fix(taxonomy)` 那次提交里。系统给"商业分析师（管培）"打了 35.1 分。
陈屿看到 35.1，认为"这可能是合理的，因为简历里确实没写财务报表"。
我看到 35.1 的第一反应是"这不可能"——因为我知道工商管理专业的人写"财报"不写"财务报表"，
这是我的日常用词。

**这个 bug 他修不了，不是能力问题，是信息问题。** 他能查出来"关键词没命中"，
但他无法判断"应该命中"。没有我，这个 bug 会一直在，而且他永远不会知道它存在。

**（2）他设计不出标签体系。**
44 个标签里，每一个的边界都要靠领域判断。举个具体的争论：
"竞品分析"和"行业研究"要不要拆成两个标签？
他倾向合并（都是"看别人"），我坚持拆开——因为竞品分析是横向比同类产品，
行业研究是纵向摸产业链，JD 里要求这两项的岗位完全不同（前者是产品/市场，后者是投资/战略）。
最后拆了。这个决定的依据只存在于我的经验里，不在任何文档里。

**（3）他不知道什么叫"合理的权重"。**
他问我"Excel 权重给 0.9 行不行"。我说不行，因为 Excel 是入场券，
给 0.9 会让"会用 Excel"变成核心竞争力，而实际上没人因为 Excel 好被录取。
**他缺的不是调参能力，是"这个数字在真实招聘里意味着什么"的感觉。**

### 3.3 一句话版本

> 他能把任何明确的规则变成可靠的代码，但不能判断规则本身对不对。
> 我能判断规则对不对，但没法让规则稳定地跑 24 遍。
> **我们各自缺的那一半，恰好是对方有的，且都不是短期能补的。**

## 四、协作机制（我们怎么防止"各做各的"）

C3C 明确说"你写代码我写文档"不算。我们为了避免掉进这个坑，定了 4 条规则：

### 规则 1：规格先行，代码后写

任何功能开工前，我写规格（输入/输出/验收标准），他确认"能不能实现"。
规格在我还不会写代码的时候就写了 v1.0，这是故意的——
**只有不懂技术的人写的规格，才不会被实现细节污染。**

反面案例：10 月中旬他直接改了打分公式（把加法改成加权平均），没走规格。
结果我的 24 条标注分数全变了，我花了半天重新核对。之后定了这条规则。

### 规则 2：改打分必须同时补回归用例

这条来自 C3A 的反馈（我上一次挑战被指出"改了没验证"）。
执行情况：`tests/test_regression_calibration.py` 就是 BUG-004 的固化产物。
**任何人删掉"财报"这个 alias，测试会红。** 这是防止"为了分数好看改词表"的机制。

### 规则 3：谁的地盘谁签字

- 标签内容、权重、分数是否合理 → 只有我能改，他只能提意见
- 代码结构、算法、测试、打包 → 只有他能改，我只能提需求

我试过越界一次：我让他"把加分项系数改成 0.3"，他说"可以，但你要给我一个能写进注释的理由"。
我给了（人工核对 24 条 JD 的统计），他才改。**他逼我把直觉变成论据，这是我从他那儿学到的最重要的一件事。**

### 规则 4：每次教学后立刻做事，不做"纯听课"

四次教学，每次都是"讲 40 分钟 + 当场动手 60 分钟"。
我不接受"你先看我操作，回头你自己试"——回头就不会试了。

## 七、这个项目对我们各自的意义

**景雪晴：** 我从"我不会编程"变成"我能读懂一个 Python 包在做什么，能改它的数据结构，
能在它出错时定位到是哪一层"。具体证据见前后对比文件。
但更重要的是：我学会了一种把模糊判断说清楚的方式——**验收标准**。
现在我写任何东西（论文、方案、需求）都会先想"这条怎么判定对错"。

**陈屿：** 我原本以为技术能力就是"能不能实现"。这个项目让我发现：
**实现从来不是瓶颈，定义才是。** 我可以一天写完 parser，但我无法独自决定
"财报"和"财务报表"是不是一个词。这让我重新理解了"需求方"的价值——
以前我觉得产品经理是"传话的"，现在我知道他们提供的是**我无法自己生成的信息**。

## 八、如果重来一次，我们会改什么

1. **第一周就定"分数是否合理"的判定方式**，而不是等到 10 月才发现两个人对"合理"的理解不同。
2. **早点做校准实验台**。我们直到最后一周才把它做出来，之前所有"分数变好了"都是口头结论。
3. **先写 20 条标注再写代码**。我们是边写代码边标注，导致标签体系改了 3 次，代码跟着改了 3 次。
4. **陈屿应该更早承认"我看不出这个分数对不对"**，而不是硬着头皮判断。
   （他事后说："我怕说'我不知道'显得没用。" —— 这是协作里最贵的成本。）
