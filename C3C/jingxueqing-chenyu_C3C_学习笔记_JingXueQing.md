## 第一段：Python 与 Git（S1，09-25）

### 1.1 学了什么

| 概念 | 我现在的理解（自己的话，不是定义） |

| 字典 | 就是 VLOOKUP。给一个编号，直接跳过去拿到那一条，不用从头翻 |

### 1.2 卡在哪

**卡点 A：`ModuleNotFoundError`，卡了两天（10-09 到 10-11）**

报错原文：

```
ModuleNotFoundError: No module named 'jd_insight'
```

我以为是我把代码写坏了。我的处理是：删掉 `jd_insight` 文件夹，从微信里重新下载一份，
再跑，还是报错。反复两次。

**我当时的心情：** 不是"我不会"，是"我可能不适合做这个"。因为报错信息里没有一个字
我能看懂，"No module named" 我猜是"这个模块没有被命名"——完全理解反了。

**怎么突破的：** 陈屿只问了一句"你在哪个目录下跑的"。我发截图，路径是 `/Users/jingxueqing`。
他说"命令行只在你站的目录里找东西"。

**我当时的反应：** "就这么简单？" 然后有点生气——不是生他的气，
是生气这件事没有人提前告诉我。**安装教程教了怎么装，没教"装完要站在哪儿"。**

**突破之后我做了什么：** 在便签上写了 `pwd`，贴在显示器边上，现在每次开终端先敲一次。

**卡点 B：`FrozenInstanceError`，卡了 15 分钟**

```
FrozenInstanceError: cannot assign to field 'weight_default'
```

我想在代码里改一个权重，改不了。我第一反应是"这个设计很蠢，为什么不让我改"。

**怎么突破的：** 陈屿反问我"你要的 AC-2 是能溯源，如果权重能随时变，溯源还成立吗"。

我当场意识到：**这个限制不是技术选择，是我自己在规格里提的要求带来的后果。**
我写"必须能溯源"的时候，没想到它意味着"数据不能变"。

**学到的东西（不是技术）：** 一条需求写下去，会有我没预料到的代价。
现在写规格我会多想一步："如果按这条做，会牺牲什么？"

**卡点 C：不知道标签该加在哪一行，卡了 15 分钟**

我把新标签加在文件最末尾，结果是 `taxonomy` 命令输出里它跑到了最后一个域的末尾，
而不是"业务与行业"那一段。

**为什么卡住：** 我以为"代码就是一堆指令，顺序不重要，机器会自己找"。
实际上列表的顺序就是输出的顺序。

**怎么突破的：** 陈屿让我看 `DOMAINS` 这个列表，说"你改它的顺序，看输出变不变"。
我改了，输出跟着变了。

**我当时的原话（记在微信里）：** "原来代码里的顺序也是信息。"
陈屿说"当然啊"，但对我来说这是个新发现。

---

### 1.3 这段我真正带走的（一句话）

> **报错不一定是代码错，可能是我站错地方了。**
> 遇到报错先分三类：环境的、路径的、代码的。分对了才知道该干什么。

## 第二段：测试与读报错（S3，10-23）

### 2.1 学了什么

| 概念 | 我现在的理解 |
|---|---|
| 断言 | 一句"我认为应该是这样"，机器帮我核对 |
| 单测 | 把我已经决定的事锁住，谁想改就得先跟我打招呼 |
| 假绿 | 测试通过了，但它检查的不是我以为它检查的东西 |
| 红-绿-红 | 先让它红（证明它在检查）→ 让它绿 → 再故意弄坏，确认它又红 |
| `AssertionError` | 唯一一种"红得有用"的报错 |

### 2.2 卡在哪

**卡点 A：我写的测试是"假绿"，但我很自信**

我写的版本：

```python
def test_weight_in_range(self):
    for t in tx.tags_in_domain("数据分析"):
        self.assertGreaterEqual(t.weight_default, 0.4)
```

跑，绿了。我准备提交。

陈屿问："如果我把某个权重改成 0.1，这条会红吗？"

我试了——把"协作工具"的权重改成 0.1，跑，**还是绿的**。
因为我只遍历了"数据分析"这一个域，"协作工具"在"工具与平台"域。

**我当时的感受（很重要）：** 不是"我写错了"，是"**我刚才差点把一个没用的测试交上去，
而且我会一直以为它在保护我**"。

这比写错代码可怕。写错代码会崩，写错测试不会崩，它会一直给你假的安全感。

**怎么突破的：** 陈屿让我把断言改成遍历 `all_tags()`，再试，红了。然后改回来，绿了。

**突破之后我做的改变：** 我给自己定了一条规矩——
**写完任何检查，先故意弄坏一处，看它红不红。不红就是没在检查。**

这条规矩后来在 S3 的作业里抓到了一个真 bug：
我写"同一个词不能在同一域内指向两个标签"这个用例，跑起来红了，
查下去发现 `需求文档` 同时挂在 PRD01（需求分析）和 PRD02（文档撰写）上。
陈屿说这个 bug 一直存在，但没人发现——因为同域内两个标签，
消歧逻辑会随便选一个，结果"随机但稳定"，测不出来。

---

**卡点 B：分不清"断言失败"和"代码报错"**

第一次看到 `AssertionError`，我以为代码崩了，去改代码。改完更崩。

**怎么突破的：** 陈屿教我读最后三行：

```
AssertionError: '数据分析' not found in []
```

他说：`AssertionError` 后面那句话就是"我以为的"和"实际是的"的对比。
`not found in []` 说明实际是空的。

**学到的东西：** `AssertionError` 是"我的预期错了"，其他 Error 是"程序错了"。
**这两种错的下一步完全不同**：前者去改预期或改实现，后者去改代码。

---

**卡点 C：我不理解为什么"测试要红"**

我最初的想法是：测试的目的就是通过，为什么要故意让它失败？

**怎么突破的：** 陈屿说"你写一条 `assertEqual(1, 1)`，它永远绿，它保护你什么？"

我懂了：**一个永远不会红的测试，和一个没有测试，是等价的。**
区别只在于后者不会让你产生"我有测试"的错觉。

---

### 2.3 这段我真正带走的（一句话）

> **"绿了"不等于"对了"。要通过必须能通过，也要能失败。**

## 我额外学到的（不在教学计划里）

### 从陈屿身上学到的：把"我觉得"变成"可判定"

S2 那天我让他把"结果要稳定"改成可测的句子，他说"这个我能写测试"。
我当时很惊讶——**我以为"稳定"是一种感觉，他居然能把它变成一行代码。**

后来我发现这不是他的天赋，是他的习惯：**听到任何模糊的形容词，第一反应是
"这个怎么判定"**。我现在写论文、写方案也会这样问自己。

具体例子：我以前写"要加强用户调研"，现在会写成"完成 18 人次访谈，输出 1 份画像"。
后者可以被核对，前者不能。

### 从项目里学到的：不要为了让结果好看而改标准

11-06 那天我发现财务岗分数只有 35.1，我第一反应是"把权重调低一点让分数上来"。
陈屿说："你确定是权重的问题？"

后来查出来是关键词没覆盖到。**如果我当时直接调权重，问题会被掩盖，
而且以后每遇到一个不合理的分数我都调权重，最后权重表会变成一堆补丁。**

这件事让我理解了"改标准"和"改实现"的区别。
