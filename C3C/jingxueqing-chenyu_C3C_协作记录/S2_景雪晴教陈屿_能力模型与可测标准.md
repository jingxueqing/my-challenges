## 二、教学大纲

### 2.1 KSAO 是什么，为什么要砍成 6 个域（20 分钟）

**景雪晴在白板上画：**

```
K = Knowledge  知道什么（财务报表、供应链概念）
S = Skill      会做什么（SQL、Excel 建模）
A = Ability    能做到什么程度（逻辑推理、抗压）
O = Other      其他特质（动机、价值观）
```

**陈屿的第一反应：** "这不就是四个分类吗，为什么要有名字？"

**景雪晴：** 因为分类是有顺序的，而且 K 和 S 的区别很关键：
K 是"知道"，S 是"会做"。一个人可以知道财务报表长什么样，但不会做财务分析。

**陈屿：** 那我的代码里怎么区分？

**景雪晴：** 你不用在代码里区分，我要你区分的是**能不能被 JD 原句命中**。
K 和 S 通常能命中（"熟悉 SQL"、"了解会计准则"），A 和 O 基本命中不了
（"抗压能力强"这句话对应的能力，没法从文本里判断）。

**于是有了第一条设计原则：**

> **只收「能被 JD 原句命中」的能力。** 主观项（如抗压）不单独建标签，
> 改为"出现明确措辞才命中"（如"高压/加班/快节奏/多任务并行"）。

**陈屿当场质疑：** "那 A 和 O 就完全不用了吗？"

**景雪晴：** 用，但不作为标签，作为**信号**。比如 JD 写"抗压能力强、适应快节奏"，
我不会给他加一个"抗压"标签，但我会告诉你：这句话的意思是这岗位很累，
你面试时要问清楚加班情况。这是给人看的提示，不是给分的东西。

**陈屿：** 那这个提示怎么进代码？

**景雪晴：** 先不进去。**不是所有判断都要进代码。** 有些判断只适合放在文字建议里。

> 📌 这是陈屿在 AAR 里记下的"被改变的一个认知"：
> "我原来的思路是'能把所有规则都写成代码才叫工程化'。
> 她的观点是'有些判断写进代码反而会变坏，应该留给人'。
> 我后来在报告里保留了 `advise` 字段，就是纯文字建议，不参与打分。"

### 2.2 JD 的语义分层（25 分钟）

景雪晴带陈屿逐句拆 1 条真实 JD（J07 产品经理 B 端）：

```
岗位职责：负责需求分析与需求评审，撰写 PRD 与规格说明，设计业务流程并推动落地。
任职要求：具备流程设计与 SOP 沉淀经验；会用 Figma 或 Axure 出原型；
          有项目管理与跨部门协同经验；了解低代码平台者优先。
```

**景雪晴的四层划分：**

| 层 | 例子 | 处理方式 |
|---|---|---|
| ① 岗位职责 | "负责需求分析" | 也要提取！很多人只提"任职要求"，但职责段往往才是真正在考的东西 |
| ② 硬要求 | "具备流程设计经验" | 正常权重 |
| ③ 软要求/客套 | "有责任心" | 不建标签 |
| ④ 加分项 | "了解低代码平台者优先" | 降权 |

**陈屿的发现（这是本次会话最重要的技术产出）：**

**陈屿：** 等一下，如果职责段和硬要求都提取，那"需求分析"这个词在一条 JD 里
会出现两次，是不是就被算重了？

**景雪晴：** 那不正好了吗——它出现两次，说明它更重要。

**陈屿：** 但如果一条 JD 把同一句话抄了两遍（招聘网站很常见），那就变成"抄得多=重要"了。

**景雪晴：** 所以上限要封顶。

**于是有了次数增益的设计：**

```python
def weight_multiplier(self) -> float:
    return min(2.0, 1.0 + 0.3 * (self.count - 1))
```

**为什么是 0.3 和 2.0：**

- 出现 1 次 → 1.0
- 出现 2 次 → 1.3
- 出现 3 次 → 1.6
- 出现 4 次及以上 → 2.0（封顶）

**景雪晴的理由：** "第 4 次重复基本不再增加信息量，只说明写 JD 的人啰嗦。
但完全不封顶会很危险，有人把一句话复制五遍就能把这个要求顶到最高。"

**陈屿：** 那 0.3 这个数怎么来的？

**景雪晴：** 我拍的。但有一个约束：**必须保证"出现 2 次"的权重不超过
"两个不同标签各出现 1 次"的总和**，否则重复比多样更重要，那就错了。

**陈屿当场算：** 0.3 的话，2 次是 1.3，两个不同标签各 1 次是 2.0。满足。

> ✅ 这条后来写进了 `parser.py::TagStat.weight_multiplier` 的注释里。

### 2.3 什么叫"可测"（10 分钟）

这一节是 S2 的核心，也是景雪晴"能教"的最硬的一项。

景雪晴给陈屿看她写的 AC 列表（当时只有 3 条，后来扩到 7 条）：

| 原始写法（不可测） | 改后（可测） |
|---|---|
| "结果要稳定" | "同一份 JD + 同一份简历，跑 100 次结果完全一致"（AC-1） |
| "要给理由" | "任何缺失判定都必须能定位到 JD 的某一句原话"（AC-2） |
| "要合理" | "我在简历里多加一条相关经历，分数不许下降"（AC-3） |

**陈屿看到 AC-3 的反应（原话）：**

> "这个我能写测试。"

**景雪晴：** 怎么写？

**陈屿：** 就是给两个简历文本，一个比另一个多一句，然后断言后者的分数大于等于前者。

**景雪晴：** 那如果相等呢？

**陈屿：** ……相等也算通过。因为"不许下降"。

**景雪晴：** 对。这就是为什么"不许下降"比"必须上升"好——前者是下限，后者是要求，
要求会限制实现方式，下限不会。

> 📌 这句话陈屿记在了笔记里，并在 AAR 里引用：
> "把需求写成下限而不是目标，会给实现留出空间。这是我第一次从业务方嘴里
> 听到一句可以直接指导我写代码的话。"

**当场写出的测试（现存于 `tests/test_matcher.py`）：**

```python
def test_more_evidence_never_lowers_score(self):
    r1 = mt.match(JD_FULL, "会 SQL")
    r2 = mt.match(JD_FULL, "会 SQL，掌握 Excel 数据透视，能统一口径")
    self.assertGreaterEqual(r2.total, r1.total)
```

### 三个具体的分歧（每个都很值钱）

**分歧 1：J08 里的"能读懂数据看板并独立做归因"，陈屿没提取。**

**陈屿：** 我觉得"归因"太模糊了，不知道对应哪个标签。

**景雪晴：** 归因就是"找到指标变化的原因"，这在运营岗里是核心能力，
对应"数据分析"域的指标能力。你漏了它，等于把这条 JD 最重要的一条要求丢了。

**陈屿：** 那我要不要建一个"归因"标签？

**景雪晴：** 不要。归因不是一个独立技能，它是"指标体系 + 统计分析"的组合。
建独立标签会让体系膨胀，而且每次遇到新词都要建新标签，维护不住。

**规则由此产生：** 遇到新词，先问"它是已有标签的组合，还是一个新能力"。
**组合 → 加 alias；新能力 → 建标签。** 不能反过来（先建标签最省事，但会长成 200 个标签的垃圾场）。

**分歧 2：J13 里的"组织述职与人才盘点会议"，陈屿只提取了"人力资源"。**

**景雪晴：** "组织会议"这四个字是项目推进能力，不是 HR 专业能力。
这条 JD 要的是一个能张罗事的人。

**陈屿：** 但它在 HR 岗的 JD 里，我默认它属于 HR 能力。

**景雪晴：** 这就是你的默认偏见。**一个能力属于哪个域，不由它出现在哪类 JD 里决定，
由这个能力本身是什么决定。**

> 📌 陈屿 AAR 原文："我一直以为分类是看上下文，她说分类是看本质，上下文只影响权重。
> 这两句话差别很大，前者会让标签体系随 JD 变化，后者不会。"

**分歧 3：J22 里的"有算法竞赛经历者优先"，陈屿建了新标签。**

**景雪晴：** 这个不该建标签。它是加分项，而且"竞赛经历"不是一个能力，是一个荣誉。

**陈屿：** 但它确实反映算法能力。

**景雪晴：** 那它应该命中"算法与数据结构"这个已有标签，并且因为是加分项而自动降权。
你建一个新标签，等于给它开了一个后门。

**陈屿：** ……我懂了，我是在用建标签来绕过"加分项降权"这个机制。

**景雪晴：** 对。**任何让你想绕过机制的冲动，都是在提醒你机制可能有问题，或者你在偷懒。**
