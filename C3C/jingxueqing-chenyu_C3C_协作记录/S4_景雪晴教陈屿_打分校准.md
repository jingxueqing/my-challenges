## 二、教学大纲

### 2.1 为什么覆盖系数不能是 0/1（20 分钟）

景雪晴在黑板上写了两份简历片段：

```
A：熟悉 SQL。
B：熟悉 SQL 取数，实习期间用 SQL 完成多表关联的交叉分析，输出 20 余张图表。
```

**景雪晴：** 对一个要求 SQL 的岗位，A 和 B 谁更匹配？

**陈屿：** B。

**景雪晴：** 差多少？

**陈屿：** ……不好说。B 明显强，但强多少取决于你怎么定义。

**景雪晴：** 现在看你的代码：`coverage = 1.0 if hits else 0.0`。按这个，A 和 B 都是 1.0。

**陈屿：** 是的。因为关键词只命中一次（"SQL"），文本里其他内容不参与。

**景雪晴：** 那你的系统认为 A 和 B 一样好。

**陈屿：** ……这对吗？从关键词提取的角度看对，从招聘的角度看不对。

**分歧就此暴露。** 接着是这段对话：

**景雪晴：** 我不指望你解决"B 比 A 强多少"这种问题，那是语义理解。
但至少"提到一次"和"反复提到"要有区别。

**陈屿：** 那"提到一次"给多少？

**景雪晴：** 0.85。

**陈屿：** 为什么不是 0.5？

**景雪晴：** 因为 0.5 等于判定他"可能不会"。而 A 是真的会 SQL，只是写得单薄。
**简历写得不好不等于能力不行**，工具不该把这两件事混在一起罚。

**陈屿：** 那 0.85 这个数字……

**景雪晴：** 是我拍的。但我能说清它的约束：
- 必须显著低于 1.0（否则"提到"和"反复提到"没差别）
- 必须显著高于 0.5（否则一次命中就近乎归零）
- 三种状态（0 / 0.85 / 1.0）的差距要能拉开排名，但不能让一个次要项的多次出现
  盖过一个核心项的单次出现

**陈屿当场验算第三种约束：**

核心项权重 0.15（归一化后）出现一次 = 0.1275
次要项权重 0.05 出现三次 = 0.05 × 1.0 = 0.05

0.1275 > 0.05 ✅ 约束满足。

> ✅ 这段验算被写进了 `matcher.py` 的注释：
> 「单次命中的满分设为 0.85，是为了让"重复出现"能拉开差距，
> 同时又不至于让只写了一次的关键技能被判为零——我们选择宁可系统性偏松，
> 也不要系统性误杀。」

### 2.2 为什么加分项必须降权，以及为什么是 0.5（20 分钟）

景雪晴拿出她手工统计的表（见 `docs/权重校准口径.md` 第五节）：

| JD 类型 | 加分项条数 | 加分项中"任职要求"里没提过的 | 占比 |
|---|---|---|---|
| 技术岗（3 条） | 3 | 3 | 100% |
| 数据/分析岗（6 条） | 8 | 5 | 63% |
| 运营/产品岗（8 条） | 11 | 6 | 55% |
| 财务/HR 岗（7 条） | 7 | 3 | 43% |

**景雪晴：** 六成的加分项是"额外的东西"。这意味着如果我给加分项和硬要求同权，
一个"加分项全中但硬门槛缺两项"的人，会排到"硬门槛全中但没加分项"的人前面。

**陈屿：** 那在真实招聘里是反的？

**景雪晴：** 是反的。硬门槛是筛人的，加分项是选人的。**先过筛，再选优。**

**陈屿：** 那应该给 0.1 才对吧，让它几乎不影响。

**景雪晴：** 不行。因为确实存在"两个人都过硬门槛，一个会加分项"的情况，
那时候加分项必须是决定性的。所以它要有分量，但不能翻盘。

**0.5 的界定：** 一个加分项的价值 = 半个硬要求。这样"多两个加分项"能抵"少一个硬要求"，
但"少三个硬要求"就抵不过。

**陈屿当场算了一个例子（他后来写进了 AAR）：**

> 假设 A 硬门槛 5 项全中、加分项 0 项；B 硬门槛 3 项、加分项 4 项全中。
> 加分项系数 1.0 时：A = 5，B = 7 → B 赢。
> 系数 0.5 时：A = 5，B = 3 + 2 = 5 → 平手。
> 系数 0.3 时：A = 5，B = 3 + 1.2 = 4.2 → A 赢。
>
> "我发现 0.5 正好是那个临界点。她不是随便拍的，她是在找一个'刚好不翻盘'的数。"

### 2.3 为什么不能一票否决（10 分钟）

**景雪晴：** 你的公式里，一项完全不命中，它会扣掉多少？

**陈屿：** 扣掉它的权重份额。如果权重是 0.15，总分就少 15 分。

**景雪晴：** 那如果一条 JD 里 8 个标签，我只会 1 个，总分是多少？

**陈屿（当场跑）：** 大概 12 分。

**景雪晴：** 那这个 12 分有意义吗？

**陈屿：** ……没有。它和 0 分没区别，都是"别投"。

**景雪晴：** 所以你的输出里，0–40 分这一段是没有信息量的，全是"别投"。
但我需要的不是"别投"，我需要知道"**差多远**"——差一点和差很远，我的决策不一样。

**于是有了分档结论：**

| 分数 | 结论 |
|---|---|
| ≥ 80 | 强匹配 |
| 65–79 | 可投 |
| 45–64 | 需补短板 |
| < 45 | 不建议投 |

**景雪晴：** 45 分以下才叫"别投"，不是 12 分以下。因为 45 分意味着
"你有一半的硬要求达标了，补两项就能上"，这是一个有用的信息。

**陈屿的疑问：** 但这样会不会让"其实完全不行"的人也拿到 40 分，产生虚假希望？

**景雪晴：** 会。所以我要求报告里必须同时给**硬缺口清单**。
分数负责"大致位置"，缺口负责"具体差什么"。**两者缺一不可，只看分数会误导。**

## 三、动手环节（70 分钟）

### 任务：陈屿独立完成三件事

**任务 1：把三个系数从魔数改成带理由的常量**

```python
BONUS_FACTOR = 0.5          # 加分段落系数
PRESENCE_ONCE = 0.85        # 命中 1 次的得分系数
HARD_GAP_THRESHOLD = 0.08   # 硬缺口阈值
```

**要求：** 每个常量的注释必须能回答"为什么不是相邻的那个数"。

**陈屿第一版注释：** `# 加分项权重系数`（被景雪晴打回）

**第二版：** `# 加分项降权系数，取 0.5 是因为加分项中 40-60% 是额外的要求，同权会导致排名反转`（通过）

**景雪晴的打回理由：** "你写的是'这是什么'，我要的是'为什么是这个数'。
以后有人想改成 0.6，看到你的注释他才知道改了会发生什么。"

**任务 2：写一个能验证 0.5 是临界点的实验**

这个任务催生了 `tools/calibrate.py` 的雏形。当时的版本只做一件事：
对比"开/关加分项降权"两种情况下的岗位排名，看有没有反转。

**陈屿的发现：** 在 24 条 JD 上，系数从 1.0 改到 0.5，有 3 个岗位的名次发生变化。
他记录了这 3 个岗位，确认"变化的方向符合业务预期"（加分项多的岗位下降）。

**任务 3：解释一遍整个打分公式，用中文，不许出现代码符号**

**陈屿的第一次尝试：**

> 总分等于所有标签的权重乘以覆盖率的和，再乘一百。

**景雪晴：** "覆盖率"是什么？我没听过这个词。

**陈屿：** ……就是你有多少。

**景雪晴：** 那你说"你有多少"不就行了。

**最终版本（现在是 `README.md` 里那段）：**

> 总分 = 100 × 每个要求的重要性 × 你满足了多少 之和。
> 其中"重要性"由三个因素决定：这个能力本身多重要、JD 里提了几次、它是在硬要求还是加分项里。
> "你满足了多少"有三种情况：完全没提（0）、提到一次（0.85）、反复提到（1.0）。

**景雪晴：** 这版我能懂。**你要教我的时候也用这个说法，别用"覆盖率"。**
