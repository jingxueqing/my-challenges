# C5A AI 协作日志

> 记录方式：按「我提出什么 → AI 做了什么 → 拿到的原始证据 → 我采纳/否决了什么」四段式，逐轮记录。
> 全程标准：**任何结论必须有 API 原始返回支撑，AI 的推断不能直接当事实写进报告。**

---

## 第 1 轮：搞清挑战到底要交什么

**我的提问**：提交 C5A 挑战。

**AI 的动作**：
1. 先查挑战列表拿到内部 ID；
2. 用内部 ID 拉完整挑战定义（含 required_deliverables、rubric、deadline）；
3. 查 GitHub 绑定状态。

**遇到的真实问题（值得记下来）**：
- 直接传 `challengeId: "C5A"` 拿到的是 `{"ok":false,"error":{"code":"NOT_FOUND","message":"…挑战不存在"}}`。**页面上的编号不是 API 的 ID**，必须从 `list-challenges` 里取形如 `ch-20260717031511-x5c6t1` 的内部 ID。
- AI 没有擅自改用「C5」的旧资料。检查发现 C5 是另一个挑战（`ch-20260717031503-ihozqu`，对应 `sias-local-map-agent` 仓库），与 C5A 无关。

**拿到的关键事实**：

| 项 | 值 |
|---|---|
| 挑战内部 ID | `ch-20260717031511-x5c6t1` |
| 标题 | C5A GitHub 入门与仓库理解 |
| 必交交付物 | `*仓库分析*`、`README.md`、`*AI日志*` |
| 截止 | 2026-12-31 23:59 |
| 评分总分 | 100（基础 25 / 交付完整 20 / 技术执行 15 / AI 使用 20 / 反思质量 20） |
| GitHub 绑定 | `jingxueqing`，`bound: true` |

**我的判断**：交付物模式是「通配符 + 精确名」混排——两个带 `*` 的可以放在任意子目录，`README.md` 是精确名。这解释了为什么先把三份文件统一放进 `C5A/` 目录，再校验一次文件命中情况。

## 第 2 轮：不写空话，先把仓库数据抓成事实

**我的要求**：所有数字都要有出处，不要凭印象说「这个仓库大概有几十个文件」。

**AI 的动作**：抓 `/repos`、`/git/trees?recursive=1`、`/commits`、`/readme` 四类接口，落盘到本地 `raw/` 后再统计，而不是让 AI 直接口述数字。

**这一步抓到的、纠正了我原先想法的数据**：

- 我原以为「430 个路径 = 430 个文件」，实际 **tree 条目 430、真实文件（blob）367**，差额是目录条目。这是统计口径错误，AI 明确指出并改成以 blob 为准。
- 顶层目录不是 9 个挑战，而是 **9 个挑战目录 + 根目录 3 个文件**（`README.md`、`paper.tex`、`references.bib`）。后两个明显属于某次挑战的成果却放在根上——这个细节后来变成了报告里的 P3 问题。

**AI 提出的、被我否决的说法**：
- AI 一度想说「仓库结构混乱」。我要求给证据：实际每个挑战目录内部是自包含的（文档 + 代码 + 报告），结构其实清楚，问题只是「根目录越界」和「缺横向索引」。**改成有证据的具体表述，而不是笼统的差评。**

## 第 3 轮：找对照仓库，避免只分析自己

**我的要求**：「读懂他人仓库」不能只读自己的，必须有一个成熟仓库做对照。

**AI 的动作**：选 `fastapi/fastapi`（同为主语言 Python、体量适中），抓取同样的树与元数据，然后做结构层面比对。

**对照中真正有价值的三条**：

1. **`docs_src/` 与 `docs/` 分开**：文档里的示例代码是被测试覆盖的真实文件，不是贴进 md 的片段——这解释了它文档可信的原因。这是我自己读仓库时绝不会想到要看的层次。
2. **`.github/` 26 个文件暴露治理方式**：`ISSUE_TEMPLATE`、`DISCUSSION_TEMPLATE/translations.yml`、`dependabot.yml`、`build-docs.yml`。结论「看 `.github/` 就能判断治理水平」由此而来。
3. **文档与代码接近 1:1**（`.md` 1705 / `.py` 1219）：说明文档是产品的一部分，不是附属品。

**我主动收窄的地方**：AI 一开始倾向说「my-challenges 应该学 fastapi」。我否掉了——课程交付不需要 649 个测试文件，照搬结构是错的。最后只保留三个**低成本可迁移项**：LICENSE、topics、`.github/ISSUE_TEMPLATE`。

## 第 4 轮：按分数结构组织，而不是按我的写作习惯

**我的决定**：rubric 里「反思质量」和「AI 使用」各占 20 分，合计 40 分，比「技术执行」15 分更高。所以：

- 仓库分析不能只堆数据，必须包含**判断**（问题清单 + 优先级 + 成本）和**局限**（哪几条我没验证）。
- AI 日志不能写成流水账，必须体现**AI 说错了什么、我如何纠正**——这次真实发生的两处是「430 路径≠430 文件」和「结构混乱」的过度概括。

**最终交付三份文件**：

| 文件 | 侧重 |
|---|---|
| `JingXueQing_C5A_仓库分析.md` | 事实 + 对照 + 判断 + 局限，9 个章节 |
| `README.md` | 入口与复现方式，含统计口径说明 |
| `JingXueQing_C5A_AI日志.md` | 协作过程与纠错记录（本文件） |

## 第 5 轮：提交前的自检

**做的检查**：

1. 文件名是否命中 `*仓库分析*` / `README.md` / `*AI日志*` 三个必交模式；
2. 全文是否含密钥形态字符串（sk- 前缀长串、键名加等号再跟引号内容的赋值写法）——**已排除**，提到密钥时只描述检查思路，不留任何取值；
3. 报告里每个数字能否回溯到 `raw/` 下的原始 JSON；
4. 是否有「未验证却写成已验证」的句子——已把「未做 clone 验证」「提交只取 30 条」写进局限章节。

**留给下次的教训**：

- 平台编号 ≠ API ID，永远先 `list-challenges` 取内部 ID；
- 统计仓库规模先分清 tree 条目和 blob 文件；
- 分析类交付物里，「我没验证什么」和「我验证了什么」同样重要，评分表里反思分往往就压在这里。
