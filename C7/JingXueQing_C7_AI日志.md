## 1. 第一步不是写稿，是「建事实台账」

C7 最危险的地方不是写不出来，是**写出来的东西是假的**。

因为文章讲的是「我做过什么」，AI 完全有能力把「24 个测试」写成「上百个测试」——语法通顺、语气自信、读者不会怀疑、但那是编的。

所以我给 AI 的第一条硬约束不是「写得好看」，是：

```text
禁止生成任何我没有提供的事实。
文章里出现的每个数字，必须来自我给你的素材清单，且能指回具体交付物。
如果某个数字需要但素材里没有，直接写「待确认」，不要估算。
```

然后我先做了一件事：**扫自己过去所有的交付目录，把能核验的事实抽成一张表。**

【实测】实际执行记录：

```bash
$ ls ~/Desktop/挑战的产物 | cat -n     # 16 个条目（不含本次 C7）
$ find "<C7资料包>" -maxdepth 3        # 挑战包：CHALLENGE.md / rubric.json / challenge.json / materials/C7.pdf
```

抽出来的事实台账（节选，共 30+ 条）：

| 事实 | 出处 | 核验方式 |
|---|---|---|
| 排版技能 1419 行、26 测试、128 断言 | `~/.workbuddy/skills/wechat-publisher-pro/` | `wc -l` / 跑 eval |
| starter 380 行、12 个缺陷、5 个致命 | C4B 交付的 AAR 与文章源文件 | 逐条比对 |
| 网页应用 3080 行、25 项自测、FCP 0.94s | C6 交付的 AAR §2 | 交付物内表格 |
| 地图 Agent：77 个离线单测、M1/8GB、Gemma 4 E2B | C5 交付的 README | 仓库内 `tests/` |
| 翻译：31 篇 + 3 PDF，30/31 通过质检 = 96.8% | C1 交付的 README §2 + `reports/quality_report.json` | 文件存在性 |
| 公众号基线篇：2026-10-06 12:47 发布 | WebFetch 实际抓取线上页面 | 见 §3 |

:::key 这一步的价值
后面所有文章的数字，都从这张表里来。
**没有台账，就没有「真实经历」；只有台账，文章会变成表格。**
所以台账只做原料，排序和取舍交给大纲阶段。
:::

## 2. 真实迭代轮次（11 轮，含 4 次自我打脸 + 4 轮排版返工）

【工具产出】以下是本次会话真实发生的顺序，不是事后编的流程。

### R1 · 读挑战包，先定「不能做什么」

读 `CHALLENGE.md`（306 行）、`rubric.json`（5 个维度）、`challenge.json`（交付物字段）。

得到的第一个判断不是「写什么」，而是：**交付物里有一项我物理上做不到**——`数据截图` 要求真实阅读量，而发布要扫码。

**决定：先把能做的做到最好，把做不到的如实标注，绝不造假。**
这条决定影响了后面每一个文档的写法（所有数据字段写「待回填」而不是「约 200」）。

### R2 · 扫既有交付物，抽出事实台账

见 §1。这一步花了本次会话大约 1/4 的时间，但后面写稿几乎没再查资料。

### R3 · 第一次打脸：公开数量算错了

我最初的选题判断是：「做了十几个挑战，**只有 1 个**（那篇公众号）公开过。」

这是个很有冲击力的开头。我差点就用了。

但我在写稿前做了一次核对：

| 我查了什么 | 结果 |
|---|---|
| WebFetch 抓 `mp.weixin.qq.com/s/alqul0Zf...` | ✅ 可访问，公众号 SnowKitty，2026-10-06 12:47，河南 |
| 翻 C5 交付的 README | 发现 GitHub 仓库是**公开**的：`github.com/jingxueqing/sias-local-map-agent` |
| 翻 C6 交付的 app 链接 | 发现应用是**公开可访问**的：`wechat-studio-57144.app.workbuddy.host` |

**真实数字是 3，不是 1。**

:::danger 这是本次最重要的一个教训
「只有 1 个」比「只有 3 个」更抓人。
**如果我先写标题再核对，我一定会舍不得改——因为改完之后文章没那么「惨」了。**
所以我现在的顺序是：**先核数，再定标题。**
:::

改完之后，文章反而更有说服力了——因为它精确到能被人验证（「16 个条目，3 个公开」）。

而且我顺手加了一句更狠的：16 个条目里，**公众号只有 1 篇，之后停了近一个月**。这个数字比我原来的夸张说法更难看，但是真的。

### R4 · 第二次打脸：环境依赖缺失

【实测】按常规用托管版 Python 跑排版技能，直接失败：

```text
$ python3 -c "import markdown, bs4, lxml, pygments, PIL"
ModuleNotFoundError: No module named 'markdown'
```

我没有去 `pip install`（那会污染系统环境，而且 C4B 那次我就在自己的技能里明确禁止了自动装依赖）。

改成先探测哪个环境齐备：

```text
$ ~/.workbuddy/binaries/python/envs/default/bin/python3 -c "import markdown; print('md ok')"
md ok
```

**修法：换解释器，不动环境。** 这也是我 C4B 技能里那条设计（「缺依赖就打印指引并退出，绝不擅自动手」）的一次自我遵守。

### R5 · 第三次打脸：写完之后自己查出 3 处口径问题

A1 初稿写完，我通读了一遍，改了 3 处：

| 问题 | 原文 | 改成 | 为什么 |
|---|---|---|---|
| 数字不精确 | 「十几个交付目录」 | 「16 个条目——15 个成品目录，加 1 个打包 zip」 | 标题写了 16，正文必须能对上 |
| 时间夸大 | 「一年前我开始做挑战」 | 「今年我开始做挑战」 | 全部交付物集中在 2026 年，写「一年前」是虚的 |
| 时间错位 | 「去年十月，我把…发在公众号」 | 「上个月…」 | 实际是 2026-10-06，距今不到一个月 |

第三条尤其典型：**「去年」比「上个月」更有沧桑感，但它不是真的。**

### R6 · 写 A2 / A3，做「一鱼三吃」的结构改造

三篇不是同一篇改标题，是三种结构：

| 篇 | 结构 | 为什么这样改 |
|---|---|---|
| A1 公众号 | 痛点开场 → 3 个结论 → 选题表 → 行动 | 公众号偏叙事，需要一个「我」的转变弧线 |
| A2 公众号 | 全貌表 → 7 步逐条 → 成本表 → 互动 | 干货型，读者要能边读边抄，所以每步都给可复制的提示词 |
| A3 知乎 | 结论先行 → 6 个项目逐个「做了什么/难点/结果/搞砸」 → 能力分层 → 局限 | 知乎只看前 3 行，所以结论必须放最前；且知乎读者更接受「局限性说明」 |

**A3 里我专门加了「我做不到的部分」表格**（没做过用户运营、没有 code review、处理不了万行项目）。
公众号版本里没有这张表——因为公众号读者要的是「我也能做到」，知乎读者要的是「你说得靠不靠谱」。

### R7 · 排版 + 合规体检 + 结构校验

【实测】用自己 C4B 做的技能转 HTML：

```bash
$ python3 scripts/wechat_publisher.py A1.md A1.html --theme ink --toc --footer --safe-code
  篇幅      : 约 2073 字
  代码块 0｜行内代码 2｜提示框 7｜链接 0
  合规体检 : ✅ 全部通过（无违规标签 / 无 class / 无外链图）

$ python3 scripts/wechat_publisher.py A2.md A2.html --theme ink --toc --footer --safe-code
  篇幅      : 约 2372 字
  代码块 6｜行内代码 5｜提示框 5｜链接 0
  合规体检 : ✅ 全部通过（无违规标签 / 无 class / 无外链图）
```

两篇都是 0 高危。但体检器只查合规，不查结构，所以我另外做了一次硬统计（不只信体检器）：

```text
A1.body.html: div=0  class=0  style=185  table=2  h2=6
A2.body.html: div=0  class=0  style=256  table=3  h2=10
```

:::warn 为什么「链接 0」是好事
公众号正文不允许外链。我写 A1 时原本放了 GitHub 和文章地址的 Markdown 链接，
后来主动删掉了——**改写成「下期给出」，资源统一走「阅读原文」**。

所以这个 0 不是转换器丢的，是我改的。**如果是转换器丢的，读者会看到一堆点不动的蓝字，而且还查不出来。**
:::

### R7b · 排版返工 4 轮（这一段最能说明「体检器不等于验收」）

**0 高危不等于好看。** 我又用无头 Chrome 截了手机宽度（375px）的图，肉眼过了一遍，改了 4 轮：

| 轮次 | 截图里看到的问题 | 根因 | 修法 |
|---|---|---|---|
| 1 | 小节标题变成「**1. 一、**我一直以为…」，目录里也是双编号 | 我在 Markdown 里手写了「一、二、三」，转换器又自动加了一层序号 | 转换时加 `--no-number` |
| 2 | 表格里「谁主/导」「5 分/钟」——两三个字就换行 | 三列等宽，短单元格被挤 | 合并成两列：「① 选题 · 5 分钟 ｜ 做什么…· 我」 |
| 3 | 表格里 `v1.0.0` 变成红色行内代码，还在「v1.」和「0.0」之间断行 | Markdown 反引号在表格里渲染成 code span，中文断行规则不保护拉丁词 | 去掉反引号，改成「公开仓库 + 版本 tag」 |
| 4 | 375px 下「公众号排版技/能」「一个本地文件/夹」仍有两字孤行 | 单元格文字太长 | 全部压到 6 字以内（「排版技能」「一个文件夹」） |

【实测】这 4 轮里，**合规体检器一次都没报错**——它检查的是「会不会被微信剥离」，不检查「好不好看」。

:::key 这一步的教训
自动化的检查器只能证明「没坏」，不能证明「好」。
**好看的唯一验证方式是截图 + 用眼睛看**，而且要在**目标宽度**（手机 375px）下看，不是在自己电脑的宽屏上看。
:::

### R8 · 封面：换了一次方案

第一反应是用 AI 生图做封面。

后来否掉了，理由有三条：

1. **文字会错**。文章标题里有「16 个交付物」「3 个被看见」，AI 生图的中文经常糊字或错字；
2. **成本**。一次生成要消耗额度，而封面是纯排版需求，用不上生成模型；
3. **可复现**。我要的是「改一个字，重跑一条命令」，不是「重新抽一次卡」。

【实测】改用本地 Pillow 渲染，脚本在 `03_传播方案/make_cover.py`，一条命令出 4 张：

```text
saved ../02_发布稿/封面_A1.png 900x383
saved ../02_发布稿/封面_A2.png 900x383
saved ../02_发布稿/封面_A1_square.png 383x383
saved ../02_发布稿/封面_A2_square.png 383x383
```

生成后我把图打开看了（不是「生成完就算」）：

- 第一版标题写的是「我做完 16 个**东西**」——和正文改过的「交付物」不一致，改掉重生成；
- 方形版（次条/分享缩略）标题会挤到 3 行，行高收紧后才放得下。

### R9 · 传播方案与追踪表

这一步的关键判断：**C7 考的是「传播设计」，不是「发出去」。**

所以我没有只写「发群 + 朋友圈」，而是写了：

- 三档判断标准（趋势 / 群内影响 / 完成度），明确「不刷量」；
- 渠道顺序（公众号首发 → 24h 群内补一条 → 72h 知乎改写），说明为什么不错峰同步发；
- 互动硬规则（1h 置顶自评、24h 回完、48h 提取问题、7d 整理成下篇引子）；
- 追踪表字段与截图路径，全部留空待填。

## 4. 失败清单（这次真的错了的）

| # | 错在哪 | 严重程度 | 怎么发现的 | 代价 |
|---|---|---|---|---|
| 1 | 把「公开过 1 个」当成事实写进选题 | 🔴 高 | 写稿前强制核对 | 差点用最抓人的假数字开篇 |
| 2 | 托管 Python 缺 `markdown`，直接跑转换失败 | 🟡 中 | 运行报错 | 2 分钟，换解释器解决 |
| 3 | 标题写「16 个东西」与正文「十几个目录」不一致 | 🟡 中 | 通读自查 | 改标题 + 加一行精确说明 |
| 4 | 时间表述夸大（「一年前」「去年十月」） | 🟡 中 | 对照交付日期 | 2 处修正 |
| 5 | 封面第一版用词与正文不一致 | 🟢 低 | 看图复核 | 重生成 4 张 |

:::danger 一个我还没解决的问题（诚实披露）
A2 里我写「我把公众号写作拆成 7 步」。

严格说：**7 步这个数字是这次写 C7 的过程中才固化下来的。**
其中「排版」「合规体检」两步我在 C4B 那篇就用过；「素材台账」「事实核对」「去 AI 味」是这次写成流程的产物。

所以如果读者问「你真的是按这 7 步写的吗」，准确回答是：
**「这套流程是这次边写边定的，定完之后的第 2、3 篇是按它写的。」**

我本来想让 AI 把这句模糊掉（写成「我总结出了一套 7 步流程」，语气就有了资历感）。
**最后没改——因为这类模糊正是 AI 写作最擅长、也最容易毁掉信任的地方。**
:::

## 5. 这次对「AI 写作」的新认识

三条，都是踩出来的：

:::key ① AI 最容易骗你的地方，不是「写错」，是「写得太顺」
数字放大（26 → 上百）、模糊化（12 个 → 十几个）、无中生有（凭空加一句「用户反馈很好」）——
这三类错误全部语法正确、语气自信。
**所以核对不能靠读，必须靠逐个数字回溯。**
:::

:::key ② 结构可以外包，判断不能
AI 排大纲比我快十倍，且更懂「读者想看什么顺序」。
但它不知道「哪个数字能对外说」——因为它不知道那个数字背后有没有东西撑着。
:::

:::key ③ 最值钱的内容，是我原本写给自己看的
A1 的三个结论、A2 的去 AI 味四刀、A3 的能力分层，全部来自我的 AAR 和日志。
**如果没有那些没人看的复盘文档，这次一篇都写不出来。**
:::
