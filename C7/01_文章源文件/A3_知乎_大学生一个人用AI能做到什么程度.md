**结论先行：**

一个人 + AI，可以做出「能跑、有测试、陌生人能打开」的东西。

做不出的是「有人持续在用」的东西——那不是工程问题，是传播问题。

下面是我用一年时间做的 6 个项目，每个都给出：**做了什么 / 关键难点 / 可验证的结果 / 我搞砸的地方**。数字都能在仓库或文章里核到，没有估的。

---

## 先说清楚：这 6 个项目分别是什么

| # | 项目 | 类型 | 规模 | 可验证结果 |
|---|---|---|---|---|
| 1 | 斯坦福 CS146S 中文课程包 | 翻译流水线 | 31 篇文章 + 3 份 PDF | 30/31 篇通过质检（96.8%） |
| 2 | AI4Math 可靠性论文 | 学术写作 | LaTeX 正文 + 参考文献 | 可编译 PDF，可投稿状态 |
| 3 | 公众号排版技能 | 工具/技能 | 1419 行 + 26 测试 | 128 条断言全绿，已发真实文章 |
| 4 | 本地大模型地图 Agent | 本地 Agent | 7 个模块 + 77 单测 | 8GB M1 上完全离线可跑 |
| 5 | GitHub 开源仓库 | 开源发布 | 6 次语义化提交 + v1.0.0 | 公开仓库，MIT |
| 6 | 公众号 AI 写作台 | Web 应用 | 3080 行，零依赖 | 首屏 0.94s，25 项自测全绿 |

这 6 个不是六个独立的作业，是**一条链**：

翻译 → 写论文 → 做技能 → 开源 → 做产品 → 传播。

每一个的产物，是下一个的输入。这一点很关键，后面会讲。

## 项目 1：翻译一门斯坦福课程（教会我「规模」）

**做了什么**

斯坦福 CS146S《The Modern Software Developer》有 31 篇公开阅读材料 + 3 份 PDF。我做了一套中文翻译 + 双语对照语料 + 可复跑的翻译流水线。

**关键难点不是翻译，是一致性。**

31 篇文章，如果每篇单独处理，术语会漂：同一处「agentic」上一版译「智能体」、下一版译「代理」、第三版译「自主智能」。

我的做法是先抽术语表，强制全局替换，再逐篇人工校对。

**结果**

- 30/31 篇正文全译通过质检，**96.8%**
- 唯一的 1 篇没过：Medium 拦截页，离线包里就是个占位页，三种联网途径都失败
- 交付后还补抓了 2 篇原缺口文章

**我搞砸的地方**

我一开始按「篇数」统计覆盖率，算出 100%。

这个数字是假的——有一篇抓下来是 0 字节，按篇数算它「有」，按内容算它什么都没有。

后来我改成按「正文是否通过质检」统计，才有了 96.8% 这个能站住的数字。

> 教训：**覆盖率要用内容算，不能用文件名算。**

## 项目 2：写一篇可投稿的论文（教会我「约束」）

**做了什么**

AI for Math 方向的可靠性框架论文，LaTeX 排版，带完整参考文献。

**关键难点：AI 写论文，最大的风险不是写得差，是「编参考文献」。**

它会把一篇不存在的论文，配上一个格式完美、作者真实、年份合理的引用。

我的处理是三道卡：

1. **所有引用必须来自我实际读过的 PDF**，不读不引；
2. bib 文件逐条核对 DOI / 会议名 / 页码；
3. 正文里每一处「已有研究表明」，必须能定位到具体哪篇。

**结果**

可编译的 paper.pdf + paper.tex + references.bib，独立可复现编译。

**我搞砸的地方**

早期我让 AI 直接生成「相关工作」章节，它写得非常流畅，逻辑自洽。

我差点就信了。

后来抽查三条引用，两条查不到。**如果那一版交出去，就是学术不端。**

> 教训：**AI 在「格式正确」这件事上极其擅长，这恰恰让它编造的内容更难被发现。**

## 项目 3：把官方 starter 改成能用的工具（教会我「验证」）

**做了什么**

公众号排版工具。官方 starter 380 行，我改成 1419 行，配 26 个测试用例、128 条断言。

**关键难点：验证一个工具，不能用它自带的示例。**

starter 的示例文章转出来漂漂亮亮。我差点就交了。

后来我写了一份「把坑都踩一遍」的探针文档：行内代码、嵌套加粗、多段引用、带语言标注的代码块、三列表格、本地图片、SVG、分隔线……13 种边界情况。

跑完，**12 个缺陷，5 个是致命的**：

- 代码块换行被吞成一行（`p.string` 赋值，换行在 HTML 语义里等于空格）
- 加粗里的链接整个消失（`tag.string = tag.get_text()` 拍平了子节点）
- 多段引用被合并
- `<hr>` 被白名单清理逻辑整体删除
- 内联 div 把段落从中间劈开

**结果**

128 条断言全绿，20 秒跑完，可直接挂 CI（有高危项退出码为 1）。

而且它真的用上了——我用它排了一篇 2719 字的文章，发到了真实公众号。

**我搞砸的地方（这条最有价值）**

我自己的代码里，有 5 个 bug 是在「测试看起来通过了」的自信里溜过去的。

最隐蔽的一个：我给代码块加了 `white-space: pre-wrap`，测试显示缩进保留了，就以为没问题。

直到我把真实输出逐行打印出来，才发现 `return` 那行前面的 4 个空格消失了——**BeautifulSoup 会丢弃嵌套标签前面的空白**。

修法是在解析前把缩进换成私有区字符 `U+E000` 占位，解析完换回来。

> 教训：**只写「看起来对」的测试，等于没写测试。**

## 项目 4：8GB 笔记本上跑本地 Agent（教会我「取舍」）

**做了什么**

一个完全离线的本地地图 Agent。跑在 MacBook Air M1 / 8GB 上，用 Gemma 4 E2B 本地模型，7 个模块，77 个离线单元测试。

**关键难点：8GB 内存，模型和工具链要抢内存。**

能做和不能做的边界非常硬：

- 不能做：长上下文、多轮复杂规划、图片理解
- 能做：短指令解析、结构化 POI 查询、固定模板渲染

我最后的选择是：**不追求「什么都能问」，只保证「问这 10 类问题一定答对」**，内置 10 条 POI 知识库，断网也能跑。

**结果**

77 个单测全绿，公开仓库带 `v1.0.0` tag 和 MIT 协议。

**我搞砸的地方**

我一开始想让它「智能」——自由生成回答。

结果是它经常编造一个不存在的教学楼位置，语气还特别自信。

我把方案改成「检索 + 模板渲染」，牺牲了灵活性，换来了不出错。

> 教训：**小模型上的 Agent，可靠性来自限制它的自由度，不是扩大它。**

## 项目 5：把它开源（教会我「入口」）

**做了什么**

把上面那个 Agent 放到 GitHub，公开仓库，写 README、LICENSE、CONTRIBUTING、CHANGELOG、Issue 模板、PR 模板，6 次语义化提交，打 `v1.0.0`。

**关键难点：README 不是说明书，是「30 秒决策依据」。**

陌生人打开你的仓库，只想知道三件事：这是什么、能不能解决我的问题、怎么跑起来。

所以我把一句话说明放在第一行，快速开始放在第二屏，截图放在第三屏。

**我搞砸的地方**

我一度把「本机连不上 GitHub」当成客观障碍，写进交付物当结论。

真实原因是从第一天就在日志里的 `fatal: could not read Username`——是**没有凭据**，不是**网络不通**。

我把一个瞬时观测（`curl` 返回 000）当成了稳定结论。

> 教训：**报告障碍时，必须区分「超时」和「认证」，把两种报错原文都贴出来。**

## 项目 6：上线一个 Web 应用（教会我「约束前置」）

**做了什么**

公众号 AI 写作台：选题 → 标题 → 大纲 → 正文 → 排版 → 体检，一条流程走完。3080 行，零运行时依赖，静态站。

**关键难点：公众号会剥离 `<style>` 和 class。**

这条约束一确认，整个技术选型就变了：不能用 UI 框架、不能用 markdown 库、必须自己写渲染器。

**如果先做界面再发现这条，之前的界面工作全废。**

所以我把「能不能粘进公众号」当成第一约束，而不是最后验收项。

**结果**

- 首屏 FCP **0.94s**，可交互 1.28s（Performance API 口径）
- 8 步流程全通，0 页面报错
- 25 项自测全绿（渲染 15 + AI 层 10）

**我搞砸的地方**

默认模型取「列表第一个」，结果它挂住不返回——界面永远停在「正在找一个值得写的角度」，**不报错、不超时**，端到端测试等满 120 秒。

根因是我以为「列表里有的模型都能用」，实际上「能列出来」和「能稳定写中文长文」是两件事。

> 教训：**设计阶段就要问一句「外部服务不响应时，用户看到什么」。**

## 三个能力分层：AI 到底替掉了什么

这是我最想让你带走的部分。

### 第一层：AI 完全胜任（可以直接外包）

- 格式转换、样板代码、正则、boilerplate
- 把一段乱记的笔记整理成结构
- 起 10 个候选标题
- 解释一个陌生报错的可能原因

### 第二层：AI 很强但会骗你（必须核对）

- 写初稿（流畅但空洞）
- 写参考文献（格式完美但可能不存在）
- 估算工作量（永远乐观）
- 解释「为什么这样设计」（会事后编理由）

**这一层的共同特征：输出看起来越专业，越危险。**

### 第三层：AI 基本无用（只能自己来）

- 判断「这个坑值不值得填」
- 决定「哪个功能先砍掉」
- 承认「我这个方案是错的」
- 判断「这个数字能不能对外说」

第三层决定了你的东西能不能站住。**而它恰好是最难外包的。**

## 一个人做项目，最真实的三条经验

### ① 先找那个「推翻了就要重做」的约束

公众号项目里是「会剥离 style」，翻译项目里是「术语必须全局一致」，Agent 项目里是「8GB 内存」。

**这个约束找到之前，不要写第一行正式代码。**

我吃过这个亏：先画了两天界面，发现约束后全推倒。

### ② 每个结论都要有一个「能被人查」的出处

我说 96.8%，是因为有 `quality_report.json`。
我说 128 条断言，是因为能跑出结果。
我说 0.94s，是因为有 Performance API 的日志。

**没有出处的数字，一个都不要写。** 这既是诚实，也是自保。

### ③ 做完不算完，要给它一个入口

一个公开仓库、一个能打开的网址、一篇说清楚的文章。

我桌面上还有十几个做完但没公开的东西。**它们对世界的贡献是 0。**

这一条我做得最差，也是我现在在补的功课。

## 局限：我做不到的部分

诚实列一下，避免误导：

| 做不到 | 原因 |
|---|---|
| 有人持续使用我的产品 | 没有用户运营能力，也没有渠道 |
| 多人协作 / 团队工程 | 全程一个人，没有 code review |
| 处理超大项目（万行级） | 上下文和精力都是瓶颈 |
| 真正的冷启动推广 | 只会发群和朋友圈，没有投放经验 |
| 硬件/系统级能力 | 环境受限，很多验证跑不了 |

**一个人 + AI 的上限，不在写代码，在「没有人跟你互相校验」。**

这也是为什么我后来开始写文章——把东西公开出去，至少能收到真实的反馈。

---

## 如果你也想开始

最小路径，按顺序：

1. **挑一件你已经做完的事**（不用新做）
2. 把它整理成「别人能打开」的形态（仓库 / 网页 / 文章，任选一个）
3. 写清楚：这是什么、解决什么问题、怎么用、有什么局限
4. 发出去，然后**回一次评论区**

第 4 步是 90% 的人会跳过的一步，也是唯一能把「作品」变成「影响力」的一步。
