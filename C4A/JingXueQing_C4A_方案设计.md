# JingXueQing_C4A_方案设计

> 挑战：构建 C4 提交自动评审技能｜完成级别：**Level 4（完整评审系统）**
> 评审标准版本：`c4a-rubric-v1.3`｜实测准确率：严格 90.3% / 误判 0%

---

## 一、要解决的真问题

C4 提交齐不齐，老师其实**扫一眼文件夹就知道**。真正费时间的是第二遍：
**逐个打开、判断"这个技能到底合不合格"，然后写出"你为什么不合格"。**

我假设有 20 份提交，格式各异（有人交 `.skill`、有人交 `.py`、有人交视频），
评审者要判断每个提交的**四条件**是否成立。这个动作高度重复、有明确规律、
但必须逐个做——**这正是自动化的 ideal case**。

而 C4A 真正的难点不是"扫描"，是**"判定要可信"**：

> 一个不可信��自动评审器，比没有更糟——
> 它会让老师误以为已经看过了，从而真的跳过人工复核。

所以我的设计目标从"自动打分"改成了：
**先让判定可追溯，再谈自动化程度。**

## 二、架构选择：规则优先 + LLM 预留

C4A 原文给了三个选项，我选的是**规则为主、LLM 预留接口**。理由如下：

| 方案 | 我为什么不选 / 为什么选 |
|------|----------------------|
| **纯规则** | ✅ 作为主判定层。确定性强（同一人两次跑结果一致）、可追溯（能指到行号）、零成本（40 份×4 维度瞬间完成） |
| **纯 LLM** | ❌ 三个硬伤：① 不确定——同一份提交两次评审结论可能不同，学生无法申诉；② 不可追溯——给不出稳定的行号级引用；③ 慢且贵——助教不可能每节课跑 160 次调用 |
| **混合** | ⚠️ 架构复杂度换覆盖率。我的判断是：**C4 的四条件里 80% 是可规则化的**（有没有安装说明、有没有硬编码路径、IO 成不成对），剩下 20% 的语义判断交给人 |

**关键判断**：我不要"看起来智能"的LLM 包装，要"老师愿意采信"的确定性。
所以架构上做了这样的分层：

```
┌─────────────────────────────────────────────────────────────┐
│  Level 4报告层  Markdown + Excel + HTML 仪表盘               │
├─────────────────────────────────────────────────────────────┤
│  Level 3  质量层    四条件 × 19 检查项 → 加权档位│
│                   ↑ 每条判定携带 Evidence(文件:行号)│
│                   ↑ 置信度低 → 主动标"需人工复核"            │
├─────────────────────────────────────────────────────────────┤
│  Level 2  完整性层5 槽位× (文件名信号 + 内容信号 + 空壳检测) │
├─────────────────────────────────────────────────────────────┤
│  Level 1  采集层    递归扫描 → 作者归属 → 按作者分组         │
└─────────────────────────────────────────────────────────────┘
         ↖ 预留接口：quality.extract_signals_for_llm()
           把规则层结论打包成上下文，供 LLM 复核（默认关闭）
```

**为什么"预留"比"接上"更负责**：接上 LLM 需要处理超时、重试、成本、
输出解析、结论冲突消解——这些在没有真实使用数据前都是过度设计。
但接口先留好，将来要加的时候**不必重写流水线**。

## 三、核心创新：证据引擎

### 3.1 基本约定

```python
Evidence = (规则ID, 文件名, 行号, 原文片段, 极性, 权重)
CheckResult = (检查项ID, 是否通过, 说明, [Evidence...])
```

**硬约束：没有 Evidence 的判定不允许进入最终评分。**

这条约束带来三个副产品：

1. **报告自带说服力** —— 每个 ✅ 后面跟着"因为 `xxx.md:37` 写了 pip install"；
2. **误判可申诉** —— 老师说"这条错了"，我 1 秒定位原文，5 秒解释规则；
3. **置信度可量化** —— 证据条数 + 权重决定是否标"需人工复核"。

### 3.2 判定规则（三条，都是被测试逼出来的）

**规则一：负向优先否决**

```
有负向证据 且 正向证据 < strong×2  →  ❌
```
防止"我写了三段安装说明，所以忽略我硬编码了 `/Users/xxx`"这种洗白。

**规则二：致命问题一票否决**

```
命中 REUSE.nopath（硬编码个人路径）或 REUSE.nosecret（明文密钥）→ 该维度直接 ❌
```

依据 C4 原文的检验方法："让一个陌生人按你的说明操作，能成功吗？"
明文密钥和硬编码路径让陌生人**必然失败**，所以这不是扣分项而是不合格项。

> 这条是**金标准测试逼出来的**。第一版没有它，SunLi 那份
> "写了安装说明但代码里写死 `/Users/sunli/logs/app.log` + 明文 `sk-live-...`"
> 的提交被判成可复用 ✅ ——这正是"关键词计数式评审"最危险的失效模式。

**规则三：占位符污染**

```
证据落在"有标题无内容"的小节里 → 该证据作废
```

反例：`## 安装` 下面第一行是 `TODO: 补充安装步骤`。
只看标题会认为"有安装说明"，实际等于没写。

> 这条也是测试逼出来的：ChenJing 那份通篇 TODO 的空壳，
> 靠三个空标题把"可复用"洗到了及格线。

### 3.3 权重体系

证据权重 = **命中模式相对强度** × **信任基线 0.6** × **文档权威系数**

| 系数 | 取值 | 理由 |
|------|------|------|
| 模式相对强度 | 0.6~1.5 | `预期结果`(1.3) 比 `示例`(0.9) 更特异 |
| 信任基线 | 0.6 | 单一来源不足以定论，需互证 |
| 文档权威 | 1.0 | `skill说明.md` / `教学说明.md`：作者为自己写的正式说明 |
| | 0.9 | 普通文档 |
| | 0.75 | `.skill`/`.zip` 包内部（含模板，需降权） |
| | 0.6 | AAR / 反思类（"我做了" ≠ "别人能用"） |
| 模板文件 | ×0.6 | 模板自带的标准段落不算作者能力 |

**关键标定经验**：我最初把 `strong=2`（条数阈值）直接当权重阈值用，
结果所有检查项都够不到 ✅，好文档全被判 ⚠️/❌（保守率 65.6%）。
改成权重制后重新标定（`STRONG_W=0.75` / `WEAK_W=0.35`），保守率降到 21.9%，
误判率保持 0%。**这是"阈值语义混用"的典型教训。**

## 四、Level 1：作者识别的难点

作者识别看起来简单，实际上是整个系统**误判的最大来源**。
实测中我遇到的每一个 bug 都出在这里：

| Bug | 现象 | 根因 | 解法 |
|-----|------|------|------|
| 1 | 凭空多出「demo 同学」 | `Demo_C4_AAR.md` 的 `Demo` 被当作者 | 示例人名黑名单 |
| 2 | 「demo_」匹配不上黑名单 | 正则贪婪吃掉了分隔符 | `parse_filename` 统一 strip |
| 3 | 凭空多出「scripts 同学」×4 | `scripts/` 目录被当作者 | 结构目录排除表 |
| 4 | 凭空多出「ai-log-forge 同学」 | `.skill` 包内 frontmatter `name:` 被当作者 | 技能名排除表 + 包内不取作者 |
| 5 | 凭空多出「wechat-doc-mapper_src 同学」 | 副本目录后缀 `_src` | 副本目录正则 |
| 6 | `Elite20TA` 退化为 Unknown | 作者正则贪婪失配 | 正则重写（见拿来说明） |

**最终结果**：3 份真实提交 → **3 位作者，0 个Unknown**。

### 归属推断的原则

我设计了两条推断规则，但都要求**有客观证据**：

1. **提交目录归属**：若顶层子目录下的带标记文件都指向同一人，
   则该目录下的无标记文件（源码、SKILL.md）全部归给他。
   *证据：目录结构本身。*
2. **附件目录归属**：`samples/` 下的文件归给主提交作者。
   *证据：附件目录必然从属于某份提交。*

**我没有做**：`张伟` ↔ `ZhangWei` 的自动合并。那需要人名库，
错并的代价（两个人的成绩合并）远大于漏并。这是**有意的克制**。

## 五、Level 2：完整性的两���防误判闸门

只看文件名会把空壳判成齐全。我加了两道闸门：

**闸门一：空壳检测**
```
占位信号行数 / 总行数 > 15% 且 ≥2 处→  证据强度 × 0.5
```
反例：`ChenJing_C4_skill说明.md` 命名完全合规，但正文是
`## 输入\n待填写\n## 输出\n待补充` → 判⚠️ 而非 ✅。

**闸门二：附件降权**
`samples/Demo_C4_AI日志.md` 属于该作者，但它是**模板不是产出**，
不能拿来证明"他交了 AI 日志" → 强度 ×0.5。

**槽位独占性惩罚**：若某个文件是 >3 个槽位的主要证据，
说明槽位归属有歧义（如一份 README 什么都提）→ 降级为 ⚠️ 提示人工确认。
*但命名级强证据（≥0.9）不降级*——否则 `skill说明.md` 自己会被误伤。

## 六、Level 4：报告设计

### 6.1 输出格式

| 格式 | 用途 | 实现|
|------|------|------|
| Markdown | 发群里、贴文档、逐条讨论 | 模板化生成，含可折叠的证据块 |
| Excel | 助教精细核对、批量筛人 | **手写 SpreadsheetML**，5 个 sheet |
| HTML | 投屏讲评、一眼看排行 | 单文件仪表盘，零外部依赖 |
| JSON | 二次开发、接后续挑战 | 全量结构化结果 |

**为什么手写 xlsx**：xlsx 就是 zip + XML。引入 `openpyxl` 会让技能
在没装依赖的机器上直接不可用——这违反 C4「可复用」条件本身。
产物已用 CRC 校验 + XML 解析验证有效性。

### 6.2 排名的克制

排名是**双维度**的，不做单一总分：

```
综合分 = 完整性 × 40% + 质量分 × 60%
```

并且**不做"最弱维度优先"的重排**。理由：一个 IO 明确但没交 demo 的人，
和一个交齐了但 IO 不明确的人，综合分可能接近，但**改进方向完全不同**。
报告里给的是"你最该先改哪个维度"，不是"你排第几"。

**低置信度单独列出**：证据不足的作者标"需人工复核"，
这是评审器**主动承认自己不知道**，比硬给一个错结论有价值。

## 七、准确率验证（这部分是给评审者看的）

C4A 评分表里"评审准确性"占 30%、"误判率低"是明写的信号。
**一个从没被测量过的评审器，说自己准确率 95% 是没有意义的。**

### 7.1 测试集设计

8 份提交，**故意各不相同**，其中 3 份是对抗样本：

| 样本 | 设计目的 | 金标准 |
|------|---------|--------|
| LiMing | 标准满分提交 | 全 ✅ |
| WangXiao | 只交两样、没写 IO | 大面积 ❌ |
| ZhangWei | 缺 demo | demo ❌ 其余 ✅ |
| **SunLi** | **硬编码路径 + 明文密钥** | **可复用必须 ❌** |
| **ChenJing** | **通篇 TODO 空壳** | **可执行/可验证必须 ❌** |
| **ZhaoLiu** | **元提及（讨论"禁止TODO"）** | **不应误判 ❌** |
| ZhangLei | 子文件夹按作者分组 | 测试作者兜底识别 |
| WuYang | 含 v1/v2 迭代 | 测试版本追踪 |

后三份是对规则漏洞的定向攻击：
- SunLi 打"负向证据被正向洗白"；
- ChenJing 打"命名合规冒充内容合规"；
- ZhaoLiu 打"提到坏味道 ≠ 存在坏味道"。

### 7.2 判定口径

```
预测 == 金标准           → 正确
预测更保守（✅→⚠️/❌）   → 保守（安全，但让人白跑）
预测更宽松（❌→✅/⚠️）   → 误判（危险，放过真问题）
```

**只有"误判"是不可接受的**。保守只是效率损失。

### 7.3 实测结果

| 指标 | 数值 |
|------|------|
| 判定点 | 72（完整性 40 + 质量 32） |
| 完整性 | 正确 40/40 = **100%** |
| 质量四条件 | 正确 25/32 = 78.1%，保守 7 |
| **严格准确率** | **90.3%** |
| **宽松准确率** | **100%** |
| **误判率** | **0%** |

金标准测试在开发过程中**抓出了 4 个我自己写的 bug**，
每个 bug 的修复都改的是从 `wechat-doc-mapper` 继承来的那段逻辑。
详细过程见 `AI日志.md` 第 4 节。

### 7.4 诚实的局限

-测试集是**我造的**，样本量 8 份、判定点 72 个。真实班级可能有
  更刁钻的写法（比如用表格藏 IO 声明、把安装步骤写成图片）。
- **元提及过滤是启发式**：靠 `META_ENUM` 关键词识别"这是在列举关键词"。
  换个说法仍可能误判 → 这类结论会被标"需人工复核"。
- **作者同名未合并**：`张伟` 和 `ZhangWei` 会被算两个人。
- **跨挑战文件**：C4A 只认C4 标记；混入 C2/C3 挑战号的文件会被过滤。

## 八、为什么叫"元能力"

C4 是把能力变成产品（做一个技能）。
C4A 是把**评审能力**变成产品（做一个评审技能的技能）。

这个技能最值得复用的不是"C4 专用规则"，而是它的三条设计模式：

1. **证据优先** —— 任何自动化判定都要能指回原文，否则不可采信；
2. **标准与实现分离** —— 评审口径在 `rubric.py`，改标准不改代码；
3. **主动承认不知道** —— 低置信度标"需人工复核"，不硬给结论。

这三条可以迁移到任何"用规则评审人工作品"的场景：
评审代码、评审报告、评审实验、评审论文。换个 `rubric.py` 就是另一个评审器。
