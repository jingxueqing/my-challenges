## 一、AI 工具与协作方式

| 项 | 内容 |
|----|------|
| **主要 AI** | WorkBuddy（Claude 驱动的 agent，本机执行代码、改文件、跑测试） |
| **辅助** | 无第二家AI；评审标准的定义参考了 C4 挑战原文 + `skill-explainer` 的四维矩阵 |
| **协作模式** | 人给方向与判据 → AI 写实现 → **我亲自跑测试并裁定对错** → AI 修|
| **人的核心投入** | ① 定义"什么算误判"；② 造对抗样本；③ 裁定金标准；④ 决定架构取舍 |

**分工原则**：我不让AI 决定"判得对不对"，只让它执行判定。
理由：金标准是我定的，测试是我跑的，对错是我裁的。
AI 负责把意图翻译成代码，不负责给自己打分。

## 二、迭代过程（共 5 轮，每轮都有实测输出）

### 第 1 轮：骨架落地，跑通全流程

**我做的**：读完 `wechat-doc-mapper` 全部源码 → 定四层架构 → 让 AI 实现 8 个模块。

**【实测】** 首次跑通，对自己的 C4 提交输出报告。**结果全是错的**：

```
识别提交：2 位作者（实际 1 位）
jingxueqing 完整性 0/5 ⚠️（实际 5/5 齐全）
可复用 ✅（但检出 2 处问题信号仍判✅）
```

**我判断**：4 个 bug。定位过程：

| 现象 | 根因 | 定性 |
|------|------|------|
| 冒出「demo 同学」 | `samples/Demo_C4_AAR.md` 的 `Demo` 被当作者 | 误判 |
| 5 个槽位全判 ⚠️ | 独占性惩罚把 `skill说明.md` 也算成"身兼多职" | 逻辑bug |
| 完整性 0/5 但证据强度 1.00 | 惩罚逻辑写反，强证据被降级 | 逻辑 bug |
| 检出硬编码路径仍判可复用 ✅ | 负向证据只影响"检查项通过率"，没有否决权 | **危险 bug** |

**第 4 条最严重**：一份把密钥写死在代码里的提交被判"可复用"——
这是会把别人机器搞砸的误判。我当时就决定：**这个必须用测试钉死，不能靠眼看。**

### 第 2 轮：造金标准测试集（本项目最关键的一步）

**我做的**：手写 8 份测试提交 + 人工标注金标准。

关键设计是**3 份对抗样本**，专门打规则的漏洞：

- **SunLi**：内容漂亮但代码里`LOG_PATH = "/Users/sunli/logs/app.log"` +
  `API_KEY = "sk-live-9f8a..."`。期望可复用 ❌。
  *（我特意把明文密钥写成 `sk-live-` 前缀 + 32 位hex，模拟真实泄露形态）*
- **ChenJing**：通篇「待补充 / TODO」。期望可执行 ❌、可验证 ❌。
- **ZhaoLiu**：文档里正经讨论「禁止硬编码路径 / 不要留 TODO」，
  还列了 `[编码检查, 路径检查, TODO 检查]` 这样的关键词清单。期望**不误判**。

**【实测】** 首次跑测试，直接暴露 5 个误判：

```
严格准确率 86.1%  误判率 6.9%
❌ 误判明细：
  - [质量] SunLi.可复用: 预测 ✅ / 金标准 ❌   ← 危险！
  - [完整性] ChenJing.skill_doc: 预测 ✅ / 金标准 ⚠️
  - [质量] ChenJing.可复用: 预测 ✅ / 金标准 ❌
```

**我裁定**：SunLi 那条是**不可接受的误判**（放过真问题），
其余属"保守"，可以接受但要修。

### 第 3 轮：修致命误判（引入三条判定规则）

**我做的**：给出规则设计，AI 实现。

| 改动 | 目的 | 文件 |
|------|------|------|
| `FATAL_CHECKS` 一票否决 | 明文密钥/硬编码路径 → 该维度直接 ❌ | `quality.py` |
| `absence_is_pass` | 纯负向检查项"零证据即通过" | `evidence.py` |
| 负向检查项权重降到 0.45 | "没犯错"≠"写清楚了" | `quality.py` |
| 空壳检测 | 命名合规但正文是占位 → 降级 ⚠️ | `completeness.py` |
| 占位符污染过滤 | 「## 安装」+「TODO: 补充」不算有安装说明 | `quality.py` |

**【实测】**

```
严格 87.5% → 误判 1.4%（仅剩 ChenJing 可复用）
```

第4 项（空壳检测）立刻见效：完整性误判从 2 条降到 0。

**中途的一个弯路（诚实记录）**：我第一版空壳检测加了
「正文 < 200 字符 → 强度 ×0.7」，结果**12 个判定从正确变保守**（保守率 30%），
因为正常的教学说明本来就短。**这是我凭直觉设的阈值，没有数据支撑。**
改成只按"占位信号密度 >15%"判定后，保守率回落到 21.9%。
教训：**阈值必须有数据，不能靠感觉。**

---

### 第 4 轮：权重标定（误判率归零）

**我做的**：把准确率当优化目标，逐条看误判、调阈值。

这一轮我改了**四版阈值**，过程如下：

| 版本 | 改动 | 【实测】严格准确率 | 误判率 | 保守率 |
|------|------|----------------|--------|--------|
| v1.0 | 初始版（按条数计数） | 86.1% | 6.9% | — |
| v1.1 | +致命否决+空壳检测 | 87.5% | 1.4% | — |
| v1.2 | +占位符污染过滤 | 90.3% | 0% | 21.9% |
| v1.2-b | 权重改阈值语义混用版 | 70.8% | 0% | **65.6%** ⚠️ | 
| v1.3 | 重新标定 STRONG_W=0.75 | **90.3%** | **0%** | **21.9%** |

**v1.2-b 是一次倒退，值得记下来**：
我把 `strong_threshold=2`（意思是"2 条证据"）直接当成权重阈值 2.0 用，
结果所有检查项都够不到 ✅，好文档全被判 ⚠️/❌。
**根因是"条数阈值"和"权重阈值"语义混用**——这是我在写 `evidence.py` 时
没有想清楚的代价。后来按实测权重分布重新标定才修好。

**最终【实测】结果**：

```
【完整性判定】正确 40/40 = 100%
【质量四条件】正确 25/32 = 78.1%，保守 7
严格准确率90.3%  宽松准确率 100%  误判率 0%
```

### 第 5 轮：真实多提交压力测试，又抓到 3 个 bug

**我做的**：把 3 份真实 C4 提交（`wechat-doc-mapper`、`skill-explainer`、
本人的 `ai-log-forge`）组装成模拟 WeChat 群文件夹，跑完整流水线。

**【实测】** 第一次跑：3 份提交识别出 **8 位作者**。错的。

| 虚假作者 | 根因 |
|---------|------|
| `scripts`（×4 个文件） | `scripts/` 目录被当作者 |
| `ai-log-forge` | `.skill` 包内 frontmatter `name:` 被当作者 |
| `wechat-doc-mapper_src` | 副本目录后缀 `_src` |
| `skill-explainer_src` | 同上 |
| `Elite20TA` 退化为 Unknown | 作者正则贪婪失配 |

**这一轮我修的东西，全都是"从 `wechat-doc-mapper` 继承来的那段逻辑"。**
具体加了：结构目录排除表、技能名排除表（预扫描 `.skill` 包收集技能名）、
副本目录正则、作者正则重写、提交目录归属推断。

正则重写这里有个细节值得记：
`Elite20TA_C4_skill-explainer` 原版正则**整条失配**。
我第一版改成"非贪婪"后仍失配，最后发现是 `[A-Za-z\-]+` 里
连字符让作者段可以无限膨胀。正确写法是允许**内部连字符但不认下划线**：

```python
r"^(?P<author>[A-Za-z](?:[A-Za-z\-.]?[A-Za-z0-9]){0,29}|[\u4e00-\u9fff]{2,8})"
r"[-_](?P<challenge>C\d{1,2}[A-Z]?)[-_](?P<part>.+)$"
```

**【实测】** 修复后：**3 位作者，0 个 Unknown** ✅

## 四、被测试抓出来的 4 个 bug（最有价值的部分）

这 4 个 bug **全部是我自己写的**，全部由金标准测试暴露，
全部改的是从 `wechat-doc-mapper` 继承的逻辑：

| # | Bug | 危害 | 根因 | 修法 |
|---|-----|------|------|------|
| 1 | 硬编码路径 + 明文密钥被判可复用 ✅ | **会把别人机器搞砸** | 负向证据没有否决权 | `FATAL_CHECKS` 一票否决 |
| 2 | 通篇 TODO 的空壳靠空标题洗成及格 | **放过未完成品** | 只看标题不看正文 | 占位符污染过滤 |
| 3 | 正常短文档被判篇幅不足 | 保守率 30% | 200 字符阈值凭感觉设的 | 改按占位信号密度 |
| 4 | `scripts` 目录变成 4 位作者 | 排名完全错乱 | 父文件夹兜底没排除结构目录 | 结构目录排除表 |

**如果只写代码不写测试，这 4 个 bug 会全部带进提交。**
这是我认为"AI-First"真正的价值：AI 写得快，
但**"什么算错"必须由人定义并用测试钉死**。

## 五、我负责判断、AI 负责执行的分界

明确一下人机分工，避免"全是AI 做的"这种含糊：

| 环节 | 谁主导 | 具体 |
|------|-------|------|
| 架构选型 | **我** | 我在"纯规则/纯 LLM/混合"里选了规则优先，理由是评审要可复现可申诉 |
| 证据引擎设计 | **我** | 我提出"没有证据的判定不许进评分"，AI 实现 |
| 评审维度定义 | **我** | 19 个检查项的信号与阈值，逐条我定 |
| 误判定义 | **我** | 我定义"预测更宽松 = 误判（不可接受），更保守 = 可接受" |
| 金标准 | **我** | 8 份样本的期望档位全部人工标注 |
| 测试裁定 | **我** | 每轮跑完由我判断"这条能不能接受" |
| 代码实现 | AI | 8 个模块共 3,580 行（含测试集生成脚本712 行） |
| 边界测试 | AI | 空目录/非目录/垃圾文件/超大文件 |
| 文档撰写 | AI 起草 + **我审校** | 全部文档我逐份核对过数据与实测输出 |

**一句话**：AI 负责把"判定规则"变成"可运行的代码"，
我负责定义规则本身并裁定它对不对。

## 六、诚实的不足

1. **测试集是我造的**（8 份 / 72 判定点）。样本量不大，
   真实班级的刁钻写法可能超出我的对抗样本设计。**90.3% 不能外推到任意班级。**
2. **元提及过滤是启发式**。靠 `META_ENUM` 关键词识别"这是在列举关键词"，
   换种写法仍可能误判 → 这类结论已标"需人工复核"。
3. **作者同名未合并**。`张伟` 与 `ZhangWei` 会被算两个人，
   我选择不自动合并（错并代价大于漏并）。
4. **LLM 深审只是预留接口**，没有真正接上。架构上留了位置，
   但没有真实使用数据前接上属于过度设计。
5. **Excel 是手写 SpreadsheetML**，只支持我需要的样式（表头加粗+底色）。
   复杂图表、冻结窗格、多条件格式没有实现——因为自己用不上。
