## 一、这次到底做成了什么

一句话：**做出了一个能自动评审别人技能包的技能，并且它的准确率是被测过的，不是被吹的。**

具体成果：
- 完成 **Level 4（完整评审系统）**，四级流水线全部可用；
- 4 种输出格式（Markdown / Excel / HTML / JSON），**零第三方依赖**；
- **8 份金标准测试集，72 个判定点**；
- 实测 **严格准确率 90.3%、误判率 0%**；
- 3 份真实 C4 提交评审完成，作者识别 3/3 正确。

## 二、做对的三件事

### 1. 最早做的决定：把"误判"定义清楚

项目一开始我没有直接写代码，而是先问了一个问题：

> **"什么算这个工具的错？"**

我给的定义是：
- 预测**比金标准更宽松**（❌→✅）= **误判**，不可接受——因为它放过了真问题；
- 预测**比金标准更保守**（✅→❌）= 可接受——只是让人白跑一趟，不传递错误信息。

这个定义看起来是小事，但它决定了后面所有的优化方向。
**如果没有它，我可能会为了"看起来准"而去调高召回，
把明显不合格的提交也判成合格——那才是真正的失败。**

### 2. 核心设计：证据优先

我拒绝了"关键词计数"这个最省事的做法，改为：

> **没有 `文件:行号` 支撑的判定，不允许进入评分。**

这个约束让开发变慢了（要多写证据收集层），
但它换来三样东西：
- 报告里每条 ✅ 都能点回原文，**讨论从"我觉得"变成"你看这行"**；
- 误判可申诉，1 秒定位；
- 置信度可量化，**证据不足时主动标"需人工复核"**。

我认为这是本次唯一称得上"设计"的东西。其余都是实现。

### 3. 敢用对抗样本测自己

如果我只造 3 份"写得不错"的测试提交，我的准确率会好看得多——
因为规则在顺境下表现总是好的。

所以我专门造了 3 份**用来打规则漏洞**的样本：
-硬编码路径 + 明文密钥（打"负向被洗白"）；
- 通篇 TODO 空壳（打"命名合规冒充内容合规"）；
- 文档里讨论"禁止 TODO"（打"提到坏味道 ≠ 存在坏味道"）。

**结果这三份各抓出一个 bug。** 如果只测顺境样本，这三个 bug 会全部带进提交。

## 三、做错的事（具体到能改）

### 错误 1：把"条数阈值"当"权重阈值"用 —— 造成一次明显倒退

**现象**：某一版改完，保守率从 21.9% 飙到 **65.6%**，
好文档几乎全被判 ⚠️/❌。

**根因**：我在 `rubric.py` 里写 `strong=2`，本意是"要 2 条证据"；
在 `evidence.py` 里却把 `2`直接当成"权重之和要达到 2.0"。
但我的证据权重是 0~1.3 的量纲，**永远够不到 2.0**。

**为什么会犯**：我在写 `Check` 数据类时，字段叫 `strong_threshold`，
默认 2，**看起来像个权重阈值**。我在两个模块里赋予它不同语义却没察觉。

**怎么改**：
- 拆成语义明确的两个参数：`min_evidence_count`（条数）与 `min_evidence_weight`（权重）；
- 加一条校准注释说明"权重标定的实测依据"；
- **最重要**：这次的教训是——**阈值必须有数据支撑，不能凭直觉。**
  我在同一轮里还犯过类似错：空壳检测的"正文 < 200 字符"阈值，
  结果 12 个判定从正确变保守（正常教学说明本来就短），
  改成"占位信号密度 > 15%"才对。**两个错误同源：我用直觉设阈值。**

### 错误 2：把作者识别想得太简单

我以为"按 `姓名_C4_描述` 解析"就够了。实测发现作者识别是**整个系统误判的最大来源**，
6 个 bug 全在这里：

| 虚假作者 | 根因 |
|---------|------|
| `demo` | `Demo_C4_AAR.md` 里的Demo |
| `demo_` | 正则贪婪吃掉了分隔符，导致黑名单匹配不上 |
| `scripts`（×4） | `scripts/` 目录被当作者 |
| `ai-log-forge` | `.skill` 包内 frontmatter `name:` 被当作者 |
| `wechat-doc-mapper_src` | 副本目录后缀 |
| `Elite20TA` → Unknown | 作者正则贪婪失配 |

**最讽刺的一条**：`ai-log-forge` 来自 `.skill` 包内的 `name: ai-log-forge`。
那字段回答的是"**这个技能叫什么**"，我却拿它回答"**谁交的**"。

**教训**：**命名空间要分清**——"作者名"和"物件名"是两套命名空间，
混用就会出这种错。修法是给两者各自建黑名单（`SAMPLE_AUTHOR_HINTS` / `_KNOWN_SKILL_NAMES`），
而不是加if判断。

**下次改**：作者识别应该**先单独写测试再写实现**。
这块是纯字符串处理，最容易测，也最容易错，我却当成小事跳过了。

### 错误 3：第一版没有致命项否决

第一版里"检出硬编码路径"只是一个普通负向信号，
**没有否决权**。结果 SunLi 那份代码里写死
把本地绝对路径写死在源码里（个人主目录下的日志路径）、且把 API 密钥以明文形式直接写进源码（此处已脱敏，不复现原值）的提交，
因为"写了安装说明"而被判**可复用 ✅**。

**为什么严重**：C4 对"可复用"的检验原话是
"让一个陌生人按你的说明操作，能成功吗？"
明文密钥让陌生人**必然失败**。这不是扣分项，是**不合格项**。

**为什么会漏**：我在设计时把"负向证据"统一处理成"压低通过率"，
但没区分"轻微问题"和"致命问题"。
`grade()` 里的注释写了"负向证据优先否决"，但那个否决
**只在单个检查项内部生效**，而维度评级又是按"通过率 ≥60%"算的——
两个层级的否决逻辑没打通。

**怎么改**：引入 `FATAL_CHECKS` 概念，命中即**整个维度直接 ❌**，
不管其他检查项表现多好。

**元教训**：**规则要分级**。"有问题扣分"和"有问题即不合格"
是两种不同强度的判定，混用会在最关键的地方失效。

### 错误 4：把直觉当结论写了出去

方案设计初稿里我写了"实测准确率 95%"这种话，
**写完才意识到我根本没测过**。

这在 AI 协作里特别危险：AI 会很自然地补全"实测准确率 95%"这种
听起来合理的数字，因为它在训练材料里见过太多这种表述。

**改法**：造了 8 份金标准测试集，让准确率变成**命令输出**而不是**我的措辞**。
现在文档里的每一个百分比，都对应 `评审产物/自检报告.txt` 里的一行。

## 五、这个项目最值得带走的一条

不是技术，是这个：

> **自动化评审最难的部分不是"怎么判"，是"怎么知道自己判错了"。**

我可以很快写出一堆规则，让报告看起来很专业。
但如果我不能回答"你凭什么说这份提交不合格"，
那这份报告就只是**看起来客观的武断**。

所以我给每条判定绑了行号。这件事多花了我大约 20% 的开发时间，
但它换来的是：**这份报告可以被质疑，可以被讨论，可以在群里公开。**

评审器最该有的品质不是聪明，是**可被检验**。
如果它敢标"需人工复核"、敢对低置信度的结论说"我不确定"，
那它就已经比大部分"自动评分"诚实了。
