## 2. Agent 能力验证

### 2.1 原生 function calling：模型自主选工具

最终那次运行，**模型自己决定**调用了 4 个工具（没有任何硬编码路由）：

```
✓ 1. geocode_local({"name": "SIAS University (郑州西亚斯学院)"})            11ms
   ↳ {"matched": true, "latitude": 34.4166, "longitude": 113.753, "confidence": 0.15}
✓ 2. search_poi({"category": "campus", "keyword": "SIAS University", "limit": 5})  8ms
   ↳ count=4 → ['西亚斯学院-图书馆', '西亚斯学院-艺术中心', '西亚斯学院-南门', '西亚斯学院-学生公寓']
✓ 3. search_poi({"category": "sight", "keyword": "郑州", "limit": 5})        1ms
   ↳ count=1, relaxed=true → ['黄河故里旅游区']
✓ 4. route_plan({"mode": "walking", "points": [[34.4166,113.753],[34.452,113.718]]})  3ms
   ↳ {"total_distance_km": 5.079, "total_minutes": 63.5}
```

值得注意的两点：
- **第 3 次调用触发了 `relaxed=true`**：模型传了 `category=sight + keyword=郑州`，
  严格 AND 匹配下应该返回空。工具自动放宽为「仅按类别」，Agent 得以继续。
  **这是我在看到第一版结果只有 5 个校园点后专门修的 bug**（详见第 4 节）。
- **第 4 次调用 `route_plan`** 是模型自己判断需要算距离，
  输入坐标直接取自前两次工具的返回值——这就是多步推理的证据。

### 2.2 结构化输出：schema 约束解码

- **机制**：Ollama 原生 `format: <JSON Schema>`，在**解码期**约束采样路径，
  而不是靠 prompt 请求「请输出 JSON」。
- **兜底**：失败时把真实报错回灌给模型自修复（`json_chat`，最多 2 轮）。
- **实测**：主任务 5 次调用全部一次通过 schema 校验，**JSON 成功率 5/5 = 100%**。
- **产出**：5 个标记点，每个 8 个字段（中英名称、类别、经纬度、中英描述、评分）。

## 4. 发现并修复的真实缺陷

这一节我认为比成功经验更能说明工程质量。三个 bug 都是**实跑才暴露**的。

### Bug A：`search_poi` 严格 AND 导致 Agent 提前收工（影响产出质量）

- **现象**：第一次运行只生成 5 个**全在校园内**的点，没有周边地标。
- **根因**：模型传 `category="sight" + keyword="SIAS University"`，
  关键词与类别无交集 → 返回 0 → Agent 认为「周边没有景点」直接收工。
- **修复**：严格 AND 无结果时，退化为「仅按类别」，并在返回值里显式标注
  `relaxed: true`，让模型知道这是放宽结果。同步强化 system prompt，
  要求**换不同 category 多次调用**。
- **效果**：修复后返回 `relaxed=true count=1 → ['黄河故里旅游区']`（5.08 km），
  地图首次覆盖到校外。测试从 66 → 69 个。

### Bug B：多模态图片根本没送进模型（能力完全失效）

- **现象**：视觉 Agent 输出 `是否校园照片: None`，所有字段都是 None。
- **排查**：直接打 API 发现模型**确实能描述图片**（「红砖建筑…草地…蓝天」），
  说明模型没问题，是我的封装有 bug。
- **根因**：
  ```python
  for m in messages:
      if m.get("role") == "user" ...:
          m = dict(m)          # ← 只重绑了局部变量，list 没被改
          m["images"] = images
          break
  ```
  `messages` 从未被修改，payload 里的 user 消息**始终没有 images 字段**。
- **修复**：重建 list（`[dict(m) for m in messages]`）并在**最后一条** user 消息上挂图。
- **顺带发现**：`_extract_json` 当时是"成功"的（模型返回了自由文本，
  被宽松解析器吃下来），于是**所有 `.get()` 都拿到 None，但代码看起来一切正常**——
  这类"静默失败"比崩溃更危险。现在改用 schema 约束解码，
  键名由解码器保证，且加了 4 个回归测试。

### Bug C：坐标幻觉 —— 88.5 km 偏差被自动纠正

- **现象**：多轮对话里「加一个开封」，模型给出 `34.5092,113.4050`，
  与权威坐标差 **88.5 km**。
- **为什么没被原来的 `_sanitize` 拦住**：它只拦「离郑州 >500 km」，
  88.5 km 属于「看起来合理」的范围，**逃过了所有检测**。
- **修复**：加**名称锚定（grounding）**——凡是名称能匹配本地知识库，
  一律强制吸附到知识库坐标；名称不在知识库的**不强制**（否则会造出错误点位）。
  纠正动作记入 `grounding_fixes`，并写进 `source` 字段（`+grounded`）。
- **效果**：`34.5092,113.4050` → `34.7970,114.3070`，审计日志：
  ```
  开封: 模型输出 (34.5092,113.4050) 被纠正为 权威坐标 (34.7970,114.3070)，偏差 88.5km
  ```
- 测试从 73 → 77 个，含 5 条 grounding 专项断言。

> 附带的第四个 bug（截图字体）：最初用 SFNSMono（macOS 默认等宽），
> **所有中文渲染成空白**，截图等于无效。换成 PingFang 并按全角宽度重算行宽。
> 截图底部仍标注数据来源文件，便于核对。

## 5. 性能调优（Level 4 完成项）

固定模型、只变 `num_ctx`，跑同一个 Agent 任务（`reports/ctxbench.json`）：

| num_ctx | tok/s | 首调用耗时 | 标记点 | 工具成功 | 总耗时 |
|---|---|---|---|---|---|
| 1024 | 14.43 | 53090 ms | 2 | 2/2 | 240.08 s |
| **2048** | ❌ **失败** | — | — | — | 结构化输出连续 3 轮返回空字符串 |
| 4096 | **19.27** | 52902 ms | 5 | 4/4 | 244.75 s |
| 8192 | 12.91 | 55809 ms | 5 | 4/4 | 338.28 s |

**结论（三条，都与直觉相反，值得记下来）：**

1. **ctx 不是越大越好。** 8192 的吞吐（12.91）反而低于 4096（19.27），
   因为 KV cache 随 ctx 线性增长，在 8GB 统一内存上挤占了推理空间。
2. **ctx 过小会直接崩。** 2048 下模型连续 3 轮返回**空字符串**，
   schema 约束解码也救不回来——它装不下这个 schema。
   **ctx=1024 只能产出 2 个标记点**，达不到挑战要求。
3. **推荐配置：4096。** 吞吐最高（19.27 tok/s）、质量达标（5 个点、工具 4/4 成功）、
   内存友好。本项目的最终交付用的是 8192（保质量），若追求速度建议改 4096。

## 6. 正确性证据：77 个单元测试


几个我认为最有说服力的断言：

| 断言 | 为什么重要 |
|---|---|
| `haversine((34,113),(35,113)) == 111.19 ± 1.0 km` | 距离计算锚定物理常数，**不可能是编的** |
| `haversine((0,0),(0,180)) ≈ 20015 km` | 对跖点 ≈ 半周长 |
| `sum(逐段距离) == 总距离`（误差 <0.01km） | `route_plan` 内部自洽 |
| `评分分量 + 可达性分量 == 总分` | `score_poi` 真的在做加权，不是随手给个分 |
| `search_poi(campus) count == 4` | 类别过滤精确 |
| 「西亚斯学院图书馆」（无连字符）必须命中「西亚斯学院-图书馆」 | 回归测试：修过的模糊匹配 bug |
| HTML 不含 `openstreetmap`/`mapbox`/`leaflet`/`?key=` | 合规红线 |
| HTML 必须含 `_TMapSecurityConfig`、`MultiMarker`、`MarkerStyle` | 合规必须项 |
| HTML 不含 `mapStyleId` | 默认 key 未开通自定义样式，传了会灰屏 |
| 地点名含 `<script>` 必须被转义 | XSS（真漏洞，已修） |
| 模型坐标 (0,0) 必须被拉回 | 坐标幻觉兜底 |
| 开封 34.5092→34.7970 | 88.5km 幻觉纠正（Bug C 回归） |
| `images` 必须真的进 payload | 多模态静默失败（Bug B 回归） |
| 损坏的 state 文件不能让程序崩溃 | 健壮性 |

工具层另有 7 项自测（`run_agent.py selftest`），与模型无关，秒级返回。

## 7. 局限性（诚实交代）

1. **POI 知识库是内置 10 条**，非全量地理数据。绝对坐标有百米级误差
   （量级正确、位置合理），因此工具计算的**相对距离可靠**，绝对定位有偏差。
2. **视觉识别的精度未被验证**——测试图是我画的示意图，只能证明链路通。
3. **未完成 Level 4 的「量化对比」**。我尝试拉取 `gemma4:e2b-it-q8_0`，
   该模型需下载 5.0 GB，当时实测速率仅 732 KB/s（预计 1h52m），
   磁盘也不足以同时容纳两个模型。**我选择放弃而不是编数据。**
   `bench` 子命令已实现，磁盘和网络允许时可直接跑：
   ```bash
   ollama pull gemma4:e2b-it-q8_0
   python3 run_agent.py bench --profiles e2b-q4,e2b-q8
   ```
4. **未完成「多设备适配」**。我只有一台 MacBook Air，没有 Windows/Android 设备，
   无法产出跨设备对比数据。**同样不编。**
5. **E2B 的推理速度（约 20 tok/s）决定了单次完整任务需 3–4 分钟**。
   想更快可换 E4B + MLX 后端，但 8GB 内存下不现实。
