## 0. 一句话概述

我做的是一个叫 **`sias-local-map-agent`** 的技能包：用**跑在自己 MacBook Air 上的 Gemma 4**（经 Ollama，
零 API 费用、零数据外传）通过**原生 function calling** 自主调用 5 个真实工具，把一句自然语言
变成一张**中英双语、可交互的腾讯地图**。目标级别 **Level 3（Gold）**，并完成 Level 4 的
多量化档位对比。

## 1. 为什么选 Gemma 4 E2B 而不是更大的模型

挑战列了四款模型。选型不是拍脑袋，是被**我这台机器的真实约束**决定的：

| 约束 | 实测值 | 影响 |
|---|---|---|
| 芯片 | Apple M1（8 核） | 无 CUDA，走 Metal 后端 |
| 内存 | **8 GB**（统一内存，CPU/GPU 共享） | 这是最硬的天花板 |
| 可用磁盘 | 25 GB | 只能装 1–2 个模型 |
| macOS | 14.5 | — |

对照挑战给出的选型表：

| 模型 | 4-bit 最低内存 | 我这台机器的结论 |
|---|---|---|
| **E2B**（~2.3B 有效参数） | ~5 GB | ✅ **唯一稳定档位**。8GB 统一内存下留足系统余量 |
| E4B（~4.5B 有效参数） | ~5 GB | ⚠️ 可加载但推理时会大量触发 swap，实测已记录在验证报告 |
| 26B MoE（3.8B active） | ~18 GB | ❌ 装不下 |
| 31B Dense | ~20 GB | ❌ 装不下 |

**最终选择：`gemma4:e2b-it-q4_K_M`（Q4_K_M 量化，有效参数 2.3B，128K 上下文）作为主档位。**

选它的三个理由：
1. **Apache 2.0**，无使用限制，可离线部署。
2. E2B 官方定位就是「mobile-first / IoT / 设备端」，是最贴合 8GB 设备的一档。
3. 更重要的是——**它足够小，所以我能在一台 Air 上把 Agent 全链路跑通并做量化对比**，
   而不是只能跑个 demo 就交卷。这才是这个挑战真正想考的东西。

## 3. 五个工具：为什么它们是真的

评审最容易怀疑「工具是不是空壳」。我的应对是：**每个工具都能独立跑通并给出可验证的输出**，
且都写进了单元测试。

| 工具 | 输入 | 输出 | 可验证性锚点 |
|---|---|---|---|
| `geocode_local` | 地名字符串 | 坐标 + 置信度 | 三级模糊匹配；`tests` 断言 8 个查询的命中情况 |
| `reverse_geocode` | 坐标 | 最近地标 + 距离 | haversine 最近邻 |
| `search_poi` | 关键词/类别 | POI 列表 | 类别过滤计数断言（campus 恰为 4） |
| `route_plan` | ≥2 个坐标 | 逐段距离 + 总时长 | **断言「逐段之和 == 总距」**，浮点误差 <0.01km |
| `score_poi` | 坐标 + 评分 | 0–100 分 + 分项解释 | **断言「两项分量之和 == 总分」** |

`haversine` 的正确性用物理常数锚定：**1° 纬度实测 111.20 km，理论 111.19 km**。
对跖点距离 20015 km ≈ 半周长。这两个断言让「距离计算」这件事不可能是编的。

## 4. 三个关键工程决策

### 决策一：小模型的 JSON 不稳，是结构性问题，不是 prompt 问题

E2B 只有 2.3B 有效参数，在长 prompt 下会漏字段、裹 markdown、给解释文字。
我的解法是**分层降级**（`llm.json_chat`）：

1. **第一轮**：用 Ollama 原生 `format: schema` 做**解码期约束**——不是让模型「记得输出 JSON」，
   而是让采样器在词表层面就只允许走合法 JSON 路径。这是唯一真正可靠的手段。
2. **第二轮**：若后端不支持或仍失败，退回纯文本模式，并把**真实报错文本**回灌给模型让它自修复。
3. **兜底**：`_extract_json` 做外科手术式修复（剥代码块 → 截配对括号 → 去尾逗号 →
   `None/True/False` → JSON 字面量）。

实测成功率见验证报告的 JSON 成功率一节。

### 决策二：坐标必须做几何自检，否则整份产物不可信

2B 模型在结构化输出里**会产出格式完美但地理上完全错误的坐标**（最典型：把郑州点位吐到 `0,0`，
即几内亚湾）。这类错误肉眼极难发现——JSON 合法、字段齐全、描述通顺。

所以 `_sanitize()` 做了三道闸：
- 丢弃非法坐标（非数字 / 越界）
- **离郑州 >500km 的坐标判定为幻觉，强制拉回校园附近**
- 上限 12 个点

这不是「美化」，是**正确性兜底**。测试里专门有一条回归断言盯着它。

### 决策三：证据与代码彻底分离

设备信息、模型版本、tok/s 这些数字**在任何文档里都不允许手写**。
`config.collect_server_info()` 从 `sysctl` / `sw_vers` / `df` 实采，
`CallStat` 从 Ollama 返回的 `eval_count` / `total_duration` 实算。
截图脚本 `make_evidence.py` 只负责把真实日志**排版成 PNG**，并在每张图底部标注数据来源文件。

这样做的目的很直接：让「AI 日志」和「验证报告」里的每个数字都可被第三方一条命令复现。

## 5. Agent 能力覆盖（对照 Level 3 五个扩展方向）

| 扩展方向 | 是否实现 | 实现位置 | 说明 |
|---|---|---|---|
| 多轮对话 Agent | ✅ | `MapAgent.edit()` / `chat` 子命令 | 增/删/改/重生成，状态落盘 |
| 多工具调用 | ✅ | `tools.py` 5 个工具 | 模型自主选择，无硬编码路由 |
| 代码生成 Agent | ✅ | `advanced.CodeGenAgent` | 模型写码 → 受限子进程执行 → 报错回灌自修复 |
| 视觉理解 | ✅ | `advanced.VisionAgent` | Gemma 4 原生多模态，`images` 字段喂本地图片 |
| 多语言地图 | ✅ | `map_render.py` | 中英双语名称 + 双语描述 + 英文 UI 兼容 |

**另加一项挑战没列但我认为更有说服力的：地图合规。**
最初我打算按挑战示例用 Folium/Leaflet + OpenStreetMap，但那是境外地图源，不合规。
改为**腾讯地图 GL JS**，并严格遵守代理模式规范（前端零密钥、GCJ-02、不传 `mapStyleId`、
`MultiMarker`/`MarkerStyle` 类名规范）。测试里有 4 条专门的合规断言（禁止出现
`openstreetmap`/`mapbox`/`leaflet`、禁止 `?key=`、必须含 `_TMapSecurityConfig`、
禁止 `mapStyleId`）。

## 7. 已知局限（诚实交代）

1. **POI 知识库是内置的 10 条**，不是全量地理数据。这是刻意的取舍——为了保证
   「断网也能跑」这一 C4D 核心主张。需要全量在线检索就得接腾讯地图地点搜索 API，
   但那样就失去了离线能力。
2. **E2B 在长指令下坐标精度有限**，复杂地理推理建议用 `--profile e4b-q4` 复核。
   我实测了 E4B 在 8GB 上的表现，数据见验证报告——结论是能跑但性价比不划算。
3. **视觉理解依赖模型原生多模态**，E2B 的图像理解弱于 E4B，这是模型能力上限，
   不是代码问题。
4. **未做 Level 4 的「多设备适配」**：我只有一台 MacBook Air，没有 Windows/Android 设备，
   无法诚实地产出跨设备对比数据。**宁可不写，也不编。**
