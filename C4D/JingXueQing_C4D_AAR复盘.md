> 标注约定：`[实测]` = 本机跑出来的原始报告；`[推断]` = 我基于实测的归因，未做隔离实验。

---

## 1. 事前预期（开跑前我以为会怎样）

挑战目标是「本地部署 → 有记忆与技能的 Agent → 能力可用 → 对比本地与云端」。开跑前我的预期是：

1. 8GB M1 上只要能拉起 2B 级模型，"能不能调工具"主要看模型本身是否支持 function calling；
2. 结构化输出失败是 prompt 没写清，多调几轮 prompt 就能收敛；
3. 主要风险在显存/速度，不在稳定性。

## 2. 实际发生（做了什么，跑出什么）

| 环节 | 结果 | 关键实测值 |
|---|---|---|
| 环境自检 | 通过 | Ollama `0.40.2`，`gemma4:e2b-it-q4_K_M`（4.6B / Q4_K_M），Apple M1 / 8 核 / 8GB [实测 doctor.json] |
| 工具层单测 | 7/7 通过 | geocode conf=0.5；route_plan 1.421km / 17.8min；score_poi 96.1；haversine 实测 111.20km vs 理论 111.19km [实测 selftest.json] |
| 地图 Agent 主任务 | 成功出图 | 5 个标记点，中英双语，单文件 HTML 可直接双击打开 [实测 run_report.json] |
| 代码生成 | 成功 | `prime_count=25`，`first_five_primes=[2,3,5,7,11]`，31 行代码，1 次尝试，18.28 tok/s [实测 codegen.json] |
| 视觉理解 | 判定正确但分类错 | is_campus_photo=true、confidence 0.85，但 `guess_category=nature`（应为 campus/建筑）[实测 vision.json] |
| 上下文档位对比 | 4 档中 1 档失败 | ctx=1024 ok(14.43 tok/s)、**ctx=2048 失败**、ctx=4096 ok(19.27 tok/s)、ctx=8192 ok(12.91 tok/s) [实测 ctxbench.json] |

**第一个预期被证伪的地方**：2B 级模型确实能自己选工具、自己填参数（4096 档跑到 4 次工具调用），但**吞吐代价很大**——单次地图任务 wall time 240.08s（1024 档）/ 244.75s（4096 档）[实测 ctxbench.json]。也就是说"能跑通"和"能用"之间差了一个数量级的等待时间。

## 3. 差距与根因

### 差距一：ctx=2048 结构化输出直接崩

- 现象：`RuntimeError: 结构化输出在3 轮内失败：模型返回空字符串` [实测 ctxbench.json]
- 根因 `[推断]`：schema 约束解码会占用一部分输出预算，2k 窗口下 prompt + 历史 + 工具观测把可用输出空间挤到接近 0，模型返回空串。**这不是 prompt 写得不好，是窗口不够的结构性问题**——同一套 prompt 在 4096/8192 下都正常。
- 我的原预期（"结构化失败 = prompt 问题"）在这里被否掉了。这也成了技能里的第一条设计原则：先上 Ollama 原生 `format` schema 约束解码，失败才退回文本模式 + JSON 自愈修复，而不是反复重写 prompt。

### 差距二：vision 高置信度但分类错

- 现象：`is_campus_photo=true`、`confidence=0.85`、tags 里写对了「教学楼/行政楼/砖建筑」，但 `guess_category=nature` [实测 vision.json]
- 根因 `[推断]`：类别词表过宽 + 单轮零样本，模型在"这是室外建筑"和"这是自然景观"之间按字面特征滑了过去；而置信度只反映自我一致性，不反映正确性。
- 教训：**自报置信度不能当正确性用**，必须对枚举字段做 allow-list 校验或后置规则修正。

### 差距三：首轮结果不合格，靠加 grounded 约束才收敛

- 现象：`run_report_v1.json` 与 `run_report.json` 两版标记点不同，v1 偏校园内点位，final 版把分类与来源标注（`source: local-gemma4+grounded`）补齐 [实测两份报告对比]
- 根因 `[推断]`：v1 的指令没强制"坐标必须来自工具返回"，模型倾向自己编合理坐标；补上 grounded 约束后才稳定。

## 4. 做对了什么（可复用的部分）

1. **工具层与模型解耦**：`selftest` 不需要模型、秒级返回，7 条检查覆盖精度与异常路径，出问题能立刻判断是工具坏了还是模型坏了。
2. **量化精度自证**：haversine 手算校验到 111.20 vs 111.19 km，属于"敢写进文档的精度"。
3. **失败留证**：ctx=2048 那条失败记录我没有删，也没有改成"全部通过"——它本身就是最有价值的结论。
4. **产物单文件化**：地图 HTML 单文件、前端零密钥、代理模式，换台机器双击就能看。

## 5. 如果重来，我会改什么（具体动作）

| 改进项 | 具体做法 | 触发依据 |
|---|---|---|
| 把窗口下限固化为前置检查 | `doctor` 增加 `num_ctx >= 4096` 断言，低于直接报错并给建议档位 | ctx=2048 空字符串失败 |
| 枚举字段加 allow-list | `guess_category` 只接受注册过的类别，越界时回退到 `unknown` 并降权 | vision 分类错 |
| 预热与缓存 | 首次调用拉长 load 时间，改为启动时预热一次；同参数结果做缓存 | 单次 240s+ 等待 |
| 默认 grounded 模板 | 主任务 prompt 内置"坐标只能引用工具返回值"约束，而不是事后补 | v1 → final 的修订 |
| 输出预算单独计量 | 记录 eval_tokens / num_predict，用于判断是"窗口不够"还是"prompt 太长" | 需要区分根因 |

## 6. 没解决 / 诚实的遗留问题

- 只测了 `gemma4` 单模型家族，跨模型泛化没有验证（技能里预留了 `--profiles` 多档对比接口，但没跑满）。
- 8GB 机器上的并发能力未测，多轮长对话在 8192 档的稳定性只覆盖了单次 benchmark。
- 视觉分类的修正方案（allow-list）目前是设计，未回灌成代码实测。

---

**一句话结论**：这次真正学到的不是"本地能跑 Agent"，而是**小模型的失败模式是结构性的（窗口、枚举、自报置信度），不是靠把 prompt 写得更细就能糊过去**；把失败场景固化成检查项，比多写几段 prompt 有用得多。
