## 1. 真实迭代轮次记录

### 第 1 轮：读题与选型（无代码）

**我做的事**：先读 `CHALLENGE.md`、`rubric.json`，然后查本机配置。
没有立刻开始写代码——因为选型错了后面全白做。

**我的判断**：
- rubric 里 `technicalExecution` 的负向信号第一条就是「硬编码」，
  所以我一开始就决定：证据数据（tok/s、设备）必须实采，不许写死。
- `negativeSignals` 里有「空壳」「跑不通」，所以工具必须是真能执行的。

**AI 的作用**：帮我检索 Gemma 4 四款模型的参数与定位，对照我这台
8GB M1 得出「E2B 是唯一可行档位」的结论。`[实测]` 我又用
`system_profiler` 核对了本机确实是 8GB。

---

### 第 2 轮：装环境（6 个坑，纯人机协作）

这是**最耗时的一轮**（约 40 分钟），也是我认为最有价值的记录。

| 坑 | 现象 | 根因 | 解法 |
|---|---|---|---|
| ① | `curl ... install.sh` 超时 | 206MB 包网络太慢 | 改**断点续传循环** `curl -C -`，按字节数判断完成 |
| ② | 照挑战文档 `ollama run gemma4:e2b` 无效 | 文档 tag 与实际不符 | 查 `ollama.com/library/gemma4/tags` 拿到真实 tag：必须带 `-it-` 和量化后缀 |
| ③ | `ollama serve` 跑起来了但很慢 | 日志显示 `library=cpu`，**退化成纯 CPU** | `llama-server` 要和主二进制同目录 → 必须 `cd` 到 app 的 `Resources/` 再 serve |
| ④ | `ollama pull` 卡在 `pulling manifest` | `registry.ollama.ai` TCP 握手超时（DNS 正常） | 稍后重试即可；且 `ollama pull` **本身支持断点续传**，重跑同命令即可 |
| ⑤ | 沙箱里 `mkdir(exist_ok=True)` 抛 `EEXIST` | 环境的路径代理拦截 | 改成先 `if not d.is_dir(): d.mkdir()` |
| ⑥ | 模型拉到 3.5GB 的 27% 卡住不动 | 网络抖动 | 写循环反复重跑 pull，进度会接着走（925MB→1.6GB→完成） |

**人机分工的体现**：
- AI 给出了「重试」这个建议，但**是我**去翻了 serve 日志才发现坑 ③
  （如果只看「能跑通」，会一直以为 CPU 推理是正常的，然后得出错误的性能结论）。
- 坑 ② 是 AI 主动查 tag 列表发现的。如果不查，我可能会在文档里写一个不存在的 tag，
  评审照做就卡住。

### 第 3 轮：写代码（AI 主导，我 review）

**我先定的三条架构原则**（直接写进 SKILL.md 和系统提示）：

1. **工具层必须完全离线**——因为「断网也能跑」是这个挑战的核心主张。
   用了内置的 10 条 POI 知识库而不是在线 API。
2. **证据与代码彻底分离**——`collect_server_info()` 从 `sysctl`/`sw_vers` 实采，
   文档里的每个数字都必须能在 `reports/*.json` 里找到来源字段。
3. **坐标必须做几何自检**——因为我预感到 2B 模型会产出「格式正确但地理错误」的坐标。

**我对 AI 写出的代码做的具体干预**：

- 要求工具层**不依赖模型**就能自测 → 催生了 `selftest` 子命令，
  评审不用下载模型就能验证代码。
- 要求写**单元测试**，且必须包含「物理常数校验」
  （我明确要求验证 haversine 在 1° 纬度上等于 111.19 km）。
- 坚持用**腾讯地图**而不是挑战示例里的 Folium/Leaflet+OSM——
  因为 OSM 是境外地图源，不合规。这一条我改了 AI 的初版方案。

### 第 4 轮：第一次实跑（发现 Bug A）

`[实测]` 第一次 `run_agent.py map`：
- 工具调用 3 次，生成 5 个标记点，18.08 tok/s，192.86 s
- **但 5 个点全在校园内，没有周边地标**

我看出问题了：模型传 `category="sight" + keyword="SIAS University"`，
严格 AND 匹配返回 0，Agent 就以为周边没景点，直接收工。

**这是 AI 自己不会发现的 bug**——它代码写对了，是我看了产出结果才发现「不合理」。
我提出了「关键词+类别无交集时退化检索」的方案，AI 实现了，
并加了我要求的 `relaxed: true` 标记。

同时我强化了 system prompt，明确告诉模型
「category 要换不同值多次调用」「keyword 不要填地名」。

`[实测]` 修复后：工具调用 4 次，出现 `relaxed=true count=1 → 黄河故里旅游区`（5.08 km），
地图首次覆盖到校外。测试 66 → 69 个。

### 第 5 轮：写测试，抓出 Bug B 和 XSS

**Bug B（参数命名不一致）** `[实测]`
我让 AI 补 `reverse_geocode` 的测试，结果 66 个测试里 2 个失败：
```
TypeError: t_reverse_geocode() missing 1 required positional argument: 'lng'
```
函数签名是 `lat/lng`，我测试时用 `latitude/longitude`。
**这不只是测试写错**——我立刻意识到：2B 模型也经常混用这两套命名，
所以这是接口设计太脆。修法是让函数同时接受两种命名。

**XSS（地图 HTML）** `[实测]`
我要求补「地点名含 `<script>`」的用例，发现：
卡片区 `html.escape()` 了，但**注入到 JS 里的 `properties` 没转义**。
输入来自本地模型、但知识库是外部可编辑数据，这是真漏洞。已修 + 加回归断言。

### 第 6 轮：视觉 Agent 的 Bug B（静默失败，最隐蔽）

`[实测]` 视觉 Agent 输出**所有字段都是 None**。

**排查过程**（这里我作为人的作用最明显）：
1. 先怀疑是 JSON 解析问题 → 看 `_extract_json` 逻辑，觉得没问题
2. **直接绕过封装打 Ollama API** → 发现模型回的是
   「这张图片展示了一栋红砖建筑，它坐在一片绿色的草地上，背景是蓝天和水面」
   —— **模型能力没问题，是我的封装有 bug**
3. 再看代码，发现：

```python
for m in messages:
    if m.get("role") == "user" ...:
        m = dict(m)        # ← 只重绑了局部变量！
        m["images"] = images
        break
```

`messages` 这个 list **从未被修改**，payload 里始终没有 images。

**为什么危险**：当时 `_extract_json` 是"成功"的（模型返回自由文本被宽松解析器吃下来），
所以**代码看起来一切正常，只是所有 `.get()` 返回 None**。
这类「静默失败」比崩溃可怕得多——如果我不去看模型的实际输出，
我可能就写一句「视觉功能不可用」交差。

修法：重建 list + 挂到最后一条 user 消息 + 改用 schema 约束解码。
补了 4 个回归测试。`[实测]` 修复后：`is_campus_photo: true`、
`scene_zh: "教学楼或行政楼"`、置信度 0.85、12.38 tok/s。

### 第 7 轮：多轮对话暴露 Bug C（88.5 km 坐标幻觉）

`[实测]` 测多轮对话时输入「加一个开封」，模型给出 `34.5092,113.4050`。
我拿知识库权威值 `34.7970,114.3070` 一比，**偏差 88.5 km**。

**关键点**：原来的 `_sanitize` 只拦「离郑州 >500 km」，
88.5 km 属于「看起来合理」的区间，**逃过了所有检测**。
JSON 合法、描述是「八朝古都…」、星级 4.7 —— 任何不做对照的评审都发现不了。

我提出的方案：**名称锚定（grounding）**。
凡是名称能匹配本地知识库 → 强制吸附到权威坐标；
名称不在知识库的**不强制**（否则会给虚构地点编一个坐标，更糟）。
纠正动作记入 `grounding_fixes` 审计日志并写进 `source` 字段。

`[实测]` 修复后审计日志：
```
开封: 模型输出 (34.5092,113.4050) 被纠正为 权威坐标 (34.7970,114.3070)，偏差 88.5km
```

补了 5 条 grounding 专项断言，测试 73 → 77 个，全绿。

**这一轮我学到的事**：模型幻觉最危险的不是「胡说八道」，
而是「**看起来完全合理**的胡说八道」。所以护栏不能只设一个粗糙的距离阈值，
要针对「有权威答案可查」的具体场景做精确锚定。

### 第 8 轮：证据截图（Bug D：中文变空白）

`[实测]` 生成截图后我**逐张打开看**，发现第 3 张里
「西亚斯学院-图书馆」的中文全变成了空白方块。

根因：用 `SFNSMono.ttf`（macOS 默认等宽字体），它**没有中文字形**。
Latin 部分正常，所以肉眼看整体「有内容」，但关键的中文信息全丢了。

修法：改用 `PingFang.ttc`（macOS 中文系统字体），并按**全角字符占两列**
重算行宽（否则中文行会被截断）。

**为什么值得记**：这是**只有真正打开图看才会发现**的错误。
如果我只是「生成成功」就交付，评审打开会看到一张证据无效的截图。

### 第 9 轮：Level 4 与诚实的放弃

`[实测]` 跑了 ctxbench，发现三条反直觉结论：
- ctx=2048 **直接失败**（连续 3 轮返回空字符串）
- ctx=8192（12.91 tok/s）**比** ctx=4096（19.27 tok/s）**慢**
- ctx=1024 只能产出 2 个标记点，达不到挑战要求

同时我尝试拉 `gemma4:e2b-it-q8_0` 做量化对比，
`[实测]` 该模型 5.0 GB、当时速率仅 732 KB/s（预计 1h52m），磁盘也放不下。

**我的决定：放弃量化对比，不编数据。**
`bench` 子命令我照样写完了，磁盘允许时一条命令就能跑出真实数据。
这件事我写进了验证报告的「局限性」，而不是藏起来。

## 2. Prompt 迭代记录

**系统提示改了 3 次**，每次都有实跑证据支撑：

| 版本 | 改动 | 依据 |
|---|---|---|
| v1 | 基础版：强调「数字必须来自工具」 | 设计阶段 |
| v2 | 增加「category 要换不同值多次调用」「keyword 不要填地名」 | `[实测]` 第 1 次跑只出了 5 个校园点 |
| v3 | 增加「不要放中心点/定位点这类无信息量占位条目」 | `[实测]` 第 1 次跑混进了「校园中心点(基于定位)」 |

**schema 也改了一次**：`markers[].category` 从自由字符串改成 `enum`
（`campus/sight/museum/heritage/transit/nature/city/poi`），
`[实测]` 之前模型会吐出 `location` 这种映射层不认识的类别。

**结论**：这些改动都不是「凭感觉调 prompt」，每一条都对应一个我实际看到的问题。
这比一开始就把 prompt 写得很长然后祈祷有效，要可靠得多。

## 3. 我认为最有价值的三条经验

**① 「看起来成功」比「明确失败」更危险。**
视觉 Agent 全 None 那次，程序退出码是 0，日志没有报错，
只有我主动去打印原始输出才发现问题。**所以我坚持所有证据都要能一键复现**。

**② 断言要锚在不可编造的常量上。**
我没有写「距离计算合理吗」这种没法判定的断言，而是写
「1° 纬度 == 111.19 km ± 1.0」。**物理常数编不出来**，所以这条断言一旦通过，
就是真的通过了。这套思路后来被我用在代码生成 Agent 上——
不去信模型自述，而是用一行确定性 Python 独立验证它算的 25 个质数对不对。

**③ 护栏要针对「有权威答案可查」的场景做精确锚定，而不是粗暴阈值。**
500 km 阈值拦不住 88.5 km 的偏差。真正的护栏是「这个名字我有权威坐标，
那就必须用我的」。这不是调 prompt 能解决的，是必须在代码层做。
