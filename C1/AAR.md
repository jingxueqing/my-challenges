# AAR 复盘（七维）

> 挑战 C1：课程资料获取与翻译（Stanford CS146S → 中文资料包）
> 复盘人：项目执行者 ｜ 周期：4 个工作日 ｜ 交付：翻译资料包 + 可复跑管线

---

## 维度 1：目标回顾（当初要打什么仗）

1. 建立完整信息获取管线：定位一手来源 → 批量抓取归档；
2. 组织"机器翻译 + 术语表 + 人工校对"流程，产出质量可控的中文课程包；
3. 用 AI 批量处理长文本：分段、术语统一、格式保持、质量抽检；
4. 以可复用方式发布：换一门课的资料，同样流程能再跑一遍。

**验收硬指标**：覆盖度 ≥80%；术语表 ≥50 条且全文一致；管线可复跑；陌生人可按 README 独立使用。

## 维度 2：结果对比（打成了什么样）

| 指标 | 目标 | 实际 | 判定 |
|---|---|---|---|
| 覆盖度 | ≥80% | 正文全译质检通过 28/31 = 90.3%；按篇数计 100%（含缺口台账；交付后补抓成功 2 篇原缺口） | ✅ |
| 术语表 | ≥50 条、全文一致 | 82 条；一致性违规 0（脚本扫描） | ✅ |
| 管线可复跑 | 换源可复用 | 4 个课程无关脚本 + 环境变量化入口，未写死任何课程名 | ✅ |
| 陌生人可用 | README 完整、目录清晰 | README 含来源/覆盖/流程/使用/缺口五要素 | ✅ |
| 交付物四件套 | README/AI日志/AAR/拿来说明 | 齐全，本文件为证 | ✅ |

未达标/打折项（诚实记录）：
- 原 5 篇抓取缺口，交付后补抓成功 2 篇（Graphite 讲稿、promptingguide 总览）；剩 3 篇为站点不可达/JS 渲染/Medium 拦截，留缺口台账；
- 4 篇超长文（2 研究文 + 2 PDF）采用"详注节译"而非逐字全译；
- 视频字幕（3 个 YouTube）与 14 个 Google Slides 未覆盖——离线包本就不含其内容。

## 维度 3：过程还原（仗是怎么打的）

- **D1 体检**：先对离线包做"尸体解剖"——逐页探测正文可提取性，5 分钟锁定 5 处缺口，避免后面把精力浪费在抓不出来的页面上。产出 page_map + 缺口清单。
- **D2 建线**：把"提取/翻译/质检"拆成三个课程无关脚本，所有课程相关量（目录名、术语表路径、引擎）走环境变量。语料与译文一一配对（slug 命名），让覆盖度可以被脚本验证而不是靠自觉。
- **D3 量产**：按文件大小分 11 批，并行子代理翻译；每批注入同一份"术语块 + 结构规则 + 产品名清单"；超长文改用"详注节译"策略（见维度 5）。
- **D4 收口**：脚本全量质检 + 人工抽检 6 篇（数字、术语、漏译三类硬伤清单式检查）；双口径覆盖度写进 README；补缺口台账与"拿来说明"。

关键决策点：
1. **"离线包优先"而非现抓官网**——离线包是给定的一手来源且带 URL 映射，现抓既慢又引入合规与稳定性问题；
2. **语料先行**——所有翻译都从统一语料目录消费，不直接翻 HTML，保证"换源可复跑"；
3. **术语表进 prompt 而非"参考文件"**——并行翻译时子代理不共享上下文，术语块必须随行。

## 维度 4：成功要素（为什么打得成）

1. **把"翻译"重构为"管线"**：覆盖度、术语一致性都变成脚本可判定的属性，AI 只负责最难的那一步（译文本身）；
2. **并行分批 + 统一约束块**：11 批并行把数天级工作量压到数小时，统一 prompt 模板把跨批次风格漂移压到最低；
3. **机器可复核报告**（quality_report.json）：验收不靠自述，评审可重跑脚本验证每一个数字；
4. **诚实的缺口台账**：不掩饰 5 处抓取缺口，反而给出每处的补抓流程，可维护性高于"假装全都有"。

## 维度 5：失败与教训（哪里打疼了）

1. **JS 渲染页是硬伤**：离线包里 5 篇正文实际抓不到。教训：拿到资料包第一天就该做"可提取性体检"（做了），但**更早该在选源阶段评估站点技术形态**（没做——离线包是给定的，但若自主选源需先查 robots/渲染方式/反爬）。
2. **术语漂移低估了**：多智能体并行翻译时，CI/CD、Embedding 出现 4 处不一致。教训：**共享约束必须内联进每个任务**，"共享文件引用"在无共享上下文的并行体系里约等于没有。
3. **v1 长文策略失败**：最初对 5–7 万字符研究文直接要求"全文翻译"，产出口径不可控（要么被截断、要么压缩成摘要）。教训：**超长文本要显式设计翻译策略**（节译模式 + 关键句全译 + 全章节覆盖约束），而不是套用短文 prompt。
4. **数据小 bug 两次**：CSV BOM 引发 `KeyError: 'en'`；manifest 占位页缺 `slug` 引发 `KeyError: 'slug'`。都是"生成物没有按消费方预期格式落地"的同构问题。教训：写完生产方立刻用消费方跑一遍冒烟测试。
5. **口径漂移**：覆盖度曾同时存在 26/31、29/31、31/31 三种算法。教训：统计口径必须一次性写进脚本，禁止口头另算。

## 维度 6：根因分析（为什么会疼）

- 缺口 1/2 的根因是**上游资源形态与管线假设不匹配**（管线假设 HTML 静态正文），而非翻译质量问题——所以解法放在"缺口台账 + 补抓入口"，而不是硬修翻译；
- 术语漂移的根因是**并行架构下的约束传递断裂**：约束块从"共享文件"改为"内联注入"后才真正闭环；
- v1 长文失败的根因是**任务定义与上下文窗口/产出长度约束冲突**：5 万字符原文 ≈ 4 万+ 字符译文，接近单次产出上限，模型只能牺牲忠实度自保。"详注节译"把任务重新定义为"结构无损 + 关键句全译"，才与模型能力对齐；
- 两个 KeyError 的根因是**接口契约没有测试**：生产方（Write 工具/manifest 生成）与消费方（csv/pipeline 脚本）之间缺一个最小冒烟用例。

## 维度 7：改进行动（下一仗怎么打）

| # | 改进项 | 具体动作 | 优先级 |
|---|---|---|---|
| 1 | 选源前置体检 | 自主选源时先查：robots.txt、是否 SPA/SSR、反爬策略、可下载性，产出《来源体检表》再动手 | P0 |
| 2 | 术语一致性前置 | 翻译前先跑"术语出现频率扫描"，把高频术语的译法写进批次模板；质检违规自动生成修正补丁而不是人工逐处改 | P0 |
| 3 | 冒烟测试脚本 | `pipeline/smoke_test.py`：构造 1 篇迷你 HTML + 迷你 CSV，30 秒内跑通 extract→translate(skeleton)→check 全链 | P1 |
| 4 | 视频字幕管线 | yt-dlp 抓字幕 → 同一语料格式 → 复用 translate.py，把 3 个 YouTube + 14 个 Slides 纳入覆盖 | P1 |
| 5 | 节译质量基线 | "详注节译"模式固化为 translate.py 的第三种引擎（`--engine digest`），带全章节覆盖断言 | P2 |
| 6 | 双语对照页面 | 语料与译文同 slug 配对，生成段落级中英对照 HTML，方便学习者逐段核对 | P2 |

---

## 一句话总结

**这场仗的本质不是翻译一门课，而是把"课程资料 → 中文资料包"这件事变成一条任何人换源即用的流水线**；翻译质量靠术语表与质检脚本守住边界，AI 负责产出，脚本负责验收，诚实台账负责不该由翻译兜底的缺口。
