# AAR：C1 课程资料获取与翻译

> 作者：jingxueqing　|　挑战编号：`ch-20260717031336-pxzwy0`　|　复盘时间：2026-09-27
> 格式：AAR（预期 → 实际 → 差异 → 教训 → 改进）

## 1. 我原本打算怎么做（预期）

任务听起来像「把英文资料翻成中文」，我一开始的设想很直接：材料下载下来，整份丢给 AI，让它按文档译完，交上去。目标定得也模糊——**「翻完」**，没有定义什么叫翻完。

## 2. 实际发生了什么（事实）

| 环节 | 预期 | 实际 |
| --- | --- | --- |
| 材料下载 | 两个文件，直接可用 | zip 解包出 44 个文件、约 22.1 MB，其中 33 个 HTML、3 个 PDF，格式混杂 |
| 语料抽取 | 顺理成章拿到正文 | 第一版抽出 **487 万字符乱码**（PDF 里的 JPEG 字节被当正文） |
| PDF 转文字 | 装上现成工具即可 | 本机无任何第三方 OCR；自己写的 Swift 版编译报 `redefinition of module 'SwiftBridging'` |
| OCR 结果 | 一次成功 | 中文课件只认出 2,772 字符乱码，原因是识别语言只声明了 `en-US` |
| 翻译 | 一轮对话搞定 | 全量是 **473 段 / 560,465 字符 / 30 批**，必须分批落盘 |
| 交付 | 交几个 md | 交付物有 4 项（README / AI日志 / AAR / 拿来说明），且要求能**证明**译全了 |

最终我把「翻完」这个模糊目标换成了三条可验证的硬指标：**源哈希一致、段覆盖率可算、术语未命中可列**。

## 3. 差异在哪（根因）

1. **把「翻译任务」误当成「单次生成任务」。** 真正的难点不在翻译质量，而在**证明覆盖度和一致性**。没有段落标记，我根本无法说清哪一段漏了——「感觉译完了」不是证据。
   → 转折点：定下 `<!-- seg:<文档名>#<三位段号> -->` 标记与 `verify` 校验。
2. **低估了「抽取」这一步的脏活程度。** 487 万字符的噪声让我意识到：语料没洗干净，翻译和覆盖率统计全是错的。加了段长/可打印率双闸门后降到 398 段 / 451,541 字符，噪声清零且未误杀正文。
3. **工具链出问题时我的第一反应是「修环境」。** Swift 版本不匹配本可以耗掉一晚上。实际有效的做法是**换一条等价路径**：同样的系统 Vision，用 ObjC + clang 调用，一次编译通过。
4. **验证做得太晚。** OCR 语言配置错了，是在我拿中文课件对照时才发现的；如果一开始就抽 1 页中文做冒烟验证，能省一轮全量重跑。

## 4. 学到的东西

- **可复跑管线本身就是交付物。** `sync→extract→batch→glossary→collect→assemble→verify` 七个命令，别人（或我自己换台机器）能复现同一结果；而「对话里翻了一遍」不可复现、不可审计。
- **失败也要落盘，且要能自证。** `verify` 的 `untranslated` 清单、`glossary_unused` 清单把「完成」变成可检验项，而不是我的声明。
- **口径必须外置。** 我把翻译规则单独写成 `translation/翻译作业说明.md`，执行方按文件执行，不靠对话记忆——这也是后面把工作转交给本机 Agent 时不走样的前提。
- **术语一致性能被机械检查。** 试跑里我第一版就写了禁用词「提示工程」，被 `verify` 抓出来改成「提示词工程」。如果没有术语表和检查，这类错误会均匀地分布到 30 个批次里。

## 5. 与 AI 协作的体会

协作里最值钱的不是它替我写代码，而是**它逼我把要求写成可执行的形式**。分工大致是：

- **我做**：定口径（什么算完成）、选路线、判断哪条路能走通、验收结果、写纠正；
- **AI 做**：写管线代码、实现 OCR、批量翻译、跑校验、如实回报失败。

有两次我否掉了 AI 的方案，过程都记录在《拿来说明》里：一次是抽噪声时它打算用「猜 PDF 结构」的办法，我改成在抽取函数内加质量闸门；一次是 OCR 语言配置，它默认只认英文，我要求中文优先后重跑并对照两次字符数验证。**我学会了把「我觉得不对」变成「你怎么证明」**——比如要求它给出 `verify` 的原始输出，而不是「已完成」。

## 6. 卡点与突破

| 卡点 | 突破方式 |
| --- | --- |
| 487 万字符乱码 | 双指标质量闸门（段长 ≥200、可打印率 >0.95、字母+空格率 >0.7），跳过无 `Tj/TJ` 的内容流 |
| Swift 编译坏 | 换 ObjC + clang 调系统 Vision，不修工具链、不装依赖 |
| 中文课件乱码 | 识别语言改 `zh-Hans` 优先，重编译对同一 PDF 复跑：2,772 → 4,174 字符 |
| 译文没法校验 | 段落标记 + 逐文档覆盖率 + 源哈希三重校验 |
| 无法证明译全 | 覆盖率可算：试跑阶段 `7/473 = 1.5%`，格式已跑通，全量后按同口径出数 |

## 7. 还没做完的（如实记录）

- 全量 473 段翻译尚未完成，覆盖率、未译段数、术语未命中数要在完成后回填。
- 试跑阶段发现一个数字差异：`extract`/`batch` 统计 473 段，`verify` 只枚举出 433 段。查清后根因是**我自己的校验代码把 ≤200 字符的 40 个短片段直接跳过了**：分母变小，而且这 40 段成了**免检区**——真漏译也能报 100%。已改为「全部分段计入分母，短片段单独统计」，并清掉批次目录里 88 个早期实验残留（118 → 30）。教训：**做不到失败的校验等于没有校验。**
- 仓库推送通道还未打通（本机没有 `gh`，工作区不是 git 仓库），需要走别的通道。

## 8. 下次怎么改（改进项）

1. **先定验收口径，再动手。** 写代码前先回答「我怎么证明做完了」。
2. **小样冒烟再全量。** 任何涉及全量的配置改动（语言、粒度、编码），先拿 1 个样本验证再重跑。
3. **统计口径只允许有一个来源，且不许自带「免检区」。** 覆盖率分母应由同一处枚举产生；凡是执行过的段都必须可被判定为漏译，不能有跳过的分支。
4. **报告只报原始输出。** 没跑出 `verify` 结果就不写「已完成」，只写「进行中 + 卡在哪」。

## 9. 能力上的变化（ΔR）

- 之前：拿到「翻译资料」类任务，我会直接开写提示词，交付物是一段译文。
- 现在：我会先把它拆成**抽取 → 分段 → 术语约束 → 分批执行 → 归位 → 校验**的管线，并主动准备「覆盖率证据」。
- 证据：这条管线从零搭到全链跑通（含 OCR 与 4 类技术故障排除）在一天内完成，且第一次试跑就抓到术语违规、`skipped` 语义误读、覆盖率分母「免检区」三处真实缺陷——说明校验环节真的在工作，而不是摆设。
