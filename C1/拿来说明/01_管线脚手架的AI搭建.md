# 拿来说明 01：管线脚手架是怎么样借助 AI 搭起来的

> 对应交付物：`pipeline/extract_text.py`、`run_all.sh`
> 决策类型：架构决策——"提取脚本如何做到换课程可复用"

## 1. 原文（当时的真实约束与需求输入）

需求原文（挑战书四/验收要点）：
> "翻译流水线可复跑：换一门课的资料，同样的流程能再次产出"

我的初始想法只写了半句话给 AI：
> "写个脚本把课程离线包里的 HTML 文章提取成 markdown。"

## 2. Prompt（迭代 v1 → v2）

**v1（第一版，产出的脚本不可复用）**：
> 写个 Python 脚本把 /tmp/cs146s/CS146S_offline/pages/ 下的 31 个 HTML 提取成 markdown，去掉导航和广告。

**v2（发现 v1 把课程路径、站点选择器写死后重写）**：
> 重写为课程无关的提取脚本：
> 1. 输入用 --src/--out 参数，不写死任何课程名与路径；
> 2. 正文定位不能依赖单一网站结构：用候选选择器列表（article → main → [role=main] → .post-content → … → body）按"文本量 >400 字符"逐级回退；
> 3. 输出除了 markdown 语料，还要一个 manifest.json：每页记录来源 URL、字符数、是否占位页，供后续覆盖度统计消费；
> 4. 提取时保留标题层级、列表、表格、代码块、引用的 markdown 结构。

## 3. 产出（v2 关键代码节选）

```python
CONTENT_SELECTORS = [
    "article", "main", '[role="main"]', ".post-content", ".article-content",
    ".entry-content", ".markdown-body", "#content", ".content", "body",
]

def pick_container(soup):
    for sel in CONTENT_SELECTORS:
        node = soup.select_one(sel)
        if node and len(node.get_text(strip=True)) > 400:
            return node
    return soup.body or soup
```

配套的 `run_all.sh` 把课程名也环境变量化：

```bash
COURSE="${COURSE:-CS146S_offline}"     # 换课程只需改这一个变量
SRC="${SRC:-materials/$COURSE}"
GLOSSARY="${GLOSSARY:-pipeline/glossary.csv}"
```

## 4. 对比（v1 vs v2 的差别在哪）

| 维度 | v1 | v2 |
|---|---|---|
| 路径 | 写死 `/tmp/cs146s/...` | `--src` 参数 + 环境变量 |
| 正文定位 | 针对本课程站点的单一选择器 | 候选列表逐级回退，未知站点也能命中 |
| 副产物 | 无 | manifest.json → 覆盖度/缺口台账的统计基础 |
| 换课程 | 要读代码改逻辑 | 改一个环境变量 |
| 占位页处理 | 无（坏页直接崩） | <1KB 标记 placeholder，不阻塞管线 |

**事后验证**：把管线当成"黑盒"给另一位同学按 README 操作，不改一行代码即跑通了 extract 阶段——"换源可复跑"不是宣称，而是被复现过的。

**拿来说明的点**：需求里一句"可复跑"，落到工程上就是三件事——参数化、选择器回退、manifest 副产物。AI 负责把这三件事写成代码，但"哪三件事"是人根据验收标准推导出来的。
