## 说明 1：给 PDF 抽取加「质量闸门」，而不是换库或装依赖

**遇到什么**
讲义里有图片型 PDF。常规文本抽取把 `/Filter /DCTDecode` 的 JPEG 字节流当正文读出来，一次抽出整段 **487 万字符** 的二进制乱码，直接污染了整个语料。

**为什么这么选**
- 装第三方 PDF/OCR 工具：本机 `tesseract / ocrmypdf / pdftoppm / mutool / qpdf / gs` 全部不存在，为一次任务引入系统级依赖不划算，而且会破坏「离线可复跑」。
- 换 PDF 库：会牵动整条管线的抽取逻辑，回归面太大。
- **就地加闸门**：只改抽取函数内部一个判断，改动最小，且对以后拿到的所有 PDF 自动生效。判定用双指标（可打印率 >0.95 且字母+空格率 >0.7，段长 ≥200），同时跳过不含 `Tj`/`TJ` 的内容流——因为真正的文字内容流必然带这两个 PDF 文本算子。

**效果**
抽取从「噪声 + 正文混在一起」变成 398 段 / 451,541 字符，乱码段清零，且没有误杀正常段落（`pdf_segments: 0`）。

**动了哪些文件**
`pipeline/pipeline.py`（`looks_text()` 判定 + `pdf_text()` 的流过滤）。

## 说明 2：OCR 不用 Swift，改用 ObjC + clang 调同一套系统 Vision

**遇到什么**
两份讲义常规抽取拿不到文字（无字体表/纯图）。先写 Swift 版 OCR，`swiftc` 直接编译失败：`error: redefinition of module 'SwiftBridging'` —— 本机 SDK 是 `swiftlang-6.0.3.1.5`、编译器是 `swiftlang-6.0.3.1.10`，**工具链与 SDK 版本不匹配**。

**为什么这么选**
- 修工具链：和挑战目标（资料获取与翻译）无关，且改系统开发环境风险不可控。
- 装 OCR：同上，且本机没有任何现成 OCR CLI。
- **ObjC + clang 调同一套系统框架**：Vision 的文字识别能力本来就是我在 Swift 里想用的那套，换成 ObjC 只是换语言外壳，不受 Swift 模块版本问题影响；clang 随 Command Line Tools 自带，零新增依赖、完全离线。

**效果**
`pipeline/ocr.m` 一次编译通过，4 份讲义全量 OCR 共 **109,066 字符**（`skipped` 的语义是「该页识别结果为空」，本次仅 `how-anthropic-uses-claude-code` 第 23 页——单页无文字，不是文档失败）。语料从 398 段扩到 **473 段 / 560,465 字符**。执行方式是先拿单个 PDF 试通，再批量跑全部。

**动了哪些文件**
`pipeline/ocr.m`（源码）、`work/ocr/ocrbin`（编译产物）、`work/ocr/*.txt`（OCR 文本，已并入语料）。

## 说明 3：翻译按「1200 字符切段 + seg 标记 + 批次落盘」做，不用整篇一次性翻译

**遇到什么**
要译的是 473 段 / 56.0 万字符，而且交付标准里有两个硬指标：**覆盖度 ≥80%** 与**术语全文一致**。整篇丢给模型一次性翻译，这两件事都无法证明。

**为什么这么选**
- 切段后每段都带 `<!-- seg:<doc>#<NNN> -->` 标记，**可枚举**：源有多少段、译出多少段，覆盖率是算出来的，不是感觉出来的；漏译能定位到具体段号。
- 批次落盘（`translation/out/batch-NN.md`）而不是只在对话里输出：中途断了可以从任意批次续跑，产物是文件、可复查。
- 术语表分 `keep_en`（保留英文原词）与 `banned`（禁用译法）两类约束，`verify` 直接列术语漏检，把「术语一致」从人工印象变成可检项。
- `verify` 还比对**源文件哈希**：如果原文更新了而译文没重译，会直接报出来，避免「改了源、交了旧译」。

**效果**
语料 473 段全部可枚举、可定位、可重译；覆盖率与术语一致性都有客观输出。代价是批次调度比一次性翻译麻烦，但换来了可验收性。

**动了哪些文件**
`pipeline/pipeline.py`、`glossary/术语表.json`、`build/segments.jsonl`、`build/batches/index.json`。

## 说明 4：OCR 识别语言补上中文，并用字符数验证修复生效

**遇到什么**
第一版 OCR 只声明了英文识别（`req.recognitionLanguages = @[@"en-US"]`）。中文课件 `Vibe_Coding_Playbook.pdf` 因此被当作英文硬认，输出成乱码式伪英文，只有 2,772 字符——这份材料等于白抓。

**为什么这么选**
- 不换工具：问题不在 OCR 能力，而在**识别语言声明**。同一套系统 Vision 原生支持中文，改一行常量即可，不动编译参数、不新增依赖。
- 不靠肉眼判断「修好了没」：要求**重编译后对同一份 PDF 复跑并对比字符数**，用数字确认，而不是「看起来好像好了」。

**效果**
`ocr.m` 第 48 行改为 `@[@"zh-Hans", @"en-US", @"zh-Hant"]`（中文优先），重编译后同一份课件 2,772 → **4,174 字符**，「成为 AI 原生构建者的终极生存指南」等中文标题正常识别。全量语料随之由 472 段 / 559,065 字符变为 **473 段 / 560,465 字符**，批次重划为 30 批。

**动了哪些文件**
`pipeline/ocr.m`（识别语言常量）、`work/ocr/*.txt`（复跑产物）、`build/segments.jsonl` 与 `build/batches/*`（重建）。

## 附：这几条共同的一条原则

凡是「为了让结果可验收」而做的改动，优先选**就地最小改动 + 可复跑 + 可客观校验**的方案；凡是需要引入系统级依赖或改动与挑战目标无关的环境，一律绕开。这条原则在后面 C4/C4A 的技能类挑战里还会继续用。
