# AI 驱动的昆虫学：数百万条 AI 代码评审的经验教训（AI-powered entomology: Lessons from millions of AI code reviews）

**演讲者**：Tomas Reimers（Graphite）· 10:21

> Diamond 的开发历程说明了为什么发现 bug 只是起点：一个 AI 代码评审器必须筛选出有用的评审意见，然后衡量开发者是否据此采取了行动。

本文来自 Tomas Reimers 的一场演讲。

开始之前：熟悉拉取请求（PR）和代码评审即可；不需要机器学习背景。

## 01 · [0:16] AI 能否找出 AI 帮助制造的 bug？

随着 AI 编写越来越多的代码，它能否同时找出随之而来的 bug？正是这个问题促使 Graphite 联合创始人 Tomas Reimers 和他的团队构建了 Diamond——一个连接到 GitHub 的 AI 代码评审器。项目开始于这次演讲的大约一年前，当时团队观察到 AI 生成的代码和 bug 都在增加。Reimers 把这项工作称为 AI 驱动的昆虫学（AI-powered entomology）：关于 bug 的研究。

最初的实验很直接：给 Claude 一个拉取请求（PR），让它找出其中的 bug。结果中包括 Graphite 自身代码库中的一个具体故障：某些路径返回了数据库 ORM 类而没有对其实例化，Reimers 说这会导致服务器崩溃。另一个在 Twitter 上分享的例子，涉及 border-radius 的算术运算，他描述为除以一个负数并导致前端崩溃。

## 02 · [1:42] 正确的评审意见仍然可能不受欢迎

能找出真实的 bug，并不意味着这个评审器始终有用。与成功的捕获相伴而来的，是让代码改成它本来就在做的事情的建议、断言合法的 CSS 行为为非法的意见，以及仅仅因为代码以前是那样写的就要求恢复旧行为的请求。这些评审意见侵蚀了那些有用的意见所赢得的信任。

第一种解释是能力边界：有些问题是 LLM 能捕捉的，有些则是它无法捕捉的。让模型想象别人会在一个 PR 上留下什么评审意见，会鼓励它模仿代码评审这项活动的全部内容，既包括其能力范围内的评审意见，也包括超出其能力的评审意见。对这些能力进行分类有所帮助，但仍留下另一类令人沮丧的输出：要求为一个类写文档、把逻辑抽取成函数、或者添加测试的请求。这些意见在技术上可能站得住脚，但作为打断却未必有用。

当开发者和设计师一起回顾来自人类和机器人的历史评审意见时，这种区别变得更加清晰。对于会接受 LLM 的哪些评审意见，开发者之间的看法大体一致。设计师却觉得其中一些判断令人费解：表面上相似的评审意见得到了不同的反应。开发者所评估的不只是正确性。来自同事的某条建议他们可能乐于接受，但同样的内容来自一个自动化评审器就可能显得迂腐或讨厌。**模型能力与开发者的接受度是两个独立的维度。** 一个有用的评审器必须同时满足这两者。

## 03 · [3:55] 从真实评审中构建分类体系

Graphite 反复要求各种大语言模型对其自身及开源代码库的 10,000 条评审意见进行分类，然后对这些分类结果加以归纳。由此产生了一套用于讨论评审器实际输出内容的词汇，而不是把每条评审意见都当作 bug 报告来对待。

| 评审意见类别 | 它识别的是什么 |
| --- | --- |
| bug | 导致非预期行为的逻辑不一致 |
| 意外提交的代码 | 无意间被包含进来的代码 |
| 性能隐患 | 潜在的性能问题 |
| 安全隐患 | 潜在的安全问题 |
| 文档不一致 | 代码与其描述相互矛盾 |
| 风格类修改 | 与局部约定不一致的注释或模式 |

这些类别需要不同的判断。例如，一条文档不一致的意见只能确立"存在分歧"这一事实，却无法判断究竟是实现错了还是文字描述错了。一条风格建议则可能取决于了解该仓库遵循哪种模式。

某些非常理想的评审意见需要模型无法获取的信息。一位资深开发者可能会解释说，团队以前用过某种做法，但因某个特定原因放弃了它。如果这段历史只存在于开发者的头脑中，评审器就无法从代码中还原它。这种**部落知识（团队隐性经验）**属于分类体系中"想要但难以获得"的那一侧。

一张象限图把最佳实践和代码整洁度放在左上角，把 bug、性能和安全放在右上角，把偏好放在左下角，把部落知识放在右下角。图中按大语言模型能力与人类接受度两个维度映射了各类评审意见。

## 04 · [5:18] 最佳实践类建议需要一个出现的理由

与上面相反的问题是那些模型很容易产出、但开发者未必想要的建议：给这个函数写注释、加测试、抽取一个类型，或者把这段逻辑移进一个函数。人类评审者会施加一种局部的判断：这段逻辑在这个代码库里是否特别绕？是否有人容易误解它？抽取真的会有帮助吗？缺少这种判断，机器人几乎可以在任何地方持续产出站得住脚的整洁度建议。仅有技术上的正确，并不能决定一条评审意见是否应该出现在评审中。

更多的上下文可以改变这条边界。仓库代码、历史记录、风格指南和明确的规则，都可以帮助评审器判断哪些建议适合这个项目。Reimers 指出，随着上下文的增长，模型能够产出且开发者乐于接受的那片评审意见区域会不断扩大。实际的目标是当前可用上下文所支撑的那部分交集。

## 05 · [6:33] 评审器变化时要持续检查边界

一份离线的分类体系能提供初始方向，却无法保证一个不断变化的评审器始终保持有用。Graphite 更新了提示词，只请求那些处于模型能力范围内、且开发者希望收到的评审意见。Reimers 表示，从反馈来看接受度确实改善了。下一个问题是：随着系统演化，如何维持这种行为。

迁移到 Claude 4，或者从 Sonnet 改用 Opus，都会让这个问题再次出现：评审器是否仍然运行在图中"有用"的那片区域？增加上下文也带来一个相关的机会：也许它现在能够产出以前够不着的、有价值类别的评审意见了。Graphite 首先着手检查评审器实际产出的评审意见类型的分布。

## 06 · [7:47] 用表情反应来检测越界

Graphite 在评审意见上加入了表情点赞和点踩，作为检测能力故障的反馈渠道。点踩数量激增可能意味着出现幻觉，或者试图把评审器推向它无法可靠评估的范围。运营上的应对是再次收窄其行为。这使得表情反应对发现麻烦很有用，但另一个维度——开发者是否想要这些评审意见——仍然难以衡量。

Reimers 报告，在演讲当时点踩率低于 4%。

## 07 · [8:30] 衡量所请求的修改是否真的发生

一条评审意见通常是要求某人修改代码。因此，Graphite 开始衡量有多少百分比的评审意见之后紧跟着其所描述的修改，考察对象包括开源仓库以及通过其代码评审产品可访问的仓库。这把"有用"变成了一个可观察的结果：所请求的修改是否发生了？

Reimers 报告，人类的评审意见中约有 50% 在同一个 PR 内导致了修改。这为机器人提供了一个实际目标：达到与人类反馈相当的行动水平。观察窗口也很重要。开发者可能认同某条意见，但把修复推迟到后续的 PR；建议可能针对的是未来的工作而非当前的改动；而一条偏好意见也完全有理由不被实现。健康的评审文化会为分歧留出空间，所以一条未被执行的意见并不自动等于一次失败的评审。

Reimers 报告，截至 3 月，Diamond 的 PR 内行动转化率达到了 52%。他把达到人类基线归功于对评审器进行了恰当的提示词设计。这些是报告的行动转化率，而非 bug 检出准确率。这个结果支撑一个更窄但有用的结论：一个被约束在恰当评审意见范围内的评审器，能够让开发者以大致相当于人类观察值的比例执行它所请求的修改。

Diamond 是 Reimers 展示的用于落地这些发现的生产级产品。其底层方法把范围与反馈连接起来：筛选出模型能够处理、开发者也欢迎的评审意见类别，然后衡量这些评审意见是否产生了修改。正是这一点，把"偶尔能发现 bug 的能力"变成了一个人们真正可用的代码评审产品。

## 08 · 带时间戳讲稿的核心要点

1. AI 生成代码的数量与 bug 的数量一同上涨；Graphite 构建 Diamond 来检验 AI 是否也能找出这些 bug。
2. 早期在拉取请求（PR）上用 Claude 做的实验发现了真实的故障：一个未实例化的数据库 ORM 类会导致服务器崩溃，以及 border-radius 算术中除以负数的问题。
3. 同样的实验也产出了不可用的评审意见：要求修改本来就在做这件事的代码、错误地质疑合法的 CSS，以及要求回退到旧行为。
4. 大语言模型能力与开发者接受度是两个独立的维度；一条评审意见可以在技术上正确，但出自机器人仍然不受欢迎。
5. Graphite 把来自其自身及开源代码库的 10,000 条评审意见归类为：bug、意外提交的代码、性能隐患、安全隐患、文档不一致，以及风格类修改。
6. 部落知识（团队为什么放弃了旧做法）是开发者想要但模型够不着的；代码整洁度建议则是模型容易产出但开发者不想要的。
7. 更多上下文（仓库历史、风格指南、明确的规则）会扩大有用 AI 评审的范围。
8. 评审意见上的表情反应可以检测越界：点踩激增意味着幻觉；点踩率低于 4%。
9. 人类的评审意见约有 50% 带来 PR 内的修改；通过提示词让评审器停留在有用象限内，Diamond 截至 3 月达到了 52%。
10. 行动转化率正是把"AI 偶尔能找到 bug"变成一个可用代码评审产品的那个衡量指标。
