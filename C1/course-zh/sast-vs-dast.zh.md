# SAST vs. DAST vs. RASP：应用安全测试方法对比

学习
2024 年 12 月 18 日
Shanika Wickramasinghe

全球在信息安全上的支出预计到 2025 年将达到 2120 亿美元。这相比 2024 年增长了 15%。根据 Gartner 的分析，生成式 AI 的兴起和云的采用是这一快速增长的关键原因。该分析机构还预测，到 2027 年，生成式 AI 将参与 17% 的网络攻击。

企业需要超越传统方法的高级安全策略来应对这些日益增长的威胁。这就是为什么企业主需要了解 SAST、DAST 和 RASP 等安全解决方案，因为它们可以为应用提供多层保护。

（相关阅读：应用安全详解 & 常见软件测试方法。）


## 什么是 SAST？

静态应用安全测试（SAST）是一种白盒安全测试方法。SAST 使用应用的静态源代码或二进制文件来识别漏洞。这意味着 SAST 工具在应用未运行时对其代码进行操作。

开发人员使用 SAST 来检测各种安全风险，例如：跨站脚本（XSS）、不安全的反序列化、缓冲区溢出，以及代码中的其他 OWASP 漏洞。由于 SAST 单独无法识别运行时特有的漏洞，开发人员通常需要将 SAST 与其他测试方法结合使用，以实现全面的安全防护。

SAST 是软件开发生命周期的重要组成部分，因为它能尽早发现漏洞。越早发现问题，修复的成本就越低。由于 SAST 工具可以在开发阶段执行，开发人员现在能够在产品发布到市场之前编写代码并对其进行上千次（!!）测试。

SAST 可以集成到 CI/CD 流水线中，这样做之后通常被称为"安全 DevOps"或"DevSecOps"。SAST 通过自动化具备很强的可扩展性。实现覆盖 SAST 技术的自动化测试的能力，使其成为快速应对代码级风险的高效解决方案。


## 什么是 DAST？

动态应用安全测试（DAST）是一种黑盒测试方法。DAST 中的"动态"一词表明，该方法是在应用运行时评估应用的安全性。与 SAST 不同，DAST 不需要访问应用的源代码。相反，它会：

1. 模拟外部攻击者的行为。
2. 从外部对应用进行测试，以识别只在运行时才出现的漏洞。

DAST 有能力识别各种安全缺陷，例如拒绝服务（DoS）漏洞和不安全的服务器配置。通过模拟真实世界的攻击场景，DAST 工具会评估应用如何响应这些模拟的威胁。借助这种方法，开发人员可以识别 SAST 等静态测试方法可能遗漏的弱点。

通常，开发人员会在软件开发生命周期的后期阶段执行 DAST，往往是在部署之前。通过在应用的实际运行环境中进行测试，DAST 提供了运行时安全的清晰概览，并支持性能更好、能够抵御潜在攻击的应用。


## SAST 是如何工作的？

开发人员使用 SAST 工具，应用预定义规则和其他检测方法——例如模式匹配和数据流分析——来识别编码错误和其他漏洞。他们将这些工具集成到 IDE 或 CI/CD 流水线中，以便在编码和测试阶段自动执行扫描。


### 常见的 SAST 方法

以下是 SAST 中使用的一些方法。

模式匹配：扫描代码库中已知的非安全编码实践模式。例如，使用弱加密算法或不安全的 API 调用。

数据流分析：跟踪数据在应用中的流动方式。通过追踪不可信输入路径到敏感操作，可以识别 SQL 注入或缓冲区溢出等漏洞。

控制流分析：可以分析应用的控制结构。例如，通过分析循环和条件语句来发现逻辑缺陷或竞态条件等潜在漏洞。

自定义规则创建：许多工具允许开发人员创建自定义规则来落实编码最佳实践。以下是一些自定义规则的示例：

- 标记 SQL 查询中任何未经过净化处理的输入。
- 识别将用户提供的数据未经正确转义就输出到浏览器的代码。
- 突出显示使用易受攻击或已弃用函数的情况，例如 JavaScript 中的 eval() 或 C 语言中的 strcpy()。
- 检测源代码中硬编码的 API 密钥和密码，并标记任何对用户提供的数据缺少输入验证的情况。

依赖扫描：一些 SAST 工具会分析应用中使用的第三方库和框架，以识别依赖项中的漏洞。

语义分析：通过解读代码的含义而不仅仅是其结构，SAST 工具可以检测到不安全的配置或 API 的误用。

机器学习模型：先进的 SAST 工具会引入机器学习算法，通过分析大型数据集中的模式来识别以前未知的漏洞。


### 使用 SAST 工具时的性能考量

SAST 工具通常需要大量 CPU 和内存资源。在分析大型代码库时，这可能是一个重大问题。对一百万行代码进行完整扫描可能会消耗数 GB 的内存。

SAST 扫描所需的时间可能因代码库大小而有巨大差异，从小型项目的几分钟到企业应用的数小时不等。这会影响：

- 构建流水线的时间安排
- 开发人员的生产力

建议考虑使用支持增量扫描的现代 SAST 工具，使你只需分析发生变化的代码，而不是整个代码库。

此外，通过规则选择和范围界定进行性能调优也至关重要。配置不当的 SAST 工具可能会不必要地分析非关键代码路径，在没有带来安全收益的情况下浪费时间和资源。


## DAST 是如何工作的？

DAST 工具模拟真实世界的攻击——例如，向输入字段发送各种形式的恶意数据，以观察应用如何处理它们——来识别应用行为和响应中的漏洞与弱点。


### DAST 的步骤

该过程通常包括以下步骤。

第 1 步：扫描。扫描 Web 应用以发现入口点（例如 URL、表单和 API）。这一步骤会绘制出应用的结构，并识别潜在的攻击面。

第 2 步：攻击模拟。通过向应用发送精心构造的请求来模拟恶意活动。这些请求会尝试利用入口点，以测试跨站脚本和跨站请求伪造等漏洞。

第 3 步：漏洞检测。分析应用的响应以识别安全弱点。它评估应用在攻击下是否按预期运行。例如，可以注入恶意数据来检测 SQL 注入缺陷。

第 4 步：报告。生成包含检测到的漏洞和修复建议的报告。开发人员可以使用报告中的结果来修复已识别的问题。

现代 DAST 解决方案可以融入高级功能，例如 AI 驱动的分析和实时数据集成。它们会自动创建测试集。动态适应应用的结构，并使用机器学习算法减少误报。


### 使用 DAST 工具时的性能考量

以下是使用 DAST 工具时需要记住的一些性能瓶颈。

- DAST 工具会主动与运行中的应用交互，暂时增加应用服务器和 Web 服务器上的 CPU 和内存使用率。
- DAST 扫描期间产生的大量并发请求可能会消耗大量网络带宽。
- DAST 扫描器通常通过生成唯一请求来绕过或使应用缓存失效，从而降低缓存机制的效果。
- DAST 工具创建和管理多个测试会话可能会增加应用服务器的内存使用量。

为了避免这些问题或尽可能减少其影响，请遵循以下实践。

- 在应用使用量最少的非高峰时段安排 DAST 扫描。
- 在与生产环境配置一致的预发布（staging）或预生产环境中进行扫描。
- 使用 DAST 工具中的限流功能来控制并发请求的数量。
- 在扫描期间增加应用服务器的线程池。
- 为 DAST 扫描器的 IP 配置单独的缓存策略。
- 实现当性能超过阈值时自动暂停扫描的机制。


## SAST 与 DAST：关键差异

下表总结了 SAST 和 DAST 之间的差异。

| 标准 | SAST | DAST |
|---|---|---|
| 测试类型 | 白盒测试。在可以访问源代码的情况下，由内而外地测试应用。 | 黑盒测试。在无法访问源代码的情况下，从外部测试应用。 |
| 支持的软件类型 | 支持各种类型的软件，包括 Web 应用、Web 服务和富客户端。 | 支持 Web 应用和 Web 服务，但通常不支持其他软件类型。 |
| SDLC 阶段 | 在软件开发生命周期早期执行。 | 在 SDLC 后期进行，通常在部署期间或部署之后。 |
| 检测到的漏洞 | 识别编码缺陷，例如：SQL 注入、跨站脚本（XSS）、缓冲区溢出等。 | 检测运行时问题，例如服务器配置错误、拒绝服务漏洞和应用级缺陷。 |
| 修复漏洞的成本 | 成本较低，因为问题在 SDLC 早期就被发现。 | 成本较高，因为漏洞发现得较晚，往往需要紧急修复才能按时部署。 |
| 运行时和环境问题 | 无法检测运行时特有的或与环境相关的漏洞。 | 可以识别只在运行时出现或由环境因素引起的漏洞。 |
| 深度与广度 | 提供对代码级漏洞的深入洞察。 | 提供对应用外部安全风险的广泛视图。 |
| 与工具的集成 | 与 IDE 和 CI/CD 流水线集成，实现自动化静态分析。 | 与 CI/CD 流水线集成，实现持续的运行时测试。 |
| 误报与漏报 | 由于深度代码分析，误报的可能性较高。 | 误报较少，但由于内部可见性有限，漏报的风险较高。 |
| 技术依赖 | 依赖编程语言和框架；需要与工具兼容。 | 不依赖应用框架，因为它们从外部与应用交互。 |


## SAST 和 DAST 的优缺点

### SAST 的优点
- 在软件开发生命周期的早期识别安全漏洞。
- 分析代码库，包括基础函数和复杂分支。
- 直接对源代码进行操作，无需应用处于运行状态。
- 提供实时反馈和全面的洞察，例如漏洞的确切位置。
- 生成可导出的报告，可通过仪表板进行跟踪。
- 支持自动化，因此比人工代码评审更快、更高效。


### SAST 的缺点
- 经常产生大量误报。因此可能需要人工评审。
- 无法识别运行时或环境特有的漏洞，例如配置错误。
- 需要针对每种编程语言的专用工具，因此维护较为复杂。
- 难以理解外部库、API 和 REST 端点。


### DAST 的优点
- 识别只在应用执行期间才出现的漏洞。
- 从外部运行，无需访问源代码。这对于测试第三方应用或编译后的代码非常有效。
- 模拟真实的攻击场景，识别 SAST 遗漏的风险。
- 不依赖于应用的编程语言。
- 评估整个应用和系统。这包括内存消耗、资源使用情况和第三方接口。


### DAST 的缺点
- 只关注应用的外层，可能会遗漏更深层次的漏洞。
- 在 SDLC 的后期才应用，因此修复成本更高、更耗时。
- 会遗漏某些 SAST 工具可以通过源代码分析识别的漏洞。举个例子，设想一个 Web 应用使用不安全的随机数生成器（例如 JavaScript 中的 Math.random()）来创建会话 Token。DAST 可能会遗漏这个缺陷，因为它只测试运行时行为。（而 SAST 可以检测到它。）
- 大型项目需要自定义基础设施，且需要应用的多个实例并行运行，因此资源消耗较大。


## 什么时候该用 SAST，什么时候该用 DAST？

SAST 和 DAST 在保障 SDLC 安全方面扮演着互补的角色。了解何时使用哪一种，有助于实现全面的安全覆盖。


### 何时使用 SAST

在开发的早期阶段。开发人员使用 SAST 在 SDLC 早期识别 SQL 注入和硬编码凭据等漏洞。通过在部署之前捕获这些问题，可以降低修复它们的成本和复杂性。

例如：某个 SAST 工具扫描 Python 代码，并标记出一个漏洞——源代码中嵌入了硬编码的 API 密钥。开发人员重构代码，改用环境变量来安全地存储和获取这些密钥。

在代码评审中。SAST 可集成到版本控制系统中，允许开发人员在提交代码之前进行扫描。这确保了只有安全的代码才能进入仓库。

示例：某个 SAST 工具可以检测到一个漏洞——文件路径直接由用户输入构建且未经验证，使应用面临路径遍历攻击的风险。开发人员通过净化输入并使用安全的库函数来处理文件路径来修复该问题。

在持续集成/持续部署流水线中。SAST 在 CI/CD 过程中运行自动化扫描，为开发人员提供实时反馈。


### 何时使用 DAST

预生产测试。开发人员使用 DAST 在预发布（staging）或 QA 环境中识别运行时漏洞（例如：不安全的配置、身份验证缺陷、访问控制不足）。

示例：某个 DAST 工具可以检测到暴露敏感数据的数据库配置错误。这样开发人员就可以在部署之前加固配置。

在部署后的监控中。DAST 工具会持续扫描已部署应用中由环境变化或新出现的威胁引起的漏洞。这可以保证应用长期保持安全。

测试第三方集成。DAST 可以模拟外部攻击者的视角，识别第三方 API 或互联系统中的漏洞。

例如：某个 DAST 工具测试一个 Web 应用，发现某个第三方支付 API 存在漏洞——信用卡详细信息通过未加密的 HTTP 连接传输。开发人员通过强制所有 API 通信使用 HTTPS 来解决该问题。


## 哪个更有效：SAST 还是 DAST？

SAST 或 DAST 的有效性取决于：

- SDLC 的阶段
- 所要解决的漏洞类型

SAST 在开发早期效果最佳，主要用于识别源代码中的漏洞、降低成本并促进安全编码实践。相比之下，DAST 关注预生产或已部署应用中的运行时漏洞。它可以提供对配置错误和不安全集成等问题的洞察。


### 采用混合方法

与其二选一，不如将 SAST 和 DAST 结合起来，构建一个多层安全策略，同时应对静态代码和运行时环境中的漏洞。SAST 可以集成到开发的早期阶段，在应用编译之前检测并修复代码级问题。一旦应用在测试环境中运行起来，DAST 就可以识别运行时漏洞，并评估应用在攻击条件下的行为。

在 CI/CD 流水线中同时自动化 SAST 和 DAST 扫描，可以在不牺牲安全性的前提下提供持续反馈并加速开发过程。

对于敏捷或 DevOps 环境，添加 IAST 或 RASP 等工具可以进一步增强安全性。通过关联 SAST 和 DAST 的结果，组织可以实现更全面、更有效的漏洞管理。


### 使用 RASP 作为 SAST 和 DAST 的替代方案

运行时应用自我保护（RASP）是一种高级安全解决方案，直接安装在应用运行所在的服务器上。

RASP 将自身嵌入到应用的运行时环境中。这种集成使 RASP 能够分析应用的逻辑和数据。在分析过程中，它可以：

1. 在异常行为发生时实时检测。
2. 即时阻断恶意活动。

一个关键区别是，RASP 不仅仅对潜在问题发出告警——它通过隔离和消除威胁来主动阻止攻击，而不依赖外部工具。

RASP 为 SAST 和 DAST 提供了一种动态的替代方案。与分析静态代码的 SAST 和模拟外部攻击的 DAST 不同，RASP 实时运行。它监控应用执行期间的行为，并通过终止会话或告警防御者来响应实时威胁。

RASP 在保护应用免受绕过网络防御或在开发期间被遗漏的漏洞方面尤为有效。

然而，对 RASP 过度自信可能导致组织忽视安全编码实践。此外，由于 RASP 直接在应用的运行时环境中运行，它可能会影响应用性能。RASP 无法替代修复底层缺陷的需求，但在修复工作正在进行时，它可以提供持续的保护。

正如一位 RASP 用户所评论的：

"是否使用 RASP 工具的决定，应基于对应用特定需求和安全风险状况的全面评估。"

## 未来是 SAST、DAST 和 RASP 的应用安全测试时代

应用测试的未来在于将 SAST、DAST 和 RASP 结合起来，构建全面的安全策略。随着安全挑战不断增长，将这些工具集成到 CI/CD 流水线中并实现流程自动化将变得不可或缺。

AI 和机器学习的进步将使测试更加高效，因为它们有助于减少误报并改进威胁检测。


### 金融与金融服务行业

在金融领域，AI 驱动的工具将改变漏洞的检测和缓解方式。SAST 和 DAST 将继续在开发和预生产阶段识别编码缺陷和运行时问题。

但你不会止步于此：RASP 将进一步利用 AI 监控实时交易。例如，RASP 可以检测异常模式（例如：攻击者试图实时利用某个漏洞），并阻断这些活动，同时通知安全团队。


### 物联网、边缘和联网设备

在物联网方面，这些工具的组合将在保障联网设备安全方面发挥重要作用。具体如下：

- SAST 可以在开发期间确认固件不存在漏洞。
- DAST 可以测试设备之间通信协议的安全性。
- RASP 则监控已部署的设备，检测并阻止由新出现的威胁引起的未授权访问尝试或数据泄露。

同样，使用多种方法将帮助物联网生态系统保持韧性。正如我们众多示例中所解释的，SAST、DAST 和 RASP 共同承诺了一个未来：应用的构建和部署将采用更强大、更主动的安全措施。


## 有韧性的安全始于主动测试

将 SAST、DAST 和 RASP 结合起来，可以提供覆盖整个软件开发生命周期的强大安全保障。

通过将这些方法集成到 CI/CD 流水线中并利用 AI 的进步，组织可以主动应对新出现的威胁。这些方法共同提供了一种整体性的方法，保护现代应用免受安全漏洞的侵害。
