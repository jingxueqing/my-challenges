# 规格说明已死，规格说明万岁！

### 原型是新的规格说明，而规格说明是新的……源代码？
Ravi Mehta
和
Danny Martinez
2025年7月31日
在我的职业生涯中，规格说明变得越来越短。当我在 Microsoft 开始工作时，一位产品经理的价值是以其规格说明的厚度来衡量的。多年以后，在 Tripadvisor，我们把一位带着一张写在餐巾纸上的规格说明去参加产品评审的产品经理奉为传奇。

产品团队常常把规格说明当作文书工作——在"真正的工作"（交付上线）之前的一种必要之恶。工程师因优雅的代码而受赞颂，设计师因漂亮的用户体验而受赞誉。产品经理因交付业务影响而获得掌声。但规格说明呢？它们通常被草草写完、随手丢开、然后被遗忘。

感谢阅读 Ravi on Product！欢迎免费订阅以接收新文章并支持我的工作。

这一直是一个错误。在我的
产品能力工具箱
中，功能规格说明位居榜首——十二项能力之首——这是有原因的。它是产品执行的基础，与产品交付和产品质量并列。

无懈可击的执行是优秀产品管理的基石，而一份出色的规格说明就是起跑线。

今天，我们的构建方式正在转变。工程师越来越快——快得多。AI 可以在几分钟内把粗略的想法变成可运行的代码。瓶颈不再是构建。而是知道该构建什么，并
让团队围绕这些需求达成一致。

突然之间，不起眼的规格说明不再是昙花一现的文书。它是产品管理的根基——它正在成为源代码本身。


## 为什么产品经理突然成了瓶颈
在他最近的演讲
用 AI 更快地构建
中，Andrew Ng 指出了一个前所未有的趋势：


> "我人生中第一次看到，有管理者向我提议让产品经理的数量是工程师的两倍。我仍不知道这个提议是不是个好主意，但我认为这是世界走向的一个信号。"——Andrew Ng
这印证了我们在
上一篇文章
中的预测：当工程师借助 AI 以数倍速度交付时，公司
需要更多的产品经理来支持这些高产的工程师，而不是更少
。

随着产品交付加速，产品管理的其他每个环节——理解客户需求、打磨正确的功能、验证业务影响——都承受着巨大的压力。

而所有这些压力都汇聚到一个产物上——规格说明。


## 规格说明——新的源代码
在传统软件开发中，程序员编写人类可读的"源代码"，它被编译成高度优化、机器可读的"目标代码"。"目标代码"（也称为二进制文件）是一种副产品，可以用源代码重新生成。源代码
正是
唯一事实来源。

来自 OpenAI 的 Sean Grove 提出了一个颇具争议的论点。在他最近的演讲
The New Code
中，他主张一份写得好的提示词（即规格说明）就是新的源代码。

从这个角度看，我们的 AI 开发方式做反了。我们精心编写提示词来向模型传达意图。AI 生成代码。然后我们保留代码、丢弃提示词。

"这感觉就像你把源代码碎掉，然后小心翼翼地对二进制文件做版本控制。"Grove 如此评论道。

想想看。在传统编程中，源代码是神圣的。源代码包含注释、结构和文档——理解和修改系统所需的一切。二进制文件只是一个下游产物。

但有了 AI，我们颠倒了这种关系。我们把生成的代码当作值得保留的产物，而把规格说明——提示词——当作一次性的东西。

Grove 认为这完全搞反了。代码，即使是优雅的代码，用他的话说也只是规格说明的一种"有损投影"。就像反编译一个二进制文件不会还原出原始的注释和变量名一样，阅读代码也无法告诉你它背后完整的意图。

而规格说明包含一切。一个足够健全的规格说明可以生成"好的 TypeScript、好的 Rust、服务器、客户端、文档、教程、博客文章，甚至播客。"

"一个足够健全的规格说明可以生成好的 TypeScript、好的 Rust、服务器、客户端、文档、教程、博客文章，甚至播客。"——Sean Grove，OpenAI

更重要的是，规格说明能做代码做不到的事情：它让人类和机器在共同的目标上保持一致。Grove 说得很简单："一份书面的规格说明能有效地让人类保持一致，它是你用来沟通、讨论、辩论、引用和同步的产物。"

他预测："在不久的将来，沟通最有效的人就是最有价值的程序员。从字面意义上说，如果你能有效地沟通，你就能编程。"

新的稀缺技能不是编程。而是编写能完整捕捉意图与价值观的规格说明。

对产品经理来说，这应该听起来很熟悉。这正是我们一直在做的事情——只不过现在机器也在听了。


## 等等，原型不是已经杀死了规格说明吗？
直到最近，产品生命周期都必须从规格说明（或产品需求文档（PRD）、或概念文档、或餐巾纸）开始，由它启动初期的线框图、设计、原型制作和 MVP 开发。

传统方法让人感觉是一种必要之恶。工程师构建基础的 MVP，只是为了把某种东西——任何东西——交到客户手里。"如果你对自己产品的第一版不感到尴尬，说明你上线太晚了"成了金科玉律。

我们构建产品的整个方法最近经历了一次重大转变，在这个新世界里，
规格说明往往是输出，而不是输入
。

今天，你不需要交付一行代码，就能把原型交到客户手里。像 v0、Lovable 和 Replit 这样的工具让你能在数小时而非数周内构建出可运行的原型。无需工程参与。

这不仅仅是更快——而是根本上的不同。手握一个"氛围编程"出来的原型，你可以在写下功能规格说明的第一行之前就收集真实的客户反馈。你可以验证假设、迭代流程、打磨交互。

- 旧的工作流是这样的：模糊的想法 → 线框图 → 设计 → 工程师构建的 MVP → 客户反馈 → 痛苦的规格说明修改 → 线框图 → 设计 → 重构 → 祈祷。
- 新的工作流：模糊的想法 → 快速原型 → 客户反馈 → 清晰无比的规格说明 → AI 辅助实现。

原型没有杀死规格说明。它们正在让规格说明变得更好。


## 规格说明驱动的开发实战
让我们看一个动手实例，看看这一切是如何运作的。
Danny Martinez
是 decimals 的创始人，这是一个（尚处隐身模式的）平台，让创作者经济中的专家把自己人脉中的 talent 安置到职位上。

- 你是一位正在寻找新机会的 AI 优先的产品经理吗？留下你的信息，当我们遇到有趣的机会时会通知你。
- 你是一家想招聘 AI 优先的产品经理的公司吗？申请加入我们的人才网络，我们将分享一份精心筛选的候选人名单。

Danny 将带我们了解他们的规格说明驱动开发流程——这个流程带来了两大影响：

1. 大幅改善了较大功能上与工程团队的沟通；
2. 让毫无编程经验的 Danny 也能从详细的规格说明一路走到上线功能，完成那些较小的需求。

交给你了，Danny……

这是我最近处理的一个例子。背景说明一下：我们在构建一个让专家型 influencer 把自己人脉中的候选人安置到职位上的产品。在新落地页上线后，我们需要给专家们提供一个快速访问自己页面链接的方式。


> 我们需要在页头加一个按钮，指向 company-apply 页面。我目前在忙邮件的事。如果你能接手的话，这是可以氛围编程搞定的活。
这是我联合创始人的留言，说的是一个需要交付的简单按钮。足够简单，也正是如今非技术人员可以自己交付的那类事情。

以下是这个需求在几分钟内被交付的配置与步骤：

- 项目管理工具：Linear
- IDE：VS Code
- 扩展：GitHub Copilot Pro
- 模型：Claude Sonnet 4
- MCP 服务器：Linear MCP 服务器，让 Copilot 可以访问 Linear 工单

让我们看看流程中的步骤（可对照上面的 Loom 视频跟着操作）：

1. 从我联合创始人的 Slack 消息生成一个 Linear 工单（00:14）
2. 在上面的工单中明确我希望的新文案是什么（00:25）
3. 打开 Copilot，用提示词让 Claude 打开该 Linear 工单（01:18）
4. 用提示词让 Claude 评审该工单，并结合代码库进行分析（01:52）
5. 用提示词让 Claude 创建分支并实现这些变更（02:30）
6. 测试这些变更，确保它们按预期工作（02:52）
7. 在 GitHub 上打开一个拉取请求（PR），把这些变更交付进代码库（03:55）
8. 等待工程师评审/批准该 PR

把镜头拉远，这套设置的真正威力就显现出来了。是的，这只是一个微不足道的例子，但道理不变：一个非技术人员如今可以通过对 Claude 发出的几条提示词（借助 GitHub Copilot），在 Linear 工单、代码库和工程师之间自如穿梭。

再强调一次，这一切的关键不在于代码本身：而在于规格说明。

现在，需要说明的是，要让上述流程良好运转，需要满足以下条件：

1. 具体明确：使用含糊的规格说明只会导致一个混乱的代码库。让 Claude 先起草工单初稿、评审代码库、并帮助它变得更具体，是这个流程中不可或缺的一环。在我们的案例中，我们还制定了编写优秀规格说明的准则。
2. 有所取舍：将上述方法用于较简单的任务是最理想的。工单越复杂，就越需要懂行的人参与（在这些情况下，"自助式"到头来恰恰做不到自助）。
3. 把关守门：这个方法之所以运转良好，是因为有一位真正懂行的工程师在评审变更，并确保简单性与功能性之间的平衡得以维持。

但要说清楚的是：规则已经变了。规格说明是所有参与构建产品的人——包括大语言模型——的唯一事实来源。

只要配置得当，非技术人员参与代码库的贡献完全是现实的。只要有足够的时间和耐心，你就可以开始理解代码库并自己实现变更，而不是每次都单纯依赖 Claude 来救场。

有一天，你甚至可以指望一个智能体在你啜饮咖啡时交付你的工单。

如果你是一位产品经理，正在担心 AI 会对你的工作带来什么影响，关键是要认识到：工作本身正在改变。但对所有人来说都是如此。好消息是，成为优秀产品经理所需的核心技能在这个新世界里反而更有价值了。

正如我们在
上一篇文章
中预测的，以这种方式运作的公司将需要更多而不是更少的产品经理。事实证明，这个预测相当靠谱：


## 规格说明万岁！
William Gibson，那位创造了"赛博空间"一词的科幻作家，曾说过：


> 未来已经到来——只是分布得还不太均匀。
每当我思考 AI 能做什么、不能做什么时，我都会想起这句话。今天，AI 的成果分布极不均匀。有些事情——生成代码、文本、图像——已经实现了量子跃迁。它们以
AI 速度
运转。另一些事情——与客户交谈、发现他们的需求、说服他们购买——仍然以
人类速度
推进。

这种不均匀的分布正在重塑产品团队。聚光灯正从实现性工作转向理解性工作。那些一直让最优秀的产品经理脱颖而出、无与伦比的核心技能——理解用户需求、清晰地定义问题、设计优雅的解决方案——正变得愈发有价值。

最优秀的产品经理把这些洞察转化为规格说明——让团队保持一致、指导实现，并在这个日益自动化的开发世界中作为持久产物存在的规格说明。
