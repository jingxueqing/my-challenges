# 长上下文为何失效

### 管理好上下文是智能体成功的关键
随着前沿模型的上下文窗口不断增长
1
，许多模型已支持多达 100 万个 Token，我看到许多热烈的讨论，认为长上下文窗口将解锁我们梦寐以求的智能体。毕竟，只要窗口足够大，你就可以把你可能需要的
一切
都塞进一个提示词里——工具、文档、指令等等——然后让模型处理剩下的部分。

长上下文削弱了 RAG 的热度（既然能把所有文档都放进提示词，何须再找最好的那篇！）、推动了模型上下文协议（MCP）的炒作（连接所有工具，模型就能做任何工作！），并助长了对智能体的热情
2
。

但现实中，更长的上下文并不会带来更好的回答。让上下文过载会导致你的智能体和应用以令人意外的方式失效。上下文可能被污染、让人分心、造成混淆，或产生冲突。这对智能体来说尤其成问题，因为智能体依赖上下文来收集信息、综合发现并协调行动。

下面我们来看看上下文会在哪些方面失控，然后回顾一些缓解或彻底避免上下文失效的方法。


## 上下文失效模式
- 上下文污染：当幻觉进入上下文时
- 上下文分心：当上下文压过了模型训练所学时
- 上下文混淆：当多余的上下文影响了回答时
- 上下文冲突：当上下文各部分彼此矛盾时


### 上下文污染
上下文污染是指幻觉或其他错误进入上下文，并在其中被反复引用。

Deep Mind 团队在
Gemini 2.5 技术报告
中指出了上下文污染问题，我们
上周已对该报告进行了解析
。在玩《宝可梦》时，Gemini 智能体偶尔会在游戏过程中产生幻觉，从而污染其上下文：


> 这一问题尤为严重的一种形式是"上下文污染"——上下文中的许多部分（目标、摘要）被关于游戏状态的错误信息"污染"，而这往往需要很长时间才能消除。结果，模型可能变得执着于实现不可能或无关的目标。
如果其上下文中的"目标"部分被污染，智能体就会制定荒谬的策略并重复某些行为，去追求一个无法达成的目标。


### 上下文分心
上下文分心是指上下文变得过长，导致模型过度关注上下文本身，而忽视了它在训练中学到的东西。

在智能体工作流中，随着上下文不断增长——模型收集更多信息并积累历史——这些累积的上下文可能变得让人分心而非有所帮助。玩《宝可梦》的 Gemini 智能体清晰地展示了这个问题：


> 尽管 Gemini 2.5 Pro 支持 100 万以上的 Token 上下文，但如何让智能体有效利用它仍是一个新的研究前沿。在这种智能体化设置中，我们观察到当上下文大幅超过 10 万 Token 时，智能体倾向于重复其庞大历史中的既有动作，而不是综合出新的计划。这一现象虽然只是经验之谈，却凸显了"面向检索的长上下文"与"面向多步生成式推理的长上下文"之间的重要区别。
智能体没有利用训练所学来开发新策略，而是执着于重复其庞大上下文历史中的过去动作。

对于较小的模型，分心的阈值要低得多。一项
Databricks 研究
发现，Llama 3.1 405b 的模型正确率大约在 32k Token 时开始下降，更小的模型则更早。

如果模型在上下文窗口远未填满之前就开始表现失常，那超大上下文窗口的意义何在？简而言之：摘要
3
和事实检索。如果你两者都不做，就要警惕你所选模型的分心阈值。


### 上下文混淆
上下文混淆是指上下文中的多余内容被模型用来生成低质量的回答。

曾有一段时间，似乎
人人
都要发布一个
模型上下文协议（MCP）
。一个强大模型连接到你
所有
的服务和
各种东西
、替你完成所有琐碎任务的梦想似乎触手可及。只要把所有工具描述一股脑塞进提示词，然后按下运行键即可。
Claude 的系统提示词
为我们指明了方向，因为它的主要内容就是工具定义或工具使用说明。

但即使
整合与竞争没有拖慢 MCP 的脚步
，
上下文混淆
也会。事实证明，工具确实可能多到物极必反。

伯克利函数调用排行榜
（Berkeley Function-Calling Leaderboard）是一个工具使用基准，用于评估模型有效使用工具来回应提示词的能力。如今已出到第 3 版的排行榜显示，当提供超过一个工具时，
每一个
模型的表现都会变差
4
。此外，伯克利团队"设计了一些场景，其中所提供的函数都不相关……我们期望模型输出为不进行函数调用。"然而，所有模型仍会偶尔调用不相关的工具。

浏览函数调用排行榜你会发现，模型越小，问题越严重：

上下文混淆的一个引人注目的例子见于
最近一篇论文
，该论文评估了小模型在
GeoEngine 基准
上的表现，该测试包含
46 个不同的工具
。当团队给量化（压缩）后的 Llama 3.1 8b 一个附带全部 46 个工具的查询时，它失败了，尽管上下文远未超出 16k 的上下文窗口。但当他们只给模型 19 个工具时，它成功了。

问题在于：一旦你把某些东西放进上下文，
模型就必须关注它。
它可能是不相关的信息或多余的工具定义，但模型
会
将其纳入考量。大型模型，尤其是推理模型，在忽略或丢弃多余上下文方面正变得越来越好，但我们不断看到毫无价值的信息绊倒智能体。更长的上下文让我们能塞进更多信息，但这种能力是有代价的。


### 上下文冲突
上下文冲突是指你在上下文中积累的新信息和工具与上下文中的其他信息发生冲突。

这是
上下文混淆
的一个更棘手的版本：这里的坏上下文并非不相关，而是直接与提示词中的其他信息相矛盾。

一个 Microsoft 与 Salesforce 的团队在
最近一篇论文
中精彩地记录了这一点。该团队从多个基准中提取提示词，并将其信息"分片"到多条提示词中。可以这样理解：有时，你可能会坐下来，在按下回车之前在 ChatGPT 或 Claude 里输入好几段文字，把每个必要的细节都考虑进去。另一些时候，你可能会先发一个简单的提示词，然后当聊天机器人的回答不尽如人意时再补充更多细节。Microsoft/Salesforce 团队把基准提示词改造成这种多轮交互的形式：

左侧提示词中的所有信息都包含在右侧的几条消息中，这些消息将在多轮对话中逐步发出。

分片后的提示词产生了明显更差的结果，平均下降 39%。而且该团队测试了一系列模型——OpenAI 备受赞誉的 o3 的分数从 98.1 跌至 64.1。

这是怎么回事？为什么信息分阶段收集而非一次性给出时，模型表现会更差？

答案就是
上下文混淆
：拼装起来的上下文包含了完整的对话过程，其中包含模型
在尚未获得全部信息时
尝试回答问题的早期尝试。这些错误回答留在上下文中，并在模型生成最终答案时对其产生影响。该团队写道：


> 我们发现，大语言模型常常在早期轮次中做出假设，并过早地尝试生成最终方案，然后过度依赖这些方案。简而言之，我们发现当大语言模型在对话中走错一步时，它们会迷路且无法恢复。
这对智能体开发者来说不是个好兆头。智能体从文档、工具调用以及负责子问题的其他模型那里汇集上下文。所有这些来自不同来源的上下文，都可能自相矛盾。此外，当你连接到你并未亲自创建的 MCP 工具时，它们的描述和指令与提示词其余部分发生冲突的可能性更大。

百万 Token 上下文窗口的到来曾让人感觉是变革性的。把智能体可能需要的一切都塞进提示词的能力，催生了对超级智能助手的憧憬——它们可以访问任何文档、连接所有工具，并保持完美记忆。

但正如我们所见，更大的上下文带来了新的失效模式。上下文污染嵌入的错误会随时间累积。上下文分心使智能体严重依赖其上下文并重复过去的动作，而不是向前推进。上下文混淆导致对不相关工具或文档的使用。上下文冲突制造内部矛盾，使推理脱轨。

这些失效对智能体的打击最重，因为智能体恰恰运行在上下文急剧膨胀的场景中：从多个来源收集信息、进行连续的工具调用、进行多轮推理，以及积累大量历史记录。

幸运的是，有解决办法！在即将发布的文章中，我们将介绍缓解或避免这些问题的技术，从动态加载工具的方法到建立上下文隔离区。
