# OpenAI 如何使用 Codex

## 引言

Codex 在 OpenAI 的众多技术团队中被日常使用，包括安全、产品工程、前端、API、基础设施和性能工程团队。各团队正在用它来加速各种工程任务——从理解复杂系统、重构大型代码库，到在紧迫的期限下发布新功能和处置事故。


基于对 OpenAI 工程师的访谈和内部使用数据，我们整理了这些用例和最佳实践，展示 Codex 如何帮助我们的团队更快地前进、提高工作质量，并在大规模下管理复杂性。

# OpenAI 如何使用 Codex

## 用例 1

### 代码理解

Codex 帮助我们的团队在入职、调试或调查事故时，快速熟悉代码库中不熟悉的部分。

他们经常使用 Codex 定位某个功能的核心逻辑、梳理服务或模块之间的关系，以及追踪数据在系统中的流动。它还有助于发现架构模式或缺失的文档——否则这些内容需要大量人工才能整理出来。

在事故响应期间，Codex 通过揭示组件之间的交互，或追踪故障状态如何跨系统传播，帮助工程师快速进入新的领域。

让我能快速分诊。

对于横跨

## 用例 2

### 重构与迁移

Codex 常被用于进行跨多个文件或包的修改。例如，当工程师在更新某个 API、更改某个模式的实现方式，或迁移到新的依赖时，Codex 能让修改保持一致地应用。

当同一个更新需要在几十个文件中执行，或者更新需要对结构、依赖关系的感知——而这些是正则表达式或查找替换难以捕捉的——它尤其有用。

他们还用它来做代码清理：拆分过大的模块、用现代模式替换旧模式，或为更好的可测试性准备代码。

### 来自我们团队的真实案例

扫描旧模式的每一个实例，
用 Markdown 总结影响，
然后打开包含修复的拉取请求（PR）。

### 性能优化

Codex 被用于识别并解决性能瓶颈。

在调优或可靠性工作中，工程师会让 Codex 分析缓慢或内存密集的代码路径——例如低效的循环、冗余的操作或代价高昂的查询——并提出优化后的替代方案，往往能带来效率与可靠性上的实质性提升。

Codex 也被用于维护代码健康：识别仍在活跃使用中的高风险或已弃用模式。我们的团队依靠它来帮助减少长期技术债务，并主动防止回归。

### 来自我们团队的真实案例

我用 Codex 扫描重复的
高成本数据库调用。它非常擅长
标记热点路径，并起草
我可以稍后调优的批量化查询。

Codex 非常擅长快速发现
性能问题——我花 5 分钟写提示词，
省下 30 分钟的工作。

基础设施工程师，
API 可靠性

平台工程师，
模型服务

## 用例 4

### 提升测试覆盖率

Codex 帮助工程师更快地编写测试——尤其是在覆盖率薄弱或完全缺失的地方。

在修复 bug 或重构时，工程师常常让 Codex 建议覆盖边界情况或可能失败路径的测试。对于新代码，它可以根据函数签名和周边逻辑生成单元测试或集成测试。

Codex 在识别边界条件方面尤其有帮助，例如空输入、最大长度，或那些在初始测试中常被遗漏的罕见但合法的状态。

### 来自我们团队的真实案例

低覆盖率的模块，醒来时就能看到
可运行的单元测试拉取请求（PR）。

当切换单体仓库分支很痛苦时，
我让 Codex 写测试并启动 CI，
同时我继续在自己的分支上工作。

前端工程师，
ChatGPT Desktop

后端工程师，
支付与计费

### 试试用 Codex 提升测试覆盖率，使用这些示例提示词：

包括边界情况和失败路径。

# OpenAI 如何使用 Codex

## 用例 5

### 提高开发速度

Codex 通过同时加速开发周期的起点和终点，帮助团队更快地前进。

在启动一个新功能时，工程师用它搭建样板代码——生成目录、模块和 API 存根，从而快速获得可运行的代码，而不必手工接线每一个部分。

当项目接近发布时，Codex 通过处理那些较小但必不可少的任务来帮助满足紧迫的期限，例如分诊 bug、补齐最后一公里的实现缺口，以及生成上线脚本、遥测钩子或配置文件。

它还被用来把产品反馈转化为起始代码。工程师常常粘贴一份用户请求或规格说明，让 Codex 生成一份粗略草稿，供他们日后回头完善。

因为 Codex 在后台工作。

这让人感觉超级有力量。

ChatGPT Enterprise

全栈工程师，

### 探索与构思

Codex 对于开放式的工作同样有用，例如寻找替代方案或验证设计决策。你可以用提示词询问解决问题的不同方式、探索不熟悉的模式，或对假设进行压力测试。这有助于浮现权衡、扩展设计选项，并锐化实现选择。

它还被用来识别相关 bug。给定一个已知问题或已弃用的方法，Codex 可以在代码中的其他地方识别出相似的模式，从而更容易地捕获回归或完成清理工作。

# OpenAI 如何使用 Codex

## 最佳实践

当 Codex 获得结构、上下文和迭代空间时，它表现得最好。以下是一些 OpenAI 团队正在养成的习惯，以便在日常工作中持续从中获得价值。

### 从 Ask 模式开始

对于大型改动，先用 Ask 模式让 Codex
给出一个实现计划，当你切换到
Code 模式时，这个计划就成为后续
提示词的输入。这种两步流程让 Codex
保持有据可依，并有助于避免其输出
中的错误。Codex 最擅长处理范围明确、
你自己或队友大约需要一小时完成
或几百行代码实现的任务。随着模型的
改进，可以预期它能承担的任务规模会增大。

### 持续迭代改进 Codex 的开发环境

配置启动脚本、环境变量和互联网访问，
能显著降低 Codex 的错误率。在运行任务时，
留意那些可以通过调整 Codex 的环境配置
来纠正的构建错误。这可能需要几轮迭代，
但从长远来看会带来显著的效率收益。

### 像撰写 GitHub Issue 一样
组织你的提示词

当提示词的写法接近你在拉取请求（PR）
或 issue 中描述一个改动的方式时，
Codex 的响应会更好。这意味着在相关时
提供文件路径、组件名称、差异（diff）
和文档片段。使用诸如"按照 [模块 X] 中的
同样方式实现它"这样的提示词模式
可以改善结果。

### 把 Codex 任务队列用作
轻量级待办清单

派发任务来记录临时闪现的想法、
半成品的工作或顺手可修的问题。
不必强求一次就生成完整的拉取请求（PR）。
Codex 很适合作为一个暂存区，
等你重新专注时再回来处理。

# OpenAI 如何使用 Codex

## 最佳实践

### 使用 AGENTS.md 提供持久上下文

维护一个 AGENTS.md 文件，帮助 Codex
在你的仓库中跨提示词更有效地运作。
这些文件通常包含命名约定、业务逻辑、
已知的怪癖，或 Codex 无法仅从代码中
推断出的依赖关系。更多关于如何组织
AGENTS.md 文件的内容请参阅文档。

### 利用"Best of N"提升输出质量

Best-of-N 功能让你可以针对同一个任务
同时生成多个响应，从而快速探索多个
解决方案并选出最好的一个。对于更复杂的
任务，你可以评审多个迭代，并把不同响应
中的部分内容组合起来，得到更强的结果。

## 展望未来

Codex 仍处于研究预览阶段，但它已经切实影响着我们的构建方式，帮助我们更快地前进、编写更好的代码，并承担那些原本永远不会被排上优先级的工作。


我们对前方的潜力感到兴奋——随着我们的模型变得更好、Codex 更深入地融入我们的工作流程，我们期待解锁更强大的用它开发软件的方式。我们会继续分享一路上学到的经验。
