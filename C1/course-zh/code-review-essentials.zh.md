## 软件团队的代码评审要点
2015年2月9日
代码评审是任何协作式软件项目的重要组成部分。大型软件系统通常由多人编写，因此一个运转良好的软件团队需要一套稳健的流程，让成员们以及代码库本身始终保持正确的方向。

代码评审是一个强大的工具，它能够：

1. 帮助团队成员随着系统的变化更新自己对系统的心理模型
2. 确保变更正确地解决问题
3. 开启关于设计优劣的讨论
4. 在缺陷进入生产环境之前将其捕获
5. 保持代码风格与组织结构的一致性

把这些收益看作一个需求层次结构会很有帮助。


## 让团队成员保持同步
代码评审最关键的功能是让团队的每个成员都朝着正确的方向前进。你无法安全地修改一个你不理解的系统，因此代码评审让团队在认知上保持一致。当 Bob 提交一个针对账务子系统的拉取请求（PR）时，Amy 在评审 Bob 的代码过程中更新了自己对该系统的心理模型。Amy 有机会就不理解的部分提问，Bob 则获得澄清自己的设计决策、并向他人讲解自己工作的机会。当 Amy 一个月后需要对账务子系统做修改时，她对系统的心理模型已经是最新的，随时可以投入行动。她花在阅读代码、在脑中拼凑系统结构上的时间更少，而花在思考更高层次抽象与设计上的时间更多。每个人都受益，因为每个人都保持了同步。


## 执行一次优秀的拉取请求
在写下任何一行改变系统的代码之前，先问自己以下问题：

- "这是当前值得做的事情吗？"客户、内部团队成员和其他各方总会有相互竞争的需求。这是让你在深入投入之前理清优先级的好方法。迭代/冲刺规划会议等其他流程也有助于保持方向不偏。
- "团队是否已经认可这个变更是正确的？"如果没有，最好先通过邮件或当面发起一场设计讨论。在改动系统之前人们已就设计达成一致时，你的变更更有可能被接受。
- "我如何把这个变更拆分成易于评审和理解的块？"小变更更容易思考和理解。当团队能够快速理解你的变更时，高质量的讨论才会随之而来。如果你的变更非常庞大，同事的眼睛会变得呆滞，你可能只会收到几条风格上的吹毛求疵。
- "我打算如何测试这个变更以消灭缺陷并确保正确性？"你可能有 QA 部门，但交付高质量可用的软件仍然是开发者自己的职责。易于测试的软件通常耦合更低、被拆分成更小的块、也更容易推理。你需要为所有变更准备测试计划。

我发现提前回答这些问题从长远来看为我省去了许多头疼的事。最不希望发生的事情是：花好几天编码实现一个变更，结果却因根本性的设计缺陷或团队分歧而被拒绝；或者变更被卡住，因为没人能验证其正确性。再说一次，目标是在让其他团队成员同步了解你的变更的前提下修改系统。问自己如何把工作拆分成小块并逐块测试，会在多个方面带来帮助：

- 它降低风险
- 它让变更更容易推理
- 它推动你走向更好的设计

你宁愿用手术刀做许多小而精准的切口，也不愿用砍刀砍出一个巨大的伤口。在大多数增量式开发中我偏好"手术刀驱动"的开发方式，而把砍刀留给删除大段无用代码的时候。


## 发起拉取请求
好了，你已经获得团队对你变更的认可，并实现了你最初想要的设计。那么实际发起拉取请求最有效的方式是什么？你一直在为变更努力工作，你希望团队其他成员关注你的拉取请求并给你快速反馈。如何做到？

还记得我之前说过，代码评审最重要的部分是让团队的集体心理模型保持一致吗？你的其他同事可能正在做与你的工作完全不同的事情，也许在系统的一个完全不同的部分。他们的大脑处于完全不同的上下文中，所以你必须通过提供他们所需的、有帮助的指引来克服这一点。这意味着要写一份组织良好的变更描述：你做了什么变更、为什么这么做，以及其他任何仅靠阅读代码无法获得的相关信息。不要让同事做超出必要的脑力劳动。

我们来看几个拉取请求描述的好坏示例：

反面示例：


```
Title: Fix uninitialized memory bug
Description: 

This is the bug Bob and I talked about earlier. I had
trouble with the compiler but managed to make this work. Let me
know what you guys think.
```
如果你是这个拉取请求的开发者，请停下来，换位到你的代码评审者的角度想一想。标题含糊不清，引出的问题比回答的还多：内存缺陷在哪里？这个变更有多关键？你和 Bob 之前讨论的缺陷是什么？你在编译器上遇到了什么麻烦？描述没有提供关于问题的任何有用上下文，也没有对你的变更给出任何有用的说明。如果这个拉取请求很长，评审者将不得不深入代码、做一番脑力体操来获取上下文，才有机会思考这个变更如何融入系统的整体设计。

下面是一个改进后的示例，它有助于澄清这个变更集：


```
Title: Fix process crash on startup from uninitialized memory [#54633]
Description:

This bug was causing process crashes on boot due to a memory
initialization error in our statistics Counter class. I talked this
over with Bob, and we both agree the crashes are a rare edge case
that don't warrant a hot-fix release. Here's a summary of the
changes:

  - Moved the underlying int variable into the class initializer
    to prevent ununitialized memory in the Counter.
  - Reworked the Counter interface to simplify caller conditional
    logic and prevent further off-by-one counting problems.
  - Added a unit test that exposes the crash

Testing: I've verified the test suite still passes, and verified
manually that the crash doesn't happen locally.
```
这个拉取请求描述有几处改进：标题足够具体，能让评审者快速获得上下文，并吸引他们点开邮件了解更多。评审者知道这是一个进程崩溃（这通常是非常糟糕的事情），而且还有一个缺陷报告编号，如果评审者想进一步了解问题，可以查阅更多细节。新的描述还指明了问题发生的位置，并帮助说明这个修复有多关键。描述中有一个摘要，列出拉取请求中的高层结构变更，这让评审者在看代码之前就能在脑海中形成变更的整体图景。代码评审者不应对自己看到的内容感到意外。这个示例还说明了已执行的测试，这会让评审者相信这些变更经过深思熟虑、经过充分测试、可以合并。把你的评审者设置成"一点即合"——让他们轻松到只需点击"merge"。


## 评审者：给出建设性反馈
评审流程中下一个要考虑的环节是给同伴提供建设性反馈。如果目标是清晰与一致，那么给出高质量的建设性反馈能帮助每个人更好地理解系统，并推动代码变得更好。

避免说这样的话：

- "这个设计烂透了。"为什么烂？怎么改好？这样的表述伤害信心、挫伤自尊。
- "我不喜欢这个变更。"为什么不喜欢？你想要什么样的？不喜欢某样东西没关系，但你应该表达清楚你的想法，并就代码如何改进提供有用的线索。
- "你能重写得更清楚一点吗？"我现在写的有什么问题？我该怎么重写？哪里不清楚？这样的评论本身就不清楚，也没有给出一条简单的改进路径。

相反，应该说这样的话：

- "这段代码如何处理负整数？"这种反馈是具体的，会促使开发者自己思考各种结果。作为评审者，你可能知道这段代码在遇到负整数时会崩溃，但让开发者自己领悟到这一点更好。这样的提问也可能暗示着测试上的缺口，或者需要对范围做进一步说明。
- "这一节让我很困惑，我不明白为什么类 A 要和类 B 通信。"如果开发者没有提供有用的描述，代码结构也不够清晰，这类评论有助于推动设计的清晰度和更整洁的代码。
- "看起来你在这里破坏了一个接口边界。这会对用户产生什么影响？"你指出了你注意到的问题，同时默认他们是有意为之。现在他们可以思考破坏接口边界带来的看不见的后果，要么为其决策提供理由，要么选择改掉它。

总的来说，把反馈以提问的形式表达出来，是推动清晰性和正确性的好方法，同时也能帮助开发者在未来改进他们的设计。这通常也是高质量的创意写作小组互相反馈的方式。在创意写作的场景中，说"我不喜欢这个角色"是有害的，而同样的意见可以被更清楚地重述："在第一章里你的角色温暖而富有同情心，现在却冷漠而冰冷。他对我来说不像一个真实的人。"这样就出现了具体的反馈，可以通过进一步澄清来找出问题所在。

程序员喜欢解决问题、指出毛病，因此他们天生就喜欢发现并指出缺陷。把代码评审当作在同事代码里找问题来证明自己有多聪明的方式，这种诱惑是存在的。别这样做。代码评审是让更多人审视一个变更、找出关键问题的途径，但你的目标应该是以一种鼓励团队成员提升技能的方式来进行评审，同时解决眼前的问题。


## 风格问题
括号位置、变量/函数命名、缩进与空格问题应该被指出，但它们不是优秀代码评审的核心目的（注意我把它们放在代码评审金字塔的顶端）。如果你发现团队把 90% 的时间花在挑剔缩进和变量名上，那你可能是在把大家的时间浪费在大部分可以自动化的事情上。写一份风格指南，在提交时强制检查缩进和空格问题，然后把时间花在更高价值的问题上。我并非要贬低风格一致的重要性。恰恰相反，拥有一致且符合语言习惯的风格是让你的代码库易于阅读和理解的最简单方法之一。尽管如此，如果你把代码评审的全部精力都放在这些简单任务上，请问问自己：你是否在回避更难也更重要的问题——让团队在认知上保持一致，并思考更高层次的设计。
