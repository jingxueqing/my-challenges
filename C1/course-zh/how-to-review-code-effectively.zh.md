作为 GitHub 的资深工程师（staff engineer），代码评审是我日常工作中的重点之一。过去八年里，我评审了超过 7,000 个拉取请求（PR）。为什么这么多？因为代码评审对构建优秀软件至关重要，另一双眼睛往往能发现你自己会错过的问题。

我把代码评审视为我工作中最重要的内容之一。事实上，每当我看到队友有一个拉取请求（PR）等待代码评审时，我更愿意放下手头正在做的分支，转而去评审他们提交的改动。毕竟，他们的拉取请求（PR）已经闯过了持续集成（CI）的重重关卡，并且达到了他们自己判断的"完成"标准，所以它大概率比我正在进行中的工作更接近可发布状态。我宁愿帮他们的代码冲过终点线，也不愿再耗费未知多的时间打磨自己的代码。

我越早给出反馈——"这里可以是 nil 并导致错误"、"这看起来像一个 n+1 查询"、"这里最好有一个方法签名"——反馈就能越快被处理，bug 就能越快被消灭，功能就能越快发布。

我想分享我进行代码评审的方式，希望我们都能发布更好的代码。


## 什么是代码评审？
严格来说，代码评审——通过 GitHub 上的
拉取请求（PR）评审
——允许协作者对拉取请求（PR）中提出的改动发表评论、表示认可，或在拉取请求（PR）合并之前要求进一步修改。

我把拉取请求（PR）看作一段对话的开始。我把它理解为作者在说："我认为这比我们现有的方案更好。"代码评审是塑造产品实现的绝佳机会。作为代码评审者，我的职责是与作者来回讨论，通过提问、质疑假设来改进他们的代码，总体上充当第二双眼睛。


## 打磨你的代码评审流程

### 如何找到需要评审的拉取请求（PR）
我常年泡在
GitHub 通知收件箱
里。它是我浏览器中固定的少数几个标签页之一，因此随手可及。每当我在等 CI、处于任务间隙、刚开启一天的工作，或者有任何空闲时刻，我都喜欢查看收件箱。我评审的大多数拉取请求（PR）都是在那里发现的。GitHub 的团队通常有一个作为大本营的 Slack 频道，那是分享"可评审"拉取请求（PR）的好地方——这也是我发现拉取请求（PR）的另一条主要途径。

使用
GitHub Slack 集成
把 Slack 频道订阅到与我团队相关的新拉取请求（PR）上，效果也很好。为了筛选哪些拉取请求（PR）出现在 Slack 中，我会使用团队专属的标签，然后在 Slack 中使用类似
/github subscribe your/repo pulls +label:"your-team-label"
的 'subscribe' 命令。

我喜欢用类似
is:open archived:false is:pr org:github -is:draft team-review-requested:github/relevant-codeowner-team
这样的查询来搜索可能需要评审的未决拉取请求（PR）。通过这个查询，我可以找到 GitHub 组织内的
open
（打开）、
unarchived
（未归档）、
不是
drafts
（草稿）并且已将
相关 codeowner 团队设为请求评审人
的拉取请求（PR）。我通常会省略
review:required
这个搜索限定符，因为即使队友已经评审过某个拉取请求（PR），我也乐于再评审一次。毕竟，评审代码不仅帮助作者，也帮助我及时了解影响我所负责代码的变更。


### 使用评审人团队来管理通知
你不希望某次代码变更通知到一个过大的团队，以至于团队里的每个人都默认评审该变更不是自己的
责任
。这会导致拉取请求（PR）要么迟迟无人评审，要么过早被合并，因为关键评审人在通知的洪流中错过了它们。这两种情形都会影响产品质量。

如果条件允许，我建议精简你所在的
code owner
团队数量，让通知保持在可管理的范围内。这样，进入你收件箱的拉取请求（PR）就不只是噪音，而是你确实觉得应该评审的内容。大而全的兜底型 code owner 团队可以作为后备选项，但作为自动评审请求的第一线默认设置并不合适。保持你仓库的 CODEOWNERS 文件组织良好，并配以清晰定义的代码边界，以减少通知、帮助评审人避免通知疲劳。

另一种限制基于团队的通知的方法是创建一个"第一响应人"团队，然后使用自动化按排班添加和移除团队成员。这样可以让你的团队专注于日常代码库，而轮值的第一响应人会收到你们团队服务范围内拉取请求（PR）的通知。例如，借助
PagerDuty API
，你可以确定某一天谁是第一响应人。然后使用
Octokit 库
来添加和移除团队成员。


### 用自动化在团队间统一代码评审标准
仓库级别的配置和自动化，例如使用
CODEOWNERS 文件
和
分支保护规则
，有助于在各个团队之间强制执行评审流程标准。而另一些标准，比如拉取请求（PR）中哪些内容值得评论，则必须由我们人类来维护。把团队内的代码评审方式写成文档，确保任何提供代码评审或提交拉取请求（PR）的人都知道：如何让自己的拉取请求（PR）得到评审、评审的预期周转时间，以及使用了哪些自动化来辅助评审。

有些团队使用项目看板来追踪哪些拉取请求（PR）进入了评审环节；我见过这对管理共享 API 的团队很有效——API 是一个经常被团队外部人员修改的区域。另一些团队仅依赖 GitHub 通知，当代码所有权划分得很紧、团队又严格地在拉取请求（PR）到来时及时评审时，这种方式运转良好。

如果你的团队遵循一套独特的流程，自动化可以帮助你与团队外的人沟通预期。例如，如果很多其他团队依赖你们团队的评审，你可以用一个机器人自动在所有请求你们团队评审的拉取请求（PR）下留言，告知作者何时能收到你们的反馈。


## 什么样的代码评审是好评审，什么是差评审？
好的代码评审能增加清晰度，并推动代码从初始状态走向更好的状态。

作为评审人，清晰的沟通是关键。你要明确指出哪些评论只是个人偏好，哪些是批准的阻塞项。给出你建议方案的示例，可以提升代码评审的质量，让你的意思更加清楚。如果你能提供来自与该拉取请求（PR）同一仓库的示例，那就更好了——这通过鼓励实现方式的一致性，进一步支撑你的建议。

相反，糟糕的代码评审缺乏清晰度。例如，不加任何评论的一揽子批准或拒绝，会让拉取请求（PR）作者怀疑这次评审是否认真做过。哪怕只是在批准时重述一下你对拉取请求（PR）作者意图的理解，也能暴露出你们两人的理解是否一致。

一份没有说明建议何时应被实施的代码评审，对作者来说也是一种糟糕的体验。指出既有的、未被改动的代码应当重构，或应当处理某个额外的情况，这没有问题，但重要的是要说明这些是否是批准的前置条件。如果拉取请求（PR）在不上马你的建议的情况下也可以合入，请务必明确说明。保持一个小的差异（diff）、把那些建议作为单独的拉取请求（PR）另行提交，往往更安全。

下面是一条展现具体性、清晰传达建议实现的代码评审评论：

"我看到你的新方法沿用了本文件中的既有风格，接受 [X] 个参数。这么多参数会损害可读性，也暗示这个函数承担了太多职责。你觉得在以后的拉取请求（PR）里重构这个方法和既有方法、减少参数数量怎么样？"

这条评论做得好的地方：

- 提供了具体的细节。
- 引用了具体的代码或问题。
- 针对问题提出了解决方案。
- 给出了依据或解释

与之相对，下面是一些可以写得更好的评审评论示例：

"我不喜欢这个。"
——评审人不喜欢什么？他们脑中是否有一个可以明确说出的替代方案？

可能的改进：

- "这一行做了太多事情，能不能简化一下以提高可读性？"
- "我认为这会因为 n+1 查询产生性能问题。"
- "能不能用 [首选框架] 的方案来解决这个问题，而不是自己写一个自定义实现？"

"这样行不通。"
——为什么行不通？

可能的改进：

- "这样行不通，因为 [X]，参见这个相关的 issue：[issue 链接]。"
- "之前在 [拉取请求（PR）链接] 里尝试过，因为 [X] 而没有成功。"
- "如果你在 [X] 上遇到问题，可以试试 [替代方案]。"

"我觉得这修复了一个 bug。"
——我很乐意看到这个说明，但有没有额外的上下文，比如 issue 链接，能让它更清楚？

可能的改进：

- "我认为这修复了 [issue 链接]。"
- "这是在修复 [issue 链接] 里的那个 bug 吗？"
- "这看起来就是我们之前在 [失败构建链接] 里遇到的 bug。感谢修复！"


## 如何给出好的代码评审

### 提问
我把拉取请求（PR）作者视为对其改动拥有最完整上下文的人。我可以基于我自己的经历指出我看到的问题——比如我在 Ruby on Rails 单体应用、TypeScript 或高流量数据库方面的工作经验——但我信任作者对我问题的回答。我认为他们对细节的理解比我更准确。

我也很喜欢围绕代码中的假设提问。他们处理的数据是什么形态？是否存在不符合该形态的数据？代码能否妥善应对这种情况？代码是否资源密集？性能表现会好吗？作为评审人，我最希望看到的回应是作者提供一个自动化测试来验证这些场景下的行为。第二好的回应是经验数据，比如来自我们数据仓库的一条查询，或一张说明这些场景不成问题的 Datadog 图表。

作为拉取请求（PR）作者，我很乐意收到提问。当有人提问时，这为我创造了空间去解释为什么我对自己的改动有信心，并在必要时引用 issue、查询或图表作为依据。这也让我能与别人分享我的知识和经验。不仅作者能看到我的回应，其他评审人以及未来追踪某个历史决策上下文的读者也能看到。


### 给予肯定
除了提问之外，对拉取请求（PR）中你认同的部分发表评论也是很好的实践。这些评论可以表明你阅读并理解了被修改的内容，或者你验证了代码中的某个假设。举几个例子：

- "看起来这与本模块中其他类使用的模式一致。"
- "感谢为这里添加了测试！"
- "这比之前可读性强多了。"

以我的经验来说，收到这样的评论本身就令人愉快。接收代码评审有时让人身心俱疲。当我要同时应对来自多方的提问和建议时，收到几条不向我索取任何东西、而是支持和肯定我已投入工作的评论，是一种很好的鼓舞。


### 留意偏见与假设
你对评审对象、或对方正在修改的代码区域的偏见，很容易影响你的评审。你习惯了某个人在某个领域工作，或习惯了对方具备某种资历，于是假设他们知道自己在做什么——但
每个人
都会犯错。你用眼睛审视他们的改动，用提问检验他们的假设或验证自己的假设，就能在问题部署之前把它抓住。

我非常推崇编写测试，因为测试能消除一部分偏见。当你编写测试来检查代码是否正常工作时，
你不必听信作者的口头保证
，只需看测试是否通过——当然，前提是你的测试本身写得对。😅

我同样非常推崇初级开发者在代码评审中向资深开发者提问，哪怕他们觉得自己的问题很傻或答案显而易见。如果这个问题对你来说并不显而易见，那就是合理的。它对别人来说也不会显而易见！把问题问出来，给作者留下写下答案的空间，并把这点知识留给后来的人。


### 批准还是不批准
我把自己的评审视为一道可以阻止别人改进我们产品的阻塞闸门，所以我会审慎地保留批准。我常常会有个人偏好，会建议一些我希望作者做出的可选改动，但我不会仅凭这些就扣住批准。如果我对某人的拉取请求（PR）有建议，但该拉取请求（PR）按现状不会破坏生产环境、不会给用户带来负面影响、也不会造成其他问题，我会在附上这些评论的同时予以批准。作者可以选择在合并拉取请求（PR）之前处理我的反馈，也可以在另一个分支中跟进。

评审代码时，请权衡你建议的重要性。为了落实你的建议而推迟发布，值得吗？值得让作者经历看到你的反馈、做出修改、等待 CI、再次评审、部署、最终合并这一整套循环吗？如果缺少某条建议不会让任何人的日子变难过，就让作者自行决定是否以及何时做出该改动。

'Request changes'（请求修改）选项
会阻止拉取请求（PR）被合并，直到评审人回来批准它。我极少使用它，因为它通常显得过于强硬。我相信我的团队知道何时该批准拉取请求（PR），所以队友的批准可以代替我的。同样，我也信任拉取请求（PR）作者会尊重并考虑我的反馈，而不是因为别人批准了、我没有批准就盲目合并。我唯一会选择 'Request changes'（请求修改）选项的情形，基本只有当我认为存在迫在眉睫的安全问题、且担心对方在合并前看不到我的担忧时。


## 如何从代码评审中获得最大收益

### 评审你自己的代码
GitHub 高级软件工程师
Paul Smith
教会我在请别人评审之前先评审自己的拉取请求（PR），我也建议你这样做。先过一遍，在那些不明显的改动上留下行内评论，或者对那些如果出现在别人的拉取请求（PR）里你会追问的改动留下评论。自我评审还有助于判断一个拉取请求（PR）是否过大、是否值得
拆分
。

特别推荐：
如果你在意保持拉取请求（PR）的小体积，可以利用
lerebear/sizeup-action
自动为拉取请求（PR）打上标示其复杂度和规模的标签。


### 欢迎合并后的评审
如果我碰巧在别人有机会评审之前就合并了某个拉取请求（PR），我依然欢迎他们的评审。如果我的拉取请求（PR）破坏了什么或产生了意外后果，在拉取请求（PR）上留下评论就能留下面包屑轨迹，帮助未来的读者追查发生了什么！

如果我收到针对已合并拉取请求（PR）的评审，我会像它在合入前那样处理这些反馈。也许我会用一条评论解释我的视角，也许我会提交额外的拉取请求（PR）来迭代我最初发布的代码，也许我会创建新的 issue 来记录待完成的额外工作。


### 使用草稿拉取请求（PR）
创建新拉取请求（PR）时，你可以选择将其设为草稿。我非常依赖
草稿状态
来表明我是否想要评审。例如，如果某个必需的 CI 构建正在失败，或者我还没写完，我会保持草稿状态。我对别人的拉取请求（PR）也有同样的预期：如果是草稿，我就假定作者还没准备好接受评审。如果它被标记为"可评审"，我就假定距离他们部署该拉取请求（PR）只差足够的批准数了。

草稿状态意味着拉取请求（PR）尚未完成，所以在解决合并冲突或处理评审人反馈时，我会把拉取请求（PR）移回草稿状态。如果我必须修改代码，我会先把拉取请求（PR）标记为草稿，以免给已经评审过的人造成负担。当我把它移回"可评审"状态时，GitHub 会向那些评审人发送通知，让他们可以再看一眼。


### 保持友善
"相比醋，蜂蜜能捕到更多的苍蝇"这句俗语浮现在脑海中。我希望自己的拉取请求（PR）得到评审，所以我喜欢回复拉取请求（PR）上的评论——尤其是当我不同意评审人时。即使我不写回复，我也常常会添加 👍 反应来表示同意，或用
❤
表示感谢。

我希望评审人相信他们的建议不会被遗忘，所以我会通过评论让他们始终知情。如果我认同他们的建议——比如进一步重构既有代码——我可能会这样说，但同时说明为什么不在当前拉取请求（PR）里做这个改动。当我在之后的拉取请求（PR）中处理了他们的反馈时，我会回来附上链接，让评审人知道他们的反馈没有被忽视。

我还会在后续实现了建议改动的拉取请求（PR）中 @ 他们，并附上一句"本拉取请求（PR）落实了 @某某 在 <之前拉取请求（PR）的 URL> 中的反馈"。这既为其他读者提供了上下文，也是对原评审人的一次致意，认可了想法的出处。

当你在后续分支中兑现处理反馈的承诺时，这有助于与评审人建立信任，让他们在批准你未来的拉取请求（PR）时更放心，因为他们知道你不会让事情半途而废。


## 结语
代码评审对产品质量的重要性再怎么强调都不为过，尤其是在 AI 代码生成的时代。在我的职业生涯中，很多次正是凭借这第二双眼睛，才抓住了 bug 或避免了一次事故。代码评审非常值得投入时间——无论是花在日常评审上、在打磨流程上，还是在构建支撑它的自动化上。对开发者来说，现在彻底地评审拉取请求（PR），远比之后处理一个已经发布到生产环境的问题更快、更轻松。

感谢你对代码质量的重视，读完了我的代码评审理念。你最近查看过
你的评审队列
了吗？也许现在正是把这些想法付诸实践的好时机。
