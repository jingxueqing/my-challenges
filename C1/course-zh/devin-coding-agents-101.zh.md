# 编码智能体 101：真正把事情做好的艺术

现在是 2025 年。
编码智能体并非魔法，但它们已经是我们拥有的最接近魔法的东西。
我们注意到，一些工程师——尤其是资深到骨干（staff）级别的工程师——比别人更快地取得了成功。在这里，我们分享一些源自客户和我们自身经验的重要经验。

关于本指南：

## 产品无关
我们讨论的技巧将帮助你在任何编码智能体上取得成功。


## 战术性强
我们提供我们最喜欢的可操作建议。


## 技术性强
虽然编码智能体对许多人都很有价值，但本指南是写给工程师的。

开发者工具一直在快速演进。十年前，是自动补全和智能感知（intellisense），能够建议方法名并执行程序化重构。四年前，是副驾驶（copilot）和 Tab 补全，能够为你写下接下来的几行代码。两年前，是生成式聊天机器人，能够协助你的开发并为你生成完整的文件。今天，是自主智能体，能够在几乎没有人工干预的情况下，从最初的描述一路做到最终的拉取请求（PR）。在过去的两年里，我们通过构建 Devin 专注于实现这一愿景。如今，对自主智能体的关注正达到新的高度，尤其是随着近期类似产品的发布¹。这些智能体可以以多种形态出现，包括 Web 应用、移动应用，以及与 Slack、GitHub、Linear 和 Jira 等流行工具的集成。

[1]
除 Devin 之外，近期发布的产品还包括 OpenAI 的 Codex 和 Google 的 Jules。一些本地智能体（如 Cursor 和 Claude Code）可以在并行工作区中运行，以复制类似的效果。

虽然人类与 AI 助手搭档所能达成的成就超过任何单独的 AI，但自主智能体端到端处理任务的能力带来了全新水平的多任务处理，把每位工程师都变成了工程经理。

适应与这些新 AI 同事高效协作可能需要一些时间。有趣的是，我们观察到资深到骨干级别的工程师往往最快上手并熟练掌握这些工具。最终，这些工具将在工程领域的各个层级变得司空见惯。基于我们的经验和客户反馈，我们希望分享关键见解和经验教训，帮助每个人将这些工具成功融入自己的工作流。

## 提示词基础

以下这些基本准则将帮助你在 2025 年有效地与编码智能体交互。即使别的什么都记不住，你至少应该记住这些。


### 说清楚你希望事情怎么做，而不仅仅是做什么

把智能体当作一个决策能力不太可靠的初级编码搭档来对待。简单的任务可以直接描述，但对于更复杂的任务，请从一开始就清楚地说明你偏好的方案。预先向智能体提供整体架构和逻辑，不仅能提高它成功的几率，还能减少你评审代码的时间，因为你已经熟悉了预定的方法。


#### 示例：

与其说"添加单元测试"，不如指明要测试的功能、识别重要的边界情况，并澄清哪些内容需要 mock（如果有的话）。


### 告诉智能体从哪里开始

想想如果你自己处理这个任务会从哪里入手。即使你不知道具体的文件或函数名，也要提到仓库、相关文档以及涉及的关键组件。清楚地指出这些要素可以最大限度地减少浪费的精力与困惑。


#### 示例：

"请为我们的代码添加对 Google 模型的支持。你应该查看[这里](link)的最新文档，并在 model groups 目录中创建一个新的实现文件。"


### 实践防御性提示词

想象一下把同样的提示词交给一位新实习生。哪些地方可能产生困惑或错误？预判这些点，并主动澄清你的指示以避免歧义。


#### 示例：

"请修复我们搜索模块的 C++ 绑定，使其通过新的单元测试。要小心，每次修改代码后你很可能都需要重新编译绑定，然后再测试。"


### 提供 CI、测试、类型检查和代码检查工具的访问权限

智能体的许多魔力来自它们修复自身错误并根据错误信息进行迭代的能力。通过类型检查器、代码检查工具（linter）和单元测试等工具提供强反馈回路，可以大幅提升它们的表现。考虑用带类型的 Python 替代纯 Python，或用 TypeScript 替代 JavaScript。教会你的智能体如何运行常见的检查和测试，确保它拥有所有必要的包和访问权限。如果智能体可以与浏览器交互，请提供关于如何运行你的前端开发环境的清晰说明。


#### 示例：

我们的团队从基本无类型的 Python SDK 全面转向了带类型的 SDK（这对编码智能体来说也是一个理想的任务）。


### 发挥你的专业能力

当你熟悉自己的代码库时，上面的一切都会变得更容易。即使是简单的任务，也能从你验证逻辑和结果的能力中受益。人类的监督仍然不可或缺——最终，你要为代码的最终正确性负责。即使这些工具变得越来越精密，所有权与验证仍将是人类工程师的关键职责。

## 在工作流中使用智能体

一旦掌握了与智能体对话的基础，就该把这些 AI 助手引入你的日常工作流了。以下是一些让智能体成为你日常一部分的实用方法：


### 立即承接新任务

想象一位队友给你发消息："嘿，我们能快速做个 X 吗？"或者"我们需要调整一下 Y。"与其让它打断你的节奏，不如直接给自主智能体发一条简短提示词，让它去调查或做出更改。这让你能继续专注于手头的主要任务。有了一个有趣的副业项目点子？需要快速做原型、抓取数据或复现研究？交给你的智能体，稍后再回来查看。


#### 示例：

许多团队在讨论缺陷修复或小型功能更新时，直接在 Slack 上 @Devin。


### 随时随地写代码

想象你在通勤或旅途中，一个紧急缺陷突然出现，或者你意识到代码里可能留了个错误。别担心！自主智能体通常支持移动端访问，让你能立即处理这些问题。无论是通过 Slack 的移动应用还是专门的移动应用，许多智能体都让你随时随地解决问题，即使你的 Wi-Fi 不太稳定。


#### 示例：

拥有这种可选择性，让我们自己的团队在坐车和坐飞机时都高效了不少。


### 把杂活交出去

还在为查找老提交而二分调试，或为新功能更新文档而烦恼吗？把这些重复性任务交给你的智能体。你会省下宝贵的时间，专注于更有创造性和影响力的工作。


#### 示例：

在我们的团队中，工程师发布一个变更后，让智能体更新所有相关文档和面向用户的文案，这是很常见的做法。


### 跳过分析瘫痪

还在纠结一次重构是否真的能简化你的代码？在两种架构方案之间难以抉择？让智能体把两种方案都实现出来。有了具体示例可供比较，决策变得直观，而且丢弃某个方案也不会伤害任何人的感情。


#### 示例：

在为文本编辑器在 Lexical 和 Slate 之间做选择时，我们让智能体分别实现了两者。Slate 凭借更好的最终效果胜出。


### 配置预览部署

将你的 持续集成/持续交付（CI/CD） 流水线设置为在每个新 PR 上自动创建预览部署，为你提供即时的可访问 URL。在评审 AI 智能体完成的前端任务时，这尤其方便。

当你的拉取请求的规模和复杂度超过几个文件时，一次性处理它们就变得很困难。然而，掌握如何委派中大型任务（通常为 1-6 小时的工作量）正是自主智能体带来最高投资回报率的地方。你不只是省下几分钟，而是可以夺回数小时的生产力。较小的任务或许毫不费力，但把智能体的能力发挥到处理更大的任务，才能带来最大的回报。


### 自动化你的初稿

对于大型任务，使用自主智能体创建 PR 的初稿可以启动进展并大幅减少你的工作量。成功的关键在于预先清楚地沟通你期望的方案。把自己想象成指导初级开发者的架构师。清晰、详细的指示有助于避免把不必要的时间浪费在纠正智能体代码中根本性的误解上。

| 领域 | 起草 | 打磨 |
|---|---|---|
| 新闻业 | 记者收集初步信息，撰写文章初稿 | 编辑审阅稿件、核实事实、润色并定稿发表。 |
| 餐厅 | 帮厨准备食材并制作初步的菜品。 | 副主厨添加调料并调整菜品口味，然后才送到食客面前。 |
| 编码 | 自主智能体根据初始计划开始任务并创建初稿方案 | 人类开发者评审初稿 PR，给出反馈，并在合并前进行人工打磨 |

🛑 记住，大型任务还不能完全撒手不管（至少目前如此）。对于更具挑战性的任务，要预期多轮反馈循环，并为打磨工作预留一些人工修改。现实的目标是节省大约 80% 的时间，而不是完全自动化；你的专业能力在验证和最终质量保证方面仍然至关重要。


### 共同编写 PRD

对于复杂或定义模糊的任务，与你的自主智能体协作制定一份详细的计划会非常有效。如果你一开始并不了解每个细节或需求，那完全没关系。可以先让智能体探索一些发现性问题，例如"我们的身份验证系统是如何工作的？"或"哪些服务可能受到影响？"你还可以让智能体为你识别具体的相关代码目标，以便你尽早确认。

某些智能体（例如 Devin 和 Claude Code）提供专门的规划模式，专注于阅读和探索现有代码，而不是立即修改它。如果你希望在委派任务之前做更深入的准备，像 deepwiki.com 和 Devin Search 这样专门的代码库搜索工具可以快速提供对代码库的洞察，帮助你简化流程。


### 设置检查点

对于多部分任务，尤其是涉及多个代码库的任务，要在过程中建立清晰的检查点：

计划 → 实现分块 → 测试 → 修复 → 检查点评审 → 下一个分块

明确要求在每个重要阶段之后暂停，尤其是对于跨多个层级（例如数据库、后端、前端）构建的复杂功能。利用这些检查点确保实现符合你的预期、澄清疑问（例如"解释一下身份验证流程并确认其安全性"），并尽早纠偏以避免问题级联扩散。


#### 示例：

"我希望你实现这个跨越我们数据库、后端和多个前端界面的功能。请先规划出需要的数据库模式（schema）变更，完成后告诉我，以便我执行迁移。" -> "现在请实现后端变更，并添加测试确保 XYZ 正常工作。完成后告诉我。" -> "现在在我们的 Web 和移动两个界面中实现调用新后端端点的变更。"


### 教会它验证自己的工作

在给出反馈时，不要只是简单指出问题（"这个函数不好使"）。清楚地阐述你的测试过程，使智能体能够独立验证未来的任务。对于你会经常重复的测试模式，把它们整合到智能体的永久知识库中（参见"添加到智能体的知识库"）。


#### 示例：

在 Devin 中，我们会主动提示用户将关键的测试流程保存到智能体的持续记忆中，从而简化未来的交互。


### 提高 AI 热点区域的测试覆盖率

目前，智能体尚不能通过交互式测试彻底覆盖所有场景。在经常被 AI 修改的区域增强测试覆盖率，可以让你对智能体的输出更有信心。扎实的测试意味着那些看起来正确的代码可以放心合并，无需担忧。


#### 示例：

在放心让我们的 AI 把实现从 Python 翻译为 C 之前，我们的团队先强化了代码库中一个关键区域的单元测试。

## 自动化工作流

智能体对传入事件的响应速度远快于人类，而且它们比人类同事更愿意做枯燥、重复的工作。


### 为你最重复的工作创建快捷方式

工程团队经常遇到重复性的例行任务。它们是用智能体实现自动化的绝佳候选。常见的例子包括：

- 移除功能开关（feature flag）
- 升级依赖
- 为新功能 PR 修复和添加测试

为了高效地进行这样的设置，通常由一位有经验的工程师创建一个健壮、可复用的提示词模板²，可以在这些场景下反复运行。

[2]
在 Devin 中，这些被称为 playbook。


#### 示例：

我们的一位客户在每次开发新功能时，都会自动触发三个专门编写单元测试的智能体。


### 智能代码评审与规则执行

虽然已经有专门的快速代码评审工具³，但自主智能体可以是一个提供更精准洞察的有趣选择，尤其是当它们已经为你的仓库的功能建立了索引时。

[3]
例如 Greptile 和 CodeRabbit。


#### 示例：

在 Cognition，我们喜欢维护一份工程师最常犯错误的清单，并把它提交到代码库中。然后，我们不再编写传统的 lint 规则来捕获这些错误（这通常做不到），而是让一个智能体在每个新 PR 上运行，检查这些错误。


### 接入事件和告警

你还可以设置自主智能体，使其在响应特定事件时自动触发。例如，Devin 提供了易用的 API，其他智能体可以通过 CLI 命令集成到自定义工作流中。这些配置与 MCP 结合使用来摄取第三方错误日志时效果尤佳。

⚠️ 在对生产服务中的问题进行分类处理时，AI 的调试能力并没有那么强。与其让 AI 端到端地修复随时出现的缺陷，不如让 AI 只标记出最可疑的错误、变更等，这往往更实用。

## 自定义与提升性能

### 环境配置

没有什么比不完整或不匹配的环境更能拖慢智能体的速度了。为了让一切顺畅运行，请让智能体的配置与团队完全一致。这包括语言版本、包依赖和自动化检查。例如，pre-commit 应安装在智能体的环境中，环境配置（密钥、语言版本、虚拟环境、浏览器登录）应通过 .envrc 等工具或自定义的 .bashrc 配置自动加载。

我们为智能体的浏览器设置了预认证登录，省去了手动认证的麻烦，让测试容易得多。


### 构建自定义 CLI 工具和 MCP

MCP 随处可用，可以快速搭建并试验将你的智能体连接到外部工具⁴。但很多人忽视了为智能体设置简单的 CLI 脚本。举一个简单的例子，你可以给智能体一个脚本，根据任务单 ID 拉取 Linear 任务单的信息。你可能还想给智能体一个工具来可靠地执行工作流中常见的部分，例如重启本地开发环境的脚本。

[4]
在 Devin 中，MCP 仍处于测试阶段，我们正在摸索支持它们的最佳方式。请联系我们获取访问权限！


#### 示例：

我们有一位客户，通过创建一个只显示测试套件中第一个失败测试的 CLI 工具，取得了很大成功。这个 CLI 引导智能体只专注于该测试并提供详细的错误信息，使智能体在长任务上拥有更高的成功率和更快的完成速度。


### 添加到智能体的知识库

如果你的智能体犯了一些常见错误，这正是把你的反馈固化到智能体知识库的好时机。在 Devin 中，有一个专门的知识管理系统。许多产品都提供 .rules 文件或 .md 文件，供智能体永久摄取。不要只告诉它你正在使用的框架的准则，还要告诉它项目的整体架构。告诉它不同类型的任务通常采用什么类型的测试、如何运行重要的命令，以及你推荐使用哪些工具。

## 自主智能体的局限性

### 调试能力有限

缺陷报告可能看起来出奇地简单。但许多缺陷不仅需要访问数据库和日志，还需要超出当今大多数 AI 智能体水平的调试能力。如果使用 AI 辅助调试，我们建议让它列出可能的原因清单，而不是试图自己调试并修复一切。然后，人类可以根据自己的经验判断哪个才是真正的根本原因。不过一旦原因已知，智能体在实现修复方面仍然相当有帮助。


### 精细视觉推理能力差

总体而言，当今的模型在匹配设计截图或 Figma 模型所需的细节层面上的视觉推理能力并不出色。它们在可以用代码层面描述的视觉内容上最为可靠（例如，把 Figma 生成的代码给它）。如果你想让它匹配你的视觉风格，你应该使用带有可复用组件的优秀设计系统。


### 知识截止

每当你要使用一个新库时，都应该明确地让它参考最新文档。否则，由于预训练基座模型的知识截止，大多数智能体会沿用这些库的旧模式。一个好的智能体在你指引文档后可以克服这一点，但你必须对此保持警觉（记住，智能体甚至不知道这些库有新版本）。

## 管理时间并减少损失

并非你每次使用智能体都能取得成功。在 2025 年，这些智能体的结果存在实实在在的方差。这项工作的一部分，就是学会如何使用智能体，以最大化碰到成功结果的几率，同时最小化浪费的时间和 Token。


### 愿意尽早止损

智能体新手的一个常见错误是执意让某次交互取得成功，即使智能体的工作已经跑偏。如果你发现自己有"它不听我的指令"或"这东西在原地打转"的想法，你应该可以放心地终止那次对话或手动接管。发更多消息，更多情况下说明的是你的任务本身的固有复杂度高于智能体的能力，而不是某个可以纠正的简单错误。


### 让你的实验多样化

如果你刚开始与智能体协作，我们建议你在一开始分散下注。尝试一系列不同的提示词和想法。在智能体天然表现好的任务类型上加倍投入——在它们表现不好的任务上及时止损。不必强求你的智能体每次都成功。


### 没有进展时就重新开始

与人类相比，重新开始往往是与智能体协作时更正确的答案。如果你给了一个智能体任务，而它难以处理反馈或纠正方向，那么用一个新智能体、把所有指示从一开始就一次性给足地重新开始，往往能更快走向成功。智能体挽救一个已经搞砸的环境的能力，远不如它从零开始生成新鲜代码的能力。

## 安全与权限

### 为你的智能体创建账号

一个一次性邮箱有助于安全地测试网站。如果智能体需要访问云资源，请为它创建自定义的 IAM 角色。


### 给它一个开发/预发布环境

理想情况下，智能体使用的测试配置与团队中的工程师相同。我们建议完全避免让它访问生产服务。使用远程智能体时，你可以在智能体的远程机器上运行完全隔离的测试环境。


### 只读 API 密钥

在可能的情况下，给它只读权限。我们发现，任何与外部服务交互的脚本仍由人类手动运行会更有保障。
