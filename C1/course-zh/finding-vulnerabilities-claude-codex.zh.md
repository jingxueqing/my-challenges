TL;DR（要点速览）：
我们评估了 AI 编码智能体在真实代码中发现漏洞的有效性。

- 方法：我们让 Anthropic 的 Claude Code（v1.0.32，Sonnet 4）和 OpenAI Codex（v0.2.0，o4-mini）在 11 个流行且大型的开源 Python Web 应用中查找漏洞。两者合计产出了 400 多条安全发现，由我们的安全研究团队逐一评审。
- AI 编码智能体能发现真实漏洞：Claude Code 找到了 46 个漏洞（真阳性率 TPR 为 14%，误报率 FPR 为 86%），Codex 报告了 21 个漏洞（TPR 18%，FPR 82%）。其中约 20 个是高危漏洞。
- AI 能把握上下文，却在数据流上卡壳：Claude Code 最擅长发现不安全的直接对象引用（IDOR）类缺陷，真阳性率（TPR）达 22%（59 条报告中有 13 条正确），但它在跨多个文件和函数执行污点追踪时表现挣扎——SQL 注入的 TPR 仅为 5%（2/38），XSS 为 16%（12/74）。OpenAI Codex 几乎无法报告任何正确的 IDOR（TPR 0%，0/5），SQL 注入（0%，0/5）和 XSS（0%，0/28）表现也很差，但令人意外的是，它报告的路径遍历问题正确数比 Claude Code 更多，TPR 达 47%（8/17）。
- 非确定性是真正的难题：在完全相同的代码库上多次运行完全相同的提示词，往往会得到截然不同的结果。在一个应用上，三次相同的运行分别产出了 3 条、6 条和 11 条不同的发现。

核心要点
：

- 配有相对简单的安全导向提示词的 AI 编码智能体，已经能够在真实应用中发现真实的漏洞。
- 但是：根据漏洞类别的不同，结果可能相当嘈杂（误报率很高），尤其是在传统的注入式漏洞类别上，如 SQL 注入、XSS 和 SSRF。
- 详细的评估和基准测试是理解某种方法在挖掘漏洞方面究竟有多有效的关键（这一直都是真理，但在大语言模型这类非确定性工具出现的今天更是如此），也是判断你的改进方向是否正确的依据。
- 这是我们的"利用和增强 AI 挖掘漏洞"系列文章的第一篇！

本文将涵盖：

- 常规静态应用安全测试（SAST）基准的问题，以及它如何影响 AI SAST 评估
- 关于基于 AI 的漏洞挖掘的一些开放性研究问题

## 关于基于 AI 的漏洞挖掘的开放研究问题
为引导我们的调查，我们把"大语言模型擅长发现缺陷吗？"这个宽泛的问题拆解为更具体、可度量的子问题。

- 基于大语言模型的漏洞挖掘，其误报率和漏报率是多少？它是否随编程语言、框架、代码库规模或漏洞类别而变化？对代码书写方式的敏感度如何？
- 误报和漏报的常见原因是什么？
- 分析的确定性如何？每次运行都能得到相同的结果吗？

针对注入类漏洞，我们特别想知道：

- 大语言模型在追踪用户输入从源（source，例如用户提供的值）到汇（sink，例如消费原始 SQL 查询的方法）之间的能力如何？
- 它能跨函数、跨文件追踪数据吗？
- 它能对净化（sanitization）函数和其他安全控制进行推理吗？
- 它能对来自第三方开源依赖的函数进行推理吗？


## 常规 SAST 基准的问题：缺乏真实性
在深入我们的发现之前，先谈谈我们如何衡量 AI 的表现。目前许多研究/主张依赖的基准虽然有价值，但并不能完全捕捉真实世界代码的复杂性。

- 带已知漏洞的应用：这些基准只使用带有已知漏洞的开源应用；得益于 Kinnaird McQuade，很多应用都可以在 vulnerable-apps 中找到。如果你读过这篇博客，可能会认出一些名字：WebGoat、JuiceShop、OWASP Benchmark 等。但这里有一个问题：当前的大语言模型很可能已经摄入了这些仓库的代码，以及互联网上大量公开的分析文章，从而拥有了先验知识，扭曲了结果。这些应用的代码通常不够真实——大量注释、注解和变量名在暗示或直接描述代码中漏洞的位置或如何利用它们。有时，工具的运行结果甚至被提交进了仓库。以 juiceshop 的 javaspringvulny 的 SearchService.java 为例，挑战名本身就是文件名的一部分……
- XBOW 提供了面向自动化渗透测试工具的基准，但并不适配静态分析：代码往往过于刻意和简单化，不能代表真实应用。ZeroPath 在清洗（sanitize）这些数据方面做得不错，但只清洗了一部分。此外，每个测试用例都是微型应用，专为刺激某一特定攻击场景而设计。如果我们聚焦 Python 基准，XBOW 有 45 个；45 个不同的小型应用，平均代码量不到 98 行、3 个 Python 文件。这太小了，无法捕捉在整个代码库或众多函数中进行搜索和推理的复杂性。
- CVE 记忆偏差：由于大语言模型是在来自互联网的海量公开数据上训练的，其中包括 CVE 被发现和修复的那些代码库本身。这造成了根本性的数据污染问题。AI 可能并非通过新颖的分析检测到漏洞，而只是识别出了它在训练期间记忆的模式。

最近，学术界设计了一些基准，例如
CyberGym
、
Eyeballvul
或
SecVulEval
。这些基准显示出巨大的进步，更接近真实世界的例子，但它们要么缺乏对现代 Web 应用的关注，要么把漏洞从更广泛的应用上下文中孤立出来。

- EyeballVul：Timothée Chauvin 推出的较新基准，从开源项目中提取经过人工审核的真实漏洞，并以最小化、可复现的测试用例形式呈现。虽然基于真实代码，它仍然把漏洞从更广泛的应用上下文中孤立出来，使搜索问题变得更容易。
- SecVulEval 和 CyberGym：这些套件旨在评估 C 或 C++ 中的漏洞。虽然在各自领域有价值，但它们对 C 和 C++ 的关注意味着这些数据不适用于主导现代云原生开发的 Python/JavaScript 及其他以 Web 为中心的语言。

虽然以上每种方法都有用、也应在适当时候使用，但它们不一定反映现代软件开发的现实。真实世界的应用不是干净、孤立的函数。它们是由依赖、框架和业务逻辑构成的复杂网络。

我们的方法有所不同。我们在
11 个大型、基于 Python、持续活跃维护的开源项目上测试，这些项目使用常见的 Web 框架（Django、Flask、FastAPI）编写
。我们的方法是对前述方法的补充，而且我们相信它是独一无二的，原因在于：a) 它力求代表真实世界中 AI 驱动的漏洞挖掘（相对于小型、孤立的合成示例）；b) 它没有被模型训练数据污染；c) 它代表了大多数开发者和公司实际在构建的应用类型——使用现代语言和框架的 Web 应用。

### 我们的发现
- Claude Code 和 Codex 今天都已可用：它们能发现真实的安全漏洞，但非常嘈杂。总体噪声仍然很高，但它们确实在这些流行的开源 Python Web 应用中发现了真实的安全漏洞。总体而言，Claude Code 找到了 46 个漏洞（TPR 14%，FPR 86%），Codex 报告了 21 个漏洞（TPR 18%，FPR 82%）。
- 许多 IDOR 缺陷初看是正确的，且 Claude Code 给出了可信的修复建议：大语言模型不仅能发现这些缺陷，还能提出可信的修复方案，例如参照代码库中已有的模式注入新的权限检查。IDOR 问题可能难以分诊，我们不得不对大多数问题进行实际测试才能确认，这使得真阳性率明显降低。
- Claude Code 能否作为优秀的"护栏"工具？许多发现在技术上虽然是误报，但仍是不错的"护栏"建议，或看起来像护栏建议。例如，模型经常会建议对一个本来已经安全的 SQL 查询进行参数化。虽然不是漏洞，但这加强了代码。我们仍将其计为误报，但严重程度低于其他误报。然而，这些代码加固建议并非总能被信任。我们发现若干案例，尤其是在客户端 JavaScript 代码中，AI 试图修复它认为与 DOM 操作相关的问题，但实际上破坏了代码（在我们观察到的案例中是 HTML 被双重转义），尽管那里本来并不存在安全问题。
- XSS 和 SQL 注入——难以把各组件拼起来：模型很难追踪数据从服务端框架到客户端组件（XSS 的常见模式）的流转，也难以穿透复杂的应用层级。它常常被静态定义的数据搞混，或未能识别出服务端的净化处理。
- 重复提示词有助于获得更多结果：大语言模型的概率性本质意味着，用略微不同的方式提出同一问题可能带来新的发现，这凸显了分析的不一致性。在同一代码库上多次重复同一提示词会给我们不同的答案，但最终还是会绕回相同的发现。
- OpenAI Codex 有时无法报告有效的 SARIF。在我们预期的 66 份报告中，有 9 份不是有效的 SARIF。我们把这些文件中报告的所有发现都计入了，但它们确实不是有效的 SARIF 或 JSON。Claude Code 在我们尝试的所有案例中都没有出现这个问题。


## 同样的代码、同样的 AI，每次发现不同的缺陷：AI 编码智能体的非确定性问题
为了探究非确定性在实践中如何表现，我们选取了其中三个应用，用相同的提示词多次运行，针对同一种安全问题：IDOR。一个模式浮现出来：
每次运行测试，AI 的发现都不一样
。

在漏洞检测的场景下，这是一个重大问题。首先，作为安全工程师，理想情况下我们希望得到比"希望这次模型搜得够彻底"更强的保证，确保代码中重要的漏洞类别都已被扫描。

其次，间歇性地检测到漏洞会给你的安全工具或漏洞管理系统带来不一致和噪声。例如，如果你使用的是 SAST 平台、ASPM 或内部自建的系统，这些系统通常假设：当先前检测到的漏洞不再出现时，它已被修复。但在大语言模型驱动的检测中未必如此——单次扫描可能漏掉它，于是后续扫描再次发现同一问题时会创建一条"新"发现，导致重复的 JIRA 工单和开发者的沮丧。

以下是我们观察到的一些具体例子：

- PY-APP-007：第一次运行中，AI 发现了一个"缺失的搜索授权"漏洞，而另外两次运行没有发现它。第二次运行标记了仅在该次运行中出现的问题。第三次运行又发现了它自己独有的一组漏洞。
- PY-APP-006：情况类似：第一次运行在用户 API 中挖出一个漏洞，而后续运行聚焦在代码库的不同部分，例如事件摘要和笔记模块。
- PY-APP-002：这里的波动也许最为明显。发现的漏洞数量从第一次运行的 3 个跳到第二次的 6 个，再到 11 个。每次运行呈现的发现只有部分重叠。

那么，这背后的原因是什么？我们认为关键因素是所谓的
上下文腐化（context rot）
和
压缩（compaction）
。当 AI 智能体被要求分析整个代码库时，它要处理海量信息：上下文腐化导致它无法从自身上下文中准确检索。为了管理这一点，大语言模型使用一种有损压缩（有时称为 compaction），这意味着一些更细粒度的推理细节——比如函数名、路径等——可能在摘要过程中丢失。

可以把它想象成试图总结一部长而复杂的小说。你会抓住主要情节，但必然会漏掉一些微妙之处和细微差别。同样，AI 可能会忘记某个特定的架构模式或某条微妙的数据流，导致它在某次运行中漏掉一个漏洞，而在另一次运行中却发现它。我们在 PY-APP-006 中看到了一个明显的例子：AI 提出的一份修复方案不完整，因为它没有复用一个已有的用户授权基类——这是一段关键的上下文，显然在那次特定的运行中丢失了。

这种非确定性对我们对待 AI 原生 SAST 的方式有重大影响。一方面，AI 每次都以不同方式"思考"的能力，意味着它可以探索更广泛的潜在攻击向量，就像一支视角多元的人类渗透测试团队。另一方面，它引入了一种不确定性水平，可能导致混乱或错误行为。

- 覆盖不完整：单次运行可能给人虚假的安全感，因为它可能漏掉后续运行才能发现的关键漏洞。
- 缺乏可重复性：无法复现结果，使人难以验证 AI 的发现，也难以以一致、可重复的方式信任其输出。
- 成本和时间增加：为了获得更完整的图景而需要运行多次审计，会显著增加所需的时间和计算资源。注意：对于传统软件，一旦你写好它，基本上可以"免费"地再次运行（不算硬件、电力等成本）。但重度依赖大语言模型的工具并非如此——在本案例中，读取一个代码库并对它进行推理，每次扫描可能产生数十到数百美元的 Token 成本。对于今天的模型，这个成本可能随时间下降，但更新的模型可能更贵。


## Claude Code 新的 /security-review 命令效果如何？
Anthropic 为 Claude Code 发布了一个
新命令，叫做
/security-review
。它被设计为在拉取请求（PR）上运行，检查变更的文件并提出问题以识别具体的安全问题。
你可以在这里找到它的提示词
。

在整个代码库上运行该命令时，我们发现其识别出的安全问题相当有限。很多时候，它无法找到我们让 Claude Code 一次只搜索一种特定安全问题时能够发现的问题。

我们在 PY-APP-003、PY-APP-002 和 PY-APP-008 上运行了该命令，它在所有这三个应用上总共只发现了一个 XSS，这与我们在整体实验中得到的结果大相径庭。


## 回答我们的问题
让我们根据所学重新审视最初的研究问题。

- 误报/漏报率是多少？对于在真实代码上直接运行的 AI，误报率非常高：最好的情况是 Codex 在路径遍历上 53% 的误报率或 Claude Code 在 IDOR 上 78%，最坏的情况是 Claude Code 在 SQL 注入上 95%，以及 Codex 在 SQL 注入或 IDOR 上 100%。不同应用之间的表现差异也很剧烈：从 PY-APP-002（Claude Code）上 100%（10/10）的真实 IDOR，到 PY-APP-007 上 0%（0/7）。在所有应用和所有报告的问题中，Claude Code 找到了 46 个漏洞（TPR 14%，FPR 86%），Codex 报告了 21 个漏洞（TPR 18%，FPR 82%）。由于我们使用的是真实应用，本实验无法准确测量漏报。我们将在即将发布的博客文章中介绍测量漏报率的技术！
- 它为什么会失败？我们观察到的主要弱点是缺乏对代码执行流程的深度语义理解，这在注入类问题上尤为明显。模型在跨过程污点流和隐式流上表现挣扎，而这恰恰是传统 SAST 引擎通常擅长的事情。部分局限也来自上下文压缩和上下文腐化。我们将继续更深入地探索这些局限，并探索缓解它们的解决方案。
- 脚手架和智能体工作流有多重要？它们不仅重要，而且正在变得不可或缺。AI 在安全评审中的未来不是单一、庞大的模型，而是一个智能体系统（包括像我们案例中的编码智能体），它们能使用工具、对证据进行推理并协作以发现和验证漏洞。虽然我们（目前）还没有关于"使用能访问 Claude Code 的智能体"与"更典型的上下文工程（即构建脚手架来提供所有相关代码）配合推理模型"之间差异数据，但我们观察到，智能体系统在走完复杂流程并在报告安全问题的途中做出有依据的决策方面，能力差异巨大。话虽如此，一个反例是 Sean Heelan 通过足够的上下文工程，让一个推理模型报告出了漏洞（8% 的时间成功率）。我们强烈建议你阅读他的博客文章。
- 那么成本呢？遗憾的是，我们未能在 Claude Code 和 Codex 之间统一追踪成本。Claude Code 的总成本是 114 美元，覆盖了所有这些漏洞和所有这些应用（不包括非确定性测试和 /security-review 命令的运行）。


## 数据集：即将发布
我们今天不会发布数据集，也不会公布所分析的开源应用名称，因为我们正处于负责任披露的过程中，正在联系应用开发者，让所有安全问题得到修复和验证。一旦完成，我们才会放心发布这些数据。


## 结论
大语言模型不是明天就会取代人类安全工程师的银弹，事实上，它们在端到端发现高危注入式漏洞方面相当薄弱。然而，它们是一个非常强大的工具。我们的研究表明，通过理解它们的优势（上下文推理）和弱点（代码的深度语义），并围绕它们构建结合先进静态分析引擎的复杂智能体系统，我们可以创造出比以往任何工具都强大得多的新一代安全工具。
