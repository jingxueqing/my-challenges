模型上下文协议（MCP）可以让大语言模型智能体使用可能多达数百个工具来解决现实世界的任务。但我们如何让这些工具发挥最大效能？

在这篇文章中，我们介绍了我们在各种智能体 AI 系统中提升性能的最有效技术¹。

我们首先介绍如何：

- 构建并测试你的工具原型
- 使用智能体创建并运行全面的工具评估
- 与 Claude Code 等智能体协作，自动提升你的工具性能

最后，我们总结了在这一过程中总结出的编写高质量工具的关键原则：

- 选择正确的工具去实现（以及不该实现哪些工具）
- 通过命名空间划分工具，在功能上定义清晰的边界
- 让工具向智能体返回有意义上下文
- 针对 Token 效率优化工具响应
- 对工具描述和规格说明进行提示词工程

构建一套评估体系可以让你系统地衡量工具的性能。你可以使用 Claude Code，依据这套评估自动优化你的工具。

## 什么是工具？

在计算领域，确定性系统在给定相同输入时每次都产生相同的输出，而非确定性系统——例如智能体——即使起始条件相同，也可能产生不同的响应。

当我们传统地编写软件时，我们是在确定性系统之间建立契约。例如，像 getWeather("NYC") 这样的函数调用，每次被调用时都会以完全相同的方式获取纽约市的天气。

工具是一种新型的软件，它体现的是确定性系统与非确定性智能体之间的契约。当用户问"今天我该带伞吗？"时，智能体可能会调用天气工具、根据通用知识回答，甚至先提出一个关于地点的澄清性问题。有时，智能体也可能产生幻觉，甚至无法理解如何使用某个工具。

这意味着我们在为智能体编写软件时需要从根本上重新思考我们的方法：我们不应像为其他开发者或系统编写函数和 API 那样编写工具和 MCP 服务器，而需要为智能体来设计它们。

我们的目标是扩大智能体能够有效解决各类任务的覆盖面，让它们通过使用工具来推行多种成功的策略。幸运的是，根据我们的经验，对智能体最"符合人体工学"的工具，对人类来说也往往出奇地容易理解。


## 如何编写工具

在本节中，我们将介绍如何与智能体协作，编写并改进你提供给它们的工具。首先搭建一个快速的工具原型并在本地测试。接着，运行一次全面的评估来衡量后续的改动。与智能体协同工作，你可以不断重复"评估—改进"的过程，直到你的智能体在现实世界的任务上取得出色表现。


### 构建原型

如果自己不动手，很难预测哪些工具对智能体好用、哪些不好用。先搭建一个快速的工具原型。如果你正在使用 Claude Code 编写工具（甚至可能一步到位），为 Claude 提供你的工具所依赖的软件库、API 或 SDK 的文档（包括可能的 MCP SDK）会很有帮助。对大语言模型友好的文档通常可以在官方文档站点的扁平化 llms.txt 文件中找到（例如我们的 API 文档）。

将你的工具包装在本地 MCP 服务器或桌面扩展（DXT）中，你就可以在 Claude Code 或 Claude Desktop 应用中连接并测试你的工具。

要将本地 MCP 服务器连接到 Claude Code，请运行 claude mcp add <name> <command> [args...]。

要将本地 MCP 服务器或 DXT 连接到 Claude Desktop 应用，请分别前往 Settings > Developer 或 Settings > Extensions。

工具也可以直接传入 Anthropic API 调用中进行程序化测试。

亲自测试这些工具，以发现任何粗糙之处。收集用户的反馈，围绕你期望工具支持的使用场景和提示词建立直觉。


### 运行评估

接下来，你需要通过运行评估来衡量 Claude 使用你的工具的效果。首先基于真实世界的使用场景生成大量评估任务。我们建议与一个智能体协作，帮助分析结果并确定如何改进工具。完整流程可参见我们的工具评估手册。

生成评估任务

有了早期原型，Claude Code 可以快速探索你的工具并创建数十组提示词-响应对。提示词应源于真实世界的使用场景，并基于真实的数据源和服务（例如内部知识库和微服务）。我们建议避免过于简单或肤浅的"沙箱"环境，它们无法以足够的复杂度对你的工具进行压力测试。强的评估任务可能需要多次工具调用——甚至可能多达数十次。

以下是一些强任务的示例：

- 安排下周与 Jane 的会议，讨论我们最新的 Acme Corp 项目。附上我们上一次项目规划会议的笔记，并预订一间会议室。
- 客户 ID 9182 报告说他们的一次购买尝试被扣款了三次。找出所有相关的日志条目，并判断是否还有其他客户受到了同一问题的影响。
- 客户 Sarah Chen 刚刚提交了一个取消请求。准备一个挽留方案。确定：(1) 他们离开的原因，(2) 什么样的挽留方案最有吸引力，以及 (3) 在提出方案之前我们应注意哪些风险因素。

以下是一些较弱的任务：

- 安排下周与 jane@acme.corp 的会议。
- 在支付日志中搜索 purchase_complete 和 customer_id=9182。
- 查找客户 ID 45892 的取消请求。

每条评估提示词都应配有一个可验证的响应或结果。你的验证器可以简单到只做基准答案与采样响应之间的精确字符串比较，也可以先进到让 Claude 来评判响应。避免使用过于严格的验证器，它们会因为格式、标点或有效的其他措辞等虚假差异而拒绝正确的响应。

对于每一组提示词-响应对，你还可以选择指定你期望智能体在解决任务时调用的工具，以衡量智能体在评估过程中是否成功理解了每个工具的用途。但是，由于正确解决任务可能存在多条有效路径，请尽量避免过度指定或对特定策略过拟合。

运行评估

我们建议使用直接的大语言模型 API 调用，以程序化方式运行你的评估。使用简单的智能体循环（while 循环包裹交替进行的大语言模型 API 调用和工具调用）：每个评估任务一个循环。每个评估智能体应被给予单条任务提示词和你的工具。

在评估智能体的系统提示词中，我们建议指示智能体不仅输出结构化的响应块（用于验证），还要输出推理和反馈块。指示智能体在工具调用和响应块之前输出这些内容，可以通过触发思维链（CoT）行为来提升大语言模型的有效智能水平。

如果你使用 Claude 运行评估，你可以开启交错思考（interleaved thinking），"开箱即用"地获得类似功能。这将帮助你探究智能体为什么调用（或不调用）某些工具，并突出工具描述和规格说明中具体的改进方向。

除了总体准确率之外，我们建议收集其他指标，例如单次工具调用和任务的总运行时间、工具调用的总次数、Token 总消耗量以及工具错误数。跟踪工具调用可以帮助揭示智能体常见的操作流程，并为工具合并提供机会。

分析结果

智能体是你的得力伙伴，可以发现各种问题并提供反馈——从相互矛盾的工具描述，到低效的工具实现，再到令人困惑的工具模式。但请记住，智能体在反馈和响应中省略的内容，往往比它们写出来的内容更重要。大语言模型并不总是说出它们真正的意思。

观察你的智能体在哪里卡壳或困惑。通读评估智能体的推理和反馈（即 CoT），找出粗糙之处。查看原始记录（包括工具调用和工具响应），捕捉智能体 CoT 中未明确描述的行为。要读懂字里行间的含义；记住，你的评估智能体并不一定知道正确答案和策略。

分析你的工具调用指标。大量冗余的工具调用可能表明需要调整分页或 Token 限制参数；大量因无效参数导致的工具错误可能表明工具需要更清晰的描述或更好的示例。当我们发布 Claude 的网页搜索工具时，我们发现 Claude 会不必要地在工具的 query 参数后附上 2025，这使搜索结果产生偏差并降低了性能（我们通过改进工具描述把 Claude 引向了正确的方向）。


### 与智能体协作

你甚至可以让智能体为你分析结果并改进工具。只需将评估智能体的记录拼接起来，粘贴到 Claude Code 中。Claude 是分析记录和一次性重构大量工具的专家——例如，确保在做出新改动时，工具实现和描述仍保持自洽。

事实上，这篇文章中的大部分建议都来自我们使用 Claude Code 反复优化内部工具实现的过程。我们的评估建立在我们的内部工作区之上，模拟了我们内部工作流的复杂度，包括真实的项目、文档和消息。

我们依靠留出测试集来确保我们没有对"训练"评估过拟合。这些测试集表明，即使是超出我们用"专家级"工具实现所达到的水平，我们仍然可以提取出额外的性能提升——无论这些工具是由我们的研究人员手动编写的，还是由 Claude 自己生成的。

在下一节中，我们将分享从这一过程中学到的一些经验。


## 编写高效工具的原则

在本节中，我们将把学到的经验提炼为编写高效工具的几条指导原则。


### 为智能体选择合适的工具

工具越多并不一定带来更好的结果。我们观察到的一个常见错误是，工具只是对现有软件功能或 API 端点的简单包装——而不论这些工具是否适合智能体。这是因为智能体与传统软件具有不同的"可供性"（affordances）——也就是说，它们感知可以通过这些工具采取哪些潜在行动的方式是不同的。

大语言模型智能体的"上下文"是有限的（也就是说，它们一次能处理的信息量存在上限），而计算机内存则便宜且充裕。以在通讯录中搜索联系人为例。传统软件程序可以高效地存储并逐个处理联系人列表，逐个检查后再处理下一个。

然而，如果一个大语言模型智能体使用了一个返回所有联系人的工具，然后不得不逐个逐 Token 地读完每条记录，它就是在把有限的上下文空间浪费在无关信息上（想象一下你在通讯录里找联系人时，从上到下读完每一页——也就是暴力搜索）。更好、更自然的方法（对智能体和人类皆然）是先翻到相关的页面（或许可以按字母顺序查找）。

我们建议构建少量经过深思熟虑、针对特定高影响工作流的工具，使其与你的评估任务相匹配，并由此逐步扩展。在通讯录的例子中，你可以选择实现 search_contacts 或 message_contact 工具，而不是 list_contacts 工具。

工具可以整合功能，在底层处理可能多个离散的操作（或 API 调用）。例如，工具可以在工具响应中补充相关的元数据，或者在单次工具调用中完成经常串联的多步任务。

以下是一些示例：

- 与其实现 list_users、list_events 和 create_event 工具，不如考虑实现一个 schedule_event 工具，用于查找空闲时间并安排日程。
- 与其实现 read_logs 工具，不如考虑实现一个 search_logs 工具，只返回相关的日志行及其周边上下文。
- 与其实现 get_customer_by_id、list_transactions 和 list_notes 工具，不如实现一个 get_customer_context 工具，一次性汇总某位客户所有近期与相关的信息。

确保你构建的每个工具都有清晰、独特的目的。工具应使智能体能够像人类在拥有相同底层资源时那样，对任务进行拆分和求解，同时减少原本会被中间输出消耗掉的上下文。

工具过多或功能重叠的工具也会分散智能体追求高效策略的注意力。对你构建（或不构建）的工具进行审慎、有选择性的规划，真的会带来回报。


### 为工具划分命名空间

你的 AI 智能体可能会获得数十个 MCP 服务器和数百个不同工具的访问权限——包括其他开发者提供的工具。当工具在功能上重叠或用途模糊时，智能体可能会搞不清该用哪个。

命名空间（将相关工具归入共同前缀之下）有助于在大量工具之间划清边界；MCP 客户端有时默认会这样做。例如，按服务划分命名空间（例如 asana_search、jira_search）和按资源划分命名空间（例如 asana_projects_search、asana_users_search），可以帮助智能体在正确的时间选择正确的工具。

我们发现，基于前缀还是后缀的命名空间选择，会对我们的工具使用评估产生不容小觑的影响。效果因大语言模型而异，我们建议你根据自己的评估来选择命名方案。

智能体可能会调用错误的工具、用错误的参数调用正确的工具、调用过少的工具，或者错误地处理工具响应。通过有选择性地实现那些名称能反映任务自然划分的工具，你可以同时减少加载到智能体上下文中的工具和工具描述的数量，并把智能体计算从上下文中卸载回工具调用本身。这降低了智能体犯错的整体风险。


### 从工具返回有意义的上下文

同样地，工具实现应当注意只向智能体返回高信号的信息。它们应优先考虑上下文相关性而非灵活性，并避免返回低层技术标识符（例如 uuid、256px_image_url、mime_type）。像 name、image_url 和 file_type 这样的字段，更有可能直接指导智能体的下游行动和响应。

智能体在处理自然语言名称、术语或标识符时，也比处理晦涩的标识符要成功得多。我们发现，仅仅把任意的字母数字 UUID 解析为更具语义、更易解读的语言（甚至是一个从 0 开始编号的 ID 方案），就能通过减少幻觉显著提升 Claude 在检索任务中的精确度。

在某些情况下，智能体可能需要同时与自然语言和技术标识符的输出交互的灵活性，哪怕只是为了触发下游的工具调用（例如 search_user(name='jane') → send_message(id=12345)）。你可以通过在工具中暴露一个简单的 response_format 枚举参数来同时支持两者，让智能体控制工具返回"简洁"还是"详细"的响应（见下图）。

你可以添加更多格式以获得更大的灵活性，类似于 GraphQL 中你可以精确选择想接收哪些信息。以下是一个用于控制工具响应详略程度的 ResponseFormat 枚举示例：


```
enum ResponseFormat {
   DETAILED = "detailed",
   CONCISE = "concise"
}
```

### 针对 Token 效率优化工具响应

优化上下文的质量固然重要。但优化工具响应返回给智能体的上下文数量同样重要。

我们建议对任何可能消耗大量上下文的工具响应，实现分页、范围选择、过滤和/或截断的某种组合，并设置合理的默认参数值。对于 Claude Code，我们默认将工具响应限制在 25,000 个 Token。我们预计智能体的有效上下文长度会随时间增长，但对上下文高效工具的需求将长期存在。

如果你选择截断响应，请务必用有帮助的指示来引导智能体。你可以直接鼓励智能体采用更节省 Token 的策略，例如在知识检索任务中，进行多次小而有针对性的搜索，而不是一次宽泛的搜索。同样，当工具调用引发错误（例如在输入验证期间）时，你可以对错误响应进行提示词工程，清晰地传达具体、可操作的改进建议，而不是给出晦涩的错误码或堆栈跟踪。

### 对工具描述进行提示词工程

现在我们来到了改进工具最有效的方法之一：对工具描述和规格说明进行提示词工程。由于它们会被加载到智能体的上下文中，它们可以共同引导智能体形成有效的工具调用行为。

在编写工具描述和规格说明时，想一想你会如何向团队中的新员工描述你的工具。考虑你可能默认带入的上下文——专门的查询格式、冷门术语的定义、底层资源之间的关系——并将其明确化。通过清楚地描述（并使用严格的数据模型加以约束）预期的输入和输出来避免歧义。特别是，输入参数的命名应当毫无歧义：与其使用名为 user 的参数，不如使用名为 user_id 的参数。

借助你的评估，你可以更有信心地衡量提示词工程的影响。即使是对工具描述的微小改进，也可能带来显著的提升。在我们对工具描述做出精确改进之后，Claude Sonnet 3.5 在 SWE-bench Verified 评估中取得了最先进的性能，大幅降低了错误率并提升了任务完成率。

你可以在我们的开发者指南中找到其他工具定义的最佳实践。如果你在为 Claude 构建工具，我们还建议阅读关于工具如何被动态加载到 Claude 系统提示词中的内容。最后，如果你在为 MCP 服务器编写工具，工具注解（tool annotations）有助于说明哪些工具需要开放世界访问权限或会进行破坏性更改。


## 展望未来

为了为智能体构建高效的工具，我们需要将软件开发实践从可预测的确定性模式重新定位到非确定性模式。

通过我们在本文中描述的这种迭代的、评估驱动的过程，我们发现了让工具取得成功的一些一致模式：高效的工具是有意为之、定义清晰的，会审慎地使用智能体的上下文，可以在多样化的工作流中组合使用，并使智能体能够凭直觉解决现实世界的任务。

未来，我们预计智能体与世界交互的具体机制将不断演进——从 MCP 协议的更新到底层大语言模型本身的升级。通过采用系统的、评估驱动的方法来改进智能体工具，我们可以确保：当智能体变得更强大时，它们所使用的工具也将随之演进。
