## 二、学了什么（三条真学到的东西）

### 1. 「完整度」是个可以被玩坏的数字

第一版的命名规范符合率，分母是「包内所有候选文件」。结果 C1 显示 0%——因为那个包里除了交付物，还有 `pipeline/`、`corpus/` 这类工程文件，它们本来就不该按 `姓名_挑战_内容` 命名。

**改成分母只用"命中交付项的文件"**。但改完 C1 还是 0%——这次是真话：**C1 官方规格就写 `README.md`、`*AI日志*`，不要求姓名前缀。**

学到的：**同一个 0%，可以是"指标错"，也可以是"制度不一致"**。分不清这两者，指标就会变成甩锅工具。

### 2. 最难的不是匹配，是「不该算的别算」

C6A 三次致命错误全部是「多算了」而非「少算了」：

- 别人的文件算到我头上（嵌套提交包）
- 别人挑战的必填项算成本挑战的（C2A 里嵌了 C9 清单）
- 最关键的 16MB artifact 被"忽略垃圾文件"规则吃掉

**少算会被发现（有人说"我明明交了"），多算不会——多算只会显得自己很勤奋。** 这是这次最大的警觉。

### 3. 「无记录」和「未提交」是两个世界

矩阵里一个 ❌，在不同语境下含义完全不同：

| 情况 | 正确表述 | 错误表述（会伤人） |
|---|---|---|
| 本机没有这个包 | 采集不到 | 未提交 |
| 有包但缺 AI 日志 | 缺 1 项 | 未交 |
| 有包、有日志但 <=300B | 需人工复核 | 敷衍 |

所以我把状态字段拆成三个（`complete / partial / missing`），并在界面上把 `missing` 的文案统一写成「本机无记录（≠ 判定未交）」。

## 三、怎么验证的（不是"我觉得对"）

### 3.1 三层验证

| 层级 | 方法 | 结果 |
|---|---|---|
| **自洽性** | `run.py check`：状态 vs 缺失项、完整度 vs 命中数、文件命中项 vs 规格表、数据根存活 | 通过 |
| **抽样对账** | 随机挑 4 条记录（C2A/C4B/C4C/C5）逐项对照磁盘真实文件 | 全部对得上，其中 C4B 的「定制后的技能包」由 `wechat-publisher-pro.zip` 以槽位 60 分命中（低置信但正确） |
| **看脸** | 无头 Chrome 逐页截图，人眼检查排版/裁切/误导性着色 | 发现并修掉 5 处 UI 问题 |

### 3.2 一份具体的对账样例（C5）

```
✅ README      ← sias-local-map-agent/README.md        (85, glob)
✅ AI 日志      ← sias-local-map-agent/AI_LOG.md        (85, glob)
✅ 拿来说明      ← sias-local-map-agent/ATTRIBUTION.md  (85, glob)
✅ Repo 链接     ← submission/JingXueQing_C5_repo链接.md (100, slug)
✅ README 截图   ←（可选，未强求）
```

**注**：C5 的官方规格里同时存在「repo 内 `README.md`/`AI_LOG.md`/`ATTRIBUTION.md`」和「群里提交 `姓名_C5_*.md`」两套要求，所以 5 项里有 3 项来自 repo 内部——这不是误判，是规格本身要求两处都有。

### 3.3 反例：一个必须承认的不完美

`Elite20TA` 和 `WeChatGroup` 的 C4 只有 20% 完整度。**不是他们交得差，而是他们的包在评审输入里只保留了 `.skill` 与 `SKILL.md`**（评审只需要技能本体）。这条在 `provenance.caveats` 里写明了，否则会冤枉人。

## 四、哪里错了（失败清单，按严重度）

| # | 失败 | 严重度 | 如果没被抓到会怎样 | 现在的防线 |
|---|---|---|---|---|
| 1 | 把 `*.zip/*.tar.gz/*.skill` 写进忽略列表，C2G 的核心产物被判缺失 | 🔴 高 | 在群里公开说"你没交"，实际人家交了 16MB | 忽略列表只留缓存类文件；核心产物类型禁入忽略表 |
| 2 | 嵌套提交包没排除，别人的文件算到本人头上 | 🔴 高 | 数据串人，最伤信任 | 显式忽略容器目录 + 归属字段留痕 |
| 3 | 跨挑战串味（C2A 混入 C9 清单） | 🟠 中 | 无故多出 2 个"缺失项" | pattern 里的挑战编号必须等于当前挑战 |
| 4 | 用"目录名像 `Xxx_C4D_yyy`"来判嵌套包，误伤真实交付目录 | 🟠 中 | C4D/C5A 从完整变缺件 | 改用白名单，不用模式推断特例 |
| 5 | 零数据挑战的必填项标签全染成"缺失红" | 🟡 低 | 视觉上暗示"全班都没交" | 无提交人数时中性着色 |
| 6 | 深链 `#record=` 未 URL 解码，打不开 | 🟡 低 | 分享单条记录的链接失效 | 先 decode 再匹配 |
| 7 | 自检阈值 `1e-6` vs 存储 `round(,3)` 误报 | 🟡 低 | 以为数据错了，白查半小时 | 阈值对齐存储精度 |

**共性**：7 条里有 5 条是「**用模式/推断去处理本该显式的东西**」。下次先问：这件事能不能写成一张白名单？

## 五、下次怎么改（可执行，不是口号）

1. **把"忽略规则"提升为配置里的显式契约**：`ignore_file_globs` 只允许缓存类后缀，且加一条自检——「若某挑战的必填项全部未命中且包内有被忽略的同类型文件，则报警」。
2. **归属加第二证据源**：现在靠文件名/目录名。下一步读包内 `README_提交说明.md` 或 `方案设计.md` 首段，用 LLM 抽姓名做交叉验证；两个来源冲突时标 `needs_human`。
3. **提交时间换成平台时间**：mtime 会被复制/解压刷新（本次 C2G 两份包 mtime 都是 10-04，实际提交可能更早）。接 EduSeed 接口或让提交包自带 `submitted_at.txt`。
4. **把"缺件提醒"从展示升级为动作**：`digest.py` 已经能生成发群文案，下一步接成「按人分条 @ 他」，并记录「提醒过几次」。
5. **给匹配加回归测试**：把这次的 7 个坑各写成 1 条断言（输入一小组造出来的文件树，断言状态），进 `run.py check`。目前自检只验内部自洽，不验"已知坑不再犯"。

## 六、如果重做一次，我会怎么开始

先写三张纸，再写代码：

1. **口径纸**：状态定义、时间定义、归属规则、忽略规则——一页写完，签字。
2. **反例纸**：先列出"什么情况下这个数字是错的"（嵌套包、跨挑战、忽略误伤、mtime 漂移）。
3. **验收纸**：先在纸上画出「我要在群里发的那句话」，再倒推需要哪些字段。

这次是先写代码再补口径，导致口径改了三轮（命名合积分母、同义项合并、报告时间近似）。**顺序反了，返工就多。**
