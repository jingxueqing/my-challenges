## 1. 我是怎么用 skill-creator 的

### 1.1 流程对照

skill-creator 要求走 intent → interview → draft → test → iterate 五步。
我的实际执行情况，**包括未完全遵守的地方**：

| 阶段 | skill-creator 要求 | 我的实际做法 | 是否遵守 |
|------|------------------|-------------|---------|
| **1. 理解 + 具体用例** | 明确技能做什么、什么时候触发 | **跳过了问用户**。直接读了 CHALLENGE.md 的能力清单和"缺少的能力"表，自己判断选 12 项 | ⚠️ 部分跳过 |
| **2. 规划可复用内容** | 分析需要哪些 script/reference/asset | 规划了 scripts/ + references/ + examples/ + tests/ 四类 | ✅ 遵守 |
| **3. 初始化** | 用 `init_skill.py` 生成骨架 | **手动 mkdir 建骨架**（我已有 starter 目录结构，且 init_skill 生成的示例文件我全都不需要） | ⚠️ 等效达成 |
| **4. 编写 SKILL.md** | 写清 purpose / when / how | 按 skill-creator 要求写 frontmatter（name/description/agent_created）+ 渐进披露结构 | ✅ 遵守 |
| **5. 打包分发** | `package_skill.py` 验证并打包 | 手动按交付规范整理（因为要按挑战命名规范输出） | ⚠️ 等效达成 |
| **6. 迭代** | 用 → 发现问题 → 改 → 再测 | **跑了 12 轮 eval**（首发 8 轮 + 发布后 4 轮），每轮按失败项修 | ✅ 严格遵守 |

### 1.2 我对 skill-creator 的一处改造

skill-creator 的 SKILL.md 模板 frontmatter 只要求 `name` 和 `description`。
我额外加了 `agent_created: true`（skill-creator 文档里有要求，我确认后加上），
这样技能后续可被 `SkillManage` 修改或删除。

**更重要的是 description 的写法。** skill-creator 强调"metadata 决定技能何时被触发"，
所以我把触发词全部枚举进 description：

```yaml
description: >
  Convert Markdown or Word documents into WeChat Official Account ready-to-paste HTML...
  This skill should be used when the user says "convert to WeChat", "公众号文章",
  "微信公众号格式", "转换成公众号", "排版公众号", "推文"...
  This skill should be used when（第三人称，不是第二人称）
```

中英文触发词都列了——因为用户可能说"convert to WeChat"，也可能说"排版公众号"。

## 3. 修 starter 的 12 个缺陷：AI 做对了什么

【实测】这些不是 review 推测的，是我写探针文档跑出来的。

### 3.1 我（人）做的：设计探针文档

starter 自带 `examples/sample_article.md`。**如果我直接用它测，一个 bug 都发现不了**——
那份示例里没有代码块、没有嵌套行内元素、没有本地图片、没有内联 div。

我写了一篇 13 种边界情况的探针文档。跑完 starter 后，输出让我发现了：

```
段落里有 <span>...inline code</span> 和 <span>加粗</span>...
还有 <script>alert(1)</script> 和 <div>一个 div</div>。
```

**这一行输出里同时暴露了 4 个 bug**：script 没删干净、div 把段落劈开了、
span 嵌套丢了 class。最关键的是——**这些全都不是 AI 事先告诉我的，是跑出来的。**

### 3.2 AI 做的：定位根因并修

以最典型的 B2（加粗里的链接消失）为例：

**我给的输入**：starter 输出里这段
```html
<p><span style="font-weight: bold;">这段加粗里嵌套了 代码 和 链接。</span></p>
```
**我的判断**：`链接` 的 `<a href>` 整个没了，不是样式问题。

**AI 的排查过程**【工具产出】：
1. 读 `convert_to_wechat.py`，锁定 `sanitize()` 里的 strong 分支
2. 定位到 `span.string = tag.get_text()` 这行
3. 解释机制：`get_text()` 递归提取纯文本，**子节点被拍平**
4. 提出修法：改标签名而非替换内容

**我的验证**：用正则断言 `font-weight:bold[^>]*>[^<]*<a\s+href=` 检查，R6 时通过。

**这个案例里 AI 的价值**：不是它比我更懂 BeautifulSoup，
而是它把"输出异常"映射到"代码某一行"的速度快，且能解释清楚**为什么**。
判断"这是内容丢失不是样式问题"是我做的。

## 4. 我自己写错的 5 个 bug（最重要的部分；发布后第 9–12 轮又添 5 个，见 §12.2–12.4）

【工具产出】以下全部是本次会话真实发生的。我特意写这一节，
因为**只记录成功的日志没有价值**。

### bug 1：h1 在错误的位置被降级

**现象**：文章标题变成一行裸文本，`#1 标题` 不见了。

**我的第一版代码**（顺序错了）：
```python
# 6.2 降级非白名单标签
for el in soup.find_all(True):
    if el.name not in ALLOWED_TAGS: el.unwrap()   # ← h1 在这里被干掉
# 6.4 h1 → h2
for h1 in soup.find_all("h1"): h1.name = "h2"     # ← 匹配不到任何东西
```

**AI 发现的**：T14 报"h1 标题块不存在"。
**根因分析**：`h1` 不在 `ALLOWED_TAGS` 里，所以**先**被 `unwrap()` 成裸文本，
**后**面的降级代码匹配不到任何元素。

**我的修法**：调换顺序，并且决定 **h1 直接 `decompose()` 不保留**
——因为公众号标题栏由平台提供，正文里再放标题既重复又违规。
这个决定是我做的，理由是"文章标题在公众号里填在标题栏"。

**遗留问题**：我的 T14 断言只查了"没有 `<h1>` 残留"，没查"标题还在不在"，
所以第一版测试是**绿的**，但功能已经坏了。**我又补了一条断言。**

### bug 2：BeautifulSoup 会静默吞掉代码缩进 ⭐

**这个最隐蔽，值得完整记录。**

**现象**：`white-space:pre-wrap` 已加上，测试显示缩进保留了，我以为没问题。
**我做的事**：把真实输出逐行打印出来看。

```
<span>...<span>def</span>...\n    <span>return</span> a</span>
                ↑ 这行 4 空格缩进消失了
```

**AI 的排查**【工具产出】：做了最小复现实验
```python
h = '<span><span>a</span>\n    <span>b</span>\n    plain</span>'
BeautifulSoup(h, "html.parser")  # → 缩进被吃掉
BeautifulSoup(h, "lxml")         # → 同样
```

**根因**：BeautifulSoup 解析时**丢弃嵌套标签前的空白**，
它认为标签之间的空格是格式噪音。这个行为在 `html.parser` 和 `lxml` 上一致。

**修法**：解析前把缩进替换成私有区字符（`U+E000`）占位，解析完再换回来。
```python
def protect_code_indent(code_html):
    return re.sub(r"(\n)([ \t]+)",
                  lambda m: m.group(1) + m.group(2).replace(" ", "\ue000"),
                  code_html)
```

**我为什么强调这条**：**如果我只写"输出看起来对"的断言，这个 bug 会一路带进交付。**
它只会让所有代码块失去缩进——而缩进对技术文章就是语义。

**这条也进了文章正文第五节**，因为我相信它对读者的价值高于任何功能介绍。

### bug 3：lxml 偷偷给我塞了 `<html><body>`

**现象**：T11 显示 5 个 callout 全部没生成，但 `stats` 里明明记了 5 个。

**AI 的排查**【工具产出】：单独调试时 `select("div.__callout__")` 明明能找到 5 个。
于是对比"单独调试"和"主流程"的差异，找到唯一不同：

| | 单独调试 | 主流程 |
|---|---------|--------|
| 解析器 | `html.parser` | `lxml` |

**验证**：
```python
BeautifulSoup('<span>x</span>', 'lxml')
# → '<html><body><span>x</span></body></html>'
```

**根因**：lxml 解析裸片段会自动补 `<html><body>` 外壳，
而我用 `str(holder)` 把它注入正文，整棵树就错位了。

**修法**：改用 `html.parser`，并且只取 `holder.contents` 而不是 `str(holder)`。

**附带收获**：修这个 bug 时我第一次尝试用脚本做文本块搬运，
结果把 `convert()` 函数搞出了两个副本，其中一个还是截断的。
**这是我自己操作失误**，靠 `ast.parse()` 语法检查才发现。
教训：改大文件时用脚本做文本替换，事后必须语法校验。

### bug 4：标题计数器位置错了

**现象**：三个小节编成 `1. / 2.1 / 3.`，但全文根本没有第 3 章。

**根因**：
```python
for h in soup.find_all(["h2", "h3", "h4"]):
    h2n += 1                                    # ← h3 也加了
    h3n = h3n + 1 if h.name == "h3" else 0
```

**修法**：改成只在遇到对应层级时递增。
**AI 提的第二种方案**（更简洁）：`h2n = len(soup.find_all("h2"))` 直接算总数。
我选了前者，因为它同时维护了 h3 的层级关系。

### bug 5：把全角标点当成了汉字

**现象**：中文排版后 "整行div：" 变成 "整行div ："，多一个空格。

**根因**：我定义 CJK 字符类是 `\u4e00-\u9fa5\u3000-\u303f\uff00-\uffef`。
后两段是**全角标点区**（。：，、），它们本身就自带右侧间距，再加一次就重了。

**修法**：`CJK = r"\u4e00-\u9fa5"` —— 只留纯汉字。

**我为什么在意这个**：一个字符范围的边界，写错了就是排版事故。
**而且这类 bug 用户一眼就能看出来**——中英文间距做出来是为了专业，
结果多出空格，比不做更糟。

**这条也进了文章正文**，因为它是"自动化断言当时是绿的"这类 bug 的典型：
T10 当时只断言了"有插入 U+2009"，没断言"标点前不该有"。

### 4.1 5 个 bug 的共同点

【本人判断】回看这 5 个，有 4 个的自动化断言**当时是绿的**：

| bug | 当时测试状态 | 怎么发现的 |
|-----|-------------|-----------|
| h1 顺序错 | 🟢 绿（断言太弱） | 新增断言 |
| 缩进被吞 | 🟢 绿（只看"有 pre-wrap"） | **逐行打印真实输出** |
| lxml 注入 | 🔴 红 | 测试直接报 |
| 计数器错 | 🔴 红 | 测试直接报 |
| 标点当汉字 | 🟢 绿（只断言"有间距"） | **肉眼看出"整行div ："** |

**结论**：4/5 是靠"看真实输出"发现的，不是靠断言。
**这直接支撑了文章正文的建议二：先写测试再修 bug，但也要真的去看输出。**

## 5. eval 套件的设计（AI 主导，人审）

### 5.1 为什么先写测试

【本人判断】决定先做 eval 而不是先加功能，理由是：
如果我边加功能边测，每加一个功能就引入 3 个新 bug，
最后分不清哪些是"没修好"、哪些是"新写的"。

先建 24 个用例锁住已知行为，再往上加功能，每轮跑一次看回归。

### 5.2 用例结构

【工具产出】24 个用例分三类：

| 类别 | 用例 | 数量 |
|------|------|------|
| 回归防护（针对 starter 缺陷） | T02–T09 | 8 |
| 新增能力 | T10–T15, T19, T20, T24 | 10 |
| 通用/边界 | T01, T16–T18, T21–T23 | 6 |

**断言风格**全是字符串级硬判断，不靠肉眼：
```python
("缩进空格被保留", re.search(r"\n {4,}\S", code) is not None),
("callout 用 p 而非 div", not re.search(r"<div[\s>]", body)),
("两次转换输出完全一致", a == b),          # 幂等性
```

### 5.3 AI 的一个贡献我采纳了

AI 在设计 T22 时提出加**幂等性测试**（同输入两次转换输出必须完全一致）。
这一条我当时觉得没必要（转换器又没有随机性），但后来证明它有实际价值：
R6 修 BeautifulSoup 缩进那次，如果输出依赖了某种不稳定状态，幂等性断言能立刻发现。

**已采纳并保留。**

## 8. 一次失败的方法论尝试（诚实记录）

【工具产出】我尝试过用正则对源码做**块级搬运**来调整函数顺序
（把 callout 渲染从 `read_markdown` 挪到 `convert`）。

## 10. 复盘：三条可迁移的经验

【本人判断】这次实践中，最有价值的不是技能本身，是三条方法：

### 经验 1：验证工具要攻击它，不是表扬它

starter 自带示例能跑通，能力清单列了 5 条 ✅。
**但那份示例里没有能暴露缺陷的内容。**

我写探针文档花了 20 分钟，测出 12 个缺陷。
如果只跑示例文章，这 12 个里我能发现的最多 1 个。

### 经验 2：`get_text()` 是 BeautifulSoup 的头号陷阱

`el.string = el.get_text()` 看起来无害，实际是**递归删除所有子结构**。
代码块换行、加粗里的链接、多段引用——三个致命 bug 全是这一行导致的。

**凡是"提取文本再赋值"的地方，都要停下来想一秒。**

### 经验 3：绿色的测试不等于正确的功能

首发那 5 个自造 bug 里，4 个在被发现时断言是绿的。

**测试只能验证"你想到要验证的东西"。**
"逐行打印真实输出"这个动作，没有任何测试框架能替代。

## 12. 真实发布后的第 9–12 轮迭代（2026-10-06）

【工具产出】文章在真实微信编辑器发布后，我用 WebFetch 抓取线上版本，
与本地 `out.body.html` 逐段对比，**发现 5 个此前 24 个用例一个都没抓到的问题**。

### 12.1 我做了什么

1. `WebFetch` 抓取线上文章全文
2. 与本地输出逐项比对：callout 数量、代码块、标题层级、裸露标签
3. 对每个可疑项**打印原始 HTML 片段查证**，不靠猜

### 12.2 找到的 5 个问题

| # | 问题 | 定性 |
|---|------|------|
| P1 | 行内代码里的 `<div>` 被改写成 `<span>` | 转换器 bug |
| P2 | callout 正则吞掉后续整节标题 | 转换器 bug |
| P3/P4 | 嵌套代码块转义失效 | 我的文章写法 |
| P5 | 少写一个 `:::`，转换器静默接受 | 诊断能力缺失 |

### 12.3 最有讽刺意味的一个（P1）

**我那篇文章的主题之一，就是"内联 `<div>` 会劈开段落"。**
而我的转换器为了修这个问题，把行内代码里本该原样显示的 `<div>` 也一起改掉了。

线上读者看到的是「内联 `<span>` 把段落从中间劈开」——
**一个讲 div 缺陷的文章，读者看到的标签名是 span。**

改法：先保护行内代码和代码块（占位符法），再降级 div，最后还原。

### 12.4 一个我漏掉的盲区

P2 和 P5 其实是**同一件事的两面**：
- P2：未闭合会导致吞内容
- P5：没人告诉我未闭合了

我第一次只修了 P2（改正则），跑测试全绿就以为完事了。
**是"数 callout 数量发现是 9 不是 10"才逮到 P5 的。**

这说明：**修 bug 时要问"这个问题的另一半是什么"，而不是"测试绿了吗"。**

### 12.5 测试的盲区

P1/P2/P5 全部是**真实发布后才发现的**，27 个用例一个都没抓到。

原因很直接：它们只在"作者写错了"时发生，而我的测试样本都是"写得对的"。

> **测试能验证工具的边界，但验证不了作者的输入是否合法。**
> 这种情况的正确解法不是加测试，是**加诊断能力**——
> 让工具主动报告"你的输入有问题"，而不是默默接受。

所以我加了 `find_unclosed_callouts()`：

```
⚠️  callout 未闭合：第 3 行的 :::danger 缺少配对的 :::
     → 这会把后续整节内容吞进上一个框，务必补上闭合标记
```

| 轮次 | 内容 |
