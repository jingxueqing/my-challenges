# 拿来说明：从 C4B starter kit 拿到了什么、改了什么、为什么

> 作者：JingXueQing ｜ 学号：2024102110351
> 改造对象：`c4b-wechat-publisher-starter.zip`（官方 starter kit）
> 产物：`wechat-publisher-pro`

---

## 一句话总结

starter kit 是一个**能演示、不能用**的骨架：它包含 5 项能力，但有 12 个实测复现的缺陷，
其中 5 个会直接毁掉内容。我保留了它 4 项正确的设计，重写了转换核心，
新增 12 项能力，并用 24 个测试用例把结论锁死。

---

## 二、我从 starter kit 拿了什么

以下 4 项是 starter 的正确设计，我**原样保留**（仅在能力范围内做增强）：

| 拿的东西 | 位置 | 为什么值得留 |
|---------|------|------------|
| **整体流水线骨架** | `convert()` 的 read → sanitize → style → clean → output 五步 | 顺序是对的，公众号排版本质就是"先保证合规、再注入样式" |
| **inline CSS 的核心约束** | `references/wechat_styles.md` 的字号/行高取值 | 16px 正文、1.75 行高、#333 而非 #000——这些是有依据的，不是拍脑袋 |
| **标签白名单思路** | `ALLOWED_TAGS` / `DROP_TAGS` | 思路正确（见下文我改了什么） |
| **docx 最小读取** | `read_docx()` 的 heading→h2/h3 映射 | 给了起点，但实现太薄（见下文） |

**结论：拿来主义的重点不是"复制代码"，是"继承判断"。**
starter 的作者知道三件事：①公众号只认 inline CSS ②h1/div/script 必须处理
③字号行高有讲究。这三条我全部继承。

## 三、我改了什么（以及为什么）

### 3.1 修 12 个实测复现的缺陷

**这些不是 review 出来的，是我用探针文档跑出来的。** 探针文档
（`tests/fixtures/` 里有完整复现样本）包含 13 种边界情况：代码块、嵌套行内元素、
多段引用、内联 div、本地图片、SVG、嵌套列表、中英混排…

| # | 缺陷 | 严重度 | 根因 | 我的修法 |
|---|------|-------|------|---------|
| B1 | 代码块换行被吞成一行、缩进全丢 | **致命** | `p.string = code_text` 赋值，HTML 里换行等于空格 | 改用 `white-space:pre-wrap` + 哨兵字符保护缩进 |
| B2 | 加粗/斜体里的行内代码与链接消失 | **致命** | `span.string = tag.get_text()` 把子节点拍平 | 改标签名而非替换内容，保留子节点 |
| B3 | 多段引用被合并成一段 | **致命** | 同 B2 | 同 B2 |
| B4 | `<hr>` 分隔线被整体丢弃 | **致命** | `hr` 不在白名单，`unwrap()` 无子节点等于删除 | 提前把 `hr` 转成带 border-top 的 `<p>` |
| B5 | 内联 `<div>` 把段落从中间劈开 | **致命** | markdown 库遇块级标签截断段落 | 进 markdown 前把 `<div>` 降级为 `<span>` |
| B6 | 图片无 `max-width` | 严重 | 从未设置 | 所有 `img` 强制 `max-width:100%` |
| B7 | 本地图片保留相对路径 → 粘贴必裂图 | 严重 | 从未实现 base64 | 自动转 base64 内嵌（相对 md 文件解析） |
| B8 | SVG 被原样输出（微信保存会消失） | 严重 | 无处理 | 显式拒绝并警告 |
| B9 | 嵌套列表被拍平成同级 | 严重 | `sane_lists` 行为 | 保留层级并加缩进样式 |
| B10 | `<ul>/<ol>` 自身无样式，缩进失控 | 严重 | `apply_styles` 未覆盖 | 补 `padding-left` + `list-style-type` |
| B11 | 中英文之间零间距 | 中等 | 无此概念 | 自动插入 U+2009 极细空格，且**排除全角标点** |
| B12 | `ALLOWED_CSS` 白名单定义了但从不执行 | 中等 | 死代码 | 真正实现 `filter_css()` |

另外修掉两个"假合规"：

| 问题 | 为什么严重 | 我的修法 |
|------|-----------|---------|
| `auto-install` 会 `pip install --break-system-packages` | 只是想转一篇文章，它却改动了你的 Python 环境 | 改为打印安装指引并退出，绝不擅自动手 |
| 文档声称"图片用 base64"但代码没实现 | 文档与实现脱节，比不写更危险 | 补齐实现，且文档与代码同源 |

### 3.2 新增 12 项能力

挑战要求"至少新增 2 项"，我加了 12 项：

| 能力 | 价值 | 难度 | 说明 |
|------|------|------|------|
| **合规体检器 `--audit`** | ⭐ 最高 | ★★ | 扫描成品 HTML 的违规项，给修复建议，高危时退出码 1，可挂 CI |
| Callout 提示框（5 种） | 高 | ★★ | `:::note/tip/warn/danger/key`，公众号排版的性价比之王 |
| 多主题系统（4 套） | 高 | ★★ | ink/forest/amber/mono，复制一份字典即可加主题 |
| 自动目录卡片 | 高 | ★★ | 带诚实的"id 锚点不可用"说明，不做假锚点 |
| 文章元数据 | 中 | ★ | YAML frontmatter：标题/作者/日期/标签/摘要/封面 |
| 页脚版权 | 中 | ★ | 自动生成，含工具署名 |
| 图片 base64 内嵌 | 高 | ★★ | 修 B7 的根治方案 |
| 中文排版间距 | 中 | ★★★ | 中英文自动间距 + 全角标点排除 |
| 代码语法高亮 | 高 | ★★ | Pygments class → inline style（公众号不允许 class） |
| 批量转换 | 中 | ★ | 带汇总表 |
| 手机预览页 | 中 | ★ | `--preview phone`，375px 模拟，交作业截图用 |
| Word 表格/列表/图片 | 中 | ★★ | starter 的 `read_docx` 只有段落 |

### 3.3 三个我自己的设计判断

**① 目录不做成可点击的。**
公众号会剥离 `id` 锚点，所以很多工具生成的"可点击目录"其实是死的。
我选择生成**静态目录卡片**，并在卡片底部用一行小字诚实说明这个限制、
给出在微信编辑器里手动加书签的替代做法。

**② 体检器是机制，不是知识。**
"记住公众号不许用 div"是知识，会过时。
"`--audit` 每次替你检查"是机制，不会过时。所以我把它做成了 CLI 一等公民。

**③ 体检器自己也要被测试。**
`--audit` 的第一版会误报——因为我的一篇测试文章里正好有句
"内联样式 position:absolute 的文字"，纯正文，却因为含 `position:` 被判违规。
修法是只扫 `style="..."` 属性内部。现在这条也有断言守着。

## 五、我认为"拿来主义"最该注意的事

starter kit 的示例文章能跑通，能力清单也列了 5 条"✅ 已实现"。
**但它示例文章里没有代码块、没有嵌套行内元素、没有本地图片、没有内联 div。**
——那些会暴露缺陷的内容，它一个都没有。

所以我做了一件看起来很笨的事：先写一份"把坑都踩一遍"的探针文档，再跑它。

:::note 这一步的回报
探针文档跑一次，测出 12 个缺陷。如果只跑它自带的示例文章，这 12 个缺陷里
我能发现的最多 1 个（图片裂图，因为那是我真实遇到过的问题）。

**验证工具，必须用它最擅长的场景去攻击它，而不是用它最擅长的场景去表扬它。**
:::

## 六、诚实声明

- 12 个 starter 缺陷全部是**实测复现**，不是 code review 推测。
  复现样本在 `tests/fixtures/t01`–`t09`，可直接验证。
- 我自己写错了 5 个 bug（详见 AI 日志与文章正文第五节），
  其中"BeautifulSoup 吞掉代码缩进"和"lxml 注入 `<html><body>`"两个，
  都是靠逐行打印真实输出才发现的，自动化断言当时是绿的。
- 当前测试覆盖到"输出结构正确"。**我没有在真实公众号编辑器里粘贴验证过**
  （我没有公众号账号），所以"微信粘贴后是否 100% 保真"这一点，
  依据的是官方限制文档 + starter 参考文档，不是实测。
  这一点在 SKILL.md 的 Known Constraints 里也明确写了。

## 七、真实发布后的追加发现（2026-10-06）

技能第一次进入真实微信编辑器后，发现了 **5 个新问题**，
其中 2 个是转换器的真 bug，3 个是我文章写法的错误。
这一节记录它们，因为它们的性质和前面 12 个不同——
**前面是 starter 的问题，这一轮是"我的技能在真实环境下的边界"。**

| # | 问题 | 定性 | 修法 |
|---|------|------|------|
| **P1** | 行内代码里的 `<div>` 被改写成 `<span>` | **转换器 bug** | `inline_div_to_span()` 改为先保护行内代码和代码块（占位符法），处理完再还原 |
| **P2** | callout 正则贪婪匹配，吞掉后续整节标题 | **转换器 bug** | 正文禁止含块级标题（`#`~`######` 独占一行），越界即终止 |
| **P3** | 嵌套代码块用 `\``` 转义，高亮失效 | 文章写法 | 改为引用块 + 独立代码块，不依赖转义 |
| **P4** | 转义符 `\``` 泄漏到正文 | 文章写法 | 同 P3 |
| **P5** | 我少写一个 `:::`，转换器静默接受 | **诊断能力缺失** | 新增 `find_unclosed_callouts()`，输出未闭合告警并给出行号 |

### 7.1 P1 是最值得记的一个

这篇文章的主题之一就是"内联 `<div>` 会劈开段落"。
而我的转换器为了修这个问题，**把行内代码里本该原样显示的 `<div>` 也一起改掉了**。

线上版本里，读者看到的是：

> ⑤ 内联 `<span>` 把段落被从中间劈开

**一个讲 `<div>` 缺陷的文章，读者看到的标签名是 `<span>`。**
事实被改错了，而且改得很隐蔽——颜色、字号、位置全都正常。

**根因是我做 B5 修复时用了全局正则，没考虑"这个标签可能在代码里"。
这正是我自己在文章里写的那条教训：「批处理式的替换，要先想清楚作用域」。**

### 7.2 P5 暴露的是诊断能力不足

我少写一个 `:::`，转换器**没有任何反应**——照常输出，照常通过合规体检。
直到我在验证成品时逐个数 callout 数量（9 而不是 10）才发现。

修法是让它主动报告：

```
⚠️  callout 未闭合：第 3 行的 :::danger 缺少配对的 :::
     → 这会把后续整节内容吞进上一个框，务必补上闭合标记
```

**这和 P2 是同一个问题的一体两面**：
P2 是"未闭合会导致吞内容"，P5 是"没人告诉我未闭合了"。
修了一个必须补另一个——否则下次还是踩。
