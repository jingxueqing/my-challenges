## 1. 消融的目的

我的方案在 SOTA 栈（PR #1394 → #1493）之上只加了两个东西：**SRD** 和 **TTDS**。所以消融要回答三个问题：

1. **单独贡献**：SRD 单独加，是好是坏？TTDS 单独加，是好是坏？
2. **协同效应**：SRD + TTDS 一起加，是否**大于**两者单独之和？
3. **机制验证**：如果协同成立，是不是因为 SRD 降低了模型对深度的敏感度？（这是我给的解释，需要单独验证）

第 3 条是很多人不做、但我觉得最关键的一条。**没有机制验证的消融只是一张数字表。**

## 3. 先验登记（Pre-registration）——跑之前写下，跑之后不改

### 3.1 三个主假设

| 假设 | 内容 | 我的预期 | 置信度 | 如果错了说明什么 |
|---|---|---|---|---|
| **H1** | SRD 单独会让 BPB **略微变差** | **+0.001 ~ +0.003** | 中 | 若反而变好 → 随机深度本身是正则化收益，那更好，但我的机制解释需要修正 |
| **H2** | SRD + TTDS **净变好**，且 > 单独之和 | **−0.005 ~ −0.015** | **低** | 若成立 → 原创点成立；若不成立 → **原创点失败，照实写** |
| **H3** | TTDS 单独（无 SRD）**明显变差** | **+0.005 ~ +0.02** | 中高 | 若不变差 → 说明递归块本来就深度鲁棒，SRD 是多余的，应去掉 |

### 3.2 机制验证的预期（G7）

G7 是我在别人的提交里没见过的一种消融：**把训练好的模型在不同递归深度下评估，画出「深度 → BPB」曲线**，对 G0（固定深度训练）和 G1（SRD 训练）各画一条。

**我预期看到**：

```
BPB
 │   G0 (固定 d=2 训练)          G1 (SRD 训练)
 │        ╲                          ╲
 │         ╲                          ╲___
 │          ╲___                          ╲___
 │   d=2 ●●●●                             
 │              ╲                          
 │               ╲  ← d=3 处陡升             ← d=3 处平缓
 └────────────────────────────────────────→ 递归深度
      0   1   2   3   4
```

- **G0 曲线**应在 d=2 处最凹（因为就是按 d=2 训的），**d 偏离 2 就陡升**；
- **G1 曲线**应更平缓，**d=3 处的上升幅度明显小于 G0**。

**量化判据**：定义 `slope = BPB(d=3) − BPB(d=2)`。我预期 **G1 的 slope 显著小于 G0 的 slope**（差值 ≥ 0.003，p<0.05）。

**如果 G1 的 slope 不小于 G0**，那我的机制解释（"SRD 降低深度敏感度"）就是错的，即使 H2 侥幸成立也只是偶然，我会如实说明。

## 4. 判定规则（写死，防止事后找补）

跑完之后按下面的规则判定，**不允许根据结果反过来改规则**：

| 结论 | 判定条件 |
|---|---|
| **原创点成立** | (G3 − G0) ≤ −0.005 nats，p<0.01，**且** (G3 − G0) < (G1 − G0) + (G2 − G0) − 0.002 |
| **原创点部分成立** | (G3 − G0) ≤ −0.005 nats，p<0.01，但不满足协同条件 |
| **原创点失败** | (G3 − G0) > −0.005 nats，或 p ≥ 0.01 |
| **机制解释成立** | G7 中 G1 的 slope 比 G0 小 ≥ 0.003，p<0.05 |
| **机制解释失败** | 上述不成立（即使原创点成立，也照实标注"机制未验证"） |

**协同条件的含义**：SRD 和 TTDS 的联合效果必须**明显优于**两者单独效果的简单叠加。如果 G3 只是等于 (G1 单独 + G2 单独) 的和，那它们只是**叠加**，不是**协同**，我的"成对设计"说法就不成立——那我会改口说"两个独立改进恰好互补"，而不是宣称协同。

## 5. 组合效应：为什么 SRD 和 TTDS 必须成对

这是我最想说清楚的一点，也是我方案里唯一的原创逻辑。

```
                  评估时用的深度 d
                 d=1    d=2    d=3
训练方式
─────────────────────────────────────
固定 d=2 训练      ?      ★最优    ✗失配
（现有做法）                        （TTDS 在这里崩）

随机 d∈{1,2} 训练   ✓      ✓       ~外推
（SRD）                             （TTDS 在这里可能活）
```

现有做法把参数优化在 d=2 这一个点。想用 TTDS 把评估推到 d=3，就必然 train/test 失配——**历史上"训练一个条件、推理另一个条件"几乎总是失败**，这是我给自己方案定的最高风险（见方案设计 R3）。

SRD 的作用**不是让模型变好**，而是**让模型在 d=1 和 d=2 都被优化过**，从而把"深度"从一个硬约束变成一个模型不那么敏感的变量。这样 d=3 虽然是外推，但落在一条更平缓的曲线上。

**所以 SRD 是可以单独失败、但整体仍然成立的**：如果 G1（仅 SRD）变差一点，而 G3 变好很多，我的设计目的就达到了——**SRD 是给 TTDS 交的保险费，不是它自己的收益来源。**

这也是为什么我在 §3.1 里把 H1 的预期写成"变差"。

### 6.3 这三条数据说明什么、不说明什么

**说明的（都是关于"管线正确性"，不是关于榜单）：**

1. **BPB 口径正确**。byte-level tokenizer 下 `scored tokens == scored bytes == 152,207`，精确相等。这条排除了我最担心的 R1（分母算错）。
2. **量化方向正确**。post-quant 一律比 pre-quant 差（+0.006 ~ +0.016），符合"量化有损"的预期。**如果量化后反而变好，那说明量化/反量化链路有 bug**——现在它是对的。
3. **artifact 链路完整**。raw 989,696 B → 压缩 346,148–347,196 B → + code 50,771 B → 总计约 397 KB，远低于 16 MB 上限，断言通过。
4. **H3 得到初步支持**。**3 个 seed 的 TTDS delta 全部为正（+0.055 / +0.067 / +0.097，均值 +0.073）**，即"评估时展开比训练更深"确实让 BPB 变差。这与我在 §3.1 预先登记的 H3 方向一致。

**不说明的（我必须划清界限）：**

| 不能用来声称 | 原因 |
|---|---|
| "TTDS 无效" | 规模差 3 个数量级（492 K vs 约 90 M 参数；20 s vs 600 s；M1 CPU vs 8×H100）。**40 步训练出来的模型几乎是未训练的**，它的"深度敏感度"与训练充分的模型完全不是一回事 |
| "滑窗评估有效/无效" | 本跑固定 stride=32，没有跑 stride 对照 |
| "SRD 有效/无效" | 本跑没有 SRD on/off 对照 |
| 任何 FineWeb BPB 数字 | 语料是标准库源码，不是 FineWeb；byte-level 词表不是 SP8192 |

**std 偏大（0.059）的原因我也如实记录**：只训了 40 步、模型严重欠训练，seed 间差异主要来自初始化和欠训练程度，而不是配置本身。正式实验里我要求 std ≤ 0.001，达不到就先修实验流程。

### 6.4 一个我愿意承认的"漂亮但不能用"的巧合

ΔTTDS 三个 seed 全为正、方向一致，看起来像一条很强的证据。**但它不是。** 在这个规模下，任何"让模型偏离它那一点点训练条件"的改动都会变差——包括 TTDS，也包括把学习率调大、把层数加多。它证明的是"欠训练模型对分布偏移敏感"，而不是"TTDS 这个具体想法不成立"。

**所以我在 §3 的先验登记一个字都不改，D 组该怎么跑还怎么跑。**

## 9. 实测补充：G0 类实验的**本地低配版**（stride A/B，两轮）

这是一份**真的跑出来的**消融，不是设计。它与 §3 登记的实验编号 G0 对应（"关掉滑窗评估"），只是把赛道配置换成了本机跑得动的规模。**我做了两轮，第一轮有缺陷，第二轮修正后重跑——两份都保留，因为第一轮的教训本身就是消融报告的一部分。**

### 9.1 第一轮（2026-10-04）：**被污染的 A/B，已作废**

同权重、只改 `eval_stride`。**跑完之后我在复核时发现了污染**：三种 stride 的 `scored_bytes` 不一致（151,709 / 152,175 / 152,111）——它们评的**不是同一个 token 集合**，且旧版 `_windows()` 的尾窗会与最后一个窗口重叠，部分 token 被重复计分。测得"滑窗差 +0.042"，但这个数字**不可比**，本节仅存档。

**教训（已写进 AAR）**：A/B 实验的第一断言不是 BPB 差值，而是 **"各条件计分的 token 集合是否相同"**。集合不同，一切差值无意义。

### 9.2 第二轮（2026-11-06）：公平 A/B——按构造保证同集合

重训 3 seed（180 s，155/151/144 步，2.04M 参数），评估协议重写：

- **所有 regime 计分同一 token 集 `[seq_len, n)`，每个 token 恰好一次**（构造保证，并逐 seed 断言）；
- `block` = 官方 baseline 口径（不重叠分块，块内前缀上下文）；
- `slide<S>` = 窗口 `val[end-seq_len:end]`，只计分最右侧的新 token（上下文 ≥ seq_len−S）。

| regime | seed 42 | seed 0 | seed 1234 | mean | vs block |
|---|---:|---:|---:|---:|---:|
| block（不滑窗 = baseline 口径） | 3.218866 | 3.233591 | 3.247889 | **3.233449** | — |
| slide256（stride = seq_len 的滑窗） | 3.218752 | 3.233485 | 3.247790 | 3.233342 | −0.0001 |
| slide128 | 3.277981 | 3.277889 | 3.287315 | 3.281062 | +0.0476 |
| slide64（滑窗） | 3.292856 | 3.289025 | 3.296251 | **3.292711** | **+0.0593** |

**集合相等性断言**：slide128 与 slide64 计分集合完全相同（152,047 tokens，逐 seed 验证）。block 与 slide256 各比全集少 593/594 个 token——这是**官方协议本身的性质**（每块首 token 在窗内没有预测者，`logits[:-1]` vs `targets[1:]` 的固有行为），不是我实现的缺陷。这 593 个 token 是各块内上下文最少的**最难** token；若把它们补回 block，block 的 BPB 只会**升高**。因此真实差距比 +0.059 **更小但不翻转**（粗界：+0.59% 的 token 以高 NLL 计入，block 最多变差 ~0.01–0.02，方向不变）。

### 9.3 结论：负结果，4/4 实验同向，且第一轮的解释性假象已排除

按 §3 的登记口径，**H0（滑窗评估带来 −0.03）在本机规模下被否证**——公平口径下我实际量到的是 **+0.059**（3/3 seed 同向）。第二轮同时**排除了第一轮怀疑的实现假象**：同集合构造保证 + 尾窗重叠已消除 + `slide256 ≈ block`（−0.0001，两者结构等价，互为交叉验证）。

我不认为这份结果能推翻榜单那条 −0.0319，理由必须说清楚：

| | 榜单记录 | 本机公平 A/B |
|---|---|---|
| seq_len | 8192（SP8192） | **256** |
| 训练量 | 600 s × 8×H100 | **180 s × 1×M1 CPU，144–155 步** |
| 模型 | 完整栈 11L×512d | **6L×192d，2.04M** |
| 语料 | FineWeb | **CPython 标准库源码** |

差距是**量级级**的，不是参数级。滑窗收益的机制——"把上下文最差的那些 token 抬起来"——只有在模型**真的会用长上下文**时才兑现；训了 ~150 步的模型大概率不会。而且公平 A/B 给了一个第一轮没有的**机制线索**：`block`（上下文 0–255 均匀分布）好于 `slide64`（上下文恒 ≥192），说明这个欠训模型在**短上下文位置上的预测分布**反而更匹配评估流——与"尺度相关的收益"假设一致。

正式状态：**"未决（低配证据，一致指向负方向，实现假象已排除）"**。

### 对计划的实际改动

§7 第 1 步的**校准闸门**从"稳妥"升级为**硬门槛**：

> G0 校准：stride=1024 必须量到 **−0.03 ± 0.005**。量不到就 debug，**不往下走**。

如果滑窗在赛道规模上同样不兑现，Level 1 的整个路线要换。**在花掉第一个 $13 之前知道这件事，比之后知道便宜得多**——这正是我把它写进消融报告而不是删掉的原因。

## 10. 2026-11-06 实测补充（二）：TTDS 复测 + SRD 最小对照 + 正式形状短跑

针对 AI 初评"SRD/TTDS 缺乏实测验证、无正式配置真实 BPB"三条，补做了三组实验（`opt2_*.log`，全部 `[实测]`）。

### 10.1 TTDS 复测：4/4 同向变差

同权重、只改展开深度（`extra`: 训练深度 → TTDS 深度），公平口径：

| 条件 | seed 42 | seed 0 | seed 1234 | mean Δ |
|---|---:|---:|---:|---:|
| ΔTTDS extra 1→2（slide64） | +0.004953 | +0.012489 | +0.004820 | **+0.007421** |
| ΔTTDS extra 2→3（正式形状，见 §10.3） | — | — | — | +0.003483 |

**4/4 同向：评估时展开超过训练深度一律变差。** 预先登记的 H3 在两个不同规模上均成立。TTDS 按当前设计是**负结果组件**；它唯一的存活路径是 §5 的成对假设（SRD 训练让它变得不敏感），而 §10.2 表明这一对在本机规模上无法兑现。

### 10.2 SRD 最小对照：本机规模无可测效应

同配置同 seed 同 180 s 预算，只切 `SRD_ENABLED`（步数因随机深度消耗算力不同而不同，已如实标注）：

| seed | SRD on（步数 / post-quant BPB） | SRD off（步数 / post-quant BPB） | Δ |
|---:|---|---|---:|
| 42 | 155 步 / 3.292834 | 141 步 / 3.280998 | on 差 +0.0118 |
| 0 | 151 步 / 3.288986 | 133 步 / 3.309434 | on 好 −0.0204 |
| 1234 | 144 步 / 3.296229 | （未跑） | — |
| **mean** | **3.292683（n=3）** | **3.295216（n=2）** | **−0.0025（SRD on 略好）** |

**判定：本机规模下无可测效应。** −0.0025 远小于单 seed 间噪声（±0.01 量级），且步数不对齐（155/151/144 vs 141/133），不构成证据。§5 的成对假设（SRD 是给 TTDS 交的保险费）**在本机既不能证实也不能证伪**——诚实结论就是"无可测效应"，正式消融留给算力阶段（配置矩阵 §2.2 的 D 组不变）。

### 10.3 正式模型形状短跑：真实 BPB + 一个重要的超限发现

**目的**：回应"至少在可用算力上跑一次正式配置"。8×H100 不可得，我跑的是**正式模型形状 × 本地预算**：11L × 512d × 8H/4KV · mlp 4× · tied embed · **31,862,365 参数** · seq_len 1024 · byte vocab · CPython 语料 · 312 s · **19 步** · M1 CPU。

| 指标 | 值 `[实测]` |
|---|---:|
| final train loss | 3.48643 |
| pre-quant BPB | 4.027773 |
| post-quant BPB | **4.024624** |
| ΔTTDS extra 2→3 | +0.003483（再证 H3） |
| artifact 原始 / 压缩 | 63,791,616 B / 20,375,949 B |
| **16 MB 上限判定** | **❌ OVER CAP（20.43 MB > 16 MB，`artifact_ok=false`）** |

**超限发现比 BPB 数字更重要**：31.9M 参数按 6-bit mat + 8-bit embed 量化压缩后 20.4 MB，**超出 16 MB 上限 27%**。这意味着 `方案设计.md` 假设的"11L×512d 全栈"在当前量化管线下**装不进 16 MB**——正式配置的参数预算必须 ≤ ~24M（在 6/8-bit 下），或者压缩管线必须升级（熵编码 / 更低位宽）。官方 SOTA 记录全部合规，说明其有效参数量本就在此之下。**这是设计层的硬约束修正，已在 `submission.json` 的 `design_constraints` 登记。**

（19 步 / loss 3.49 的 BPB 4.02 显然是严重欠训数字，只用于证明脚本在正式形状下端到端可运行，**不构成任何成绩**。）
