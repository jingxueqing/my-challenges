## 0. 一句话摘要

**我不打算先动模型，我打算先动「尺子」。** 把评估方式从「不重叠 1024-token 块」改成「stride=64 的滑动窗口」，在**训练、权重、artifact 大小三者完全不变**的前提下，把 post-quant val_bpb 从 1.2244 压到约 1.1925（**−0.0319**）。这是官方榜单历史上单组件收益最大的一次改动，且它只花评估预算、不花训练预算。

## 1. 门槛问题一：你打算把 baseline 从 1.2244 往哪个方向压？

**方向：评估侧 —— 滑动窗口长上下文评估（Sliding-Window Evaluation）。**

不是 tokenizer、不是 optimizer、不是架构、不是量化。是**评估方式**。

### 1.1 问题的根源：baseline 的"尺子"本身是有偏的

官方 baseline 评估时把 FineWeb validation 切成**互不重叠**的 1024-token 块，每块独立送进模型。后果是：

- 每一块的**第 1 个 token 上下文长度为 0**，第 k 个 token 只有 k−1 个 token 的上下文；
- 全块平均下来，**每个 token 只有 ~512 token 的有效上下文**；
- 而模型训练时见到的是满窗 1024 上下文。

也就是说：**评估时的上下文分布，比训练时短了一半。** 我们不是在测模型的能力上限，是在测模型"只有半截上下文时"的能力。这是一个被忽略的系统性低估。

### 1.2 修改方式

滑动窗口、stride 前进、只给最右侧窗口打分：

```
TRAIN_SEQ_LEN = 1024, EVAL_STRIDE = 64

窗口 #1: [tok 0    .. tok 1023]  → 只给 tok 960..1023 打分（上下文 ≥ 960）
窗口 #2: [tok 64   .. tok 1087]  → 只给 tok 1024..1087 打分（上下文 ≥ 960）
窗口 #3: [tok 128  .. tok 1151]  → 只给 tok 1088..1151 打分
...
```

关键性质（也是它合规的原因）：

- **每个 token 仍然只被打分一次** —— 满足官方 Issue #1017 的 Condition 4（Single pass），没有重复计分、没有 rescoring；
- **严格因果** —— 每个位置只用前缀 token 打分，满足 Condition 1（Causality）；
- **不修改模型任何一个参数** —— 不存在"训练到验证集"的问题；
- **artifact 字节数不变** —— 权重一模一样。

### 1.3 为什么选这个方向，而不是题目给的那四个

我把官方 `records/track_10min_16mb/` 里 33 条记录的 `submission.json` 全部解析出来，算了每条记录相对其前一名的增量。**按"单组件收益绝对值"排序，前四是：**

| 排名 | 改动 | Δ BPB | 代价 |
|---|---|---|---|
| **1** | **滑动窗口评估** | **−0.0319** | **0 训练代价，只花 ~54s 评估时间** |
| 2 | SP4096→SP8192 词表 | −0.0123 | 重训 + 重做 tokenizer + 嵌入变大 |
| 3 | 并行残差 + mini 深度递归 | −0.0084 | 重训 + 架构改动 + 调参 |
| 4 | MuonEq-R + All-Int6 GPTQ | −0.0067 | 重训 + 量化管线改动 |

**第一名是第二名收益的 2.6 倍，而代价接近于零。**

更关键的是成本结构：这个挑战给了**两个独立的 600 秒预算**——训练 600s、评估 600s。baseline 的评估只用了 **16 秒**，也就是说 **584 秒的评估预算被白白浪费了**。滑动窗口把它用到 70 秒，还剩 530 秒。

在一个"每一字节、每一秒都要算账"的比赛里，**先去捡地上那 584 秒**，比去啃一个需要重训的架构改动，是更理性的第一步。

### 1.4 一个反直觉但重要的观察

我核对了那条记录的原文：它的 **pre-quant val_bpb 是 1.2196，比 baseline 的 1.2172 还略差一点点**。而 post-quant 却是 1.1925 vs 1.2244。

也就是说：**模型本身一点没变好，分数却好了 0.032。**

这说明 baseline 那个 1.2244 里，有相当一部分根本不是模型的问题，是**测量方式**的问题。我认为这是整个榜单最值得先修的东西。

## 2. 门槛问题二：你怎么知道这个方向有效？

### 2.1 证据来源（可复核，非道听途说）

**证据 A（主证据）—— 官方 repo 记录 `2026-03-19_SlidingWindowEval`**

- 路径：`openai/parameter-golf` → `records/track_10min_16mb/2026-03-19_SlidingWindowEval/`
- 作者：Matthew Li，日期 2026-03-19
- README 原文表格：

| Metric | Naive Baseline | This Submission |
|---|---|---|
| Pre-quant val_bpb | 1.2172 | 1.2196 |
| **Post-quant val_bpb** | **1.2244** | **1.1925** |
| **Improvement** | — | **−0.0319** |
| Eval time (8×H100) | ~16s | 70s |
| Artifact size | 15,863,489 | 15,874,829 |

- README 原文结论句（逐字）：*"The pre-quant BPB is nearly identical (training is the same). The 0.032 improvement comes entirely from scoring tokens with richer context during evaluation."*
- 我核对过它的 `train.log`：`final_int8_zlib_roundtrip_exact val_bpb:1.19250007`，eval 耗时 `69881ms`。数字对得上。

**证据 B —— 官方基线定义 `2026-03-17_NaiveBaseline`**

- `final_int8_zlib_roundtrip_exact val_bpb:1.22436570`，train 600038ms，artifact 15,863,489 bytes。这是 1.2244 的来源，也是我要复现的目标（允许 ±0.005）。

**证据 C —— 规则依据**

- 官方 README「What are the restrictions on evaluation?」原文：*"you're free to evaluate however. As with modded-nanogpt, we allow evaluation at any sequence length."* —— 明确允许自定义评估方式。
- 同一段明确训练 10 分钟与评估 10 分钟是**两个独立上限**（*"This limit is in addition to the 10 minutes of training time allowed!"*）。所以评估侧优化不吃训练预算。

**证据 D —— 这个技巧没被时代淘汰**

- 2026-04-09 当前榜首（1.0810）的 README 里，"Sliding BPP" 一栏仍然是 **1.0827**，TTT 之后才是 1.0810。**滑窗评估今天仍是 SOTA 栈的地基**，不是被弃用的老技巧。我打算在 Level 2 站在它上面。

### 2.2 我自己的机制性解释（不是照抄结论）

光有数字不够，我要能解释"为什么"。我的解释：

语言模型的 BPB 对上下文长度高度敏感，因为自然文本有长程依赖（指代、话题连贯性、专有名词复现）。在 512 平均上下文下，模型被迫用高熵分布去猜；在 960+ 上下文下，大量 token 变成"近乎确定性"的续写。

滑动窗口把被评分 token 的上下文从"均匀分布在 0~1023"变成"全部 ≥960"，等价于把评分分布整体右移。这不是 tricks，这是**把评估条件对齐到训练条件**——本来就该这么做。

**可证伪的推论（我会去验）**：如果我的解释对，那么 `EVAL_STRIDE` 越小（上下文越长），BPB 应该**单调下降**，并且下降曲线应该在 stride 接近 1024（= 满上下文）时趋于饱和。如果 BPB 对 stride 不敏感、或者非单调，说明我的机制解释错了，我会按第 4 节处理。

## 3. 门槛问题三：你打算跑多少次实验？每次看什么指标？$25 怎么花？

### 3.1 预算换算

- 8×H100 SXM ≈ $20/小时 → **$25 ≈ 75 分钟 ≈ 7 次整跑**
- 1×H100 ≈ $2.5/小时 → 环境搭建 / 数据准备 / 冒烟用它，便宜 8 倍

**核心省钱设计：本方案不需要为每个 stride 重训一次。** 同一个 checkpoint 可以做任意多种评估。所以"扫描 4 个 stride"只花 1 次训练的钱。

### 3.2 实验矩阵（按执行顺序）

| # | 实验 | 硬件 | 训练 | 评估 | 看什么 | 预估花费 |
|---|---|---|---|---|---|---|
| E0 | 环境 + 数据校验 | 1×H100 | 0 | — | `fineweb10B_sp1024` 落盘、tokenizer 加载、dataloader 吐 batch 正常 | $2.5 |
| E1 | **baseline 复现** | 8×H100 | 1×600s | stride=1024 | 是否复现 `1.2244 ± 0.005`；artifact < 16MB | $2.0 |
| E2 | **stride 扫描**（复用 E1 的 ckpt） | 8×H100 | 0 | stride ∈ {512, 256, 128, 64} × 4 | BPB vs stride 曲线是否单调；eval 耗时 | $1.0 |
| E3 | **3-seed 确认** | 8×H100 | 3×600s | 最优 stride | 3 seed 均值 ± std，p 值 | $6.0 |
| E4 | 合规自检 | 1×H100 | 0 | — | artifact 字节数、BPB 独立校验器对照、日志完整性 | $1.0 |
| — | **机动 / 失败重试** | — | — | — | — | **$12.5** |

**合计约 $12.5，留一半机动。** 如果 E2 结果异常，我有机动预算做第二轮扫描，不会卡死。

### 3.3 每次跑要看的指标（写进日志，不是只看最终数字）

主指标：
1. **`final_int8_zlib_roundtrip_exact val_bpb`** —— 唯一上榜数字。

对照指标（用来证明增益来源，防止自欺）：
2. **pre-quant val_bpb** —— 必须与 baseline 的 1.2172 基本相同（±0.005）。**如果它变了，说明我不小心改了训练，实验作废。**
3. **val_loss（nats/token）** —— 与 BPB 互相校验。
4. **eval wallclock** —— 硬红线 600s，我的内部目标是 **≤480s**（留 20% buffer）。
5. **artifact bytes** —— 硬红线 16,000,000，内部目标 ≤15,950,000。
6. **train steps / tokens seen** —— 确认训练侧真的没变。

统计口径：3 个独立 seed（0 / 42 / 1234），报 mean ± std；申报改进需满足官方要求 **≥0.005 nats 且 p<0.01**。

### 3.4 我会先修的一个坑

BPB 的分母是**原始 UTF-8 字节数**，不是 token 数。这是这类任务最容易算错、且算错会让分数"虚假变好"的地方。

我会在 E4 里写一个 **~100 行的独立 BPB 校验器**：拿一个常量 n-gram 模型跑同一份 val 集，手工核对字节数口径，确认我的 `val_bpb` 与官方定义一致。**校验器没通过之前，我不会提交任何榜单数字。**

## 4. 门槛问题四：失败怎么办？

我按"最可能失败"排序准备预案。

### 4.1 失败情形 A：BPB 没降，或者降得比 0.032 少很多（概率我认为约 30%）

**第一反应：不怀疑技巧，先怀疑我的尺子。**
- 跑 3.4 的独立校验器。**历史上这类"巨大收益"最常见的真相是字节数口径错了**——比如用 token 数当分母、或者 val 集切片时丢了尾部字节。
- 校验器若发现我算错：**我不会提交**，修正后重跑 E1–E3。我宁可交一个"没提升但正确"的结果，也不交一个"看起来很棒但算错了"的分数。

**第二反应：怀疑 stride 没生效。**
- 检查是不是 `EVAL_BATCH_SEQS` 太大导致窗口被截断、或者窗口边界处理把最右侧 64 个 token 漏了。打 debug 日志确认"被打分 token 总数 == val 集 token 总数"。

### 4.2 失败情形 B：收益只有 −0.005 ~ −0.015，达不到 0.005 nats 的显著性门槛（概率约 20%）

- 说明"上下文长度 → BPB"的弹性比我预期小。这时候：
  1. 扫更激进的 stride（32 / 16），看曲线是否继续下降；
  2. 同时把 `TRAIN_SEQ_LEN` 从 1024 提到 2048 —— 训练侧也变长上下文，让"评估长上下文"有配套的模型能力支撑。**这是我最想试的第二刀**，因为它检验的是另一件事：评估上下文变长后，模型是不是被训练时的短上下文卡住了。
- 结果无论正负都写成报告。

### 4.3 失败情形 C：评估超时（>600s）（概率约 15%）

- 硬红线，必须退让。优先级：**stride 64 → 128 → 256**，同时把 `EVAL_BATCH_SEQS` 从 1024 往上调换取吞吐。
- 如果退到 stride=256 就超时，说明这台机器比榜单机器慢，我会记录机型与实测 tokens/sec，并在报告里标注"本结果在该机型下取得"，不做跨机型硬比。

### 4.4 失败情形 D：完全没收益，甚至变差（概率约 10%）

- 那说明我对"上下文长度是瓶颈"的判断错了。我会：
  1. **保留这次的全部日志和 checkpoint**，写一份 negative result；
  2. 按官方 README「Non-record Submissions」明确鼓励（*"even interesting negative results"*），把"滑动窗口评估在当前配置下无效 + 我测到的 stride-BPB 曲线"提交到 non-record track。一条有曲线的 negative result，比一条没验证过的正result 有价值；
  3. **转向第二优先方向：SP1024 → SP8192 词表升级**（证据：PR #1394 @clarkkev，README 原文 "Increase the vocabulary size from 4096 to 8192"，Δ 约 −0.012）。选它做 Plan B 的理由和主方向一致：**它也是数据/预处理侧改动，不需要重新设计架构，风险可控**；
  4. 在 Level 2 的 RFC 里明确写"主方向失败，转 Plan B，原因如下"。

### 4.5 失败情形 E：收益大得离谱（>0.05）（概率约 5%）

- **这种情况我最警惕，不会庆祝。** 远超历史记录的收益，大概率是 bug 或者违规（比如不小心用了 val 数据、或者单 pass 被破坏成多 pass）。
- 处置：立刻冻结提交，跑合规 4 条（因果性 / 归一化分布 / 先打分后更新 / 单遍）逐条自查，跑独立校验器。**确认干净之前不发 PR。**
