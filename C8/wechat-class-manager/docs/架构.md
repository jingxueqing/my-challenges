# 架构说明

> 一页看懂：数据从哪来、经过什么、最后变成什么，以及几个关键取舍的**理由**。

---

## 1. 三层蛋糕

```
┌───────────────────────────────────────────────────────────────┐
│ Layer 3 · 班级管理 Skills（本项目的 skills/）                  │
│  提交追踪 · Q&A 沉淀 · 学生画像 · 报告 · 查询 · 催办草稿        │
├───────────────────────────────────────────────────────────────┤
│ Layer 2 · Agent 认知层（本项目的 wcm/）                        │
│  分类 → 关联 → 抽取 → 推理（预警/画像）→ 生成（报告/看板）      │
│  这条链就是 KSTAR：看到(S) → 理解(K) → 决定(T) → 执行(A) → 结果(R)│
├───────────────────────────────────────────────────────────────┤
│ Layer 1 · 通道适配（本项目的 wcm/bridge/）                     │
│  replay（JSONL）· chatlog（HTTP）· sqlcipher（直连库）· fs_scan │
│  统一输出 UMF：msg_id / timestamp / sender / type / content    │
└───────────────────────────────────────────────────────────────┘
```

**为什么分三层**：换数据源不该动业务逻辑。现在换群换学期，只改 `config/`；
换取数工具，只加一个 adapter（`ReplaySource` 和 `ChatlogSource` 的接口完全一致）。

---

## 2. 数据流

```
微信群 ─┬─ 本地 DB / 导出 JSONL ──▶ bridge ──▶ messages.jsonl（UMF）
        └─ 磁盘提交包 ─────────────▶ fs_scan ──▶ submissions_fs.json
                                              │
        messages.jsonl ──▶ classifier ──▶ classified.jsonl（意图+置信度+依据）
                       ──▶ linker     ──▶ linked.jsonl（challenge_ref）
                                              │
        linked + submissions_fs ──▶ submissions ──▶ submissions.json（矩阵/缺件）
        linked               ──▶ qa         ──▶ qa.json（问答对+质量分）
        linked+subs+qa       ──▶ profile    ──▶ profiles.json（画像）
        全量                 ──▶ alerts     ──▶ alerts.json（7 条规则）
        全量                 ──▶ report     ──▶ report.md / report.json
        全量                 ──▶ dashboard  ──▶ dashboard/index.html
        全量                 ──▶ ingest     ──▶ graph.db（Property Graph）
```

每一步都落盘成文件，**任何一步都能单独重跑**，也方便对比"我今天改的这条规则影响了多少条"。

## 3. 领域模型（Property Graph）

```
Student ──SENT──▶ Message ──TAGGED_WITH──▶ Challenge
Student ──SUBMITTED──▶ Submission ──ABOUT──▶ Challenge
Student ──ASKED──▶ QAPair ◀──ANSWERED── Student
Student ──MENTORED──▶ Student        （回答关系推断的"谁帮了谁"）
Teacher ──SENT──▶ Message
```

7 类节点 / 7 类边，完整定义在 `schemas/domain-graph.yaml`，实现与 `wcm/ingest.py` 一一对应。

**规模实测**：20 学生 × 20 挑战 + 268 消息 → 7 类节点 400+、702 条边，
`out/graph.db` 约 1MB，全量重建 < 2 秒。

## 4. 关键取舍（这部分是本文档的重点）

### 4.1 存储：SQLite 实现 property graph，而不是 Neo4j

| 方案 | 优点 | 为什么不选 / 选 |
|---|---|---|
| Neo4j | 原生图查询、可视化 | 要装服务、要 Java，交给老师部署就是灾难。**不选** |
| NetworkX + pickle | 上手快 | 每次要全量载入内存，无法增量。**不选** |
| **SQLite：nodes/edges + JSON props** | 零依赖、可增量、可 SQL、能带 FTS5 | **选它**。图语义用 `neighbors()` 包一层，接口和真图库一致 |

代价：多跳查询要自己拼 SQL。目前查询深度 ≤2 跳，够用；真要 5 跳再换后端。

### 4.2 分类：打分规则，而不是纯 LLM

- 268 条消息全量过 LLM ≈ 几十秒 + 费用，而规则是 40ms。
- 更重要的是**可解释**：每条输出带 `signals`，老师能看懂"为什么判成提问"。
- LLM 保留为「低置信度复核」通道（`--llm-review`），只处理 confidence<0.45 的约 20% 消息，
  成本和延迟都可控。

代价：换群要重新校准（已在局限里写明）。

### 4.3 提交判定：以文件为准

群里说"我交了"不算，磁盘上有文件才算。原因很现实：老师验收看的是文件，
系统的口径必须和验收口径一致，否则数字对不上账，工具就没人用了。

### 4.4 关联：显式 ID > 文件名 > 关键词 > 上文继承

四种证据分权重（1.0 / 1.0 / 0.85 / 0.35）。继承的证据单独标记 `link_method=inherited`，
在查询里可以过滤掉——因为"上文在聊 C4B"不等于"这条也在聊 C4B"。

### 4.5 预警：每条必须有 evidence 和 action

没有证据的预警会制造噪音，噪音会让人关掉通知，关掉通知等于系统死了。
所以 `alerts.py` 里每个 `add()` 都强制填 `evidence`（哪几条数据）和 `action`（建议怎么办）。
测试里有一条专门断言"每个预警都有 evidence"。

### 4.6 写回：默认关闭

自动发消息需要登录态或第三方协议，风险落在老师身上；催交又是语气活，机器写容易生硬。
所以只产出草稿（`nudges.md`），发不发、怎么发，人来定。

### 4.7 看板：单文件 HTML，而不是 Web 服务

老师要"打开就能看"，不是"先装环境再 run 服务"。
所有数据和样式内联，零 CDN，断网可开，发到群里对方下载就能看。
这个选择在 C6A 上被真实使用验证过（19 个真实提交包 → 一个 html）。

## 5. 可解释性怎么落地

| 产出 | 可追溯字段 | 例子 |
|---|---|---|
| 分类 | `signals` / `scores` | `["question:问号结尾","question:疑问词 请问"]` |
| 关联 | `link_method` / `link_evidence` | `explicit_id` / `["文本含 C4B"]` |
| 提交 | `artifacts[].file` / `issues` | 具体到文件名与 msg_id |
| 问答 | `evidence.cited_by_reply` | 是引用答的还是时间窗猜的 |
| 预警 | `evidence` | `{"challenge":"C8","days_left":2,"missing":[...]}` |
| 查询 | `evidence`（节点 id 列表） | `["student:wxid_linyz", "challenge:C8"]` |

## 6. 性能与规模

| 操作 | 实测（本机 M 系列 / Python 3.13） |
|---|---|
| 全链路（268 消息 + 20 挑战 + 14 提交包 + 图重建 + 看板） | ≈ 0.9 s |
| 分类 268 条 | ≈ 0.04 s |
| 图全量重建 | < 1 s |
| 查询单次 | < 50 ms |
| 62 个测试 | ≈ 1.1 s |

两个数字值得单独说，因为它们改过：

- **图重建从「偶尔十几秒」变成 0.9 s**：`upsert_node` / `add_edge` 是逐条 commit 的，
  默认配置下重建一次要 ~1100 次 fsync。现在 `journal_mode=MEMORY` + `synchronous=OFF`
  （图是可重建的派生数据，源真相在 `out/*.jsonl`，崩了删掉重跑几秒），
  顺带把「磁盘瞬时 IO 抖动导致整条流水线失败」这个坑填了——本机真踩过一次 `disk I/O error`。
- **`graph.db` 体积封顶**：反复 ingest 会留下空闲页，实测一路涨到 836K；
  现在每次写完 `VACUUM` 一次，全新重建回到 520K。

瓶颈其实在磁盘扫描（235 个文件 stat）和 SQLite 逐条 commit。
上万条消息时把 `upsert_node` 的 commit 改成批量提交即可（已在 `upsert_many` 留了口子）。

## 7. 如果重来，我会改什么

1. **分类器先做标注集再做规则**：我是边写规则边标数据，导致前两轮"改规则→标注跟着动"的返工。正确顺序是先把 100 条标完冻结，再调规则。
2. **提交检测早点和磁盘扫描合并**：一开始只做消息流，结果发现"文件才是真相"，重构了一次 `submissions.py`。
3. **看板先出低保真再美化**：第一版花了太多时间在 CSS，后来发现信息密度不够，又重排了一次布局。
4. **所有"报给人的数字"一律回头查库，不用内存里的计数器**：交付前对账时发现，
   图的边逐类相加 711、总数 702（差的 9 条被唯一索引去重），节点逐类相加 401、实际 402
   （`Teacher` 没进计数字典）。两处都不是算法错，是"汇报口径"和"库里事实"不是一个来源——
   这种数字一旦被拿去写周报，就没人敢信后面的所有数字了。现在改成写完 `SELECT ... GROUP BY type` 回查，并补了测试。
5. **下游动作要自带一道兜底**：分类器把 6 条陈述句判成了提问，直接导致催办草稿里出现
   "某某在群里问：…我自己测是这样"。正确做法不是回去改分类器权重（会牵动另外 267 条），
   而是在"催人回答"这个动作前加 `looks_like_question()`——**上游可以不准，下游不能不加检查就发出去**。

这五条写在 AAR 里，不是自谦，是下次真会这么做。
