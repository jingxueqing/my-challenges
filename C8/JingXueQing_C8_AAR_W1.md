## 三、差值分析

### 完成了什么

- **功能面全通**：L1→L4 每一级的验收点都有可复现的证据（见 `验收记录.md`）。
- **可验证性做到了**：91.8% 有混淆矩阵，44 项提交能追到文件名，702 条边可查。
- **"不做什么"守住了**：没有自动发消息、没有解密微信库、没有上 Neo4j。
- **三个额外产出**（不在 R̂ 里）：`doctor` 自检、`watch` 增量、`nudge` 草稿。

### 没完成什么

1. **真实微信群没接上**（R̂ #11）。这是最伤的一项——C8 的核心要求是"真实"，而我的消息流是合成的。
2. **预警第 7 类（deadline）默认不触发**，要 `--as-of 2026-12-29` 演练。理由：C8 截止 12-31，
   当前 11-04 距离 57 天，规则设计为"临期 3 天才报"。**这在逻辑上是对的，但验收时容易被认为"少一类"。**
3. **部署时间没测**（R̂ #9）。我没有找到第二个人做冷启动。
4. **"运行 1 周真实数据"没做到**（L4 要求）。我用 14 天脱敏回放替代了。

### 意外发现（这些比计划内的收获更有价值）

1. **"以文件为准"这个决定救了整个提交模块。**
   最初我按"消息里说交了"来判，跑出来 7 个人显示"已交但缺件"，
   实际是他们根本没发全文件。改成以磁盘/文件消息为准之后，数字立刻和老师的手工核对一致。
   → **口径错了，功能再全也没人用。**

2. **预警会自己把自己搞死。**
   第一版 41 条预警，同一条规则刷 15 次。我原本以为"多报一点更安全"，
   实际是"吵 → 关掉 → 等于没有"。聚合后 23 条，high 从 19 降到 1。
   → **预警的价值不是覆盖率，是"每条都值得看"。**

3. **我自己的数据脚本破坏了自己的测试场景。**
   给"沉默学生"样例派了填充闲聊，导致 `silent_count = 0`。
   → 造数据时要显式保护负样本，这个坑在真实数据里不会出现，但在演示数据里必然出现。

4. **AI 会给出"听起来对"的错误归因。**
   C8 显示"7 人已交 0 人完整"时，AI 第一反应是"学生没交齐，建议催交"。
   实际是我 config 里 C8 的必备件写错了（`deliverable` 写成 `proposal` 的同义词错误）。
   如果我照它说的去催 7 个人，会在真实场景里得罪人。
   → **原始数据 > 解释。**

## 四、失败分析（诚实版）

### 失败 1：真实微信群没接上

- **哪里失败了**：L1 的 Bronze 验收写的是"从**本地微信数据**中提取 ≥100 条群消息"。
  我做的是"从导出/回放文件中提取"。**这不算完成原意。**
- **根本原因**：WeChat 4.x（macOS）把 `message_*.db` 用 SQLCipher 加密，
  密钥只在微信进程内存里。取出需要 root + `task_for_pid` attach 到运行进程。
  **这不是技术难度问题，是我主动选择不做**——它属于侵入式操作，会碰到全部聊天记录。
- **看起来像根本原因但不是的**：
  - ❌ "chatlog 装不上" → chatlog 我没装，因为即使装了也需要 key，**装不装不是关键**。
  - ❌ "macOS 限制多" → 限制是真的，但 Windows 上一样要解密，只是工具多。
  - ❌ "时间不够" → 时间不是瓶颈，取 key 的风险判断才是。
- **我做了什么替代**：写了 3 条路径（chatlog / 导出回放 / 直连带 key），
  把 `chatlog` adapter 实现完整（代码在，本机未验证），
  并在 `doctor` 里把"本机 64 个 .db，抽样 20 个中 19 个加密"作为可复核证据打印出来。
- **这件事的教训**：**我应该在 proposal 里把"数据可达性"标成一条风险，而不是当成已知条件。**
  我的 R̂ #11 写得像"计划"，其实是"假设"。**没有验证过的假设不该写进 R̂。**

### 失败 2：7 类预警只实测 6 类

- **哪里失败了**：deadline 规则默认不触发，因为 C8 距截止还有 57 天。
- **根本原因**：我把"规则正确"和"场景可复现"混在一起了。
  规则对（临期才报），但验收时看不到它触发，就等于没证明。
- **看起来像但不是**：❌ "规则写错了" → 规则没错，`--as-of 2026-12-29` 一跑就出。
- **修法（已做）**：`alerts --as-of` 参数 + 测试 `test_deadline_rule_fires_near_due_date`
  用构造日期断言它触发。**"能演练"比"能触发"更适合交付。**

### 失败 3：部署时间没验证

- **哪里失败了**：R̂ 说"新人 15 分钟内跑出看板"，但我没有第二个人。
- **根本原因**：单人项目的结构性缺陷——**我无法验证"别人能不能用"**。
- **看起来像但不是**：❌ "README 写得不够清楚" → 可能清楚，只是我没测。
- **下一步**：找一位同学做冷启动，记录他卡住的第一个地方（这比我再写 1000 字文档有用）。

### 失败 4：把 4 周压成 1 天，代价是什么

- **哪里失败了**：R̂ 的 W1–W4 节奏没有真实发生，AAR 只有一份。
- **根本原因**：我按"能连续工作"来排计划，但**压缩掉的不是时间，是"反馈间隔"**。
  W1 做完桥接本该让老师看一眼再往下做，我直接做到 L4。
- **具体代价**：
  - 看板的信息密度返工一次（第一版太空，重排布局）。
  - 分类器调参多花了一轮（因为没有机会先收集真实提问再定标签体系）。
- **如果重来**：**每个 Level 结束时停 2 小时，让别人用一次。** 这不是流程洁癖，
  是因为我这轮所有的大返工（提交口径、预警聚合、看板布局）**都是"没人用"导致的**。

## 六、拿来更新（本周新增参考）

> 课程要求每周 AAR 必须有这一条。我按"发现了什么 → 比原方案好在哪 → 我换了吗"写。

### 本周我发现了 SQLite FTS5，它比我之前的方案（`LIKE '%关键词%'`）更好，因为：

- **中文场景下 LIKE 只能匹配字面子串**，"GitHub 的常见问题" 这种查询会漏掉
  说 "仓库/公开/私有" 但没有出现 "GitHub" 字样的问答；
- FTS5 建虚拟表后按词命中，且**完全在库内，零依赖、零服务**；
- 代价是并非所有 SQLite 编译版本都带 FTS5 → 我做了 `try/except` 退化 + `doctor` 检测。

**已替换**：`wcm/store.py::search()` 优先走 FTS5，缺失时退化 LIKE。

### 本周我评估了 Neo4j 和"LLM 全量分类"，但现有方案仍然是最优的，因为：

| 候选 | 更好的地方 | 为什么仍不换 |
|---|---|---|
| Neo4j 原生图 | 多跳查询、可视化强 | 我的图 400 格 / 702 边，SQLite 全量重建 <2 秒；换 Neo4j 等于让老师装 JVM——**部署成本 > 查询收益** |
| LLM 全量分类 | 泛化好、不用调规则 | 268 条全量调用慢且不可解释；我保留它做低置信度复核（约 20% 消息），成本可控且能补规则的短板 |

**这个"评估后不换"的记录本身也是证据**：说明我在持续检索，而不是方案定了就不再看。

## 八、我学到的（能迁移的）

1. **口径 > 功能**：提交判定那次返工，让我以后先问"验收的人怎么判"，再写逻辑。
2. **噪音是功能的一部分**：预警不是越多越好，是"每条都值得看"。
3. **可演练 > 可触发**：看不到效果的规则，等于没写。
4. **交付物要写"不做什么"**：三个"不"（不自动发、不解密、不评质量）
   让这个系统敢给别人用。
5. **别信"听起来对"的解释**：AI 的归因和我自己的直觉都要拿原始数据校验。

**迁移场景**：下一份工作里任何"从消息流/日志流里提取状态"的系统都用得上这套
—— 尤其是"以事实（文件/事件）为准，以描述（消息）为辅"这条。
