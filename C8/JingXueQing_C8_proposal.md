#### 我对这个领域的理解

班级管理的真实痛点不是"信息不够"，而是**信息都在，但取不出来**：

1. **提交追踪**：老师说"我翻群文件翻了半小时"——不是没交，是找不到。
2. **参与度**：C3 要求"高质量参与"，但"谁在参与"目前靠印象，无法举证，学生也不服。
3. **问答沉淀**：好问题三天后沉底，同一个问题一学期被问 11 次。
4. **通知确认**：发了通知，不知道谁看、谁动。

而这四件事的共同点是：**微信里全都有，只是以消息流的形式存在。**
所以正确做法不是"再做一个新平台"（没人会用），而是**在消息流上加一层可查询、可追踪、可行动的结构化层**。

这也是我对"数字孪生"落地这件事的理解：孪生的前提不是建模技术，
而是**能持续、低成本地把现实状态同步进模型**。微信群就是这个班级的传感器，
缺的只是采集端和一层本体。

### 拿来的部分（直接复用）

**1. chatlog 的"HTTP API 暴露本地数据"这个形态。**
它解决了一个关键矛盾：Agent 需要一个稳定的数据接口，而微信数据在加密库里。
chatlog 把"解密 + 查询"封成一个本地 HTTP 服务，我的 `ChatlogSource` 只写了一个 30 行的 HTTP 客户端，
就拿到了数据流。**这个设计让我不需要碰解密逻辑。**

**2. wechat-cli 的 CLI 参数形状。**
`--group / --days / --output` 这三个参数直接照搬。理由是课程验收命令就是
`python wechat_bridge.py --group "Elite20" --days 7 --output messages.jsonl`，
**接口对齐验收标准，比接口"设计得优雅"重要**。

**3. C6A 的管线骨架。**
C6A 是 `扫描 → 归一 → 计算 → 出 dashboard + xlsx + 日报`。这次是
`桥接 → 分类 → 关联 → 矩阵 → 画像 → 预警 → 报告 + 看板`。
同构，所以我直接把"每步落盘、可单独重跑"的做法搬过来。

**4. C4A 的"每条判定可追溯"。**
C4A 里我要求每条评审结论能追到源文件行号，这次变成每个分类结果带 `signals`、
每个预警带 `evidence`、每个查询答案带 `evidence` 节点 id。

**5. SQLite FTS5 做检索。**
"关于 GitHub 的常见问题有哪些"这类问题，用 `LIKE '%GitHub%'` 会漏（分词问题），
FTS5 建一个虚拟表就能查，而且**零服务、零依赖**。

**6. KSTAR 与三层分层的骨架。**
Layer1 通道 / Layer2 认知 / Layer3 技能，不是我发明的，是课程材料里的 P3394 术语。
我把它落成目录结构：`wcm/bridge/` · `wcm/*.py` · `skills/`。

### 修改 / 删除 / 重构的部分

#### 我准备去掉的

| 去掉什么 | 原因 |
|---|---|
| **wetrace 的取证思路**（全量导出、证据链签名） | 一个班级管理场景不需要司法级完整性，反而把 1.5GB 数据全量搬运是浪费。**按需取最近 N 天**才对。 |
| **chatlog 的 TUI** | 老师不会用 TUI。我只要它的 API，人机界面用看板。 |
| **Neo4j / Memgraph** | 课程建议"Platinum 用原生图查询"，但 20 学生 × 20 挑战 = 400 格的规模，装 Neo4j 是给老师增加部署负担。**用 SQLite 模拟 property graph，接口保持图语义**（换后端只改一个类）。 |
| **LLM 全量分类** | 268 条消息全过 LLM：慢、贵、且不可解释。课程允许"规则/LLM/混合"，我选**规则 + 上下文，LLM 只复核低置信度 20%**。 |
| **自动写回群**（双向通道） | 需要登录态或第三方协议，风险落在老师身上；催交又是语气活。**只出草稿，人决定发不发**。 |

#### 我准备重构的

| 重构什么 | 怎么改 | 原因 |
|---|---|---|
| **提交判定逻辑** | 从"看消息里有没有说交了" 改为 **"以磁盘文件为准，消息只补时间线"** | 重构前：老师问"某某交了吗"，系统说"他说交了"，但文件不在。**口径必须和验收口径一致**，否则数字对不上账就没人用了。这是我在 Day 3 推倒重来的一次。 |
| **分类器从 if-else 改为打分** | 每个意图独立累计证据分数，取最大 | if-else 的判定顺序会变成隐形优先级，改一条规则经常把别的类改坏。打分制加规则时影响面可控，且天然产出"凭什么"的说明。 |
| **预警从"每规则一条"改为可聚合** | 提交率过低规则聚合为一条，列出所有挑战 | 第一版跑了 41 条预警，同一条规则刷了 15 条——老师说"这东西太吵了我就关了"。**噪音会杀死系统**。 |
| **看板从 Web 服务改为单文件 HTML** | 数据与样式内联，零 CDN | 老师要的是"双击打开"，不是"先装环境再 run"。C6A 已经验证过这个选择。 |

#### 我准备新增的

| 新增什么 | 为什么必须做 |
|---|---|
| **四路 adapter（replay / chatlog / sqlcipher / fs_scan）** | 换一台机器、换一个群、换一个人接手，取数方式就不同。把取数和标准化拆开，下游一行不改。 |
| **脱敏回放集 + 人工标注（268 条）** | 团队评审和 CI 不能碰真实聊天记录；而且没有标注集，准确率就是嘴说的。 |
| **`doctor` 环境自检** | 交付给别人时，"为什么你这里能跑我这里不能"是最贵的问题。自检把答案写在第一屏。 |
| **`watch` 增量 + checkpoint** | 每次全量重跑会把"本周新增"的统计和告警搞乱。第二次运行必须返回 `new: 0`，这条有测试守着。 |
| **`nudge` 草稿（默认不发送）** | 系统发现问题 ≠ 系统该去说话。草稿让人保留语气和判断权。 |

### 创造性组合：三个来源拼出来一个来源给不了的东西

```
chatlog  →  我能拿到数据（但只有原始消息）
C4A      →  我知道怎么"可追溯地判定"（但没有班级语义）
C6A      →  我知道怎么把数据变成看板（但数据是静态扫描）
NEOLAF   →  上层骨架：Channel → Agent Runtime → Skill
───────────────────────────────────────────────
组合结果：一个"能持续读群、能判定提交、能解释每个判定、能自己发现异常"的闭环
```

单独任何一个都做不出：chatlog 没有语义，C4A 没有数据源，C6A 没有实时性。
**C8 的"组装"就发生在这里。**

### S（Situation）：当前问题是什么

**现状**：一个 20 人的课程群，14 天 268 条消息、74 个文件。
提交靠老师翻群文件；参与度靠印象；问答沉底；通知发了不知道谁动。

**痛点**（按老师原话排序）：

1. "我翻了半小时群文件，还是不确定谁没交。"
2. "C3 要评参与度，我只能凭印象打分，学生不服。"
3. "同一个问题被问 11 次。"
4. "文件命名五花八门，归档要手工改名。"

**约束条件**：

| 约束 | 影响 |
|---|---|
| 本机微信库 SQLCipher 加密（实测 `message_0.db` 头为 `bc00 2ab8…`，非 `SQLite format 3`） | 真实群消息**接不进来**，必须走导出/回放，且要诚实标注 |
| 老师电脑不能装服务、不能联网 | 交付物必须零依赖、离线可用 |
| 单人开发、非全职 | 优先做"能验收的最小闭环"，不做炫技功能 |
| 数据隐私 | 不能上传任何真实聊天记录 |
| 群规模 20 人、挑战 20 个 | 图库选型不需要 Neo4j |

谁没交 / 谁需要关注 / 这个问题以前怎么答的 / 这周班级什么状态，
并且**每个数字都能点回证据**。

**子任务分解**：

| **Week 1** | 数据桥接（4 个 adapter）+ UMF schema + 脱敏回放集与标注 | ≥100 条消息入库，字段可追溯，CLI 可重复运行 |
| **Week 2** | 分类器 + 挑战关联 + 提交检测 + Q&A 抽取 | 准确率 >70%，≥5 个提交事件，≥10 组问答 |
