## 一、我的判定标准（先立规矩，再选来源）

拿之前我先定了五条筛子，任何来源过不了就不进项目：

| 标准 | 问题 | 为什么重要 |

## 三、逐个说清（拿什么 / 不拿什么 / 为什么）

### 1. sjzar/chatlog —— ✅ 采用为取数路径

**拿什么**：
- **形态**：把"解密 + 查询本地库"封成一个**本地 HTTP 服务**，Agent 通过 HTTP 取数据。
- **思路**：不要求调用方理解 SQLCipher 的表结构，只暴露"按会话、按时间取消息"。

**不拿什么**：
- **TUI**：老师不会用终端界面。人机界面我用看板（`dashboard/index.html`）。
- **全量导出**：一个班级管理场景不需要把 1.5GB 数据全搬一遍，按需取最近 N 天。

**为什么**：它解决了这个项目最硬的那道墙——**我不需要碰解密逻辑**。
我的 `ChatlogSource` 只有约 40 行（HTTP 客户端 + 按天切片 + 去重），
就把"加密库"变成了"可查询的数据源"。这是整个 L1 能成立的前提。

**实现位置**：`wcm/bridge/sources.py::ChatlogSource`
**当前状态**：代码完成，**本机未跑通**（未安装 chatlog / 微信库加密），已如实标注在 README 与 `docs/数据说明.md`。

---

### 2. freestylefly/wechat-cli —— ✅ 采用接口形状

**拿什么**：
- **CLI 参数形状**：`--group / --days / --output`。
- **输出策略**：JSON Lines，一行一条，方便管道。

**不拿什么**：
- 它的内部实现（我只需要"取到数据"这个能力，不需要重写它的解析）。
- 它的 Python 依赖栈（我的目标是零依赖）。

**为什么**：课程 L1 的验收命令就是
`python wechat_bridge.py --group "Elite20" --days 7 --output messages.jsonl`。
**接口对齐验收标准，比接口"设计得漂亮"重要。** 我照抄这三个参数名，验收时不用解释。

---

### 3. afumu/wetrace —— ❌ 否掉

**为什么否**：
1. **平台**：仅 Windows，我的交付环境是 macOS。
2. **思路不匹配**：取证级的核心价值是"证据链完整、可公证"，代价是重、慢、全量。
   班级管理的核心价值是"每天几分钟内知道谁没交"。**目标不同，工具就不该复用。**
3. 过不了我自己的标准 ①（平台）和 ②（成本）。

**但它的思路我留下了一条**：导出要保留"原始消息 id"。
所以我的 UMF 强制要求 `msg_id`，并保留 `raw_type` 原始类型字段——
出问题时能回到微信原始数据核对。

---

### 4. JettChenT/wechat-exporter —— ⚠️ 只当备份方案

**拿什么**：macOS 上"一次性导出"的可行性判断（证明这条路走得通）。
**不拿什么**：作为主路径。**因为它不能增量**——每天重新导一次全量，Watcher 就没意义了。

**为什么保留在备选**：如果哪天 chatlog 挂了，至少有一条能让系统继续跑的路径。
这就是我在 README 里写"三条路（chatlog / 导出 / 直连）"的原因——**交付要给退路。**

---

### 5. SQLite FTS5 —— ✅ 采用

**拿什么**：
- `CREATE VIRTUAL TABLE ... USING fts5(...)` 做消息与问答的全文检索。

**为什么需要**：
"关于 GitHub 的常见问题有哪些"这类查询，用 `LIKE '%GitHub%'` 只能匹配字面，
中文分词更是问题；FTS5 建虚拟表就能按词命中，而且**零服务、零依赖**（数据库自带）。

**不拿什么**：外部分词器（ICU 等）。中文场景我的替代方案是：
先按挑战 ID / 关键词过滤（结构化），再在候选集里做 FTS，够用。

**代价（诚实记录）**：FTS5 不是所有 SQLite 编译版本都有。
所以 `store.py` 里做了 `try/except`，**没有 FTS5 时自动退化为 LIKE 查询**，
功能不中断、只是检索质量下降。`doctor` 会把 FTS5 是否可用打印出来。

### 6. Neo4j Property Graph Model —— ✅ 采用模型，不采用引擎

**拿什么**：
- **概念模型**：节点（带类型和属性）+ 有向边（带类型和属性）。
  我的领域模型 `Student / Challenge / Submission / Message / QAPair / Report` 与
  7 类边 `SENT / TAGGED_WITH / SUBMITTED / ABOUT / ASKED / ANSWERED / MENTORED` 就是这套。
- **查询语义**：`neighbors(id, edge_type, direction)`。

**不拿什么**：
- **Neo4j 引擎本身**。课程材料建议 Platinum 用原生图库，我否了。

**为什么否（这是本项目最重要的一个取舍）**：

| | Neo4j | SQLite 模拟 |
|---|---|---|
| 部署 | 要装服务、要 JVM | 一个文件 |
| 老师能不能装 | 不能 | 能 |
| 我的规模 | 20×20 = 400 格 | 400 格 |
| 多跳查询 | 原生强 | 要拼 SQL |

**规模不需要，部署成本却是硬约束。** 所以实现方式是
`nodes(id, type, props JSON)` + `edges(type, src, dst, props)` 两张表 + FTS5 索引，
**外面包一层图语义接口**（`wcm/store.py::GraphStore`）。
真要换 Neo4j，只改这一个类，上层 12 个模块一行不动。

**放弃它的条件**（写下来，避免以后凭感觉）：图规模超过万级节点，或需要 5 跳以上路径查询。

### 7. 我自己的 C6A / C4A —— ✅ 结构性复用

这两份是我自己前两个挑战的交付物，属于"拿自己的"。

**从 C6A（提交数据仪表盘）拿的**：

| 拿什么 | 用在哪 |
|---|---|
| `扫描 → 归一 → 计算 → 出 dashboard + 报告` 的管线骨架 | `wcm/cli.py::run_pipeline` 的 12 步 |
| **每步落盘、可单独重跑** | 每个模块都有独立 CLI（`classifier.py` / `submission_detector.py` …） |
| **口径写在页面上** | 看板页脚、周报第八节 |
| 单文件零依赖看板 | `dashboard/index.html` |

**从 C4A（技能提交自动评审）拿的**：

| 拿什么 | 用在哪 |
|---|---|
| **每条判定可追溯到源** | 分类的 `signals`、预警的 `evidence`、查询的 `evidence` 节点 |
| **准确率是测出来的** | `out/metrics.json` 的混淆矩阵，不是形容词 |
| **自检报告** | `python3 -m wcm.cli doctor` |

**不拿什么**：C6A 依赖 `openpyxl` 出 Excel。这次我不出 Excel——看板 + JSON 已够，
少一个依赖就少一个装不上的理由。

### 8. NEOLAF KSTAR / P3394 —— ✅ 当骨架

**拿什么**：
- **三层分层**（Channel → Agent Runtime → Skill）→ 落成目录 `wcm/bridge/` · `wcm/` · `skills/`。
- **KSTAR 循环** → 落成数据流：
  `S`（消息流）→ `K`（分类/关联/图）→ `T`（预警规则/查询意图）→ `A`（报告/看板/草稿）→ `R`（AAR 对比）。

**不拿什么**：不做"形式上的 KSTAR 标注"。我在代码里不写注释说"这里是 K 步"——
概念是给人看的，代码是给机器跑的，混在一起两边都不讨好。

## 四、我没拿的（以及为什么）

| 没拿什么 | 为什么 |
|---|---|
| **PyYAML** | 违反零依赖。改自己写 130 行 YAML 子集解析器（`wcm/yamlite.py`），代价可控 |
| **Neo4j / Memgraph** | 见上，部署成本 > 收益 |
| **LangChain / LlamaIndex** | 本项目没有"链式 LLM 调用"的需求。引入框架只为调一个可选的 LLM 接口，不划算 |
| **Wechaty（自动回复/群发）** | 合规风险 + 语气风险。改成"只出草稿"（`nudge.py`） |
| **现成的 LLM 分类 API** | 268 条全量调用：慢、贵、不可解释。改成规则 + 低置信度复核 |
| **Jupyter / Streamlit** | 交付对象是老师，不是我自己。要能双击打开的东西 |
| **Excel 输出（C6A 的做法）** | 少一个依赖。要看表就用 JSON + 看板 |

## 五、拿来的比例（诚实估算）

| 类别 | 占比 | 说明 |
|---|---|---|
| 直接复用（代码/形态） | ~15% | adapter 形态、CLI 参数、FTS5 用法、管线骨架 |
| 改造后使用 | ~30% | 提交判定（改成以文件为准）、预警（改成聚合）、分类器（改成打分） |
| 自己写 | ~55% | 领域模型、7 条预警规则、参与分口径、查询路由、看板、回放集与标注、62 个测试 |

**这个比例我不打算美化。** 拿来的部分让我少走弯路（尤其是 chatlog 的形态），
但真正让这个系统能用的是那些"没有现成可拿"的部分：
**口径、阈值、噪音控制、以及"哪些东西不该做"的判断。**
