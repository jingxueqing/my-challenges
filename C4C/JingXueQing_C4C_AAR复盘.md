## 二、三个关键失败（详细复盘）

### 失败 1：`dsolve` 返回了"形式完美但错误"的解

**现象**：`y' + 2y = 0` 求解结果为 `y = C₁ - 2xy`

**为什么危险**：

```
y = C₁ - 2xy  ⟹  y(1+2x) = C₁  ⟹  y = C₁/(1+2x)
代回：y' + 2y = 4C₁x/(1+2x)²  ≠ 0
```

这个答案：
- ✅ 由**可信的符号引擎**（sympy `dsolve`）产出
- ✅ 步骤完整、格式正确
- ✅ LaTeX 排版正常
- ❌ **数学上是错的**

**根因**（两层）：

1. 我用 `re.search(r"y(\'\'\')?\s*=\s*(...)")` 抓方程，
   对 `y'' + y = 0` 会匹配到**末尾的 `y = 0`**
2. 修正后，`_fix_implicit_mul()` 与 `y→y(x)` 替换的**顺序**颠倒，
   导致 `2y` 中的 `y` 没被替换，方程退化成 `Eq(2*y + Derivative(y(x),x), 0)`

**我的应对**：写了个临时脚本手工验证：

```python
yexpr = C1/(1+2*x)
simplify(diff(yexpr,x) + 2*yexpr)   # → 4*C_1*x/(2*x+1)**2
```

**由此催生了 `verify.py` 模块**——这是本次最有价值的副产品。

> **反思**：我最初的反应是"结果出来了，格式也对，应该没问题"。
> 但"看起来对"和"实际对"之间，往往隔着一行验证代码。

### 失败 2：物理题"顺序猜测"的翻车

**现象**：

```
题面：一质量为 2 kg 的物体受合力 10 N，求加速度
初版输出：a = 1/5 m/s² = 0.2 m/s²      ❌
正确答案：a = 5 m/s²
```

**为什么这个bug 比失败 1 更隐蔽**：

| 检查项 | 初版答案 | 是否暴露问题 |
|--------|---------|------------|
| 步骤完整性 | 写出了 F=2, m=10 | ❌ 看起来完整 |
| 单位 | m/s² | ❌ 正确 |
| 量纲 | kg·m/s² | ❌ 相容 |
| 求解过程 | F/m = 2/10 | ❌ 逻辑清晰 |
| **数值** | 0.2 | **全错** |

人工抽查时，这个答案看起来**非常专业**。

**根因**：我最初的设计是"按数字出现顺序取数 + 单位反推物理量"。
这在测试时碰巧能过（我特意让测试数据的顺序和语义一致），
但一旦题目顺序变化就全错。

**修复**：改为**标签锚定**——只有当数字旁能找到所属物理量的名称
（`质量为 2 kg` / `F = 10 N` / `q_1 = 2 C`）才采用，
并显式校验"变量名↔单位"相容性。

```python
_NAME_UNIT_OK = {
    "h": {"m"}, "g": {"m/s^2"}, "F": {"N"}, ...
}
```

> **反思**：这是**测试设计缺陷**导致的假绿灯。
> 我造的测试数据恰好符合我实现里的隐含假设，
> 于是测试通过了，能力却是假的。
>
> **教训**：造测试数据时，要刻意**违背**实现的隐含假设。

### 失败 3：线性相关性结论完全错误（最严重）

**现象**：程序输出"线性无关"，正确答案是"线性相关"。

**根因**：`find_matrix_rows()` 用 `re.search` 只返回**第一个** bmatrix。
题面给的是三个向量 v1, v2, v3，但函数只匹配到 v1（3×1），于是：

```
rank = 1
向量数 = min(rows, cols) = min(3, 1) = 1     ← 错在这里
判定：rank == 向量数 → "线性无关"
```

**为什么所有防线都没拦住**：

| 防线 | 表现 | 为什么没拦住 |
|------|------|-------------|
| 符号引擎 | ✅ 正常返回 | 它只是忠实执行我给的错误输入 |
| 解题步骤 | ✅ 完整 | 步骤基于同样的错误前提 |
| 求解器验证 | ✅ pass | 验证检查的是"rank 与向量数一致"，而两者**都错** |
| 单元测试 | ✅ 全绿 | 测试里没有这个题型 |
| PDF 渲染 | ✅ 正常 | 排版不关心对错 |

**唯一发现它的方式**：我**手算了一遍 det(A)**。

**修复过程中还连带发现两个 bug**：
1. `_all_text()` 把 text 与 math_expressions **重复拼接**，
   导致向量数从 3 变6（第一版修复后仍然错）
2. nullspace 组合的索引写错，`dot product (6,1),(3,1)` 维度不匹配

**最终修复后**：

```
以各向量为列构成 3×3 矩阵（共 3 个向量）
rank(A) = 2
秩 2 < 向量个数 3 ⟹ 线性相关    （det A = 0）
例如存在非平凡线性组合 -2·v1 + 1·v2 + 0·v3 = 0
```

### 由此新增的两道防线

**防线 1：结论断言**（不只是断言"解出来了"）

```python
_ANSWER_ASSERT = [("P12", "线性相关")]
# 测试时断言答案必须包含"线性相关"这个关键词
```

**防线 2：见证组合验证**（判"相关"必须给出证据）

```python
# 判定为相关时，必须能给出非平凡零组合
ns = A2.nullspace()
has_witness = bool(ns) and any(simplify(c) != 0 for c in ns[0])
verdict_ok = indep or has_witness
```

> **最大的反思**：
>
> 我建立了一整套验证体系，却漏掉了"验证自己"。
> 那句 `验证 pass` 给我的虚假安全感，比没有验证更危险——
> 因为它让我**降低了警惕**。
>
> **教训**：
> **验证模块本身也需要被验证。**
> 一个从未被挑战过的检查员，等于没有检查员。

复盘不能只讲失败。以下几件事我认为值得保留：

如果基线复现不出来，说明 starter 的数字不可信，

### 3.2 环境探测放在最前面

10 分钟的`which` / `curl` 探测，让我提前 4 小时发现"PDF 出不来"这个架构级约束。

### 3.3 保留 starter 原文件，一行未改

好处：

- 基线可复现（这是"不退化"论证的基础）
- 体现"拿来主义"而非"推倒重来"

### 3.4 负例测试是刻意的设计

我的测试里有3 道"看起来该支持但确实不支持"的题：

```python
("N1", "一个物体的加速度是多少？", False),
("N2", "求方程 x²+1=0 的解。", False),

```

它们的作用是**守住"诚实失败"这条底线**。
如果只有正例，系统可能悄悄输出错误答案而没人发现。

### 3.5 拒绝伪造数据

本机没有 API key，我就写"未真实调用"，
而不是把符号引擎的结果包装成"模型解出的"。

`local` 后端不伪装成模型，明确标注 `degraded=True`。

P9 库仑定律没有实现验证，就标 `unverified`，不冒充 pass。

> 学术诚信的底线是：**报告里出现的每个数字，都能在日志里找到出处**。

## 四、改进方案（具体可执行）

| 序| 改进项 | 具体做法 | 优先级 |
|----|--------|---------|--------|
| 1 | **验证模块自身被验证** | 每条验证规则写正例+反例；断言"验证能抓到反例" | 🔴 高 |
| 2 | **人工答案回归集** | 建 30-50 题的 gold-standard 集，每轮 CI 回归对比 | 🔴 高 |
| 3 | **测试数据反直觉化** | 造测试时刻意违背实现的隐含假设（如交换题目中的数据顺序） | 🔴 高 |
| 4 | **目视检查前移** | 每个阶段都可导出 PNG，不等到最后 | 🟡 中 |
| 5 | **路由关键词可观测** | 把"为何路由到某引擎"的原因输出，便于发现漏判 | 🟡 中 |
| 6 | **补库仑定律量纲验证** | P9 现在是 unverified | 🟡 中 |
| 7 | **接入真实 API key** | api 后端代码完整但未真实验证 | 🟡 中 |
| 8 | **P12 路由漏判** | 分段函数极限被路由到 LLM 而非 starter 微积分内核 | 🟢 低 |
| 9 | **图形自动生成** | matplotlib 绘图（CHALLENGE Level 4 要求） | 🟢 低 |
| 10 | **拉普拉斯变换法** | `known_limitations` 已声明 | 🟢 低 |

### 关于第 8 项的补充

P12 是分段函数极限，属于 starter 微积分内核的能力，
但因为路由关键词表里没匹配到，被路由到 LLM 路径导致失败。

**这说明路由关键词表有漏网**。改进方向：
不是继续加关键词（会越来越脆弱），而是**改用问题类型分类**——
starter 的 `parse_problems.py` 已经能给type（limit/tangent/calculation），
应该让 `type` 优先于关键词匹配。

## 五、这个项目让我学到什么

### 5.1 关于技术

**排版类 bug 只有看图才能发现，逻辑类 bug 只有手算才能发现。**

我统计过 9 个 bug 的发现方式：

| 发现方式 | 数量 |
|---------|------|
| 跑单元测试 | 5 |
| 看 PDF 图片 | 3 |
| 人工手算 | 1 |

**测试通过率 100% 不等于能力正确。**
测试只能证明"代码按我以为的方式运行"，不能证明"方式是对的"。

### 5.2 关于 AI协作

AI 擅长的是：快速生成候选实现、穷举边界情况、把想法变成可运行代码。

AI 不擅长的是：
- **判断结果对不对**（它会把 `y = C₁-2xy` 当成正确解）
- **怀疑自己的设计**（"按顺序取数"这种直觉做法它不会主动质疑）
- **看图**（它不会自己去看排版好不好看）

所以人必须做的是：**不满足于"看起来对"**。

### 5.3 关于学术诚信

我在文档里做了大量"如实标注"：
- 未调用真实 API → 写明未调用
- 无验证项 → 标 unverified
- 自编作业 → 声明不是官方原件

这些标注**会让我的数字看起来没那么漂亮**
（83.3% 而非100%，9项验证而非 12 项），
但它是唯一正确的做法。

**一份注水的报告，失去的是全部可信度。**
