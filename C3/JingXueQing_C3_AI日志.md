## 1. 第一步不是写发言稿，是划一条不能越的线

C3 的红线写得很硬：**「参与记录造假 → 参与质量 0 分」**。

所以开工第一件事是找「到底有没有真实群聊记录」。找过的地方：

```text
【实测】
$ ls ~/Desktop/我的挑战/挑战_C3*/                 # 只有四个挑战配置文件
$ find ~/Desktop ~/Documents ~/Downloads -maxdepth 3 \
    \( -iname "*群*" -o -iname "*提问*" -o -iname "*讨论*" -o -iname "*参与*" \)
  → 命中的全是交付目录里的 README，没有一条聊天原文
$ 检索历史会话（找「在群里发了什么」）
  → 只有两条与群聊无关的工作会话
```

**中途有一条很诱人的岔路**：C8 交付里有一套 268 条的群消息数据集
（`wechat-class-manager/data/fixtures/messages_raw.jsonl`），21 个发言人、268 条标注、字段齐全。

拿它当「我的群内发言」，这份交付物会好写十倍：有时间线、有 @、有来有回。

**但那个数据集自己的 metadata 里写着一句话**：

```json
"note": "合成脱敏数据集：人名除景雪晴外均为合成，消息内容为课程真实场景手写，用于复现与验收。"
```

【需本人确认】这是整份交付物最关键的一个岔路口。AI 的倾向很明确：
**用合成数据证明「我参与了」，比不交更糟**——它不只是假，还精心伪造了证据链的样子。

所以方案改成：把 C3 拆成「能证明的部分」和「只有群聊能证明的部分」，前者做满，后者留空 + 3 分钟回填流程。
如果本人认为「先在群里发出、再回填」更好，本包的 `02_群内发帖包/` 和 `04_群聊原文_待补/` 就是为那条路准备的。

## 2. 真实迭代轮次（8 轮，含 4 次自我打脸）

### R1 · 把「参与」翻译成可检验的东西

最初的思路是写三篇「参与感想」。写到一半 AI 自己否了：感想没有对错，也没有「推动」可言，
而 rubric 里 participationQuality 的第一条信号是「提问/回复有推动力」。

【需本人确认】改成：**三份「可发出的发言稿」+ 每份的自我审查 + 每份引用的技术事实必须能翻到具体行**。
这样评分点从「写得好不好」变成「能不能被验证」，而后者 AI 可以自己先验一遍。

### R2 · 第一次打脸：检查器把废话判成了 8 分

【工具产出】`ask_checker.py` v1.0 第一次跑的原样输出：

```text
bad_01_甩问题.txt              8 分   ← 原文只有「这个报错了怎么办」
bad_02_纯表情灌水.txt           0 分
bad_03_有报错没上下文.txt        8 分
good_01_C4D_ollama_cpu.txt     75 分  ← 自己认为写得最完整的一条
good_02_C4B_依赖缺失.txt         59 分
good_03_C4A_给同学补件建议.txt    59 分
```

两个方向同时错：

| 错在哪 | 具体 | 根因 |
|---|---|---|
| 给废话送分 | 「这个报错了怎么办」里的「报错」二字，被正则当成「提供了报错」 | 把**「提到问题」和「提供证据」混成同一个信号** |
| 给好问题扣分 | 稿子里明明写了「慢到不能用」「我以为…实际…」，一格都没识别 | 词表只有「很慢」「实际是」，**太字面** |

**这次打脸的价值大于后面所有修正**：它说明「靠词表判质量」这件事本身是脆的。
于是没有去调阈值（把通过线从 85 降到 75 就全过了），而是改评分结构。

### R3 · 结构性修：把「宽泛措辞」关进笼子

【实测】改了 6 处：

| # | 改动 | 解决什么 |
|---|---|---|
| 1 | 「真实报错」只认具体错误串（`Traceback` / `ModuleNotFoundError` / `4xx` / `timeout`…），**删掉「报错」「失败」两个词** | 堵住 bad_01 的假分 |
| 2 | 加「门控」：只有正文出现代码块，宽泛的「报错/失败/崩」才算数 | 保留「贴了日志但措辞随意」的合理情况 |
| 3 | 现象词表加 `慢到` / `起不来` / `跑不通` / `崩了` | 修 good_01 被扣分 |
| 4 | 预期词表加 `我以为` / `原以为` / `实际看` | 同上 |
| 5 | 已尝试词表加 `换了` / `跑通` / `我(没|不)敢` | 修 good_02 |
| 6 | 阶段词表加 `昨晚` / `刚刚` / `第 N 次` | 修 good_03 |

【实测】改完再跑：

```text
bad_01  0    bad_02  0    bad_03  8
good_01 100  good_02 67   good_03 67
```

坏样本压下去了，但**好样本只到 67**。这次的 67 不是工具的错，是稿子真的缺东西：
good_02 没写「我以为会怎样」，good_03 没写「排除了什么」。

这里有个分歧点当时摆着：把通过线调低到 67，样本立刻「全过」，看起来很漂亮。

【需本人确认】AI 的取向是**不改阈值、改稿子**。理由：阈值一松，工具就不再约束任何东西，
后面每一稿都会往 67 靠。改完稿子后测得的 100 / 92 / 84 才是真实水平。

### R4 · 第二次打脸：`evidence_lint` 放过了我的弱引用

写参与记录时，「该不该 pip install」这条引用了 C7 日志的 `L111`。校验器跑出来：

```text
✅ JingXueQing_C3_参与记录.md:128 → JingXueQing_C7_AI日志.md:L111
     ### R4 · 第二次打脸：环境依赖缺失
```

**它「通过」了，但那行是标题，不是证据。** 真正的证据在 9 行之后。

【实测】改成 `L120` 后重跑：

```text
✅ JingXueQing_C3_参与记录.md:128 → JingXueQing_C7_AI日志.md:L120
     我没有去 `pip install`（那会污染系统环境，而且 C4B 那次我就在自己的技能里明确禁止了自动装依赖）。
```

【需本人确认】这件事的结论：**自动校验只能保证「行存在」，保证不了「这行是证据」。**
所以工具里没有加「语义相关性打分」（那只会多一个不可靠的裁判），
而是让它**把原文打印出来**——机器负责打开，人负责看一眼。这是本次最重要的一条人机分工。

### R5 · 写 14 条测试，其中 3 条是反向验证

普通测试是「好的要过」。这次专门写了三条反着来的：

| 测试 | 它防什么 |
|---|---|
| `test_vague_complaint_gets_no_error_credit` | 「这个报错了怎么办」**必须拿不到**报错分（防 R2 的假分复发） |
| `test_bare_word_needs_codeblock` | 同一句话，加了代码块才给分（验证门控真的生效） |
| `test_short_but_real_is_not_slack` | 短 ≠ 水：一句带真实报错的短句不能被判灌水 |

【实测】

```text
$ python3 tests/test_ask_checker.py -v
Ran 14 tests in 0.762s
OK
```

一个设计细节：`test_floors` 给三条好稿设的是**分数地板**（95 / 85 / 80），不是「== 100」。
因为 `== 100` 会逼着为了测试把稿子写满；地板的意思是「以后改规则，不许把这些稿子判低」。

### R6 · 决定留空，而不是补一句「助教回复了我」

写到「群内互动被至少 1 位同学/教师回应」这一项，没有材料。

那个技术问题的答案其实是知道的（`cd` 到 app 的 `Resources/` 再 serve），
也能编出一段很像的对话。

【需本人确认】这里 AI 没有替本人做决定，而是把两种代价都摆出来：

| 选择 | 收益 | 代价 |
|---|---|---|
| 留 ❌ + 回填流程 | 整包可信，每条都能被查 | participationQuality 自评不能给满 |
| 编一段「助教回复」 | 这一项看起来满分 | 一旦被问「截图呢」就是 0 分，且整包作废 |

AI 的倾向是前者，但**这条最终必须由本人决定**——因为只有她知道群里到底发生过什么。
现在的文件是按前者写的。

## 5. 这次对「AI 协作」的新认识

**① AI 最危险的地方不是写错，是「帮你把假的说圆」**

让它生成「参与记录」，它完全有能力产出三段以假乱真的群聊：有 @、有时间、有来有回。
语法正确、语气自然、连「不完美」都模仿得很像（故意留个错别字）。
**这种假比手写假更难查。所以「有没有证据」必须先由人划线，AI 才被允许在这个圈里干活。**

**② 自动校验只能证明「存在」，不能证明「相关」**

`evidence_lint` 让坏引用通过了（`L111` 是标题）。再加一层「语义打分」只会多一个不可靠裁判。
最后的解法很土：**让工具把原文打印出来，人看一眼。**
这条大概适用于所有自动评分——包括 C3 的评分表本身。

**③ 「先做工具」是一种很体面的拖延**

这次工具做得比参与认真。技术上没错（工具确实抓出了假分规则），
但在 C3 的语境里它是跑题：**群内参与的最小单位是别人看得见的一条消息，不是一份代码。**
下次的顺序应该反过来：先用最烂的版本占住位置，再回头把工具补上。
