## 1. 项目定义

- **我想做什么**：做一个「不用维护就能活着」的家庭食材记忆体——用一句话把东西存进去，用一句模糊的话把它问出来，并且在我快要浪费它的时候主动告诉我。

- **输入**：
  - 一句中文口语：`2盒牛奶 冷藏 7天` / `半颗白菜` / `一碗剩菜` / `200g猪肉 冷藏 2天`
  - 一句模糊的回忆：`白色的粉` / `nn` / `牛乃` / `冻的半月形`
  - 一次真实动作：用掉了、扔掉了、买回来了

- **输出**：
  - 结构化的库存（食材 / 数量 / 位置 / 到期日 / 状态）
  - **一句话**的今日简报：「今天先吃：剩菜（1 天后）、豆腐（3 天后）、番茄（5 天后）」
  - 3 道「现在就能做」的菜 + 它们的缺料（进购物清单）
  - 一份浪费账本：用了多少次、扔了多少次、浪费率

- **为什么这件事重要**：
  - **对我**：我家冰箱是典型的「三层结构」——外层是常吃的、中层是被遗忘的、最里面是上一个季节的。我每次都要靠「闻一下」来判断一盒豆腐还能不能吃。这不是记性问题，是**缺少一个外部记忆**。而所有我装过的 App，都在第二周被我卸载，原因永远是同一个：录入太贵。
  - **对他人**：食物浪费在家庭端的主因不是「买多了」，是「忘了」。忘的代价被分摊到每一次「算了扔了吧」里，所以没人真的算过账。让人看见账本的唯一办法，是把记账成本压到接近零。

- **这个东西目前存在吗**：存在，而且不少（见第 2 部分）。但**没有一个是按中文家庭的语言习惯设计的**。

  - **我的版本有什么不同**：
    1. **输入是句子，不是商品**。现有产品的原子单位是「商品」——先建 product，再设单位、默认位置、默认保质期（Grocy 的做法），或者先扫条码（BEEP/NoWaste）。中文家庭的原子单位是「一句话」。我把解析器写在入库这一端，用户不需要知道「product」这个概念。
    2. **检索按「记忆的模糊程度」设计**。人不是忘了「有没有」，是忘了「叫什么」。所以支持拼音首字母、错别字、别名、特征标签（白色/粉末/袋装/半月形）。这一条我在调研的 6 个产品里**没有找到任何一个做**。
    3. **双层记录模型**（本项目的核心设计）。娇气品（乳制品/绿叶菜/剩菜/豆腐）记保质期；常备品（米面油盐糖）**只记水位、不记日期**，且「没录过就当有」。这直接回应了我在调研中读到的最有价值的一条真实用户反馈：「别全录入，只录入最娇气的几样，大米冻肉这种根本不用管。」
    4. **提醒是聚合的，不是逐条的**。每天一条「先吃这三样」，而不是「某样东西今天过期」×15。

  - **为什么之前没人这么做**：
    - **做过但做得不好**：现有产品都在优化「录入速度」（条码、收据扫描、拍照识别），但都停在「商品」这一层。再快也是每样东西 3 秒 × 30 样 = 90 秒，第二周就放弃。我换的是**记录范围**：少记一半，剩下的用常识兜底。
    - **技术条件刚刚到位**：中文口语的量词、位置、时间表达高度收敛（我统计了自己 7 天的说法，只用到 9 个量词、4 个位置、2 种时间写法），规则解析就够，**不需要大模型、不需要联网、不需要 API key**。一次解析 &lt; 1ms，可以离线。
    - **市场太小**：对这种工具，商业公司做不划算——低 ARPU、高频手工输入、留存极差。所以它天然属于个人项目。这也是我选它做 C9 的原因：**没有公司会替我做，但它对我的生活是真的**。
    - **其实有人做了我没找到**：我承认调研只覆盖了 6 个产品 + 2 篇横向对比，样本不全。但我对「中文口语入库 + 特征标签反查」这两块的缺席有较高信心，因为这两件事都需要**为中文重写一层**，而现有产品都是英文/日文生态。

## 2. 拿来主义分析

> 调研方式：中英文各一轮检索，读产品页 + 真实用户评价 + 横向对比文。
> **诚实标注**：带 ⚠ 的条目我只读到对比文章/商店页，没有实际下载使用，属于二手信息。

### 竞品 / 参考项目

### 我拿来的部分

- **从 Grocy 拿了**：`物品 + 数量 + 位置 + 最佳食用日期` 这个最小字段集，以及「到期视图是产品的价值所在」这个判断。它验证了我的核心假设——**用户打开这个 App 的唯一理由，是看「哪样要坏了」**。
- **从 Grocy 的失败里拿了**：「stock 数字会变成 fiction」这句话让我在第一天就做了一个决定——**允许不完整**。宁可只有 30% 的食材有日期，也不要一个 100% 完整但两周后没人维护的库。
- **从食光冰箱的用户评价里拿了**：双层模型。「只录最娇气的几样」这条反馈价值高于我读的任何产品文档，它直接定义了 `track=expiry` / `track=level` 的分野。
- **从 Otto 拿了**：到期日「建议」而不是「要求」——我的解析器在用户没说保质期时按品类常识补一个默认值，并**把推断依据打印出来**（`保质期：按「白菜×冷藏」常识取 14 天`）。可解释性是「建议」能被接受的前提。
- **从 BEEP 拿了**：单一路径的克制。我的主界面只有四个动作：入库、搜、用掉、扔掉。没有成就系统、没有社区、没有打卡。
- **为什么这些好用**：它们都在降低「一次录入」的成本，而我把它们组合后加了一层——**降低「需要录入的总量」**。

### 我不要的部分

- **不要「商品（product）」这一层抽象**。Grocy 要求先定义商品再入库，这是 ERP 思维。家庭场景里「一袋面粉」不需要 SKU。我不需要：单位换算、采购单位、最低库存的精细配置、价格历史。
- **不要条码优先**。中国家庭的高频食材是散装蔬菜、市场现杀、自家分装的冻肉——**条码覆盖率极低**。为覆盖率低的场景做核心路径，等于为少数情况优化。
- **不要云账号体系**。理由不是技术，是信任：一份购物清单能推出来的东西比想象中多（收入、饮食、家庭结构）。所以数据只进本机 SQLite，共享走局域网。
- **不要游戏化 / 成就 / 社区**。食光冰箱的用户已经用脚投票了。
- **不要向量检索**。菜谱匹配的检索单元是「食材集合」不是语义文本，加权覆盖率 + 主料硬约束就够，且结果可解释（「覆盖 81%，缺葱」）。上 embedding 只会让它变慢、变贵、变黑箱。
- **不要大模型做入库解析**。见第 4 部分 K 段的取舍说明。

### 我的差异化

- **核心差异一句话**：**别人在降低"每次记录"的成本，我在降低"需要记录的总量"，并且承认人是记不住名字的。**
- **为什么这个差异有价值**：
  - 前者有下限（一个条码扫描也要 1 秒 × N 样），后者没有下限（只录 8 样就够活着）。
  - 「记不住名字」是这类工具真正的死亡点：一旦用户搜不到，他就会认为「这个 App 里没有」，然后不再打开。模糊检索是把「打开」这个动作救回来的唯一办法。
- **一句话对比**：Grocy 让你把家里变成一个仓库；我想让家里保持是一个家，只是多了一个记得住事的抽屉。

## 3. 自驱动机制

> 这一部分是 C9 唯一无法用交付物证明的东西，所以我写具体一点：具体到「哪一天、什么情况下我会停」。

### 为什么我会持续做这个项目？

- **兴趣 / 好奇心（真实存在的部分）**：我确实对「一句话到结构化数据」这件事着迷。写解析器的时候，我把家里 7 天里说过的关于食物的话记了下来（`2盒牛奶`、`半颗白菜`、`昨天的排骨汤`、`那一袋白色的粉`），然后一条条喂给程序看它怎么理解错。这个过程本身对我有奖励——它像解谜，而且解的是自己的谜。
- **现实收益（可量化）**：① 我的 C9 会持续产出可复用的方法（规则解析 + 可解释打分），这套东西能直接搬到我 C8 的班级管理 Agent 和 C4 的技能包里；② 浪费率是能被测量的数字，8 周后我要拿出「基线 vs 现在」的对比；③ 这是我在 Elite20 里唯一一个「完全属于我」的作品，它进作品集的方式和作业不一样。
- **身份认同（最高一层，也是我押注的一层）**：我给自己定的身份不是「会做作业的学生」，是**「会给自己的生活造工具的人」**。这个身份有一个可检验的标准：**我做的工具，我家人在用**。如果 8 周后我妈还在用它查冰箱，这个身份就成立；如果只有我自己在演示，那它就只是一个作业。

### 如果没人监督，我如何保证推进？

- **我的节奏**：
  - **每天**：不设每日任务（设了必破）。只保留一个动作——**当天任何一次入库，必须用它，不许用备忘录代替**。这是「狗粮」（dogfooding）而不是「打卡」。
  - **每周**：一个可展示的 milestone，周末写 AAR。milestone 在开工前就写死在第 4 部分的 8 周表里，周末只判断「到没到」，不重新商量。
  - **时间盒**：每周 4 小时（周六 2h 开发 + 周日 1h 复盘 + 1h 零散修 bug）。我知道自己一旦想「等我有整块时间再做」，就会永远不做，所以把单次投入压到 2 小时以内。
- **我的公开承诺**：
  1. **Elite20 群**：每周日发一条「本周产出 + 一个截图/一条命令」的进度（最低渠道，也是我说的社会压力来源）。
  2. **GitHub**：代码持续 push，commit message 就是周报的最小单元；README 里挂「本周进度」小节。
  3. **家人**：把 Web 界面挂在家里局域网，让我妈成为**第一个非技术用户**——她的抱怨是最真实的验收。
- **我的最低标准**（最忙的一周也至少做这些）：
  - 至少 **1 个 commit**，且这个 commit 能被用户看见（新功能 / 修一个真实 bug / 加 10 条词表）。
  - 至少 **1 条 AAR**，哪怕只写 3 行，但「动力分数」必须填。
  - **不允许连续两周只写文档不写代码**——文档是副产品，不是产出。
- **我的「失败信号」**（提前定义，因为缓慢死亡是没有声音的）：

| 信号 | 判定 | 我该做什么 |
|---|---|---|
| 连续 **2 周** 没有新 commit | 我在「想」不在「做」 | 砍掉当期 milestone，只做一个最小改动（例如只加 5 个食材词），把节奏捡回来 |
| 连续 **3 周** 我自己没打开过这个 App | 产品没解决我的问题，不是我没毅力 | 停功能开发，去做 3 次用户访谈（含我妈），找出「不打开」的真实原因 |
| AAR 动力分 **连续 2 周 < 5** | 动力在死亡 | 允许换方向（C9 规则允许换一次），并把换方向的原因写进 AAR |
| 到 Week 6 仍只有我一个人在用 | 没有真实用户 = 没有真实验证 | 把范围砍到单点（只做「剩菜提醒」），换取可用性 |
| 我开始用「等这周忙完」解释延期 | 这是一切停滞的开场白 | 立刻把本周 milestone 改成 30 分钟能完成的版本，当天做掉 |

**关于「换方向」的预先声明**：C9 允许换一次。我把它留给「Week 6 仍无第二个用户」这一种情况，其余情况一律通过砍范围解决，不通过换项目解决——因为我判断这个项目的风险不在方向，在节奏。

## 4. 执行方案（KSTAR）

### K（Knowledge）

- **我已有的知识**：
  - Python 标准库（`sqlite3` / `http.server` / `re` / `unittest`）——C8 的班级管理 Agent 已经用这套零依赖栈交付过一次，我知道它的边界在哪。
  - 规则式 NLP 的基本套路：分词退化成「最长匹配 + 词表」，实体抽取用「先摘易冲突项（日期）再摘数字」的顺序。
  - 可解释性设计：C4A 的评审器要求每条结论带证据，我把同一个习惯搬到了这里——每条解析结果带 `reasons`。
  - 前端：无构建的单文件 HTML + fetch，C6 公众号创作台已经验证过这条路。
- **我需要学习的**：
  - 拼音处理：目前用「词典里手写全拼+首字母」的办法绕过了汉字转拼音，词表外的词就没有拼音能力。**这是已知缺陷**，Week 2 要么补一张常用字拼音表，要么接受局限并写清楚。
  - 保质期知识：78 个食材的冷藏/冷冻/常温天数是我按常识写的，**没有权威数据源**。我需要找到可引用的食品安全资料（如 USDA / 中国居民膳食指南的储存建议）来替换掉我的拍脑袋值。
  - PWA / 离线：Week 2 要进手机主屏，需要学 manifest + service worker 的最小可用集。
- **我可以拿来的现有资源**：
  - 菜谱：22 道菜全部是我自己写的家常做法（含「为什么这么做」的 tip），不是从菜谱站抓的。**这既是优势（真实、可执行、中文）也是瓶颈（22 道太少）**，Week 3 要扩到 60 道。
  - 词表：78 个食材 + 115 个别名是我按自己家 + 父母家的采购习惯列的。
  - 竞品的产品判断：见第 2 部分，尤其 Grocy 的失败模式与食光冰箱的用户反馈。

### S（Situation）

- **当前状态**：Week 1 已交付 **V1 而不是 MVP**——MVP 的单文件闭环（`JingXueQing_C9_mvp.py`）跑通后，我在同一天把它做扎实成了 `homepantry/`：78 食材 / 22 菜谱 / 54 个测试全绿 / CLI + Web 双入口 / SQLite 持久化 / 浪费账本。
- **我面对的约束**：
  - **时间**：每周 4 小时，且我同时在跑 C8（真实项目）和 C2（论文）。C9 不能吃掉 C8 的时间——这是 C9「必须并行」的题设，也是真实约束。
  - **技术**：零第三方依赖（自己定的约束，为了部署零成本 + 长期可维护）。代价是 UI 不能用框架、拼音要自己想办法。
  - **资源**：没有服务器预算，没有 API key 预算。所以「照片识别食材」这类能力**不在 V1 范围内**（虽然它是所有人对这类产品的第一期待，我必须在文档里承认这一点）。

## 6. 我知道这个方案会在哪里失败（预先写下的风险）

写在这里，是因为 Week 8 复盘时我需要一份「当时的判断」来对照，而不是事后聪明。

1. **最大风险：双周热情衰减**。这类工具的价值随数据量增长，而数据量取决于前两周的痛苦期能不能熬过。对策：双层模型 + 默认值推断把「前两周」的录入量压到 8 条以内。
2. **第二风险：解析器在真实口语里崩溃**。我的 78 个词表覆盖不了「半袋子我妈从老家带的干豆角」这种说法。对策：`needs_review` 标记 + UI 里一眼可见「我没听懂这条」，并把它变成词表增长的数据源。
3. **第三风险：菜谱太少，推荐没有说服力**。22 道菜在一个有 33 条库存的冰箱里只能给出 4–6 个结果。对策：W3 靠「常买清单」反向生成菜谱优先级，先保证「推荐的都能做」，再追求「推荐得多」。
4. **第四风险：我高估了家人对「记录」的容忍度**。可能我妈根本不会用，最后只有我用。这不算失败（个人项目允许单人使用），但会让我失去「身份认同」这一层动力——所以 W6 的「第二个用户」是必须打的关卡。
5. **我明确放弃的能力**：拍照识别食材。它是最符合直觉的入口，但需要视觉模型 + 云端 + 成本，且在没有准确率保证时**会制造错误数据，比没有数据更糟**。我选择不做，并在 W5 用「小票 OCR + 人工确认」做有限替代。
