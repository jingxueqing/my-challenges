# JingXueQing · C9 拿来说明

**一句话**：我拿了 6 个产品的**判断**，没拿它们的**代码**；我否决了 5 个看起来该拿的东西，每一个否决都有理由。

---

## 一、我的筛选标准（先定标准，再挑东西）

调研之前我先写下 5 条标准，避免「看到什么好就拿什么」：

1. **能不能降低"需要记录的总量"**（而不只是单次记录速度）
2. **中文口语是否被当成一等公民**（量词、位置词、「忘了叫什么」）
3. **离线可用 / 数据是否留在本机**
4. **提醒是否克制**（聚合 vs 逐条）
5. **零依赖、可维护**（我要能读懂每一行，因为 8 周后还得我改）

按这 5 条看，市面上的产品**全部在前两条上不及格**，在第 3、4 条上部分及格（Grocy、Otto），第 5 条是我自己加的约束。

## 三、我拿来的（6 项，逐项说明「拿什么 / 为什么好用 / 怎么改造」）

### 1. 从 Grocy 拿：最小字段集 `物品 × 数量 × 位置 × 到期日`

- **为什么好用**：这是 8 个产品里唯一**完全一致**的字段组合。说明它不是某个产品的偏好，是这个问题域的必然结构。我不需要再验证。
- **我怎么改**：加了第 5 个字段 `track`（expiry / level）。Grocy 没有这个维度，它的所有商品都"应该"有保质期；而中国家庭的冰箱里，一半东西**根本不该记日期**（米、面、油、盐、冻肉）。
- **落在哪**：`pantry/model.py::Item`，`pantry/data/lexicon.json` 每个食材的 `track` 字段。

### 2. 从 Grocy 的失败拿：「库存会变成 fiction」

- **原文意思**：只要你停更一周，数字就是假的，预警就变噪音，然后你就卸载了。
- **我怎么改**：把「完整性」从目标里删掉。产品明确允许 30% 的食材有日期、70% 没有。`seed.py` 里 33 条数据中只有 19 条有到期日，其余是常备品——**这是设计，不是缺数据**。
- **落在哪**：`pantry/expire.py::level_alerts` 只对"用户真的录过"的常备品报警，而不是对词典里 12 个常备品全报红。这一条是我在测试里专门锁住的（`test_level_alert_only_for_tracked`）。

### 3. 从食光冰箱的用户评价拿：双层记录模型

- **拿的是这句话**：「别全录入，只录入最娇气的几样，比如草莓、开封的牛奶之类的。真正会被忘掉而且过期了不能吃的就这些，大米冻肉这种根本不用管。」
- **为什么这是最有价值的一条**：它不是一个功能建议，是**对产品范围的重新定义**。大部分产品把「全量」当目标，而真实用户自己在做减法。
- **我怎么改**：把减法做进数据模型——`track=level` 的食材不记日期，只记水位（`min_stock`），低于阈值才提醒。
- **落在哪**：`lexicon.json` 里 16 个食材是 `level`；`shopping.py::from_level`；`recipe.py::_is_staple`（常备品没录过就视为"有"）。

### 4. 从 Otto 拿：到期日「建议」而不是「要求」

- **为什么好用**：要求用户输入日期，是把一件他不确定的事变成他的负担。建议一个日期，是把不确定性接过来。
- **我怎么改**：解析器在用户没说保质期时，按「品类 × 位置」查常识值补上，并且**把推断依据打印出来**：
  `保质期：按「白菜×冷藏」常识取 14 天`
  同时置信度会 −0.04，让「我猜的」和「你说的」在数据上可区分。
- **落在哪**：`nlparse.py` 的 shelf 推断分支；`Parsed.reasons`。

### 5. 从 BEEP 拿：单一路径的克制

- **为什么好用**：BEEP 只做一件事（扫条码→填日期），所以它干净。食光冰箱做了 8 个模块，用户评价说「食谱和成就我基本没碰」。
- **我怎么改**：主界面只有 4 个动作：**入库 / 搜 / 用掉 / 扔掉**。菜谱和购物清单是"结果页"不是"功能页"——它们由库存推导出来，不需要用户单独维护。
- **落在哪**：`ui.py` 的 5 个卡片顺序；菜谱和清单**没有**"添加"入口。

### 6. 从对比文拿：三个死亡点（输入摩擦 / 通知质量 / 数据归属）

- **为什么好用**：这是我从 6 个产品里唯一找到的"共同失败模式"总结，比任何单个产品的功能列表都有用。
- **我怎么改**：三条各对应一个硬设计——
  - 输入摩擦 → 一句话解析 + 默认值推断（目标 3 秒/条）
  - 通知质量 → 一条聚合简报（`daily_brief` 只输出一句话，不逐项推送）
  - 数据归属 → 本地 SQLite，无账号、无云（`store.py`）

## 四、我不要的（5 项，每项都有具体理由）

| 不要的东西 | 谁在做 | 为什么不要 |
|---|---|---|
| **「商品（product）」抽象层** | Grocy | 家庭食材不是 SKU。引入 product 就要引入单位换算、采购单位、默认位置、默认保质期，然后把 40 个商品配置变成一个晚上的工作。**这正是 Grocy 用户流失的地方**。我的 `Item` 是扁平的一行，没有外键。 |
| **条码优先的录入路径** | BEEP / KitchenPal / NoWaste | 中国家庭高频食材条码覆盖率极低（散装菜、市场肉、自家分装冻肉）。为低覆盖率场景做核心路径 = 为少数情况优化。我连条码字段都没留。 |
| **云账号 + 跨端同步** | 除 Grocy 外全部 | 一份购物清单能推出收入、饮食、家庭结构。我选择「数据不出本机」，共享走局域网。代价是换手机要拷一个 `.db` 文件——我接受这个代价。 |
| **游戏化 / 成就 / 社区** | 食光冰箱 | 真实用户原话：「食谱和成就系统我基本没碰」。这类功能对"留存"有效、对"解决问题"无效，而我需要的是后者。 |
| **向量检索 / embedding 做菜谱匹配** | （我原本想拿） | 菜谱匹配的检索单元是**食材集合**，不是语义文本。加权覆盖率 + 主料硬约束已经能用一句人话解释结果（「覆盖 81%，缺葱」）；上 embedding 会让它变慢、变贵、变黑箱，且**无法解释为什么推荐这道菜**。 |

**额外否决一个技术方案**：**用大模型做入库解析**。理由不是它不好，是它在这个位置是错的：① 入库是高频动作，1–2 秒网络往返会直接杀死习惯；② 家庭食材说法高度收敛（我统计自己 7 天只用了 9 个量词、4 个位置、2 种时间写法），规则够用；③ 大模型不能告诉我「它是怎么理解错的」，而规则版的 `reasons` 天然可以。

## 六、我没拿什么（这一类通常没人写）

1. **没拿 Grocy 的 API 设计**。它的 REST 是全对象 CRUD + Swagger，很完整。我的 API 只有 12 个端点（6 读 6 写），因为**目前只有我自己一个调用方**。等真有人要接，再按需求长。
2. **没拿 Otto 的家庭共享方案**。它用邀请码 + Google/Apple 登录。我不想引入账号体系，所以 W2 走局域网共享（更土，但更符合"数据不出门"）。
3. **没拿任何 UI 设计**。我没有参考任何产品的视觉，因为这类工具的界面应该是"信息密度优先"的，抄一个消费级 App 的圆角卡片反而会降低信息效率。我的界面只有三层信息：状态色条 / 一行元信息 / 两个按钮。
4. **没拿现成菜谱库**。可以用开源菜谱数据集迅速堆到 1000 道，但那些菜我大概不会做，推荐出来也没有意义。**宁可 22 道都是真的，不要 1000 道都是假的。**
5. **没拿食品安全数据**。78 个食材的冷藏/冷冻天数是按常识写的，**没有权威出处**——这是我知道的最大的数据质量问题，已写进 proposal 的「需要学习的」里。我不想假装它是有依据的。
