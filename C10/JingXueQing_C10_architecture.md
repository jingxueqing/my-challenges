## 2. Layer 1：Memory（四层记忆）

### 2.1 四层与落盘位置

| 层 | 存什么 | 位置 | 一个真实例子 |
|---|---|---|---|
| **L1 原始输入** | 笔记、观察、对话片段，未结构化 | `memory/L1_raw/YYYY/MM/*.md` | `2026-11-04-c9-无头-chrome-最小视口-500px-我拿错了.md` |
| **L2 KSTAR 经验** | S→T→A→R + R̂/R/ΔR | `memory/L2_episodes/EP-*.md` | `EP-2026-11-04-10-c9-拿错了尺子.md` |
| **L3 Skill** | 从多条经验抽象出的可执行能力 | `skills/<name>/SKILL.md` | `skills/measure-before-fix/SKILL.md`（v4） |
| **L4 Identity** | 我是谁、原则、判断偏好、工具 | `config/identity.md` + `config/tools.md` | 3 条铁律 / 9 个工具 |

> 说明（与 CHALLENGE 的细微差异，故意为之）：CHALLENGE 把 Skill 归为 L3 记忆。
> 我把 **Skill 物理上放在 `skills/`**（而不是 `memory/L3_skills/`），
> 因为 Skill 要被 Agent **直接加载执行**，它属于"能力层"而不是"记忆层"；
> 记忆层只保留"原始 → 经验"两段。`memory/README.md` 里写了这条边界。
> **逻辑上的四层没有减少，只是物理位置按"被谁读取"分开了。**

### 2.2 文件格式（frontmatter 是机器可读的关键）

L2 经验必须有这几个字段，缺一个就不算经验：

```yaml
---
id: EP-2026-11-04-10
date: 2026-11-04
title: C9 移动端"还在溢出"：我拿错了尺子
status: confirmed        # draft / confirmed
tags: [c9, 验收, 测量, css]
skills: [measure-before-fix]     # 与 L3 的双向链接
r_hat: 0.9      # 事前预测（0–1 达成率）
r: 0.45         # 事后实际（同一口径）
dr: 0.45        # 自动计算
source: 桌面/C9-交付_.../JingXueQing_C9_AAR_W1.md   # 证据来源
evidence: AAR 失败 1 与失败 3；390px 截图；innerWidth 取证
---
```

**L1 → L2 的硬门槛**：**没有 R̂ 和 R 的记录不算 L2**（`doctor` 会报错）。
这条是刻意的：绝大多数"复盘"失败，是因为把"我今天干了啥"当成了"经验"。干了啥是 L1。

### 2.3 检索实现：为什么是 BM25 + 中文二元组

```python
# 分词：拉丁词整词 + 中文单字 + 中文二元组（bigram）
"移动端验收" → [移, 动, 端, 验, 收, 移动, 动端, 端验, 验收]
# 打分：BM25(k1=1.4, b=0.7)，权重 c1=0.35 / c2=1.0 / w=1.0
# 加成：命中 title +1.2/term，命中 tag +2.0/term
# 输出：分数 + 命中理由（命中 动端、截图、移动、验收（标签命中））
```

三个理由：

1. **中文没有空格**：单字召回高但噪声大，二元组精度高，两者加权叠加是最省的可行方案
   （这也是 C1 翻译管线里"术语块"的经验迁移：**中文检索的单位不是词，是字与二元组**）。
2. **可解释**：能打印"为什么命中"。这一点直接来自 C9 的产品原则——
   `reasons` 不只是给用户看的体验功能，**它是开发效率工具**（哪一步理解错了，一眼看到）。
3. **零依赖**：不用向量库、不用分词模型，`cp -r` 就能搬走。

**代价（诚实）**：同义词不认（"溢屏" 检索不到 "溢出"）、跨语言不认。
这在语料 < 200 篇时可接受；语料过千时应该换 hybrid（BM25 + 向量），
已写进 AAR 的"下一步进化方向"。

### 2.4 索引与数据的分离

- **真相源**：Markdown 文件（人类可读、git 可 diff）。
- **索引**：`index/brain.db`（SQLite，单表 `docs`），`recall` 前自动检查 mtime 决定是否重建。
- **验证**：删掉 `index/` 与 `reports/`，`recall` 与 `dash` 照常工作。
  > 这是一个可被评审者当场验证的断言，不是设计宣称。

## 4. Layer 3：Agent Loop（KSTAR）

### 4.1 循环与文件的关系

一次循环 = 一个 `logs/runs/RUN-YYYYMMDD-HHMM.md`，结构固定：

```
K  自动执行的检索结果表（谁被命中、分数、为什么）
S  情境（约束/时间/工具/上次同类 ΔR）
T  任务（一句话 + 3–6 步）
Â  计划（用哪个 Skill、改哪一步）
R̂  预测（一个 0–1 的数，事前写）
A  执行（实际动作 + 证据）
R  结果（同一口径量）
ΔR = R̂ − R + 判定 + 解释
教训  一条可复用的句子
```

`loop close` 会同时做三件事：① 算 ΔR；② 落一条 L2 草稿（`status=draft`）；
③ 若 `|ΔR| > 0.2` 打印校准提示（指向 `skill iterate`）。

### 4.2 ΔR 的口径（这是整套系统最容易做错的地方）

- **一个 R̂ 只能有一个量纲**。C2 曾把"四件交付物交齐"和"论文有说服力"塞进一个 1.0，
  结果必然高估（ΔR +0.15）。
- **R̂ 里只放"我能单方面决定"的事**。C7 写了"至少 2 篇公开发布"，但发布权在管理员手上
  → ΔR +0.30，是纯口径错误，不是能力问题。
- **ΔR 的三种含义**：`≈0` 口径稳；`>0.2` 我高估了（多半是口径错）；`<0` 我低估了
  （通常是"验证成本被我高估"，C9 的 −0.35）。

### 4.3 真实分布（10 条经验）

```
ΔR  +0.50 ┤●                      C8 提交口径
    +0.45 ┤        ●               C9 拿错尺子
    +0.35 ┤  ●                     C8 压缩 4 周
    +0.30 ┤      ●                 C7 发布权
    +0.25 ┤●                       C8 预警
    +0.15 ┤   ●    ●               C2 / C9 9 次失败
    +0.10 ┤ ●                      C4D
    +0.03 ┤●                       C1
     0.00 ┼──────────── 0 轴 ──────
    -0.35 ┤              ●         C9 MVP（唯一一次低估）
          └────────────────────────
```

**读法**：11 次里 9 次高估、1 次命中、1 次低估。高估集中在"把假设写进计划"和"口径没对齐"
两处（占 7 条）——这就是 `identity.md` 里"证据优先 / 口径先对准"两条铁律的由来。
**一个系统如果不能让这种分布被看见，它就只能靠记忆学习。**

## 5. Layer 4：Tool / Access

对应 `Action = Plan × Access Token × Energy`：

| 因子 | 在本系统里的落点 |
|---|---|
| **Plan** | `skills/*/SKILL.md` 的 Steps（做什么、按什么顺序） |
| **Access Token** | `config/tools.md` 的 9 个核心工具（LLM / 本地模型 / Python / git / 搜索 / 部署 / 微信 / 文档 / Markdown 库） |
| **Energy** | 人（我）的实际执行，以及 `loop` 的频率——`usage.jsonl` 是它的度量 |

设计原则：**只留"能串联"的工具**。淘汰清单里写明了 4 个被否决的工具及原因
（向量库 / Notion / Neo4j / 微信库解密），避免半年后又想装一遍。

## 7. 三个原则怎么落地

### 原则 1：拿来主义（详见 `JingXueQing_C10_拿来说明.md`）

| 我拿了什么 | 从哪拿 | 改成了什么 |
|---|---|---|
| skill.md 的 frontmatter + 分节格式 | Claude Code / Agent Skills 体系 | 加了 `使用记录`+`迭代史`+`不适用`，把 Skill 从"文档"变成"有生命周期的资产" |
| R̂ / R / ΔR 的偏差学习 | KSTAR 认知循环 | 加了**口径三铁律**（单一量纲 / 只放我能决定的 / 三档含义） |
| BM25 + 中文 n-gram | 信息检索经典做法 | 加了"命中理由"输出（把可解释性当开发工具） |
| 文件夹 + 双链笔记 | Obsidian / PARA | 用 KSTAR 四层替代 PARA 四层；双链改为 `skills:` 字段（机器可算） |
| AAR（七维） | 军事复盘 / C1–C2 实践 | 压成三栏（对/错/意外）+ 一次 ΔR 表 |

### 原则 2：自进化（三个开关，都是命令）

| 能力 | 命令 | 触发条件 | 本次是否真的发生 |
|---|---|---|---|
| 从经验长出 Skill | `distill --min 3 --write` | 同标签 ≥3 条且无覆盖 | ✅ 3 提名 |
| 优化已有 Skill | `skill iterate` | 关联经验平均 \|ΔR\| > 0.2 | ✅ v3→v4 |
| 淘汰无效 Skill | `skill deprecate` | 30 天未用 / 连续失败 | ⏳ 规则已埋，未到期 |
| Skill 组合 | `iterate`（合并而非新建） | 两个 Skill 常一起调用 | ✅ CAND-ai-归因 → 合并进 measure-before-fix |

### 原则 3：长期性

| 要求 | 本系统的实现 | 能不能被验证 |
|---|---|---|
| 数据可积累 | 纯文件 + git；追加而非覆盖 | ✅ `git log` 可查 |
| 系统可扩展 | 加 Skill = 加一个目录；加命令 = 加一个函数 + 一个 subparser | ✅ 本次就加了 `note processed` |
| 可持续使用 | CLI 一条命令的成本；`doctor` 每周提醒积压 | ⏳ 需要时间证明（见 AAR 的诚实声明） |

## 8. 关键设计决策（含被否决的选项）

| # | 决策 | 备选 | 选了什么 / 为什么 |
|---|---|---|---|
| 1 | 存储 | ①SQLite 为主 ②向量库 ③**Markdown + 可重建索引** | 选③：可迁移、可 diff、模型零 SDK 可读；语料 <200 时向量收益 < 部署+黑箱成本 |
| 2 | 检索 | ①关键词精确 ②纯向量 ③**BM25 + 中文二元组 + 标签加成** | 选③：中文无空格、要可解释、零依赖；同义词缺陷已记录 |
| 3 | Skill 上线 | ①distill 直接生成 ②**只提名，人工裁决** | 选②：C8 的教训是"没验证的假设不能进 R̂"，同理"没验证的抽象不能进 Skill 库" |
| 4 | ΔR 定义 | ①多指标加权 ②**单指标 0–1 达成率** | 选②：C2 的教训——一个 R̂ 塞两个量纲必然高估 |
| 5 | 循环落盘 | ①只写日志 ②**写 run 文件 + 自动落 L2 草稿** | 选②：跑完就忘是这类系统的头号死因 |
| 6 | 使用计数 | ①手填 ②**JSONL 流水自动追加** | 选②：手填的数字无法自证；`report` 从流水统计 |
| 7 | 接口 | ①只做 Web UI ②**Markdown + CLI + 生成式看板** | 选②：Web UI 会让我为了界面而维护界面；CLI 每天真在用 |

## 9. 一次完整数据流（以"移动端溢出"为例，全程可追）

## 11. 已知局限（诚实清单）

   回填的 26 次历史使用只证明"这些做法真的被用过"，不证明"系统调度过它们"。
