## 0. 先把"使用"分三类说清楚（这是本文最重要的一节）

| 类别 | 含义 | 本次的量 | 能不能自证 |
|---|---|---|---|
| **A. 系统内真实调用** | 系统建成后，通过 CLI 真实执行的动作 | 65 次命令（20:59–21:52，2026-11-05，提交时的快照） | ✅ `logs/usage.jsonl` 逐条追加，带时间戳/参数/成败 |

## 一、A 类：系统内真实使用（2026-11-05，逐条可查）

### 场景 1：用 `add` 把 C1–C9 的观察压成 L1（13 次）

- **日期**：2026-11-05 20:59–21:06
- **输入**：桌面既有交付物里的真实段落（如 C9 AAR 的"失败 3：无头 Chrome 500px"）
- **做了什么**：`kstar.py add --title ... --tag c9 --tag 验收 --date 2026-11-04`
- **效果**：13 条 L1 按年月归档，`find memory/L1_raw -name "*.md" | wc -l` → 13
- **改进**：第一次写就发现 `--date` 必须支持回填（否则 13 条全会变成"今天"），
  已写进 `add` 的参数里

### 场景 2：用 `recall` 做 K 步（7 次，其中 3 次在 demo 录制中）

- **输入**：`recall "移动端 验收 量错"` / `recall "交付 打包 复现" --layer skill`
- **输出**（真实）：
  ```
  1. [episode] C9 移动端"还在溢出"：我拿错了尺子   score=20.29
     命中 动端、移动、验收（标签命中）
  2. [skill]   measure-before-fix               score=9.87
     命中 动端、移动、验收（标签命中）
  ```
- **效果**：**在我动手之前就把 EP-2026-11-04-10 递到面前**。
  本次构建里，我因为这条经验先查了 `which ffmpeg` 才决定 demo 形态
- **ΔR**：这一条没有独立 R̂（它服务于整个 C10 循环，归到 EP-2026-11-05-01）
- **改进（真实发生）**：命中理由里出现单字噪声（"动""图"）→ 过滤 `len<=1` 的展示词

### 场景 3：用 `loop start/close` 跑完整循环（1 次，含一次失败的尝试）

- **输入**：`loop start --task "构建并交付 C10 第二大脑系统" --rhat 0.88`
- **实际**：`loop close RUN-20261105-2122 --r 0.86`
- **输出**：`ΔR = 0.02（R̂=0.88 − R=0.86）→ 命中`，自动落 L2 草稿
- **ΔR 的自我批判**：0.02 看起来"很准"，但见 EP-2026-11-05-01 的 §ΔR——
  **这是我自己出题自己打分的结果**，真实的偏差在"权重"上，不在数字上
- **改进**：第一次 `loop start` 退出码为 1（返回 str 被 `sys.exit` 当错误消息），
  修了 `main()`；第一次 `loop close` 的 A 段和 R 段文字重复（`--actual` 被写进两处），
  已记录为待改（见 AAR「设计错的」#5）

### 场景 4：用 `distill` 让系统给我提名（3 次）

- **输出**：`ai-归因` / `c8` / `c9` 三个候选簇
- **我的动作**：1 个合并（→ `measure-before-fix` v4）、2 个拒绝（项目标签不是能力标签）
- **效果**：**这是本次唯一一次"系统主动教我一件事"**——
  它让我发现自己打标签时把"项目"和"能力"混着打了
- **改进**：`inbox/candidates/README.md` 里写下规则补丁（distill 需要标签排除表）

### 场景 5：用 `skill use` 记录 6 个 Skill 的本次调用（7 次）

- **做了什么**：`kstar.py skill use <name> --note "..." --source "本次构建"`
- **效果**：6 个 Skill 的 `uses_system` 从 0 全部变成 ≥1（`measure-before-fix` / `narrow-first-mvp` / `scope-probe-first` 各 2，其余各 1）
- **关键动作（真实返工）**：我曾**手写**过 4 条"本次使用"行 → 用 `grep -n "2026-11-05"` 对账时发现
  行数多于 `usage.jsonl` 里的 `skill.use` 次数，当场删掉重写，改由 CLI 追加（见 AAR §3.1）
- **改进**：`skill use` 的计数只认 CLI 写入；`uses_backfilled` 与 `uses_system` 分字段，永不合并

### 场景 6：用 `doctor` 体检（6 次）

- **第 1 次**：`⚠ L1 笔记 41 天未转 L2` ×4 → 发现回填时漏标 `processed`，
  且**系统没有"补标"命令** → 当场加 `note processed`
- **第 6 次**：`✓ 全部检查通过`（L1 13 / L2 11 / Skill 6 / Run 1）
- **效果**：doctor 抓到的不是数据错，是**流程缺一步**——这是它最值钱的地方

### 场景 7：用 `dash` / `report` / `export-skills` 生成交付数字（各 4/4/3 次）

- **原则**：所有对外数字都由这三个命令产出，手不碰
- **效果**：`reports/dashboard.html` 8 KB 离线可开；`reports/usage_log_auto.md` 11 条经验表

## 三、效果量化（能算的才算）

| 指标 | 有数 | 没有数（诚实标注） |
|---|---|---|
| Skill 复用率 | 11 条经验 × 6 个 Skill，平均每个 Skill 被 2.8 条经验引用 | ❌ "省了多少时间"——没有计时，不算 |
| ΔR 收敛 | 09-25 → 10-31 平均 ΔR **+0.28**（8 条）→ 11-04 之后 **+0.17**（3 条） | 样本太小，不能当趋势 |
| 返工识别 | 10 条经验里 **6 条直接来自返工**（C8×3、C9×3） | — |
| 系统内循环 | 1 次完整循环（R̂ 0.88 / R 0.86 / ΔR 0.02） | ❌ 只有 1 次，不构成统计 |
| doctor 拦截 | 3 次真实拦截（4 条未标 processed / 1 条 draft 未确认 / 退出码 bug 未拦截） | — |

**一句诚实话**：C10 的效果证据里，**"这些做法有效"比"这个系统有效"更硬**。
系统本身的有效性还需要 4 周以上的连续使用才能证明——这是下一步的事，不是现在能宣称的事。
