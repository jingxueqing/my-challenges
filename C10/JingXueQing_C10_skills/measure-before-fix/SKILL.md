# measure-before-fix · 先验尺子，再改代码

## What（做什么）

把"修 bug"的顺序固定成 **验证测量 → 对齐口径 → 定位根因 → 改代码 → 回归**。
禁止在未确认现象真实性的情况下修改代码，禁止用"调参数"代替"改逻辑"。

## When to Use（什么时候用）

- 同一个问题改了两轮还没好（**这本身就是量具可能有问题的信号**）。
- 结果为空 / 结果全绿但业务方说不对。
- 数据对不上（谁的数字是对的？口径是什么？）。
- 样式/视口/截图类问题（最容易拿错尺子的领域）。

## Input（输入）

1. 现象的一句话描述（"溢出""为空""7 人缺件"）；
2. 当前用来观察它的手段（截图 / 日志 / 看板 / 别人口述）；
3. 业务方/验收方的口径（他们怎么算这个数）。

## Steps（步骤）

1. **验量具**：把关键量**打进产物里读出来**，而不是从图像/直觉推断。
   例：页面里打印 `window.innerWidth`，而不是"看图猜 390px 有没有溢出"。
2. **对齐口径**：问清"这个数怎么算"。C8 的 7 人误判，根因是 config 里必备件字段写错。
3. **打印中间状态**：结果为空时先打印中间集合（如菜谱的 `missing` 列表），
   **不许先调参数**（limit 3→12 是最贵的偷懒）。
4. **写一个会失败的断言**：先把 bug 变成测试，再修。
5. **改根因，不改编排**：C9 的 `flex-basis` / `order` 都是"语义合理"的无效改动，
   根因是 `min-width:auto` 与行内 style 的优先级冲突。
6. **回归 + 记录**：测试留在库里，注释写明"这是曾经的 bug"。

## Tools（需要什么工具）

- 浏览器 console / 页面内 debug 输出、`curl`、日志打印
- 测试框架（哪怕只是 `assert`）
- 本仓库：`python3 scripts/kstar.py doctor`（它也在验"系统自己的口径"是否一致）

## Output（输出）

一句根因陈述（"哪个元素超出、超了多少、依据是什么"）+ 一个回归测试 + 一次口径对齐记录。
