# narrow-first-mvp · 先窄后宽

## What（做什么）

把一个模糊想法压缩成**一条能在终端里打印出结果的链路**，
用它回答"这东西有没有用"，再决定要不要投入结构化建设。

## When to Use（什么时候用）

- 自驱项目第一天，只有一个模糊念头。
- 要在两种架构之间选，但两边的价值都还没被证明。
- 上次的教训是"做了很多、但没人用"。
- 想给团队/老师看进度，但手上只有 design doc。

**不适用**：需求已经被别人验证过、只需实现（那就直接实现，别演 MVP）。

## Input（输入）

1. 一句用户故事（谁、在什么场景、想省掉什么麻烦）；
2. 3–5 条真实输入样本（**不是编的**：真实说法、真实文件名、真实数据行）；
3. 一个终端能显示出来的输出形态（一行结果 / 一张表 / 一次命中）。

## Steps（步骤）

1. **写死输出形态**：先在纸上画"终端里应该看到什么"，再写代码。
2. **单文件、零依赖**：一个 `mvp.py`，跑一条命令出结果（C9 是 200 行 / 40 分钟）。
3. **用真实样本播种**：把真实说法的样本直接当测试数据，MVP 跑的时候顺手做一次端到端自检。
4. **判断闸门**：跑通后只问一个问题——"如果只能保留这个，我用不用？"
   不用 → 砍掉方向（省下的是后面所有投入）；用 → 进第 5 步。
5. **再上结构**：分层、配置、测试（C9 是 2,434 行 / 54 测试），此时结构服务于已验证的需求。
6. **保留 MVP 作为回归基线**：单文件变成"最小可复现样例"，改架构时用它验证行为没漂。

## Tools（需要什么工具）

- Python / zsh（单文件即可）；不要引入框架
- 本仓库：这本身就是一次 MVP —— `python3 scripts/kstar.py selftest` 先跑通 5 项断言，再铺数据

## Output（输出）

一个能跑的单文件 + 一句结论（"值得做 / 不值得做"）+ 一个决策依据（哪条真实样本跑通了）。
